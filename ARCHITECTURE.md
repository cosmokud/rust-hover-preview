# Architecture

## Overview

Rust Hover Preview is a Windows 11 tray application that watches File Explorer focus and hover state, then renders a non-activating preview window near the cursor or focused item. It is split into a tray UI, an Explorer hook, and a preview renderer that communicate through lightweight shared state and message passing.

## Runtime Topology

- Main thread claims the single-instance mutex, initializes COM, config, DPI awareness, then runs the tray event loop.
- Preview thread owns the layered preview window and media decoding/rendering.
- Explorer hook thread polls Explorer state with UI Automation/MSAA and Shell COM APIs, and uses EnumWindows with CabinetWClass/ExplorerWClass class matching to count and classify Explorer browser windows so idle polling never spins up Explorer's shell automation providers.
- Wheel watcher thread installs a system-wide low-level mouse hook (`WH_MOUSE_LL`) and pumps the messages it needs, publishing a wheel-tick counter that the Explorer hook consumes so wheel scrolling refreshes the hovered item.
- Config watcher thread reloads `config.ini` when it changes on disk.

## Single Instance

The app runs as a single instance per user session. `main` claims a session-local named mutex (`Local\rust-hover-preview-single-instance`) as its first step, before DPI awareness, COM initialization, config loading, and any thread is started. A second launch — from a desktop shortcut, the Start menu, the startup entry, or the `.exe` directly — finds the name already taken, closes its own handle, and returns from `main` without creating a tray icon, Explorer hook, or preview window. The guard handle is held for the lifetime of the process, so the name is released when the app exits, including after a crash or a forced kill, and the next launch becomes the primary instance. The `Local\` prefix scopes the guard to the signed-in session, so a second user signed in over Remote Desktop still gets their own instance and tray icon.

## Core Modules

- `main.rs`: single-instance guard, process startup, COM lifecycle, DPI awareness, thread orchestration.
- `single_instance.rs`: named-mutex guard that limits the app to one running instance per user session.
- `explorer_hook.rs`: resolves hovered/focused Explorer items, handles path normalization, and sends preview messages.
- `wheel_input.rs`: system-wide mouse-wheel hook thread that publishes a tick counter, so a scroll that moves the list under a parked pointer is visible to the polling loop.
- `preview_window.rs`: layered window rendering, scale-aware sizing, animation streaming for GIF/WebP, FFmpeg-backed video playback with verified-PID process supervision (see Video Process Lifecycle), monitor-bounded placement with paint-before-show presentation, and WM_POWERBROADCAST handling to reset state on system resume and clean up on suspend.
- `pdf_preview.rs`: first-page PDF rendering through the PDF engine that ships with Windows (`Windows.Data.Pdf`), with the page size cached per file and the file's own header confirmed before a path reaches the OS renderer.
- `text_formats.rs`: the gate for text previews, holding the built-in extension and file-name lists that are written to `config.ini` and read back from there, the dot-file rule that makes a `gitignore` entry mean `.gitignore`, and the normalization that makes a hand-edited list safe to match against.
- `text_preview.rs`: reading and decoding a text file, styling a window of it on demand, laying that window out, and painting it — with a scrollbar when the file is longer — into the same BGRA frame an image arrives in.
- `text_theme.rs`: the color themes — the two bundled TextMate themes and the user's own `.tmTheme` files, each parsed once and kept — plus the scope lookups that answer "what color is a heading in this theme?", the fallback that keeps a broken file from taking the preview with it, and the reading counter that tells a cached document which version of a file it was colored against.
- `theme_files.rs`: the `theme` folder beside `config.ini` — which of its files are themes, the names they are listed and written under, and the path a name resolves to.
- `tray.rs`: tray icon and menu, configuration toggles, exit flow, and WM_POWERBROADCAST handling to re-add the icon after DWM/Explorer restart on resume.
- `config.rs`: INI-backed configuration with defaults and input sanitization.
- `startup.rs`: registry integration for the Run-at-startup setting.

## Media Pipeline

- Images (static, GIF, WebP) are decoded in the preview thread, with animated formats streaming frames into a shared queue.
- The preview window uses GDI and `UpdateLayeredWindow` to draw to a topmost, no-activate surface.
- Video previews launch `ffplay` for playback and query `ffprobe` for video geometry; the player's lifetime is supervised as described in Video Process Lifecycle.
- PDF previews render page 1 through `Windows.Data.Pdf`; see PDF Previews for the split between measuring a page and rendering it.
- Text previews are read, decoded, highlighted and painted in-process; see Text Previews for the split between the document, the layout and the frame.

## PDF Previews

A PDF preview shows page 1, rendered by `Windows.Data.Pdf` — the PDF engine that ships with Windows — so the app bundles no renderer and the user installs nothing. Two threads do this work, and both initialize a multithreaded apartment (`CoInitializeEx(COINIT_MULTITHREADED)`) before their first call, which is what WinRT requires of the calling thread.

The preview thread measures the page before anything is decoded, because the preview is positioned and sized first: the page size the engine reports (DIPs, 96 per inch) is what the layout is computed from, the same way video geometry is resolved up front. That probe is cached per path, failures included, so a file is parsed once and an unreadable file is not re-parsed on every hover. Before a path is handed to the renderer it has to carry a `%PDF-` header in its first kilobyte, which is what keeps a mislabeled file out of the OS parser.

The document is opened from bytes the app reads itself (`std::fs::read` into an `InMemoryRandomAccessStream`) rather than through `StorageFile`. The hook canonicalizes shell paths to the verbatim `\\?\` form, which `StorageFile.GetFileFromPathAsync` rejects outright, so a PDF hovered in a folder view could not be opened at all while the same file opened fine from a search result — the in-memory stream accepts every path form the rest of the app produces. The cost is that the file is held in memory while it is parsed.

The decode worker then renders page 1 into exactly the pixel size the layout asked for, after fitting the page's own aspect ratio into that box, so a page that is not the shape the layout assumed is letterboxed instead of stretched. Rendering at the target size is also what keeps a scaled-up preview sharp: `100%` is a 96 DPI page, while 200% or fit-to-screen is rendered larger rather than enlarged afterwards. Because of that, a PDF ignores the configured preview scale and is always laid out at fit-to-screen — the largest size the display allows is also the most legible one — and `effective_preview_scale` is the single place that decides it, so the layout and the render can never disagree about the size. The renderer is asked for its BMP encoder, which turns the decode on this side into a header parse instead of a PNG inflate, and the page is painted on an opaque white background so its text stays readable over any `transparent_background` mode. From there the result is an ordinary static frame: the existing spinner covers the wait, and a render that finishes after the cursor has moved on is dropped by the same generation check as every other load.

## Text Previews

A text preview shows the first screenful of a text file, colored by the syntax definition its extension names. Which files those are lives in `config.ini`, written from the built-in lists on first run and read back from there, so a user can add a format or remove one without a rebuild; `text_formats.rs` owns both lists and the normalization that keeps a hand-edited entry from matching anything but a bare extension. Both the Explorer hook's "is this previewable" gate and the renderer consult it, so the two cannot disagree about what a file is.

There are two lists because one cannot reach the files a repository is recognized by. Extensions are matched the way the filesystem reads them, which leaves out `LICENSE` and `Makefile` (no dot at all) and, less obviously, `.gitignore` — a leading dot begins a *name*, not an extension, so `Path::extension` reports none for it. The extension lookup therefore falls back to the name minus a leading dot, which is what makes a `gitignore` entry mean `.gitignore`; and a second list of names carries the extensionless files, matched whole, case-insensitively, with the same dropping of a leading dot on both sides so that `gitignore` and `.gitignore` are one entry in either list. A file is in when either list claims it, so `.eslintrc.json` is still read by its extension while `.eslintrc` is read by its name. `is_text_file` is the one gate both sides ask, so a file the hook offers is a file the renderer can draw.

Text has no size of its own, so the two-step shape of the PDF path is repeated with a different measurement: `measure` resolves the box the first screenful wants, bounded by the display it will be shown on, the layout fits that box into the space beside the cursor or focused item, and `render` is handed the box that came out and fills it. What differs is what the box means. A PDF page is a vector and is drawn at whatever size the layout asks for; text is drawn at a fixed font size scaled by the display's DPI (`GetDpiForMonitor` on the monitor under the hover, falling back to 96), so scaling the box would only stretch the window around text that stays the same size. `effective_preview_scale` therefore answers `100%` for text — never enlarged, reduced only when the space beside the cursor cannot hold it — and the renderer reads the box it is given as "as many lines and columns as fit". A two-line file gets a two-line window; a long file takes the largest box the display allows, which is the same thing fit-to-screen does for a PDF.

The `Text Preview Font Size` setting multiplies into that: `TextMetrics` scales the display DPI by the configured percentage into one scale, so the glyphs, the line spacing and the page margin grow together and a preview at 200% is the same page twice the size rather than the same page in a larger box. The size is deliberately not part of the parsed document's cache key — the styled lines are identical at any scale, and only the layout changes, so changing the size repaints from the cache instead of re-reading the file. The combined scale is bounded (0.25x to 16x), which is what lets a hand-edited `text_font_scale` of any percentage be used as written without asking GDI for a glyph taller than the screen.

Previews are also gated by kind, from the tray's `Toggle Preview Types` submenu: `image_preview_enabled`, `video_preview_enabled`, `text_preview_enabled` and `pdf_preview_enabled`, all on, switched through `config::PreviewType`. A gate is only whether previews of that kind may be shown at all — the lists and settings that decide which files of that kind are previewed are untouched, so a kind switched off and back on restores what was configured. Both halves of the app ask: the Explorer hook's media gate asks the kind of a file — video first, because only content settles the `.ts`/`.mts` the text list shares, then PDF, then the text lists, then the image extensions — and the renderer asks the same question when it measures a preview, so a preview cannot be laid out for a kind that is off. `text_preview_enabled` is checked in `text_formats::is_text_file` ahead of both lists, so turning text previews off is one gate the hook and the renderer both already consult, and the lists survive for when it is turned back on. A kind switched off takes the preview of that kind with it: the tray hands the preview thread a type change, and a preview whose own kind is the one that changed is rebuilt from the hover it came from, which drops it because the layout finds no size for a file whose kind is off — a preview of any other kind is left as it is, so a running video is not restarted by a toggle it has nothing to do with.

The colors come from the theme selection, and the selection can be a file the user wrote: `text_theme` answers from one of the two bundled TextMate themes, or from the `.tmTheme` a selection names in the `theme` folder beside `config.ini` (see Configuration). Both are read by the same reader, and a file is read when it is asked for rather than when the folder is listed, so a folder of themes costs nothing until one is chosen; the menu is what lists the folder, and opening it is also what drops the parsed files so that the next preview reads them again. A file that is missing, unreadable, or not a theme is answered with the default — Atom One Light — instead of nothing: the renderer is handed a theme it can paint with, the item keeps its place in the menu, and the selection stays in `config.ini` until another theme is chosen, so a repaired file is used as soon as the menu is opened again.

The parsed document is cached per path, modification time, length, theme and Markdown mode — plus, for a theme that came from a file, the reading of it the document was colored against, since a file can be edited under a name that does not change — so a second hover, a repaint, or a theme switch costs a layout rather than a parse. What is cached is the *text and where its lines start*, not styled lines: the line table is eight bytes per line and no parsing at all, which is what lets a preview know how tall a document is — and how far it can scroll — before anything has been colored. Styled lines are built per window by `styled_window`, kept in a small per-document cache, and indexed by absolute line number, so a window that already covers a scroll position costs nothing and the window the layout asks for is sized from the box. For a source file the parser runs from wherever it left off, or from the nearest of the checkpoints taken every few dozen lines, and only the requested lines are kept: nothing past the window is ever styled, and a jump in either direction is bounded by the checkpoint spacing. The parse state itself cannot live in the shared cache — syntect's `ParseState` holds pointers into Oniguruma's match regions and is not `Send` — so it is kept per thread in a `thread_local`, and the windows, which are plain data, are shared between the threads that measure and paint. Four producers fill that model: `syntect`, with the syntax definitions `two-face` adds on top of the ones it bundles, colors source and markup files; `pulldown-cmark` turns a `.md` file into the document it describes, handing fenced code back to `syntect` and asking the theme for the color of a heading, a quote or a link by scope, so a rendered document and a highlighted source file share one palette — it is the one producer that reads all of its input, because a rendered line's place in the document is only known once the block before it has been walked, and it keeps only the window's lines as it goes; an RTF control-word stripper reduces a `.rtf` file to the text it carries, skipping Word's own tables, once, at load; and an NFO reader decodes CP437 art and consumes its ANSI escapes into colors toned toward the page they are drawn on. The one producer whose lines are not the file's own is the rendered Markdown document: a paragraph is one line, a heading is one, and the blank line between two blocks is one the source does not have, so the walk that renders the document is also what counts what it drew — once, when the document is built — and the preview's scroll range, its scrollbar and the lines it says are left out are all measured in those lines. Reading is bounded — 2 MB and a 2000-line scroll range — and decoding decides the encoding from the file: byte order marks first, then UTF-8, then the legacy code page CP437 belongs to. Two guards keep non-text out: NUL bytes mean the file is not UTF-8 text (a UTF-16 file is recognized from where its NULs fall, and anything else is binary), and a decode that is mostly control characters is a binary file that happened to pass.

Layout keeps a document readable inside the box rather than filling it. Lines are clipped at the right edge for code, markup and NFO art, whose columns line up, and wrapped between words for prose — a rendered Markdown paragraph, an RTF document, anything no grammar claims — because a paragraph is one long line and clipping it would hide most of what the file says. A frame is pulled back until it can be filled from where it starts, so the last screenful of a document is full instead of showing two lines at the top of an otherwise empty box — the lines above a frame that would end early are walked backwards from its top while the box has room for another, which measures the pull-back in the document's own lines rather than in the lines that fit: one line can take two of the box's, and a pull-back by the number of lines that fit left the end of the document out of reach, both as a wall a few lines too high and, past the end, as a frame that painted nothing. What that leaves is one rule for the end of a document: the frame whose tail fills the box is the last one, its last line is on screen, and a position past it — a thumb dragged to the bottom of its track, a line left over from a file that was longer when the preview opened — resolves to that same screenful rather than to an empty box. A line is kept at the end for a note whenever the frame cannot show everything and no scrollbar is going to say so: a file that was cut at the read cap, whose remainder cannot be reached by scrolling either, or any document at all in a preview that does not scroll.

A document longer than its frame gets a scrollbar, drawn into the same frame the text is: a groove and a thumb whose length is the share of the document the frame shows and whose position is the share above it. The bar's geometry comes from one function used by both the painter and the hit test, so what is drawn and what a drag lands on cannot drift apart. The wheel reaches the preview through the low-level mouse hook rather than the window, because the preview never has focus and Windows delivers wheel messages to the focused window — Explorer — instead; the hook asks the preview for the pointer region, swallows the message when the pointer is inside it, and leaves the notches for the preview thread. The delta comes from the hook structure's `mouseData`: a low-level hook is handed the message identifier and a pointer to that structure, and the delta a window would find in the high word of `wParam` is not filled in there. Dragging the thumb is ordinary mouse input, which the layered window does receive: a press on the bar starts a drag with capture, a move maps the pointer back to a document line in the range the bar was drawn for — the lines the preview can reach, not every line the file holds — and a release ends it, so the bar and the thumb's drag cannot disagree about where the end of the document is.

The same messages carry a selection. A press that is not on the bar starts one, a drag extends it, and both ends of it are places in the text rather than points on the screen: the frame hands back the lines it painted with where each run of each line landed, and a point is turned into a (line, character) against those, so a selection survives the window being repainted and a point that runs off the text takes the nearest end of the line instead of being lost. The selection is painted into the frame rather than drawn over it — the run under it is split and drawn in up to three pieces, the middle one over the theme's own highlight colour — which means changing a selection costs a re-render of the window on screen; a screenful of lines is cached by then, so it is a repaint rather than a re-parse. Copying reads the same painted runs, so what is copied is what was on screen, and the lines a selection touches are joined with Windows line endings. The clipboard itself is the system one: a movable block of UTF-16 handed over with `SetClipboardData`. Keyboard copy is the piece of text editing that cannot arrive as a message — the preview never takes focus, so it would never receive the keystroke — so it is polled the way the rest of the app reads keys that belong to it: `Ctrl+C` only while there is a selection to copy. Selecting everything is the menu's `Select All` instead, which takes the whole frame, the range a Copy with nothing selected would have taken anyway. The right-click menu is asked for its command rather than posting one, so it needs no message loop and the preview never has to activate.

All of it is full mode's. With `Enable Text Preview Full Mode` off, the renderer is handed a frame that does not scroll — the text a box cannot hold is said in a line on the end of it, the way it was before any of this — the preview keeps no state to select into, and the pointer over it closes it the way it closes any other preview.

What makes all of that possible is one published pair of regions: the journey from the point a text preview was opened from — the cursor that hovered the file, or the middle of the focused item — to the preview, and the preview itself, both in screen coordinates, with the margin a hand that overshoots needs beyond the preview's far edge. Their shape is the point. A preview is placed *beside* what it belongs to rather than over it, so the pointer has to travel to reach it, across a gap and sometimes against the side the placement chose, and the journey is what that crossing is: it reaches the preview's *nearest* point and stops there, so everything it covers away from the preview is the row of the file list the pointer crosses, and it is as tall as the crossing rather than as tall as the preview. Reaching across to the preview's far corner instead — the box around both rectangles — covers the whole column of the list between the pointer and the preview, and inside the region nothing under the pointer is resolved: a text preview as tall as the display put every file in that column out of reach for as long as it was up, which read as previews failing at random in a list beside a text preview and never in one beside an image. The one place the pair reaches past the preview is the edge the journey ends at — the right edge for a preview placed to the right of the cursor, the left edge for one placed to the left — because the pointer is still moving when it arrives and what waits there is usually the scrollbar, a thin target at the very edge of the frame: the `text_scroll_far_edge_grace_pixels` setting is what keeps a hand that overshoots it from taking the preview down with it — forty logical pixels at the display's DPI, read from the configuration each time the regions are published rather than baked in, so the distance is a setting as well as a constant. Nothing past the near edge is added, since the pointer has already stopped there. The pair is published for any text preview in full mode, scrollable or not — resting on a preview is how it is selected from, and a document that happens to fit still needs that. It is recomputed from the preview loop on every tick, so it tracks the window as it is moved, and two flags published beside it say whether the preview on screen can scroll and whether the pointer is being held at all. Both are atomic reads, so the hook's check for them costs nothing until a text preview is actually up.

The Explorer hook asks whether the pointer is inside that region, and answers exactly one question with it: whether the pointer is on its way to the preview. A move is normally what resolves the item under the pointer and drops a preview whose file is no longer under it, and on the way to a preview the item under the pointer is the preview rather than a file, so while the pointer is inside the region and over no file the preview stays, and the sweep of the mouse-delay path that would raise a preview for nothing is skipped. It does not decide what is *under* the pointer: another file takes the preview over the moment one is under it, inside the region or out of it. Nothing is held over from one poll tick to the next either — the answer is read from the region as it is published, so a pointer outside it is treated as it was before the pointer ever touched the preview — and a pointer that is over the preview rather than over Explorer is not read as the user having left Explorer, since a preview is drawn on top of the window it belongs to and the check that asks whether the pointer is over Explorer cannot see under it. The wheel hook asks for the preview's own region before deciding whose wheel it is — the wheel belongs to the preview while the pointer is on it or just past its edge, not while the pointer is still crossing the row in front of it, where the wheel is Explorer's. The regions are withdrawn when the preview is hidden, so nothing else in the app has to know which previews scroll.

A theme or Markdown-mode change is different from a background change, and the preview loop treats it as such: a text preview's colors and glyphs are in its painted frame, so `Refresh` rebuilds the visible preview from the hover it came from (recorded when it was shown) instead of recompositing the frame it already has, while every other format only needs the recomposite.

Painting goes through GDI into a surface of its own: a memory DC with a top-down 32-bit DIB section, filled with the theme's background, block decorations written directly into the pixels, and every run drawn with `ExtTextOutW` against an opaque background rectangle — which is also how a code block's band and an inline code span get their fill. Fonts are created per style and size, once per paint, and the DC is handed back its original object before they are deleted, so a hover leaves no GDI objects behind. The frame that comes out is forced opaque on the alpha byte on its way out: a text preview is a page, not a cut-out, and the same composition path that paints a PDF's white page then composites it unchanged in every `transparent_background` mode.

## Video Process Lifecycle

`ffplay` is the only long-lived external process the app spawns. It is started per hover, its own window is used as the preview surface while the layered window stays hidden, and it is stopped when the hover ends — switching to another video, switching to an image, leaving the file, disabling previews, a display change, or system suspend.

Stopping is kill-only: the app requests termination and never waits for exit, because a process stuck in kernel I/O cannot be terminated by anyone in user mode, and an unbounded `wait` on the Explorer hook thread would freeze hover tracking for good. The PID of the last spawned player is therefore kept until the process is confirmed gone rather than cleared on the spot, and two checks recover a player that survived its stop: the Explorer hook re-checks the recorded PID once a second while no file is hovered and no keyboard preview is up, and the preview thread re-checks it before spawning a new `ffplay`, so a new preview cannot stack a second player next to a stalled one. Both checks terminate only when the recorded PID still belongs to `ffplay.exe`, read from the same process handle that is terminated, so a recycled PID can never hit an unrelated process; the record is cleared only after the process is gone, through a compare-exchange so a freshly spawned player's PID cannot be wiped by a stale check.

## Explorer Hook Flow

1. Detect active Explorer window and focused or hovered item via HWND/class matching and UI Automation, with input-grace helpers (should_probe_keyboard_focus, should_probe_hover_resolver, should_probe_stationary_hover) throttling probes to recent user activity and a stationary_hover_probe_done latch capping stationary-hover work to a single probe per parked cursor. A shell that answers a cursor probe too slowly too often (three probes over 700 ms) puts the cursor probes on a pause — the pause stops the asking and nothing else: the preview that is up stays, because it belongs to the file the cursor was on, the keyboard's turn is left as it is, and the preview is withdrawn only when the cursor leaves that file, which would otherwise strand it on a file the pointer is no longer on. The element a keyboard preview is resolved from is the focused one, or — when the view reports its list as focused while drawing the focus on an item, as the search results view does — the item of that list's own selection that carries the keyboard focus. A focused item that is a search result has no folder its name can be found in when the results span folders — the folders they have in common are the last place the files under them are — so the path is asked of the item itself: its own accessible value first, then the accessibility provider at the item's box, at the text the item exposes before anywhere else and then at points inside the box, which is where a view that exposes no text child keeps its name; the shell data model and the view's own focused item are asked for that box beside it. Every answer is taken only when it names the item, so a box that a scrolled list moved under cannot preview the file that took its place. A name no folder those results share can hold is walked for *below* that folder — the walk the search-root index makes, given a budget a probe can afford — because a search that began there found the file in one of the folders under it, which is the one place the shell's name does not point at.
2. Treat a wheel tick as input when the wheel is driving Explorer (the pointer is over it, or over a preview window that covers the pointer while Explorer still receives the wheel). The wheel moves the list under a stationary cursor, which changes the hovered item without any mouse movement: the stability window restarts while the wheel turns and the latch is reopened, so when the list settles the item that landed under the cursor is resolved and previewed (or the preview is dropped when that item is not media). A `ScrollSettleProbe` only acts on an item that survives two consecutive probes, because Explorer can still be animating the scroll. A scroll also ends keyboard ownership: the keyboard preview is closed, the pointer freeze is released, and the recent-keyboard-input window ends, so the mouse preview takes over the item under the cursor.
3. Treat clicks, Enter and the navigation keys as user navigation. A folder probe runs at the active cadence for a moment after such a press, so a folder that press opens is recognized before the user's next key press rather than up to a full idle interval later. Once the new view has settled the post-folder-change suspension lifts on its own, so the item that landed under a parked cursor previews without a mouse move, and the first navigation key press after the change previews the item it selects — the gate lifts on a fresh press transition (never on key-down state left over from the navigation that opened the folder), so that press is no longer swallowed as a focus baseline. A folder change that no input precedes (a programmatic renavigation, a network refresh) still waits for user input, and the auto-focused first item still never previews without a key press.
4. Normalize the resolved path and validate the file extension. The `.ts` and `.mts` extensions are shared with TypeScript sources, so those two are additionally confirmed by a short MPEG-TS sync-byte probe (`src/video_formats.rs`) before a video preview is started. The gate is what the file *is*, asked the way the renderer asks it — a video first, then a PDF, then the text lists, then the image extensions — with that kind's `Toggle Preview Types` gate applied on top, so a file whose kind is switched off resolves to nothing rather than to another kind's preview.
5. Send `Show` or `Hide` messages to the preview thread via channel.
6. Cache folder and Shell view data to reduce repeated COM work, and bound the walk that builds a Shell view index by time: it costs a COM call, a file check and a media-gate test per item on the hook thread, so a view of several hundred items is walked short rather than allowed to hold the loop for seconds while the pointer waits behind it — and the walk is then finished on a thread of its own that claims a COM apartment before it starts (every Shell call is refused without one), one per view, with nothing waiting for it. The short index is therefore a moment rather than a verdict: a file it did not reach is in the complete one the next lookup reads, which is also kept longer (30 s against 5 s) because it is the one a walk of the whole view paid for. An index that is *due* for a rebuild is read until its replacement lands rather than dropped — an index being old is a reason to walk again, not a reason to stop answering — and everything cached about a view is dropped when the location changes, because a folder remembered for a window and an index of its items describe the place the window has left.
7. Keep keyboard and mouse precedence explicit: an arrow-key preview owns the screen and is never dismissed by the parked pointer (a wheel scroll does end it, handing the screen back to the mouse), while a mouse preview is still dismissed the moment the cursor touches it. Each keyboard spawn measures the preview's own on-screen box (`preview_screen_rect`) and, when that box covers the cursor, freezes the pointer-driven triggers — `should_probe_keyboard_focus`'s companion `should_probe_preview_hover`, the hover resolver/folder probe, and mouse hover previews — until the cursor is moved more than the pointer tolerance (20 px), so jitter cannot end a keyboard preview. That tolerance is what a move has to clear for the whole of the keyboard's turn, not only while the box happens to cover the cursor: a navigation key press puts the keyboard in charge of the screen (`keyboard_screen_owner`), the state survives the keyboard previews it opens and closes, and while it holds the pointer-driven hover path is skipped even with no preview on screen. Without it, a focused item that cannot produce a preview — a file whose kind is switched off, a result whose path could not be resolved — ended the keyboard preview and left the parked pointer free to raise a preview of whatever it sat on, which the next key press dismissed in turn: on a large search-result view, where the items the keyboard walks are the ones still being resolved, that read as the two previews fighting over the screen. The focused-item baseline — its name *and* its box, so two results that share a name are two items — is cleared on mouse movement, and the focus observed after that acts immediately, so the first navigation key switches to the keyboard preview instead of being swallowed as a fresh baseline. When the mouse does take over, the file that was shown is latched (`SuppressedHover`) the way any dismissed hover is: held off the mouse path for the same-file rehover delay — long enough that the hand-over cannot flash it straight back — and released sooner when the cursor resolves a different file. A probe that meets the latch stays open instead of being spent, so a pointer left parked on that file previews it as soon as the delay has passed.

## DPI Awareness

The app sets per-monitor DPI awareness v2 on startup, with a fallback to per-monitor DPI awareness if v2 is unavailable. This avoids scaling artifacts on layered windows when Windows UI scaling is above 100%.

## Preview Window Placement

The preview is bounded to the display nearest the hovered cursor or focused item rather than the whole virtual desktop. Bounds are resolved through `MonitorFromPoint`/`GetMonitorInfoW`, falling back to the virtual screen when the monitor lookup fails, so the window no longer spills onto a neighboring display.

Each update repositions the window before installing the new frame or spinner. Crossing between displays of different scale raises `WM_DPICHANGED`, which resets the preview, so installing the content first would discard it and leave the previous display's image stranded on screen. For the same reason, the layered surface is painted before the window is revealed.

Preview size is derived from the media's native dimensions and the `preview_scale` setting, which is either a percentage of the native size or `fit` for the largest size the display area allows. The requested scale is always capped by the free space on the chosen side or quadrant, so a preview can never be clipped by the display edge — a large image at a small scale shrinks to fit, and a small image at 400% or fit-to-screen is reduced to whatever the display can hold. The same scaling is applied to the decode request, so image, GIF/WebP, and video previews all land at the computed size.

Where the preview lands on that side differs between the two position modes. `Follow Cursor` fills the roomiest quadrant around the cursor, growing away from it in both axes. `Best Position` places the preview beside the cursor or the focused item — on whichever side has more room for it — and centers it on the same line: `centered_top` puts the preview's middle on the cursor's own row (or the focused item's), and clamps that to the display, so a preview that fits under a cursor near the top edge sits where the cursor is, and one tall enough to reach an edge moves only as far as the edge allows. Before that, both modes centered the preview on the *display*, which for a cursor near the top put most of the preview below it and away from what was being hovered. The rule is shared by every format — image, GIF/WebP, video, PDF and text — because it is part of the layout both mouse and keyboard previews are computed from.

Keyboard previews are placed next to the focused item, which can put them over a parked pointer. That is allowed: while a keyboard preview is up it stays topmost and the pointer is not treated as hovering it, so it cannot be cancelled or made to blink by a cursor that happens to sit underneath. The hook confirms this from the preview's own box (`preview_screen_rect`, taken from the layered window or the `ffplay` window once visible) rather than from a cursor position test, and holds the pointer off until the mouse is moved on purpose.

## Configuration

Configuration is stored at `%APPDATA%\rust-hover-preview\config.ini`. Changes are detected by the config watcher thread and applied without restarting the app.

Themes the user adds live in `%APPDATA%\rust-hover-preview\theme`, beside `config.ini` and created on first run: a `.tmTheme` file there is listed by the tray under its own file name (the stem, `atom-one-light` for `atom-one-light.tmTheme`), read from disk the first time a preview asks for it, and re-read whenever the tray menu is built, so a file added, edited or repaired is one menu-open away from taking effect rather than a restart. The folder itself is only ever listed — a file's contents are not touched until it is chosen — and it cannot shadow a bundled theme: a file theme is written `theme=custom:<name>`, while `light` and `dark` on their own always mean the bundled Atom One Light and One Dark Pro. A file that cannot be read or is not a theme is painted with the default, which is what the menu marks while the name it was chosen under stays in the file.
