# Architecture (compact)

> How the app is put together, for a new contributor and for a tool that has to find something fast. `path::Symbol` is ground truth in code — read the code before changing behavior. Prose says what a thing is _for_ and how the pieces talk; the symbol lists are the map you grep from.

**The whole thing in one paragraph.** Hovering a file in Explorer spawns nothing and opens no document. A low-level mouse hook notices the pointer entering an Explorer list item, asks the Explorer window _at that screen position_ what file lives there, and asks a route what kind of file that is and which of five drawing hands should draw it. If the answer is cheap — a still image, a PDF page, a line of text — an in-process reader produces a bitmap on a short-lived worker thread and a layered, non-activating window composites it over Explorer. If the answer is expensive or inherently external — an Office document, a book, an archive, a video — an engine process is started, tracked on disk, and later retired. Pressing the pin key freezes the hover machinery and grows that same window into a persistent panel you can walk a folder with. Everything below is detail on those five steps: sensing input, deciding a kind, staying inside a memory budget, caching what was already made, and cleaning up every process we started.

## Runtime threads (`src/main.rs`, `src/app/`, `src/shell/`, `src/ui/`)

> Who runs where. Main boots and owns the tray loop; Preview owns the window; hook threads only sense input; heavy work (Office, probes, loads) runs off those loops so a stall never freezes hover or paint.

The app is a hover preview for Windows Explorer: you point at a file, you see it. That single constraint decides the whole process shape. Explorer owns its UI thread and will redraw it whenever it feels like it, so nothing of ours may ever block it — a preview that takes 200 ms to appear is a preview the user has already moved off. So input is _sensed_ on near-free hook threads that do nothing but notice, every decision that can be slow is pushed onto a thread that has no window to freeze, and exactly one thread owns the visible surface.

**Window styles.** `WS_EX_LAYERED` means the window has no background of its own — every pixel arrives via `UpdateLayeredWindow` with an alpha channel, which is what lets a preview be a rounded, partly-transparent card floating over a folder view. `TOOLWINDOW` keeps it out of Alt-Tab. `NOACTIVATE` is the important one: the window can be hovered and clicked but must never take keyboard focus, because taking focus from Explorer would cancel the selection the user is about to preview. `TOPMOST` because it has to stay above the Explorer window it is drawn over — unless `pin_always_on_top` is off, where the pin is an ordinary window that keeps the place the user's own clicks gave it and wears a taskbar button of its own while it is up.

**Cadences.** The preview thread is not an event loop with a 16 ms tick — it sleeps on a message and only wakes when it has something to do. A static preview redraws at most every `STATIC_WAIT_MS`; a pinned one redraws four times as often (`STATIC_PIN_WAIT_MS`) because its caption carries buttons the user is actively aiming at. Media needs a steady heartbeat rather than redraw-on-message, so `STATIC_MEDIA_REFRESH_MS` and `POINTER_HOLD_HEARTBEAT_MS` keep a playing preview alive and a held pointer recognised. Animation runs on a 60-second tick because it only needs to notice a new frame source, not drive one.

**Hook threads never touch pixels and never block.** `WH_MOUSE_LL` / `WH_KEYBOARD_LL` callbacks run inside the OS input path; if one blocks, the whole desktop stutters. They set a flag or bump a counter and return in under a millisecond. Everything expensive — reading the Shell view, probing a video, launching an engine — happens later, on a thread with no window to freeze.

**STA** (single-threaded apartment) is the COM threading model Office requires: every COM object an out-of-process Office app hands back belongs to the thread that called for it and must be released on that thread. The Office worker is therefore STA and runs a message pump (`OLE`), because without a pump an OLE call would deadlock. It is deliberately never joined — shutting an Office app down cleanly is not something this process can be trusted to finish before exit.

Single-instance: mutex first, before DPI/COM/config/threads. 2nd proc exits silently. `Local\` = per-session. The named mutex is the cheapest possible arbiter of "am I the one?". Taken before anything else, two instances launched at the same instant cannot both load config, both install a hook, and both put a window on screen. `Local\` rather than `Global\` scopes the name to the logon session, so a second user on the same machine gets their own copy instead of being refused by the first user's process.

AFK/engines: `app::afk` clock from hook's `ExplorerState`; an engine set to `Until Away` dies after `Engine → Away Timer` (default 1min) with Explorer unreachable; any other `… TTL` item uses that idle time instead. Engines are expensive to start, so the app keeps them warm between hovers. The clock is not "time since last hover" — it is "time since Explorer was last reachable and focused", because a preview engine the user cannot see is a process the user cannot tell is running. `Until Away` — the item every TTL submenu ends at, and the default — is that rule, and giving an engine a time of its own replaces it: the engine is then kept for its own idle TTL, and `Indefinitely` for the life of the run.

**readers/ vs engines/ is the single most useful distinction in the tree.** A _reader_ runs inside this process and returns a bitmap or a block of text; it is fast, cancellable, and free once it returns. An _engine_ is another process, usually a tool the user installed (LibreOffice, ImageMagick, PeaZip, Calibre, FFmpeg's `ffplay`, mpv, f3d) or Windows itself (Media Foundation, WebView2). Engines cost a process launch, cannot be cancelled mid-flight, and need a reaper — so the app reaches for one only when a reader genuinely cannot do the job. Those seven, with Microsoft Office, are the app's eight optional external engines; every other kind is drawn by Windows itself or by a reader written into the app, which is why installing one is what unlocks a kind rather than what enables it.

**formats/** holds no rendering at all. It answers questions about a file: what is it, who should draw it, is it a list, is this codec present. Keeping it separate is what lets the hook thread, the loader thread, and the layout code ask the identical question and get the identical answer.

**text/** holds the things that are painted rather than decoded — a page of text, an archive listing, an audio card, and all the pin chrome. They share one paint path and one theme, which is why they live together.

## Media pipeline (`formats/routing.rs`, `native_formats.rs`, `lists.rs`)

> Single decision point mapping a file to a kind and a drawer. Hook, loader, and layout all ask the same order so a file never previews as one kind and renders as another; `resolve` answers kind + drawer + backdrop in one call.

Three different callers need three different amounts of this answer. The hook needs the kind alone and must return in microseconds. The layout needs to know whether the thing will be a window of its own before it can place anything. The loader needs to know who draws. Rather than let each ask its own partial question — and drift — there is one kind order and one function that reads it.

Kind order (load-bearing, asked by hook + loader + layout identically): `video, audio, ebook, archive, peazip, calibre, office, libre, magick, design, vector, text, font, models, picture`. The order is not alphabetical and not aesthetic; it is a set of tie-breaks for extensions that two systems both claim. Video goes first because only the file's actual bytes can settle whether `.ts` is a transport stream or a TypeScript source, and only one of those two answers can come from the bytes. Pictures go last for the mirror-image reason: `.dds` and `.svg` are claimed by both a name list and a content sniffer, and a picture reader is the safe last answer.

- Video first (only content settles `.ts`/`.mts` vs text); pictures last (`.dds`/`svg` double-claimed).

Three callers want three different amounts of this answer, and all three read the one table. `kind_of` opens the file and is only legal on a hover. `kind_of_name` never does — it exists for the pin walk, which must classify hundreds of siblings without opening any of them. `named_as` is the exhaustive `match` that answers "would this kind claim this name", used by layout to reason about a specific kind it already knows about. A test asserts all three agree on the same inputs, which is how the three cannot rot apart.

- `routing::kind_of` (content+name, hover gate) vs `routing::kind_of_name` (name only, folder walk — no hydration) vs `routing::named_as(kind)` (per-kind check for layout). A test asserts all three agree on the same inputs, which is how the three cannot rot apart.

- `routing::resolve` → `Route { kind, DrawnBy, backdrop_of, ... }`; `DrawnBy` = who draws; `Page/Drawing/WebPage/Backdrop` enums; `engine_kind_of`, `html_is_engine_drawn`, `page_runs` vs `draws` (program vs picture).

`resolve` exists so a caller who wants the whole route pays for each probe once instead of each sub-question re-finding the file for itself. `Route.content` is what the bytes said, `Route.named` is what the name's lists claim, and `Page`/`Drawing` split the two kinds that are really two kinds each (book vs comic, SVG vs metafile). `DrawnBy` is the answer the window actually cares about — `Native`, `MediaEngine`, `Card`, `WebView`, or `Nothing` — and note it deliberately excludes engine kinds: _which_ engine is a fact about the machine, not about the file. `Backdrop` is a second exhaustive match so the six `current_*_background` settings are read once, in one place.

- `native_formats::job_for` → `NativeJob` (in-app reader for kind); `content_type::Probe` → `Content/head` (16B → 4KB); `head` still-vs-moving: GIF blocks, WebP `ANIM`, PNG `acTL`, ftyp brands, JXL header via decoder.
- `probe::GUARDS` — the names two kinds' lists both hold, settled from the file's own head rather than from list order: `pdb` (an ebook vs a program database), `vhd` (VHDL source vs a disk image), `dif` (a spreadsheet vs a DV stream). A kind the bytes name outright is that kind, a format no kind previews is drawn as nothing, and `is_video`/`is_audio` ask the route the way `is_text` already did — the `.ts`/`.mts` pair both video lists carry is what a name-only answer got wrong, a source whose probe never answered and whose pin held its swap on that same wait.

- The text kind's two gates ahead of its lists, read by every caller alike (`claim_text` and `named_as`, so the hook, the walk and the loader cannot disagree; `load_dispatch` asks the secret one again where the page is built): `text_dont_preview_secrets` (default `true`) refuses what `secret_files::is_secret_file` names — `.env` and its variants, `id_rsa`/`credentials` and their suffixed copies, key, certificate, keystore and password-database extensions, and anything under `~/.ssh`, `~/.aws`, `~/.gcp`, `~/.kube`, `~/.docker` or a coding agent's credential path — with `*.pub` and the `.env.example`/`.sample`/`.template`/`.tpl`/`.defaults` templates exempt, since those are the ones a repository means to be read; `text_show_extensionless` (default `false`) extends the kind to a name with no extension at all, where the names list covers only the repository files it names. A refusal is a name no kind claims, not a text preview of nothing, which is what keeps the hover's window away rather than opening one that is empty. And a folder is never a file whatever its name looks like (`probe_trace::is_media_file_with_facts` asks `Facts::is_file` first), so an extensionless folder is not walked into as one.

`content_type::Probe` is the read-and-forget half: sixteen bytes tell you most of a format, and if they do not you escalate to a 4 KB window. The still-vs-moving question is the interesting one, because a GIF and an animated WebP are the same extension to a user and completely different to a preview. GIF has no animation flag at all, so its frames are counted; WebP carries `ANIM`; PNG carries an `acTL` chunk before the image data; MP4 and friends carry an `ftyp` brand list; JPEG XL has no usable header of its own and is asked of its decoder.

An `ftyp` is a _run_ of brands, not the one at the front — an animated AVIF is ordinarily written `avif` in front and `avis` behind it, so the whole list is read and only a _sequence_ brand (`avis`, `msf1`) makes a sequence. `mif1`, the generic HEIF _image_ brand a single-image HEIC is written under, is the still picture it is. An AVIF carrying a sequence brand is recognised rather than played: the media engine Windows has refuses it (the codec is installed and what is missing is a demuxer for the image-sequence brands), so the still path draws what it always drew. A `.jxl` is likewise recognized in both the forms it arrives in — a naked codestream and a container.

- `*_formats` keep only list-unanswerable Qs: `text_formats` (dot-file + name list), `archive_formats` (`tar.gz`), `video_formats` (ffmpeg split + MPEG-TS sync probe), `office_formats::{app_for,page_engine,OfficeApp,OfficeContainer}`, `ebook_formats::page_spelling`, `libre_formats::engine_page_kind`, `magick_formats::is_engine_picture`, `peazip_formats::Backend::of`; `font/calibre/audio` = row/table probes. Each `*_formats` module exists because one specific question cannot be answered from an extension table. `tar.gz` is two extensions and one archive. `.xlsx` is both an Office container and a book-shaped thing. `.ai` is either a PDF or an EPS. Anything that genuinely is a table lookup stays a row in `lists`.

- `PreviewType` gate per kind (`text_preview_enabled`, ...); off kind → layout no-size → hover dropped, in-flight replay dropped. `Document` kills Office procs (from tray, worker uncancellable); `Vector/Fonts` releases browser. `render_html` (`htm/html` only) switches Text draw → WebView page, kind stays `Text`.

The gate is the user's on/off switch for a kind, checked before any work happens. Turning a kind off has to unwind cleanly: the layout gets no size, so the hover is dropped and any already-running replay for that hover is thrown away rather than revealed. Turning `Document` off is special — an in-flight Office render cannot be cancelled, so the tray kills the started processes instead of asking politely. `render_html` is the one place the drawer changes without the kind changing: an `.htm` is still "text" to the user, but the Text drawer paints glyphs and cannot do layout, so the browser engine draws it instead.

- Measure off tick for every kind: `measured_off_the_tick` keyed by (file,version,against); miss → spinner + replay (`VideoProbed`, `OfficeRenderReady`, box answers) — text, design pages and pictures joined the PDF, comic, engine, audio and video questions. A wait that ends with nothing to show ends as the pin's own cross, in the box the wait had, and comes down after `FAILURE_MARK_MS` (3 s) rather than blinking the spinner out, which a hand cannot tell from a wait still running. `effective_preview_scale` / `scale_in_room`: single place for size; `preview_scale, video_scale, audio_scale, animated_scale, ebook_scale, document_scale, font_scale, design_scale, vector_scale, text_scale`.

Measuring a file means opening it, and opening it on the preview thread is exactly the stall this architecture exists to prevent. `measured_off_the_tick` is the escape hatch: the loader says "I do not know this one's size yet", paints a spinner in a guessed box, and hands the open to a worker thread. When the answer lands it arrives as `VideoProbed` or `OfficeRenderReady` and _replays_ the hover at the correct box. The scale functions all funnel through `effective_preview_scale` / `scale_in_room` so "what fraction of the screen may this kind take" is one calculation, not ten.

## Read guards (`cloud_files.rs`, `content_type`, `paths.rs`, budgets)

> What keeps a hover cheap and safe: never download cloud files, never allocate unbounded, never hold the global config lock across disk IO, never trust a header size. Both hook and loader ask the same gate so neither can reach what the other refused.

Every one of these is a guard against a file that lies. A size field can claim 400 GB, a cloud placeholder can be a reparse point that triggers a 2 GB download, a header can claim 65535×65535 pixels. The rule is that no allocation happens before the number that justifies it has been read, and no disk read happens without a bound.

- Ceiling: `decode_budget_gb` (1GB, `Performance → Decode Budget`) checked pre-alloc incl. inflate; `catch_unwind` → miss; huge alloc = abort, so budget first (`image` limits + 3 canvas allocators + GIF/WebP/WIC).

The failure mode this prevents is not an exception, it is a process abort. A Rust allocation over the address space the OS will grant terminates the process before any `Result` exists, so `catch_unwind` cannot help and the budget check must happen _before_ the allocation, not after it. "Incl. inflate" means the compressed size is not the size: a 64 MB `.svgz` can inflate to 1 GB, and that number has to be projected before the inflate starts.

- `cloud_files`: attr-only check (no open/download) from hook's single dir-entry read (present/file/version/content-here). Same `HoverFacts` on preview thread: one `content_type::Probe` + `resolve` + `CONFIG` snapshot (drop `CONFIG` lock before IO).

The check is attributes only. Opening a OneDrive placeholder hydrates it — megabytes over the network, on a hook thread, while the user is moving the mouse — so the guard reads what the filesystem already knows (is this a file, does it have content here, what version) and never opens. `HoverFacts` is the struct that carries those answers across the thread boundary so the preview thread re-reads nothing.

- Images: header first for box; budget in `u64` (no `u32` wrap); no-dims → decode but don't cache. DDS: 148B header + first-mip/first-face only; short read = no preview; `dds_background` separate (`MediaType` own kind).

The header is read before the image so the spinner has the right box, and the budget is arithmetic in `u64` because a 32-bit multiply of width × height × 4 wraps below 4 GB and hands the allocator a plausible-looking number. A file with no dimensions at all is decoded but never cached — there is no key that would ever let the app notice the file changed. DDS gets a hard cap of the first mip and first face: a cubemap or a mip chain is hundreds of megabytes of data for a 256×256 hover.

- Archives: TOC only (zip central-dir, 7z header, RAR walk, tar 512B blocks); 20k entries, 300-char names, cancel flag; `.tar.gz` inflate capped 64MB → "stopped early".

A listing is read from the archive's index, never by extracting. Every container has a different index — zip's central directory at the end, 7z a header, RAR a chain of blocks, tar literally 512-byte headers back to back — and each is bounded independently: at most 20k entries, at most 300 characters of name each, and a cancel flag the user can trip.

- Office: 8B OOXML/OLE check only; cloud/zone-id/long-path → temp copy, read-only/hidden/no-MRU/close-unsaved; ask at hover, not rest.

Eight bytes distinguishes a zip-container OOXML file from a legacy OLE compound one. Everything after that is an engine. When the file is remote, carries a Mark-of-the-Web zone identifier, or has a path Office will not open directly, it is copied to a temp file first and opened read-only and hidden so it does not appear in Office's recent-files list, with unsaved-changes prompts suppressed. The check happens at hover time, not at rest time, so a folder of remote documents costs nothing until pointed at.

- UI Automation: `CUIAutomation8` + client timeout (fallback legacy unbounded); timeout = miss.

**UIA** (UI Automation) is Microsoft's cross-process accessibility tree — the only supported way to ask Explorer what is under a point without injecting code into Explorer. `CUIAutomation8` is its COM interface. It is asked with a client-side timeout because a hung accessibility provider would otherwise hang the hook thread forever; the pre-v8 fallback interface has no way to bound the call, which is why it is second choice, not first.

- SVG: whole-read under budget (incl. `.svgz` inflate); fonts: whole-read, parse `cmap`+`name` only; WOFF per-table inflate, WOFF2 Brotli to last-needed table; `.ttc` → copy `ttc_face` (1-10) beside profile (`file,version,face`).

An SVG cannot be header-measured usefully and is small enough to read whole. A font is read whole but parsed for two tables only: `cmap`, which says which Unicode codepoints map to which glyph, and `name`, which is the human-readable family name. WOFF stores each table deflated separately so a single table can be inflated alone; WOFF2 compresses the whole file with Brotli, which cannot be partially decompressed, so the read stops at the last table the preview needs. A `.ttc` holds several faces and must be copied into the WebView2 profile directory as a single-face file, named by file, version, and face index.

- HTML (`render_html`): app reads nothing, budget N/A; browser sandbox `allow-same-origin allow-scripts`, no pops/forms/top-nav/autoplay/file-access/fullscreen; `BROWSER_ARGUMENTS` no host; `plain_path` + `file:///C:/…` URL versioned by mtime.

For an HTML page this app reads nothing at all and delegates the sandbox decision to the browser engine. The two permissions it does grant are the minimum a page needs to run, and everything else a page might reach for is denied. `BROWSER_ARGUMENTS` lets the user add flags but is filtered so a `--host-rules` cannot turn the browser into a general-purpose proxy.

- SVG/font pages: `pointer-events:none` + `draggable=false` (+`user-select:none` specimen); HTML keeps pointer. Pinned engine drag: `settle_pinned_engine_press/drag`, `PinDrag::delivered`, `carry_pin_drag_with_the_hand` + `PIN_DRAG_*`; poll `preview channel` via `Carry` + deadline (no re-entrant pump).

An SVG or font page is drawn by the browser engine but is _not_ a document — it must never eat the click that was meant to select the file behind it, so pointer events and drag are disabled on it. An engine-drawn page (an SVG, a specimen) inside a pin needs the opposite: the drag has to be forwarded to the window that owns it, because the pin's own window only sees a child HWND in the middle. That forwarding polls the preview channel rather than running a nested message loop, which would re-enter paint and deadlock. **Inside a pin the page is one of two things, and `a_running_page_holds_the_band` is which** (it is `webview_preview::the_shown_page_runs`, so `render_html` plus an `htm`/`html` name): a page that runs keeps the pointer and stands in front of the pin as a window of the desktop's, while a document or a specimen is the pin's *picture* — its window lowered, invisible at one part in 255 and click-through, drawn into the band as a DWM thumbnail of its client (see "The page road").

## Caches

> What is remembered between hovers so the second look is free, and what key makes it valid. Frames are keyed by file version + pixel size (an edit or resize re-decodes); probes remember misses too so an unplayable file costs one probe, not one per hover.

Caching a hover preview is easy and caching it _correctly_ is the whole problem. The rule throughout: the key must change whenever the output would change. A file's bytes can change (version), the preview box can change (window resize, monitor change), the config can change (scale, backdrop, gate). Any key missing one of those will show the user a stale picture and be indistinguishable from a bug.

- Frames: `image_cache_mb` (128MB/2048/`0`=hold-none, one pool for hovers and pins, live-read, LRU-counter trim, oversize uncached) keyed (file,version,px). Miss → decode.

The frame cache is memory-only and bounded by `image_cache_mb`, a count ceiling of 2048 entries, and an LRU counter rather than a timestamp. `0` is a real setting, not "unlimited": it means hold nothing and always re-read. An image whose bitmap exceeds the whole budget is decoded for the current hover and then not stored, because caching it would evict everything else to hold one thing. The default is 128 MB because one decoded frame filling a large display is about 33 MB, and the cache is shared with pinned windows: at 64 a hover sweep evicted the frame a pin was decoded at, and the next take-up of that file paid a full decode again. It is also why `box_is_covered` is worth having — a frame decoded for a bigger box is every pixel a smaller one would have been given, so a shrink is a stretch rather than a decode and the larger pixels are still there for the enlargement back.

- Disk: `document_cache` `%TEMP%\rust-hover-preview\document\<key>.{pdf,png,none}` (`document_cache_mb` 256MB, LRU-read table, `hover_ended` at 0); magick `%TEMP%\...\image` (`image_disk_cache_mb`); separate folders so budgets survive restart. Text frames `text_cache_mb` (0 default) keyed (file,ver,opts,box,DPI,line); parsed doc keyed (path,mtime,len,theme,md-mode) + per-doc `styled_window` + `thread_local ParseState` (syntect `!Send`).

Disk caches outlive the process, so each keeps an LRU table it reads on startup. The `.none` extension is the point of the scheme: a file an engine refused to render is itself a cached answer, so the next hover costs a file-existence check instead of a process launch. Text frames additionally key on DPI and line because the same file rendered at a different scale or a different width is a different frame; the parsed (highlighted) document does not key on those. `syntect` is `!Send`, so its parse state cannot move between threads and is therefore `thread_local`.

- Subtitles: `%TEMP%\rust-hover-preview\general` (`general_disk_cache_mb` 128MB, LRU-read table, `0` = extract nothing → film drawn without them); one extraction slot (`claim` — a request for another film displaces the running one, which ends first within `EXTRACTION_HANDOVER_WAIT_SECS`); asked at launch, not probe (`extraction_due`: no sidecar, no copy yet, copyable tracks, budget > 0); a copy stops when the hover ends, the pin closes, or the pin is shown another file; `FINISHED_MARKER` written after the last file FFmpeg closed — a folder carrying it is a folder of whole files, and a half-written pass (zero-byte outputs) is ignored, deleted on the next pass and recopied; only small filter-drawable tracks ever named (`subtitle_filter`: sidecar beside the film or copied text tracks — never the film's own embedded track); `SUBTITLE_EXTRACTION_TIMEOUT_SECS` = 300; a pinned film is corrected when its copy is ready (`notify_video_subtitles_ready`) — mpv is handed the file down its pipe (`sub-add … select`, no relaunch, no black frame), and only FFmpeg's player, which can be told nothing, is begun again at the second the bar is showing.

A film's subtitles are a whole read of the film, so the copy is bounded three ways: one film at a time (a request for another drops the one running), one request per showing (asked at launch rather than at probe, so a copy only ever runs for a film actually put on screen and is asked for again the next time that film is shown), and one answer per folder (the marker says the pass finished; a pass killed with its outputs already open leaves a zero-byte file per track, and those folders are ignored — the repair for a folder of subtitle copies left half-written that kept a film unviewable for good). What the filter is ever handed is a sidecar or a copied _text_ track: a copy that failed is a film played without subtitles rather than one played from itself — its own track would stream the entire container before the first frame, measured at 15 s and 1.4 GB of reading against half a second and 41 MB from the copy — and a PGS track copied out as a `.sup` is a file the `subtitles` filter refuses outright, which used to take the filtergraph down with it. A pinned film is also corrected with the subtitles once its copy is ready, including a player a hover started and the pin adopted before the copy existed — by handing mpv the file, and only by beginning FFmpeg's player again, which is the one player that can be told nothing while it runs.

- Probes remembered: `ProbedGeometry` (incl. miss), `video_player::plays`, `audio_track::{Probed,Track,gain}`, pdf size, svg size, font parse, archive listing, `.none`/refused markers (office 2min, engine-refused run-long). WebView fail 1min; browser `note_unanswered`.

The rule is that a _negative_ answer is cached as carefully as a positive one. `ProbedGeometry` has `Measured` and `Unmeasurable` variants precisely so that "this file cannot be measured" is a memo, not a repeated probe. An unplayable video then costs one `ffprobe` for the life of the app rather than one per hover. Refusal markers expire on different clocks on purpose: a refused Office document may be fixed by the user installing something, so 2 minutes; an engine that refused on its own terms is remembered for the whole run.

- Temp sweep: `%LOCALAPPDATA%\...\update` cleanup; webview per-run profile `%LOCALAPPDATA%\...\webview\<pid>` + startup sweep; `engines\<pid>.state` + job `KILL_ON_JOB_CLOSE` (see Started Processes). Both of those folders are ones a test build keeps for itself, never the machine's — see [Test isolation](#test-isolation-the-apps-own-folders-under-cfgtest).

Everything under `%LOCALAPPDATA%` is swept at startup because it is keyed by pid and a crashed run leaves its directory behind forever. A **job object** is a Windows kernel object that owns a set of processes: when its last handle closes, every process in the set is killed. That is what makes `KILL_ON_JOB_CLOSE` the crash-safe half of engine cleanup — this process can die without running a line of cleanup code and the OS still reaps the children.

## Preview window (`ui/preview_window/`)

> The only visible surface: a channel-driven layered window. Hook posts `Show`/`Hide`, slow work replays the same hover when done; layout picks box + display, paint composites the frame. Hide and show race via a generation count so a late frame never resurrects a departed hover.

Three concerns, three files, one window. `layout` decides _where_ and _how big_; `paint` decides _what pixels_; the event loop owns the HWND and the message queue. None of them talks to Explorer, and none of them knows what a video is.

The hard problem is the race. The pointer leaves item A and arrives at item B. The hover thread hides, then shows; meanwhile a probe of A finishes and posts a frame. Naively, A's frame paints over B's preview — a flash of the wrong file, which reads as the app being broken. `HIDDEN_EPOCH` is a counter under a mutex, incremented on every hide. Anything holding a computed answer carries the epoch it was computed under; before revealing, it re-reads the counter, and a mismatch means the user has moved on and the answer is dropped.

- Msgs: `PreviewMessage::{Show,Hide,...}`, `OfficeRenderReady`, `VideoProbed`; `PreviewMessage::PinUpdate` = explorer half (loop no-op). `hide_preview` (hook thread, `HIDDEN_EPOCH` count under lock) vs show (preview thread); newest-wins drain; `ShowWindowAsync`; stall `PREVIEW_STALL_MS` → hook ends warm engines. Reveal gated by `publish_pointer_item_box` + `read_failure_is_the_same_item`.

`newest-wins` drain means the queue is emptied and only the last message acted on — the intermediate hovers between two fast mouse moves are not worth a window operation each. `ShowWindowAsync` is used instead of `ShowWindow` because the call may come from the hook thread. `PREVIEW_STALL_MS` is the backstop for the pathological case: if the preview thread has said nothing for three seconds, the hook concludes the window is wedged and ends the warm engines rather than leaving them running forever.

- Layout: `layout.rs` + `dimensions.rs` + `preview_scale.rs` + `displays.rs::display_at` (`Desktop` real / recorder). `compute_mouse_layout` (Follow=roomiest quadrant; Best=`centered_top` beside cursor/focused item); `waiting_placement/flush_at_cursor` (spinner `WAITING_BOX`/arc box at pointer corner, 1px off); `AvoidMode/AvoidRegion` (Filename default, FilenameColumn, Details; shortest clearing step, sides preferred for columns, mouse held to pointer); keyboard anchors on item tail/middle; text re-measure at fitted width (`text_box_room`, `text_scroll_far_edge_grace_pixels`=40); audio card room-and-font from `audio_box_room` (`audio_scale`: that share of the work area in both dimensions, its margin read at the share's font, the card built at that font).

`displays.rs` is a seam: `Desktop` enumerates real monitors, and under the recorder it enumerates the recorder's virtual monitor instead, so a screen capture of the app looks correct. `Follow` places the preview in whichever quadrant has the most room; `Best` puts it beside the cursor or the focused item, which is what makes keyboard navigation usable. `AvoidRegion` is the setting that keeps the preview from covering the file name it is previewing: `Filename` clears just the drawn text, `FilenameColumn` clears the whole column as the view reports it, `Details` clears every column. `flush_at_cursor` offsets the placeholder box one pixel from the pointer so the cursor never lands inside the spinner.

- Paint: `paint.rs`, `surfaces.rs`, `pixels.rs`, `loading_paint.rs` (`paint_pin_spinner`, `PIN_ARC`); `WM_DPICHANGED` drops frame → replay; paint-before-reveal; spinner only past `spinner_delay_ms` (250ms); pin wait in media band.

Paint-before-reveal is the rule that prevents a flash of empty window: the frame is composited into the layered surface _first_, and only then does the window become visible. `WM_DPICHANGED` means the monitor's DPI changed (someone dragged the window to a different-scaled display, or changed a setting); the cached frame is now the wrong size, so it is thrown away and replayed at the new scale.

- Anims: `animated.rs` (`animated_scale` vs `preview_scale` via `image_is_animated`); `StreamedFrames→Vec<ImageFrame>` (GIF/WebP/APNG/JXL-live; `heif_sequence` wired but `None` → still fallback); `MIN_ANIMATION_FRAME_DELAY_MS`.

An animated image is not scaled by `preview_scale` — it uses `animated_scale`, because a multi-frame source held to a single preview's size rules is measured differently and would otherwise blow up mid-playback. Animation frames are accumulated into a `Vec<ImageFrame>` and only advance after `MIN_ANIMATION_FRAME_DELAY_MS`, so a source that claims 1 ms per frame does not spin the preview thread.

- Tone map (`tone_map.rs`): `hdr_tone_map=reinhard|aces|srgb|off`, `hdr_exposure`, at `load_static_image` top + `dds_image` per-sample; alpha untouched. Converts scene light to display range instead of clipping.

Tone mapping is the step between "what the file stores" and "what a monitor can show". A raw DDS or HDR image stores light values well above 1.0; without tone mapping those pixels simply clip to white and the highlight detail is gone. `reinhard`, `aces`, and `srgb` are three different curves for compressing that range; exposure is applied before it. Alpha is never touched — the alpha channel is not scene light.

- Codecs (`formats/codecs.rs::Row`, `wic_image`): WIC for HEIF/AVIF/JXL-still/WebP-still/DDS-first/camera-raw/bmp-icon-cursor (`CODEC_EXTENSIONS`, the names no decoder in the binary carries — a `.dib` is handed over as a stream with its file header put back, since the codec reads that header rather than the shape); ask at planned box; miss→`None`. `Codecs` submenu: MFTEnumEx (video/audio), WIC codecs+MIME (HEIF=container+decoder), ProgID (Office/Libre), loader version (WebView2), WinRT registration (PDF). FFmpeg presence cached per menu build (tray clears).

**WIC** (Windows Imaging Component) is the OS's built-in image decoder, and using it costs no process and no code. It handles HEIF, AVIF, still JXL, still WebP, first-frame DDS, the camera raws the Raw Image Extension adds, and the bitmap/icon/cursor resources, but it is asked _at the planned box size_ — WIC decodes to whatever dimensions you ask for, so asking early means decoding at full resolution and throwing most of it away. The tray's `Codecs` submenu enumerates what is actually installed (MFT = Media Foundation Transform, for video and audio decoders; MIME registrations for WIC; ProgID = the registered class id for an application; WinRT registration for the PDF API). Rows are presence-checked when the menu is built and the cache is dropped when the tray menu is next built, so installing FFmpeg mid-session is picked up by reopening the menu.

## Explorer hook (`shell/explorer_hook/`)

> How the hovered file is found. Resolves the item under the cursor (or keyboard focus) to a real path via the Shell view at that position — never by filename lookup or filesystem walk — then gates and notifies the preview thread. Throttles probes by user activity and display state.

This is the part that most needs explaining, because the obvious implementation is wrong. You cannot find a hovered file by listing a directory and matching names — Explorer shows search results, virtual folders, shell namespace items, and un-downloaded cloud placeholders, none of which correspond to a path. The only correct source is the Shell view object at the screen position: ask it "what is at this point", get the item, ask the item for its filesystem path.

Flow: detect window+item → wheel-as-input → nav keys → entry+`plain_path`+gate → `Show/Hide` → resolve-by-position (no fs lookup) → keyboard/mouse precedence. The order matters. Keyboard input is only consulted after the mouse has been ruled out, because arrow-key navigation must not steal the wheel or mouse behaviour of a folder the user is browsing with the pointer.

- Item: one batched UIA read (box, name, `ItemIndex`, acc value); point→row walk-up; keyboard: focused or selected-of-list + child text boxes (for `Avoid`). `view_bounds` clip; metadata line never resolves.

The UIA read is batched into one call for four values, because four separate calls cost four round-trips into Explorer. A point maps to a row by walking up to the nearest ancestor that reports an `ItemIndex`. `view_bounds` clips so a point outside the list resolves to nothing at all, and the metadata line at the bottom of a details view is excluded — it reports text for the whole selection and would resolve to the wrong file.

- View: match Shell windows by frame HWND; tabs = multi views per frame; showing tab = window-under-pointer/provider window; chrome-pointer → per-view ask + agreement rule; cache per window, drop on loc change. `IFolderView2::GetItem→SIGDN_FILESYSPATH`; claim-then-file; match-with-no-file ≠ fail; pointer double-look agreement; per-(item,window) memo.

One Explorer tabbed window can hold several folder views, so the frame HWND is only half the answer — the view is matched by walking up from the item's own window. `SIGDN_FILESYSPATH` is the shell property that yields the real path, and it can come back empty for shell namespace items that have no file; that is a _match without a file_, which is not a failure, it just means there is nothing to preview. "Agreement rule" and "double-look" are the same safety property asked twice: when the pointer is on Explorer chrome rather than inside a view, two independent asks must both agree before the app acts, so a stale view answer cannot hijack a hover.

- Place: folder+URL facts (`HoverLocation`, `location_fact_key`, canonicalized); missing fact = retry, not change.

The location facts are what let the preview know _where_ it is without re-deriving it. They are canonicalized first so two spellings of one path produce one key. A missing fact is treated as "try again" rather than "the location changed" — the alternative would make every hover of a slow folder look like a folder switch.

- Pace: `ExplorerState` (focus/visible/minimized/absent → `tick_ms`/150/500/1000ms); pin forces `ActiveFocus`; `app::afk`; keyboard poll in active path only (`focus_move_input/NavigationInput`, nav+type-ahead w/o Ctrl/Alt). Tray idle-waits; `ensure_noactivate_monitor` event+timeout.

The poll rate is the whole cost model: 150 ms when Explorer is focused and visible, up to 1000 ms when it is not, and zero work when absent. A pin forces `ActiveFocus` because the pin is a topmost window over Explorer and would otherwise make the app think the user had left. Keyboard polling runs _only_ on the active path, and only for navigation and type-ahead keys — a hook that watched for Ctrl/Alt would fight Explorer's own shortcuts. A reachable Explorer window with an open pin is answered as the active arrangement whichever of the two holds the keyboard, and read while a pin is up: a pin takes the focus off Explorer on purpose, and "showing but nobody in it" is a slower loop than `Timing → tick_ms` asks for and a stale one for the idle timer. Minimized Explorer, and Explorer behind a maximized window, are unchanged — there is no listing under the pointer in either.

- Restart: `TaskbarCreated` → rebuild collection, drop views/caches, hide, re-arm gate; slow-retry missing collection.

Explorer restarts (crash, update, sign-out) and every COM pointer into its windows becomes invalid. `TaskbarCreated` is the broadcast Explorer sends when it comes back. Nothing can be repaired incrementally: the window collection is rebuilt from `EnumWindows`, all view caches are dropped, the preview hides, and the gate re-arms. If the collection is not ready yet the hook retries slowly rather than declaring Explorer gone.

- Wheel: over Explorer or covering preview → reopen latch + restart hover clock; ends keyboard ownership. Text wheel: hook reads `mouseData` delta, swallows inside preview region only.

The wheel doubles as a hover signal: turning the wheel means the pointer is over the window the user cares about, so a preview that was suppressed reopens. It also hands control back from the keyboard to the mouse. The hook reads the wheel delta from `mouseData` directly rather than installing a second low-level hook, and swallows the event only when the pointer is over the preview's own region.

- Folder-change: post-press active cadence; suspension lifts on settle; box-change = gone (`read_failure_is_the_same_item`); programmatic change waits for input; auto-focus never previews. A pin whose file was handed to another program (`take_pin_handed_off`) suspends previews the same way — the press was the pin's way out, not a pick of the row it uncovered — and the anchor is re-taken from where the pointer stands, so the hold lifts on the hand's next move.

The last item is the subtle one. When Explorer changes folders _by itself_ — a refresh, an auto-arrange — the app waits for the user to do something rather than previewing whatever is under a pointer that is no longer meaningful. `read_failure_is_the_same_item` distinguishes "this read failed because the item is gone" from "this read failed transiently", which is what stops a deleting file from being retried forever.

- Picks: gesture = two presses inside `GetDoubleClickTime`; an unanswered place carries its baseline; `press_is_a_listing` (window is Explorer's or this app's own, still there, not menu-popup chrome — current _or_ previous tick); a press the pin itself takes is neither a pick nor a no-pick — its point inside the pin's own box whatever the hit test names under it (`press_is_on_the_pin`), or read on the tick that box changed under a hand nobody moved (`press_is_the_pins_own_gesture`); click read through own windows (`is_our_own_window` = preview, engine HWND/children, or the pin's own menu) else the focused item in the click's own place; item and view caches dropped on the foreground handoff; a click that answers nothing is held and re-asked while the pointer stays put, and given up the moment this app's own window moves (`preview_window_rect`, noted on every pinned tick), so a double-click that centers a pin is not answered against the point the move uncovered.

Four judgments decide what a press or a click means, and they are the whole of the pin's follow behavior. A gesture is two presses _inside the machine's own double-click time_ — the same window Explorer itself reads the double-click that opens a folder in — so the click on a file in a listing a double-click just opened is that file's pick, not a third press of the gesture; nothing else moves (a folder opened from the keyboard still does not change the window, and a click after the mouse has moved was always one of its own). A place the shell cannot answer for now takes the baseline with it — the only place in hand is the one the item moved out of — so the first read that succeeds after a folder change is compared against the folder before it and read as a move rather than as the pick it is; what tells a key's move from a listing's own is the key rather than the place, and a folder, tab or window reached by `Enter`, `Alt`+arrow, `Ctrl`+`T`, `Tab`, a click or a mouse button is still nobody's pick. A press is a pick only where the window it landed on is Explorer's or this app's own and is still there (`press_is_a_listing`), and a press another window took is dropped rather than held for a retry — Explorer's own `View`/`Sort` popups draw over the rows and destroy themselves without the hand moving, so by the time the press is read the point is back over the listing and the row behind the menu would otherwise be answered as the file the user had picked. A click is read through this app's own windows as well as Explorer's, and wherever its own look at the point answers nothing it is read the second way a pick is: out of the item the view has the _focus_ on, which is the one reading a window standing on top cannot take away — and the third fact matters most, because the item a fresh listing puts under a parked pointer is drawn exactly where the click landed. A press on one of a pin's own buttons — the caption's, or a sound card's own controls — is asked of the geometry that button's own press reads (`pin_button_covers`); it is no pick, it spends the rest of the hand, and a click held from before it is dropped rather than answered out of the listing the chrome covered.

**A press on the pin's own menu is the pin's own as well** (`note_pin_menu_pressed` where the card's or the bubble's own press handler answers it, `press_is_on_the_pins_menu` — the note, or the pointer over the menu window this tick or the last). The menu is a layered popup that takes no input of its own, so it is never the window the press is read on, and a menu clamped under the pointer at a screen edge sits over the listing rather than over the pin: read as the listing's, a press on a row or on the panel lowered the pin behind it. Such a press now spends the hand and is neither a pick nor a no-pick, and the dismiss ask counts the menu's own window as the pin's (`pin_menu_window_is_at`) beside the bubble's, so a press that lands on the menu puts away nothing.

**A press inside the pin's own box is the pin's own, and so is one read on the tick the pin moved.** A pin shows its picture in a host, and a host answers `HTTRANSPARENT` so the press reaches the pin's chrome: `WindowFromPoint` over the pin's picture therefore names the *listing* the pin was fitted over. Read as that listing's, a press on the pin held the gap between the rows and picked no file, and the answer a press that named nothing owes is the lowering — so a maximized pin, a restored one, one given a reset size, or one whose picture was double-pressed put itself behind the listing until a click brought it back (`pin_press_was_not_a_pick`, `lower_pinned_preview`). Two readings refuse that answer. The box the watch already holds makes a press whose point is inside it the pin's, whatever the hit test under that point named (`press_is_on_the_pin`). And the same box, noted against the last tick, makes a press read on the very tick it changed neither a pick nor a no-pick (`press_is_the_pins_own_gesture`): a gesture that moves the window off the point the hand was on leaves that point *outside* the new box, so the box alone cannot refuse it. The point is still booked, so the second press of a double press that moved the window is refused as the gesture it is.

## Pin mode (`ui/preview_window/pin_*.rs`, `pin_window.rs`, `pin_chrome/`, `text/`)

> How a hover becomes a persistent topmost window. Pin key freezes hover machinery, stands a window of the pin's own with caption/transport chrome, and swaps media in place for picks or prev/next walks — same file, no re-resolve.

The design decision that shapes all of this: the pin is a window of this app's own, and the hover's window is not it. A hover is made a non-activating tool window on purpose — it appears under a pointer that may be in the middle of renaming a file, and a window that took the focus would swallow the name being typed — while what Windows decides from a window's styles (whether a click may activate it, whether it is listed, whether it can be minimized and restored) is asked of that window once, when it is made. A pin is the opposite case, so it gets `pin_real_window`'s class: `WS_POPUP` with `WS_SYSMENU | WS_MINIMIZEBOX`, layered because its edges are alpha, no band in its styles at all (the setting asks for the band when the pin is shown), and no stand-in of its own for the taskbar, because this window brings its own button — and, put away into the taskbar, supplies the still of it, which is why it is made supplying its stills and why it wears the app's own icon in both the sizes a window is asked for (`WM_SETICON` with `app_icon`, the small one being what a taskbar button draws; the stand-in a bubble's button is made from is given the same pair). Everything that would require re-resolving a file is still free — the pin already knows the folder, the window, the sort order, and the config.

- Take-up: `pin_key` (Mouse3 or Space) on settled preview (`pin_screen_is_settled`), never spinner; engine kinds install `pinned_engine_media`. `key_input`/`wheel_input` LL hooks + per-tick counter; `refresh` on config/tray.
- The key a setting names: `key_binding` reads a binding as alternatives separated by `,` and the keys of one alternative by `+` — `space,page_down`, `ctrl+alt+space`, `ctrl+mouse4` — where the last key of an alternative is the press counted and the rest only have to be held. Mouse buttons are `mouse3`–`mouse5`, carried as their Windows virtual keys so one down-state read answers for both kinds, and left and right are not names it takes; an unreadable or empty `pin_key` falls back to `DEFAULT_PIN_KEY` (`mouse3,space`). The same parse answers `trigger_key` and `toggle_key`, and every stored spelling keeps working.
- The preview shortcut (`toggle_key`, `f7` by default, named in the tray's **Enable Preview** row) is counted by the same hook on different terms: it counts only while Explorer is the foreground window, it is never swallowed — Explorer and every other program still get their own key — and a held key is one toggle, because the hook marks the main key down on the frame it arrives and only an edge counts. A press made in another program still marks its key down, so holding it there cannot become a press when Explorer comes forward.

A pin can only be taken from a _settled_ preview. Pinning a spinner would mean pinning an unknown box and an unknown kind, and both are needed to lay the pin out. The middle button or Space is the default pin key because a listing has no other use for the middle button and Space is the universal "hold this" key, but it is configurable, and the low-level hooks only count presses — the tick drains the count, so a held key cannot pin twice.

The key's other half is restore: pressed while the pin is a bubble, with Explorer in front, it puts the window back up on the file picked since the bubble went down — the same file, in the same place and the same size `Update Preview` would have shown it in; a restore returns a pin to the box it went down in whether the bubble was carried or not, and only a bubble the hand carried is placed beside (`PIN_BUBBLE_CARRIED`, `placed_pin_box`), while every restore answers the claim, so a later taskbar collapse does not come back beside the hidden bubble's old place (`restore_pin` → `placed_pin_box`); with nothing picked it does nothing rather than losing the window. It never hides a pin, wherever the keyboard is — a pin is put up and a bubble is brought back, and that is all the key does; the key typed into whatever the pin appeared over cannot satisfy it. A pin is ended by the caption's close button, a right-click on the bubble, or `Escape` in a window that holds the keyboard. Alt+F4 cannot destroy one: a key held with a modifier is swallowed in `WM_KEYDOWN|WM_SYSKEYDOWN` before it can reach `DefWindowProcW`, which is where Alt+F4 turns into a close, and a `WM_CLOSE`/`WM_SYSCOMMAND` that does arrive is answered by `request_pin_end` like any other close — so a pin that an older build destroyed outright, leaving no previews for the rest of the session, cannot be destroyed that way at all. The key also works over a file the browser engine draws — a `.html` page with **Render HTML** on, an SVG document, a font specimen — because the engine is asked whether a document is on screen as well as the app's own media (`is_showing`), so the window that comes up is an ordinary pinned one.

- Always on top (`pin_always_on_top`; the tray's `Pin Mode → Always On Top` and the caption's own mark): on, the pin is topmost and its film and its page are kept in the band above everything; off, it is an ordinary window — kept wherever the user's own clicks put it (`raise_pinned_window` asks the setting), its film placed directly below it, which is also what takes an adopted mpv window out of the topmost band (`set_ontop` down its pipe), and the browser window told `HWND_NOTOPMOST`. A window that is not on the screen is shown with `HWND_TOP` beside the demotion, so a pin brought back by its button or its bubble stands over whatever was opened over it. Such a pin wears the app's own taskbar button while it is up, and the wheel is the pin's only while the pin is the window the user is in (`pin_owns_foreground`) — a hover preview is unchanged. The app-window bit is the setting's rather than the take-up's: written on the window of the pair that owns the chrome, off while **Always On Top** is on, and the demotion asks every window the pin draws through, the chrome included. The Shell reads whether a window is listed from the show that put it on the screen, so a bit written behind a visible window's back is not re-read for it: a window that is on the screen when its bit changes pays a hide and a re-show (`a_button_is_owed`, `set_the_pin_window_appwindow`), which a test holds to the same box. **Except the pin the user is in.** A press on a pin took the caret, so the `Always On Top` click is a click on the very window the hide would be seen through: its bit is written and read at the pin's next show, while every other window — a film's host at its promotion, a pin nobody is in — still pays the show.

**Taking the ordinary band is a flip, not one write, and the place is settled after the bit road.** `HWND_NOTOPMOST` on a demoted window is the front of the band only where the process holds the foreground; otherwise it lands just under the foreground window, which is the listing the user works in — the same wall a press meets, and the same road over it (`take_the_band_and_give_it_back`, `place_the_pin_where_the_setting_names`). And the hide a visible window's button costs hands the caret to the window next in the z-order, which the pin's own `WM_ACTIVATE` answer gives the listing for good, so `settle_the_pin_after_the_setting_moved` runs after the loop's bit read and raises the pin only where the window in front is one it belongs over: the listing it was picked in, the pin itself, the desktop. A pin behind any other program is where the user's own click put it.

**A box change is not answered by a raise of this app's own.** A maximize, its restore, a reset size and the end of a resize are all made inside the pin, and the raise a show makes is a question about the foreground — which a box change leaves as a film's host, the page under the pointer or the pair's own menu as often as the listing. So a gesture's own box is left to the raise the show makes, and a pin that would still go behind after one is read from the trace rather than raised on a guess; what the same gesture used to owe the front for is the press the pin no longer answers as a no-pick (see Explorer hook → Picks). The two move roads that moved a window with `HWND_TOPMOST` beside `SWP_NOZORDER` now name no band at all, since that argument is dropped and the call read as a raise it never made.

- State: `pin_window::{PinState::Down/Up(PinUp)/Ending(Reason), PinExit, end_pin, Closed/Asked/SwitchedOff/MediaGone/Hung}`; `PinUp` = window+media+`Option<PinKeyboard>`+`Option<PinStep>` walk+cmd queue. One ender; watchdog kills post `Hung` only via loop msg. Focus: `WS_EX_NOACTIVATE` toggled (`pin_set_focusable`, `pin_take_focus` on `WM_LBUTTONDOWN`, release on `WA_INACTIVE`); authority = `GetFocus` (`pin_is_focused`).

`PinState` is a small state machine with exactly one exit path. Everything that can end a pin — the user closing it, asking to end it, a config change turning the mode off, the media disappearing, or a hang — funnels into `PinExit` / `end_pin`, so there is no path where the window survives its own state. `Hung` is the state after which the watchdog is allowed to kill, and only via a message on the loop, because killing from the watchdog thread would leave the loop painting a dead window. Focus is authority-checked with `GetFocus` rather than remembered, since Windows can move focus behind this process's back. A pinned window survives display and DPI changes (`WM_DISPLAYCHANGE`, `WM_DPICHANGED`): while hover previews are replayed from the pointer and reset on display changes, a pin keeps its window, media, and playback (`!pinned()` in `window_proc`). The next tick re-boxes it for the display it landed on (`replace_pinned_window`) — clamped to the destination work area, re-measuring the caption and transport bar at the destination DPI, and re-maximizing a maximized pin in the new room while deferring during manual drags.

What counts as "the media is still there" is answered per kind (`pin_media_is_alive`): a `BubblePause` the collapse parked — the media engine paused where it stood, or FFmpeg's player ended at a recorded second — is the pin's media still, not a window that came apart, because the restore puts it back (`settle_bubble_playback`). A video whose player has gone, and a document whose browser has gone, still come down as before. A sound's player not running is the moment between two passes, not a dead window — which is also why the sweep that clears leftover players, run once a second while nothing is hovered, leaves a pin's own player alone: a sound that ended its pass is not a player to reap, and a pinned sound can be sought and walked to. What a _hold_ is, on that same road, is asked of the player rather than of the session: `a_sound_that_is_held(paused, player, engine_paused)` keeps a player of this app's on the hold written down for it and an ended pass on the one its end leaves, and asks the engine its own for the rest (`video_player::is_paused`) — because an engine's hold is the engine's state and nothing of it was ever written down. And a reachable Explorer window with an open pin is answered as the active arrangement whichever of the two has the keyboard, so the poll cadence and the idle timer stay honest behind a window the user is looking at and working in. A collapsed pin answers a play/pause for itself (`toggle_pinned_by_key`): a park standing is given back the road a restore gives one back, a bubble with nothing parked takes the ordinary toggle — which is then what the bar would have asked with the window up — and either way the press claims the playback (`bubble_run`), so the two switches stand down until the pin is up rather than writing a park a tick later over the playback the hand just asked for; the claim is reconciled the way a park's claim is, a restore giving it back to the switches and a swap installing the incoming file's own.

- Isolation: `show_preview/show_preview_keyboard` + hover-msg gate refuse while up; `hide_preview` acts for pin; loop repaints pin band/chrome only. Hook sleeps past trigger gate (except `Update Preview`).

While a pin is up, the entire hover path refuses to do anything, and this is enforced at a gate rather than at each caller. `hide_preview` does still work — it is how the pin closes. The hook thread then goes to sleep past its trigger gate so it is not polling Explorer at all, and the only thing that can wake it is `Update Preview`. The trigger key is bound by the same idea (`trigger_key_affect_pin_mode`, default off): a pinned window is one you put there, so the key that holds back hovers is not read while one is up — up, or collapsed into its bubble; turned on, holding it brings the pin down along with the previews it stops.

- Follow/swap: `Update Preview` (pick: click+focus-agree+place `press_is_a_listing/click_is_over_a_listing/get_file_under_cursor`, or `follow_selection` when hover off); bubble holds pick (`pin_bubble_pick`). Loop: `pin_media_load` (thread, `PreviewScale::FitToScreen`) → `swap_pinned_media`; `PinnedPreview::bound` (no walk-down); `PinLoad` + `PIN_ARC` spinner over current media; engine docs shown as-asked (`PLACED/PLACE_AS…`, `box_change`; move ≠ `show`). Slow work off the loop: swap read+decode (`pin_media_load`), resize re-decode, folder walk (`PinJob::Walk` on `PinPlanner`, `PIN_JOBS` newest-wins slot), hand-off program name (`PinJob::OpenWith` → `default_app_name`); stuck capture released (`pin_capture_lost`); unshowable target stepped over, nothing left → `show_pin_failure` (`PIN_FAILURE_SIDE`, `unplayable_media` → `MediaType::Unplayable`).

`Update Preview` is the pin's version of hover: either you click a file in the folder view behind the pin, or — when the hover is off and there is nothing to click — it follows Explorer's selection. Both paths run the same resolve, so the pin never guesses. A pick needs the click, the focus, and the placement to all agree before it is accepted, which is what stops a click on the pin's own caption from being read as a click on the file behind it. The load runs on a thread and the old media stays visible with a spinner drawn over it, so a swap is never a blank flash — and a text file is measured before the pin loads it, so a page whose measure has not answered yet shows the pin's own waiting spinner instead of a placeholder square standing in for a file.

Four things a pin does slowly run on threads of their own rather than the one that draws it _and_ pumps its own messages, so its close, minimize, maximize and caption buttons never go dead for as long as it takes: the read and decode behind showing the window another file; the re-decode a resize asks for (a resize leaves the picture on screen at its old size, scaled into the new box, which is what a resized video has always done); the folder walk behind **Previous**/**Next** and the arrow keys, read once per walk rather than once per step, so ten presses cost one read; and the Shell query naming the program the hand-off button offers. A press that has nowhere to go — a folder with one previewable file, nothing this build can show, a share that will not answer — ends its wait as soon as it is asked about rather than turning the arc for fifteen seconds, and a walk landing after the pin has moved on is dropped (`PinStep` carries `from` precisely so a late answer to a press about a file the pin no longer shows is recognised as such). Where a press took the pointer and the state holding it is then thrown away without a release coming — a swap, a resize, a pin taken down while a button is still down, a window given up on because its thread stopped turning — the capture is let go (`pin_capture_lost`), so the desktop is not left swallowing every mouse message and nothing you aim at can be clicked. As a last resort, a pinned window whose thread stops turning altogether is taken down on its own, player, browser and bubble included, rather than left as a window that cannot be closed: a pin you can lose is a better answer than an app that has to be restarted.

A swap fits the new file to the window's own longest side (`PinnedPreview::bound`), so a portrait pin followed by a widescreen file is not walked down a size at a time — and the window is kept where the hand put it, rather than being placed back beside the cursor. A second video is a swap that is _held_ while the new film reaches the screen, so the film already on screen keeps its picture and the window changes only once something has been drawn — asked the way each route can answer it: the engine's own frame for a film the media engine plays, and the player's own source for one `ffplay` or mpv draws (`player_swap_wait`, `video_playback.rs`). A film drawn in the pin's host is not taken down at all for it: the registration the outgoing player's window is drawn through keeps the picture on screen, the incoming player is begun behind it, and the loop ends the outgoing one once the new source has taken the picture over (see "The film road"). **What is kept is the picture the standing registration draws**, not the newest pid — a swap that began a player and is waiting for it leaves `VIDEO_PID` naming a film nothing has drawn yet, and a second press in that gap read as "the picture is the new player's" took the media down with the band (`pin_film_host::the_picture_stands_to_keep`, `the_player_on_the_band`). **And the file the pin is on its way to is not a new pick**: `pinned_path()` is what the pin is *showing* and does not move until the incoming file is installed, so the load, the box being waited on and a held swap are written down as one file in flight (`pin_install::pin_file_in_flight`), and a press on that file is dropped rather than restarting the swap it is waiting on (`update_pinned_preview`, `PinUpdateWatch::offer`). A target the window cannot show is stepped over rather than stopped at, and where nothing is left in the folder the window stays up on the file that failed and shows a large cross on a plain panel (`PIN_FAILURE_SIDE` = 128px, `unplayable_media` → `MediaType::Unplayable`), with the caption still naming the file — deliberately a different thing from a file this build simply has no preview for, where the window carries on showing what it already had. The ask is whether the player drew *anything at all* rather than only whether it is still running, because a film that played and then failed part-way through is left alone: it is not a file this app cannot read. **Pause on Minimize** (at the top of each kind's own `Pin Mode`, one under **Video** and one under **Audio**) parks what a collapse stops (`BubblePause::{Engine,Player}`), each kind behind its own switch (`pin_pause_video`/`pin_pause_audio` — two switches because a video and a sound are two different things to want quiet, and what should go quiet while a pin is away is a question about one kind of file), and the restore tick starts it again at the second it stopped at; the same two switches govern a pin put away into the taskbar, since the away-state is the same either way. Which of the two a minimize leaves — the bubble or the taskbar stand-in — is `pin_minimize_to`, read when the button is pressed. A pinned video's volume knob is the pin's own, and it moves the tray's `Volume → Video` level only where that half's **Remember Level** is on; a level the tray's own rows or a hand-edited `config.ini` is moved to reaches a pin already playing at once (`PreviewMessage::TrayVolume` → `tray_volume_moved`, published by the config watcher as well as the menu), the wheel over the knob steps it `5%` a notch from the level in hand, and the popup's box is frozen for the duration of a drag, so no chrome or card re-layout under the hand can move the groove the pointer is measured against; and the level is given to whichever player is running — a property down mpv's pipe, the media engine's own session, and FFmpeg's player at its Windows mixer session (`ask_the_ffplay_its_level`) — so no level alone ever ends a player; `remember_audio_volume`/`remember_video_volume` write the level on release, so the next hover — or the next film, or the next sound after a film and back — plays at it. What a kind's previews are like is its own half of `Preview Settings`: **Image** holds a `Pin Mode` of its own with the two questions a picture answers — `Shuffle`, and `Zoom Background`, the band a zoom opens behind an opaque picture (`zoom_background`; a picture with a transparent pixel in it keeps its own kind's backdrop, `image_background`, see-through included, at any size), **Video** carries the film's own **Subtitles** row above **Loop** and a **Pin Mode** submenu, and **Audio** its **Loop**, the hover's own **Seek** and a **Pin Mode** submenu — `Pause on Minimize` above `Shuffle`, `End of File` (`Pause` / `Loop` / `Jump`, written `pause`/`loop`/`continue`) and, for a sound, its own `Seek` row beside the hover's own outside it. What a film and a sound are *heard at* is one `Volume` submenu of the tray's own with a half apiece (`Video` / `Audio`, each half's two switches — `Normalize` and `Remember Level` — above its levels, listed below **Background** and above **Performance**), because the level is the whole of what the two kinds answer the same way and every other row of those halves is not that question at all. A level is claimed as the player's own (`volume.playing_at`) only where the player was told it: the media engine answers for itself whether a session took the level (`video_player::set_volume`), so a pin let go of while its knob is still under the hand leaves the level owed to the next player rather than recorded as given (`set_pin_volume`, `settle_pin_volume`).

- Walk: `pin_navigation` (`read_dir` flat, `kind_of_name`, `DirEntry::file_type`, no `metadata` except Date/Size walks, per-kind reader check, capped map) + `IFolderView2::GetSortColumns/sort_key_of` else natural order, wrap; `PinStep/pin_walk/pin_step_off` (skip bad, forward-only, `show_pin_failure→MediaType::Unplayable/PIN_FAILURE_SIDE`, each other file offered at most once); `step_pinned_file` copies config (no lock across IO); arrows only when pin focused (no `GetAsyncKeyState` steal); `pin_command_request/ask_pin` single door (`navigating` flag); the chrome, a menu's rows, a bubble's rows and the taskbar's buttons ask `PreviousFile`/`NextFile`, which are the walk whatever the pin holds, while `Previous`/`Next` stay the arrows' and are the page's caret where a focused page holds one; width = per-anchor `pin_nav_image`/`pin_nav_video`/`pin_nav_audio`/`pin_nav_others` (`all`/`category`; Image/Category, Video/Category, Audio/Category, Others/All by default; old `pin_nav_file_types` seeds all four once).

The walk has to reproduce the order the user _sees_, not alphabetical order, so it asks Explorer's own view for its sort columns via `IFolderView2::GetSortColumns` and falls back to natural order only when the view will not say. The file list is read once, flat, and classified by name only — no `metadata` call, because stat-ing hundreds of siblings is the one thing that would make the next-file button feel slow. Files this app cannot read are skipped rather than fatal. `PinStep` carries `at` (where the walk landed) separately from `from` (what the press was made on) because the planner runs on another thread, and a late answer to a press about a file the pin no longer shows must be recognised as such. `advance` re-anchors to the file the pin is standing on in the order in hand, so a press made while the last step's file is still being read steps the same playlist rather than starting another. Arrows are honoured only when the pin itself has focus, and never via `GetAsyncKeyState`, which would steal keys from whatever window actually owns them.

How wide the walk is, is the anchor's own switch (`nav_mode_for`): **All** steps through every file this build could preview, so a video sits beside a sound; **Category** narrows it to the first file pinned's kind of thing — a camera raw is a picture and a book is a document, because that is what you call them. Image, Video and Audio start narrow, Others starts wide, so `PDF → MP3 → DOCX` walks end to end while `MP3 → FLAC` never reaches a document.

The walk is the pin's **session**, not one ask's answer (`PinUp::walk`, `state.walk()`/`walk_mut()`, `session_walk`, `take_pin_walk`, `pin_walk_synced_its_playlist`): one playlist (`PinStep::order`) spawned when the pin is triggered and stepped along, so every road that asks for the next file — a caption's **Next**/**Previous**, a film's end of file and a sound's — is one walk. `step` is the one place that says what a step is: back is the previous file of the order, forward the next, and a shuffled playlist respawns past its last file rather than wrapping; the file itself is never drawn, which is what makes **Previous** land on the file the walk came from and the **Next** after it the file it was interrupted on. A file that could not be shown is stepped over without being written down (`step_over`, `missed`), because nobody was ever taken off it. The question carries the playlist it is a step of the way it carries the configuration (`PinJob::Walk.session`) — the planner is another thread, and a walk it read off the pin's own state would be the pin's lock taken across a folder read — and `answer_pin_job` reconciles it against a fresh list after `pin_navigation::forget_folder` drops the cached scan, so a file copied in joins the playlist and one moved or deleted leaves it. A pick in the walk's own folder carries it on (`take_pin_pick`, `install_walk`, `pin_navigation::same_folder`), the walk rides with the window across a take-up in the same folder, and a step whose file's box was still waited on parks it rather than dropping it.

Shuffle is a playlist too, and the pool is the anchor's own kind of the list rather than two hard-coded kinds — which is why the picture's own `Shuffle` row (`pin_mode_image_shuffle`, the third kind with a next file and no end of file to jump from) is a row of the same table rather than a second bag and a second branch. The pin's own shuffle says whether the pool is drawn (`answer_pin_job`): the audio one for a walk anchored on a sound, the video one for a film, the image one for a picture, and the folder's own order everywhere else; a same-file swap restarts at the swap's start so the bar resets. A kind switched off under **Preview Types**, or one with no engine installed on the machine, is not a step either way. The walk is the folder the pin was taken up in and no subfolder of it, read on the first press rather than when the pin is taken up; each other file is offered at most once, so a folder of nothing this build can read ends the walk instead of going round for ever, and a file *you* picked in the Explorer listing is still not stepped over. What a press means is settled by the hook's four judgments (Explorer hook → Picks): a gesture is two presses inside the machine's own double-click time, an unanswered place carries its baseline, a press is a pick only on a listing window that is still there, and a press inside the pin's own box — or one read on the tick that box changed — is the pin's rather than any listing's — which is why the first click and the first arrow-key press after a double-click-opened folder, a folder change, or the window taking the keyboard all work, and a press Explorer's own popup took is dropped rather than retried.

- Chrome: same window grows (caption up, transport down; overlay kinds draw over). `pin_chrome` GDI strokes whose marks are drawn with coverage rather than in whole columns; the window group is **Always On Top**, **Minimize**, **Maximize** (where the kind offers one) and **Close**, with the pin's own four (prev/next/open/open-with-list) left-packed (`button_boxes`); as a window narrows, buttons collapse one by one from the left (`Previous` first, `Close` last) so the strip remains as a bare hairline bar (`width > 0`) instead of disappearing, and title text only reappears when all buttons fit (`buttons_fit`); tooltips (`PinTooltip/PIN_TOOLTIP_DELAY`, `AssocQueryStringW` once); `Open With`=`ShellExecuteExW(open)+plain_path` on the pin's own monitor (pin `HWND`+`SEE_MASK_HMONITOR`) then `request_pin_end` (=`WM_CLOSE` road); `Open With...`=`rundll32 shell32.dll,OpenAs_RunDLL` raw tail, carried onto the pin's box on its own thread (`carry_open_with_to`: fresh `Open With`-class windows still centred on the primary display are moved — found by `FindWindowExW`, since `EnumWindows` does not list them — re-moved while settling, a list the user moved is left), same end; no launch polling.

The window is one rectangle with fixed button slots, but it is not one surface. A film is drawn by another process's player in a window of its own, and a window of this app's cannot composite over it — so the film's host (`pin_film_host`) is a window of the desktop's standing at the whole of the pin's band, the pin's own window is an owned window of it (which is what gives the pair one band and one taskbar button), and the film reaches it as a DWM thumbnail of the player's own window (`pin_film_thumbnail`) rather than as a child. A thumbnail composes *over* its destination's own pixels, so the pin's layered surface paints an alpha-1 claim on the chrome's rows and no chrome in them, and the chrome has windows of its own — layered, **disabled** children of the pin's window at the caption's strip, the transport's and the volume popup's footprint (`pin_chrome_strips`), so they stand over whatever is in the band and stay in step with the pin's own paint. A disabled child is skipped by `WindowFromPoint`, and the host answers `WM_NCHITTEST` with `HTTRANSPARENT`, so a press on the chrome or on the band still lands on the pin and is answered by its coordinates. **A page the pin carries is the one band a child strip cannot serve**: the Shell composes a thumbnail over its destination's own content, children included (`pin_page_thumbnail`), so a caption in a child of that pin would stand *under* the picture while its buttons still took the press. Over such a page the caption rides in a `WS_POPUP` window owned by the pin and mirroring its band (`the_caption_popup_at`), `WS_EX_LAYERED | WS_EX_TRANSPARENT` — a disabled top-level popup is not skipped by `WindowFromPoint`, `WS_EX_TRANSPARENT` is (measured) — placed again on the pin's own `WM_MOVE`/`WM_WINDOWPOSCHANGED` because a window that moves repaints nothing (`follow_the_pin`), and hidden for a pin that is minimized, invisible or no longer drawing a page. Because an owned popup is a top-level desktop window rather than a Win32 child, the Shell does not hide it when its owner hides; `hide_pinned_windows` explicitly hides it (`hide_the_caption_popup`), and `follow_the_pin` checks the pin's visibility before querying pin state so closing from the caption button never leaves an unclickable titlebar orphan on the desktop. Which caption a pin gets is `pin_overlay_chrome(kind, page_runs)`: a page that runs keeps its bands, and a page the pin draws has the caption and bar floating over it. `Open With` deliberately ends the pin: it hands the file to another application, and keeping a preview up over a file the user has just opened in Word is not useful. It ends by asking for a close rather than closing directly, so there is exactly one path that tears a pin down. A hand-off is not a close: the end is noted as one (`note_pin_handed_off`, `PIN_HANDED_OFF`) and the hook holds hovers back until the pointer moves, so no card opens over the program that was just launched. The two hand-off buttons name themselves while the pointer rests on them — **Open With** names the program it would use (*Open With Adobe Photoshop*), read once when the window is pinned rather than asked of the machine on every repaint (`AssocQueryStringW` once), and **Open With...** says *Open With...*; a machine with nothing registered for the format has no program to name, so that button says nothing. The name hangs below the caption, over the picture, rather than inside the strip — a name that wide would cover the buttons it describes.

The pinned sound card's own menu holds the whole of what a pin does, and a window still standing opens the same panel on a right-click (`pin_menu::pinned_menu_paint`): `bubble_menu_rows(kind, standing)` gives it the shared rows with **To Bubble** above **To Taskbar**, and a page of text carries **Select All** / **Copy** / **Find** / **Find Next** above them, read against the media on screen on the paint and on the press alike; where the menu opens is the kind's own answer, and a film's title bar is the only way to it, the player's own band taking the clicks in the picture. A key that reaches the window with the panel up puts the panel away before it is answered, and a film is left in its own band while the panel is up rather than raised over it (`player_order` asks `pin_menu_open`). A card's menu ends in a rule and **Open in Default App** / **Open With...**, the caption's two hand-offs by another name; both are armed on the press and made on the release that follows (`pin_menu_hand_off_release`), because each raises a window under the hand that would take that release for a click of its own, and the end is noted as a hand-off (`note_pin_handed_off`) so the hook reads it as a hand-off rather than a close and holds hovers back until the pointer moves. Its two flyouts are placed by the one computation both placements ask (`menu_flyout_tier`): which side has the more room beside the menu decides which side the arrow points, and a panel narrower than the room it was measured in used to stand a whole reserve of empty space off the menu it came from, since the side was answered in the room the placement _reserves_ rather than the room the menu leaves. A window too narrow for the two panels narrows the flyout into that room beside the menu rather than moving the menu to the window's edge and splitting the two between the edges — and only a window narrower than the menu's own panel leaves no room beside it at all (`MENU_PANEL_MIN_PIXELS` is the floor a panel is never narrowed past). The bubble's own menu is the same panel painted the same way, and it gained the same playback rows plus, where the kind behind it plays something, the `Pause on Minimize` switch row, and the rules that keep them apart from the two ways out (`bubble_menu_rows`, `bubble_menu_press` — a press on a rule is nothing at all, and the menu stays up), the way the card's did; the two collapse rows name where the pin goes rather than which way the next minimize would take it, so a collapse carries its own target (`PinCommand::MinimizeTo`, `collapse_pin_to`), and `collapse_pin` is the configuration's own answer asked through it.

`PinFrame` is a band model: eight hit-test bands around the edge, corners wider than the sides so they are easier to grab, and the caption band excluded because the caption already has buttons in it. Dragging is a `SetWindowPos` and nothing else — no tracking loop, no re-layout. Every edge and corner resizes, smaller as well as larger — previously the top edge and both top corners moved the window instead of resizing it, and a picture could be pulled larger but never smaller — and the pointer's shape matches the edge under it, returning to the arrow when it is over none. A pinned drawing is draggable by the press the Explorer hook publishes rather than a message the browser's window never sends: the press and the drag's _end_ are both read off the count (`PinDrag::delivered` = false → `settle_pinned_engine_drag`), because the button's state is a level, not a transition, and a level cannot be missed the way a message can — which is what stops the window following the pointer on its own and then going dead, with buttons that no longer click and no drag or resize until something else takes the pointer away. The loop waits a few pixels of movement before it counts the drag as begun, then follows without sleeping — the rate the hand moves at, not the rate the loop turns at — and a hand that rests for a while without moving hands the loop back rather than spinning it. The picture itself no longer comes away in the hand: an `<img>` is draggable in a browser by default, and Chromium's own drag session took the pointer for itself at the same moment the window took it for its own, so the release arrived to neither and the pin froze. Telling the browser where its window has gone is a _move_, not a re-put of the document: a box that only changed place is one `SetWindowPos` and nothing else, the bounds are set only where the window genuinely resized, and the boxes are coalesced as the document always was — a drag of a thousand pointer moves is one move to where the hand ended — because an **animated** drawing's compositor is already working, and a queued put-up per move (a resume of the browser, its backdrop, its bounds, and a show) drove the engine's thread into the ground until the picture stopped following the window and then stopped answering at all. A pinned FFmpeg video plays through a drag and a resize untouched: the film is a thumbnail of a source window that is placed once and never moved by the gesture, so there is no held frame, no cover and no reload (see "The film road"). A **pan** — the picture carried *inside* a window it is drawn larger than — is the one gesture whose paint is the whole band composed through the sampler (2.3 ms of a 1920x1080 band off a 3840x2160 frame, before the surface is cleared and `UpdateLayeredWindow` is handed it), so its frames are the display's rather than the pointer's: the move writes where the picture has got to and the loop draws it on its own tick, its wait paced by the compositor while a pan is up (`a_pan_owes_a_repaint`, `pin_is_panning`, `wait_for_the_compositor`). A paint per position reported is four bands per frame of a 144 Hz display that the display never puts up, on the same thread the tick that advances a playing picture is on — which is seen as an animation that stops while the hand moves and jumps when it stops. A **resize** paints a composed band too, and is paced the same way but in place: its step is one `UpdateLayeredWindow` that is also the box's own commit, so it stays in the pointer's message rather than moving to the loop, waits on `DwmFlush` after it rather than before the next one (`apply_pin_drag`), and the tick that follows it paints the pin only when nothing has since the messages were pumped (`the_pin_owes_a_paint`, `PIN_PAINTS`) — so a resize is one paint a frame as well. What is left is the pump: a step per position reported is a `PeekMessageW` loop that never empties, which starves the tick the animation is advanced on for as long as the hand keeps moving, so the pump dispatches one move a tick while a resize is in flight and leaves the rest for the tick after it — the system coalesces them to where the hand has got to, and the tick reads the pointer live anyway (`pin_is_resizing`). The box the hand leaves behind is the one decode a resize still owes, and a box the frames in hand already cover owes none: those frames are every pixel the smaller box would have been drawn to, and the pixels every later enlargement is stretched from — so a pin shrunk and pulled back out is as sharp as it was and keeps playing where it was (`box_is_covered`, which counts the kinds that play among the kinds a box gives another size to). A playing frame used to be re-read at every box the hand left it at, which replaced those pixels with a thumbnail of them; that is the half of this answer a box keeps.

A box the frames do not cover is decoded for, and for a picture that *plays* the decode is asked for from the place the animation is at rather than from the file's first frame — a decode begins a file at its opening frame, so it would otherwise be the animation started again. The place is read once, at the box the change is fixing, and the frames before it are composited for the canvas they are part of and not scaled for a box they are never drawn in (`pin_media_load`, `resume_at`). A file answered from a place is that place to its end and then its first frame to that place: the pass that began in the middle leaves its head undecoded, so it is always followed by the pass that begins at the first frame, and that one stops where the resumed one began rather than decoding the file on under it (`load_animated_gif`, and the APNG and WebP loaders beside it). What a resumed decode holds is therefore the file in play order — its tail, then its head. Each frame carries the index it has from the file's first frame (`ImageFrame::file_index`), so the install lands the answer on the frame carrying the place and carries the wait that frame had already served with it (`keep_animation_place`): one number, whatever the decode began at, whatever the player has given back behind it, and wherever a file that has looped stands — which is why a released window and a file decoded again from its first frame can no longer lose it, and why the landing is no clamp to the frames in hand.

The answer is not installed a moment before it is the frame the picture is on. The decode is asked for at the place the box changed and lands a tick or more later, so what it begins with is behind the place the pin has played to, and installing it on arrival was the picture put back by the decode's own duration — a stutter on every step of a pulled edge (`take_pin_relayout`). The loop keeps the answer until its own stream reaches that place, and the frames drawn for the new box go on being stretched until it does. That order is also the order the player loops in: a media that has played to the end of what it holds wraps onto the frame carrying the file's first frame rather than onto the first of the list (`frame_of_file_start`), which is what a file decoded at a place could not do while index zero was the list's own first frame.

A kind that does not play has no run of frames to be part of: every one of its frames is the whole of what it shows, and it begins where it always did. This is the answer a wheel's notch already gives by decoding nothing at all (see "Wheel zoom").

What a *hold* is, is the question a play/pause press answers (`a_sound_that_is_held(paused, player, engine_paused)`): the second a player of this app's is paused at is written down, but an engine's hold is the engine's own state and was never written down for it — asking whether a _session_ exists cannot tell the two apart, and the second press asked a held sound to hold again for ever. `video_player::is_paused` is the engine's own answer to the question, the card's own play button reads the same one so its glyph says which of the two the sound is at, and the bubble parks the same two players on the same rule (a sound the engine was already holding is not parked as a playing one).

Two playback engines answer these questions in incompatible ways. The Windows media engine reports where it is and seeks directly. FFmpeg's `ffplay` reports nothing at all — it is a window with no API — so the app keeps `PinTransport`: the length from the probe, and a position computed as _this app's clock minus the start time plus the offset it launched at_. Pausing an ffplay means sending it a key and remembering the second; seeking means retiring that player and starting a new one at the new second. Keys go in via `PostMessageW` with an explicit lParam carrying the scan code, and without the repeat flag, because a key-repeat of Space would rapidly toggle.

The seek bar answers at any point in playback, not only the first three seconds, and dragging it to the far left starts the file from the beginning; it follows a seek made while paused instead of springing back to where the pause began, and the thumb lands under the press wherever on the bar the press is made — the press and the draw now share one geometry, where they were each built at a different height and only the middle of the bar agreed. A paused pin shows the last frame and nothing over it: the play triangle is gone. A pinned FFmpeg video shows no chrome of its own — the pin's caption and bar are drawn over the band the player's window fills, the way a video the media engine plays never shows any, and the player's window is held below them for as long as any strip of the pin's own chrome is showing, and never takes the keyboard, so every pinned video looks and behaves like this app's own, whatever plays it.

The row a sound's bar answers for is the bar *and the gap above it* — the band reaches eight scaled pixels *under* it as well, clamped at the card's own bottom edge so it cannot swallow the margin further down where a hand is carrying the window — and a file that does not say how long it is refuses only the seek, because its buttons are the caption's own walk and this window's own level, neither a question about the length of a file; the margin under the bar is still a handle for carrying the window, and a lengthless stream, which the card draws with a block crossing its track, has no second for a press to mean.

`End of File` (`Pause` / `Loop` / `Jump`, written `pause`/`loop`/`continue`) at `Pause`: the end holds the card instead (`audio_paused = Some(0.0)`, play button at `0:00`, session let go, the press plays the file again from its beginning) on both players, and `pinned_pass_end` is the one rule the two ends read. Normalize: `ebur128` → gain to −14 LUFS vs −1 dBTP (`audio_track::gain`, `Some(1.0)`≠`None`; `AUDIO_GAIN_TIMEOUT_SECS`); per-player gain path — which on the FFmpeg player is a `volume=` filter the tray level is folded into (`audio_volume_filter`), since that player's own `-volume` knob is silent at 100 while the filter plays the whole of the scale, the way a film's soundtrack already did.

"Start at" has four meanings and the setting distinguishes them: the beginning, the middle, wherever the pointer was in the file, or where you were last time (remembered in a capped temp file). A native player can seek once it is ready; ffplay has to be told with `-ss` on its command line or it plays from zero. For looping, the native player has a mode flag, and ffplay does not — the app wraps it with a second pass over the whole file. A pin whose end of file is `Pause` is not wrapped and is not advanced either: its end lets the session go and leaves the card held at the beginning, because a card held at the end would be a press that played the file's last moment and stopped again. Normalisation is loudness, not volume: `ebur128` measures integrated loudness in LUFS and true peak in dBTP, and the file is adjusted to −14 LUFS without exceeding −1 dBTP, which is a broadcast-style target that stops one quiet video and one loud video from being unusable next to each other. `Some(1.0)` is deliberately not the same as `None`: 1.0 is "measured, needs no change", `None` is "not measured". The loudness is measured once per file and kept, so only a file's first hover waits for it.

A sound at `Volume → Audio` 0% plays on, silently, and stays seekable — both players already read a zero as silence while they run (the engine as a mute, FFmpeg as a `volume=` filter of nothing, or a gain of nothing where a file has been measured), so a level of nothing is not answered with no player at all, which would leave the card drawn with no clock behind it and nothing to seek; a sound this machine will not play at all is still a card with no clock, which is the answer it should be. **Normalize** is FFmpeg twice over — what measures a sound's loudness and what applies the gain — so on a machine without it the row is greyed and every sound plays as the file holds it. A pinned sound stops when the pin is shown a film: the swap ends the standing file's player without letting go of its frame, where the hold used to be about the frame alone and an FFmpeg sound kept going over the film that replaced it. Which engine plays a sound is the machine's answer rather than a setting: the media engine Windows has is asked first, and an installed FFmpeg second.

- Text pin = full mode (`current_text_options`): scroll/select/clipboard (`Ctrl+C/A`, menu), scrollbar (`bar_row` shared geometry), wrap-to-width + pull-back + end rule, `text_cache_mb` frames, `Refresh` rebuilds from recorded hover; journey+preview regions published per tick. **The page is a read-only editor rather than a scroll box, and it is the one media a pin's own keyboard reaches — once a press inside its body has given it the focus**: `↑`/`↓` move a caret a line at a time with the column kept over the short lines in between, `←`/`→` a character across the ends of lines, `Ctrl`+arrows a word by the page's own run rule, `Home`/`End` the line's two ends and `Ctrl`+`Home`/`End` the document's, `PgUp`/`PgDn` a screenful (`PinCommand::CaretUp/CaretDown/Previous/Next/PageTop/PageBottom/PageBack/PageOn`, asked where the file in the window is known, the folder still walking for anything else), `Shift` grows the selection and a bare move collapses it, and the page scrolls **only** to keep the caret on it (`text_preview::moved` for the arithmetic, `text_caret` for the keys — a key writes its move down and the tick that may read the document makes it, because a window procedure may not). **A page is drawn unfocused**, with no caret and every one of those keys stepping the folder as it does over a picture, and a press on the caption — its walk, its buttons and the empty drag area, and nothing else — gives the focus up again, clearing none of the caret, its column or the selection; `Ctrl`+`A`/`C`, `F3` and `Ctrl`+`F` read the page rather than move a caret in it and are the page's either way. `Home`/`End` on a page that is held but has not been pressed into step the folder rather than being swallowed, which is what tells such a page from a pin holding no page at all (`holds_a_page`) — a picture has no beginning for `Home` to go back to. Nothing that writes reaches the document: a typed character, `Backspace`, `Delete` and `Ctrl`+`X`/`Ctrl`+`V` all change nothing, since a cut that cannot cut is worse than a chord that does nothing, while `Ctrl`+`A`/`C` still read it. The caret blinks at the pace the system names while the page has the focus and a caret. `F3`, and the page's **Find Next** row, take it to the next place the selection appears (`find_next`: exact, case-sensitive, from just after the selection, wrapping to end where it began) — or, while a find bar is up, to the next place that bar's query appears — and `Ctrl` and a wheel steps the page's own size through the tray's list (`PIN_TEXT_SIZE_DELTA`) — a size the pin carries across a resize and a walk and gives up when it closes.

**A pinned page keeps a line-number column down its left, and a hover does not** — whatever the file is: source, prose, a listing or a rendered document. The pin is the page a reader works in, where a line is referred to by its number; a hover is something looked at on the way past, and the column is width the text does not have. It is as wide as the widest number the page can reach (`gutter_width`, the document's own line numbers, `MAX_DOC_LINES` of them), so it does not move as the page is scrolled from line 9 to line 10, and it is the layout's (`LaidOut::gutter`): the wrap width, the runs' own `x`, the caret, a press turned back into a place and the wash a selection or a find lays are all measured after it, so nothing of the text is drawn under it and a copy of the page (`text_of`, `drawn_lines`) names no number at all. A wrapped line carries its number on its first painted row and none on the rest (`own_line`, `FrameLine::source`), and the room between the numbers and the text is `text_paint::scaled`, so it grows with the display like every other measurement. A selection, the word a double press takes and the place a copy is cut from are document places rather than frame places (`FrameLine::source`, `Selection` in document lines and characters), so a wrapped line copies whole, **Select All** means the page rather than the screenful, and a drag carried past the box takes the page three lines a tick toward where it left. A box change lays the page out again for the box it has reached, at the reader's own size and at the place and selection they were at (`relayout_text_for_the_box`), ahead of the window being put up around it; only a page takes that road — every other kind is sampled into the new box.

**The caption says the page is read only** (`Caption::read_only`, `pin_chrome::page_marks`): a pill at the right end of the title area, immediately left of the buttons, carrying a hand-drawn padlock and the words `Read only` — a mark built from the chrome's own primitives, so it scales and antialiases with the rest of the strip rather than being a glyph borrowed from a font. A caption too narrow for the two keeps the name and gives the pill up, the name's own room is measured against the room it actually has (a caption without a pill does not give its name up for one), and whether the pill is there is part of the strip's cache key — a page's caption repainted as a picture's would otherwise keep it.

**A find bar floats over the page** (`text_find`, `text_find_field`, `pin_chrome::find_bar`): `Ctrl+F`, or the **Find** row above **Find Next** in the page's own menu, opens a card at the page's top-right corner with the query, `current/total`, `Aa`/`W` switches and `↑ ↓ ✕`. The query is a real single-line field rather than an append-only box (`text_find_field::Field`): the caret and both ends of a selection are byte indices on character boundaries, typing lands at the caret and replaces a selection, `Backspace`/`Delete` take a character or the selection and `Ctrl` +`Backspace`/`Delete` a word, the arrows and `Home`/`End` move the caret (word-wise under `Ctrl`), and `Shift` with any of them grows the selection the way `Shift`+click and a drag in the field do. `Ctrl+A`, `C`, `X` and `V` are the field's, pasting the clipboard as one line — breaks as spaces, controls and a byte-order mark dropped, runs of space collapsed, capped in characters (`sanitize_pasted`, pure and tested, over a thin untested `OpenClipboard` read), and the copy writer is the page's own. `Ctrl+Z` undoes and `Ctrl+Y`/`Ctrl+Shift+Z` redoes, over whole-field snapshots with a run of typing coalesced into one; `Ctrl+U` is deliberately not bound. Every keystroke searches the document as it is drawn (`find_all`: document order, non-overlapping, the two switches read as the search it runs under), every match is painted into the frame with the current one distinct (`FindHighlights`, drawn under the reader's own selection), and a match off screen takes the page to it the way `F3` takes it to a selection. `Enter`/`↓`/`PgDn`/`F3` step on and `Shift`+`Enter`/`↑`/`PgUp` back, wrapping at both ends and never moving the query; a new query starts at the first match at or after the line the reader was on. A press in the field places the caret at the character under the pointer — measured from the column the query is really drawn at, so a query too long for its row is pressed where it is scrolled to, not a field's width away — a double press takes the word by the page's own run rule, and the caret blinks at `GetCaretBlinkTime`'s pace on the ticks a pin already takes, solid from every edit, with the selection washed the way the page washes its own. A query too wide for the field scrolls under the caret: the scroll is worked out from the caret as the run is measured rather than stored, so a resize, a paste or an undo cannot leave it stale, the run rests where it always did while the caret's column is inside the field and moves just enough to keep it there, a margin clear of either edge, and the run, its wash and the caret are all clipped to the field rather than drawn over the card's padding. A repaint is asked for a changed query, caret, selection, hover or blink and never for a mouse move that changed nothing. While the bar is up it owns the keyboard, and the keyboard hook stands down for the whole of it: a swallowed key never becomes the `WM_CHAR` a field types from, so every key arrives as a message and the bar's one table reads it — the page's own keys and the polled `Ctrl+A`/`Ctrl+C` are inert — and `Esc` empties a query that has text before it puts the bar away, with the page left where it is either way. The query outlives the bar while the matches do not; `Ctrl+F` over an open bar selects the query it finds rather than appending to it; a box change keeps both, because a match is a place in the document rather than a row of the frame; another file keeps neither (`keep_text_place`).

A pinned text file is a full text preview, not a picture of one: it scrolls, selects, copies, and wraps to the pin's current width, and the frames it re-renders are cached. `Refresh` after a config change works by replaying the _recorded_ hover rather than asking Explorer again, because the pin is the only thing that knows what it is showing.

### The page road (`pin_page_thumbnail.rs`, `webview_preview`'s `Host`)

> What a pinned document, specimen or page of HTML is drawn through: the film road's own pair — one source, one registration — with one decision in front of it, whether the page is the pin's *picture* or a window the user works in.

**Every kind stands in the pin's own window** (`pin_should_stand_in_its_own_window`), the browser's three included: the page is a window of this app's placed at the pin's content box, and the pin's window is the frame around it — the window Windows activates, lists and gives a button. `MediaType::draws_in_a_window_of_its_own` survives as the answer to what fills the band during a drag, which is the question a pin's taskbar mirror asks, rather than as an answer about the pin. `take_the_hover_down` does not hide a page a pin is drawing: a hover's late hide after a take-up would leave the pin standing on an empty band.

**Which of the two roads a page is on is the page, not the kind.** `a_running_page_holds_the_band` is `webview_preview::the_shown_page_runs` — `SHOWING && RUNNING_DOCUMENT`, published as two atomics because the paint that asks it must not take the engine's lock. A page that runs keeps a top-level window in front of the pin and is clicked into, so its band is a hole and a press on it is Windows' to answer: with **Always On Top** off the pin comes forward only by the band a process without the foreground can take (`take_the_band_and_give_it_back`), and the page is placed last so it ends above the raised pin. Every other page is the pin's picture.

**A source is placed once and moved after that.** `Host::put_window` puts a non-running page at the band with `HWND_BOTTOM` and `SWP_SHOWWINDOW | SWP_NOACTIVATE` the first time and only moves it after (`SWP_NOSIZE | SWP_NOZORDER`), because the picture is sampled from its client area; `put_the_page_style` gives it `ex_style_for(style, runs, source)` — `WS_EX_LAYERED | WS_EX_TRANSPARENT` at `SOURCE_ALPHA` (1/255) — and it is asked on every placement as well as on every show, since a pin taken up over a page already on screen never navigates again. The client is the surface the band samples, so `show` takes the *window's* box where `the_window_takes_the_area` finds the real `GetClientRect` differing from the band: a maximize moves the band without resizing a source, and the box last asked for would otherwise be ahead of the client. A drag is one `SetWindowPos` of the source and re-points nothing.

**The registration is the other half** (`pin_page_thumbnail`): `DwmRegisterThumbnail` from the pin to the page, its destination the band in the pin's *client* coordinates (`the_band_in_the_client`, cut to the client so a stale band is never a rectangle past the surface), `DWM_TNP_SOURCECLIENTAREAONLY`, and no crop and no scale — the Shell ignores `DWM_TNP_RECTSOURCE` here and flattens the page by the rows it was asked to cut (measured). One `Held` in a static holds it: a pair that changed (another pin, another page) is unregistered and made again, a band already handed is the Shell asked nothing — which is every step of a drag, the destination riding the pin's client — and `let_registration_go` runs when the pin's media goes down, when its siblings go down, and when the media is taken for a swap, because a hidden source is a thumbnail the Shell stops drawing rather than freezes, and one left standing would be a black rectangle over the incoming file. The registration is also what makes the pin's taskbar hover a page rather than a hole: the Shell pictures a window from what the compositor composed for it.

**A press on the band is the pin's.** The band is painted alpha 1 (`fill_band_hit_testable`) for a page the pin carries, since a layered window is hit-tested by the shape of its pixels; a page that runs claims no pixels and is clicked into.

**Every road that raises the pin places the page again, last** (`place_pinned_siblings`, from `show_pinned_window`, `raise_pinned_preview`, `put_pin_at_the_front`, `WM_ACTIVATE`'s `WA_ACTIVE`/`WA_CLICKACTIVE` and the `Always On Top` demotion): the page is a window of its own, and a raise of the pin alone leaves it behind. `raises()` claims topmost and then gives it up for a pin that does not hold the front, because `HWND_NOTOPMOST` on a window that is already non-topmost is a no-op (measured: the page stayed under Explorer while the pin was over it). `show_pinned_window` reads back the box Windows really gave the window (`GetWindowRect`) for the trace, rather than trusting the box it asked for.

**Diagnosing a run.** `RHP_PIN_TRACE` gains `page band: shown pin … client … page … client … dest …` (once per registration or band), `page band: unchanged`, `page band: register refused` / `page band: update refused`, `page thumbnail let go (reason=…)`, `caption popup: made/shown/hidden/destroyed`, `take-up: … kind … rect … window … content … bound-in … bound-out …`, `swap box: <arm> … shape … scale … bound … room … -> content …` (the arm named — `engine-drawn`, `bound`, `maximized`, `keeps-its-box`, `audio`, `waiting`, `none` — is the whole of why a box has the size it has), `pin key: … hover rect …`, `pin window: …`, `show client … area … source=… runs=…`, `put_window source placed=…`, and `pin decision the window was asked to maximize/restore`. A box in any of them is `<W>x<H>+<X>+<Y>` (`pin_trace::a_box`), so the box a swap measured reads against the box a take-up was handed rather than against another spelling of itself.

### The film road (`pin_film_thumbnail.rs`, `pin_film_host.rs`, `hover_film_host.rs`)

> What a pinned film is drawn through, whichever of the engines this app has plays it — and a model too, whichever viewer draws it: one source per picture, a window of the engine's own, shown in a host of this app's by the Shell's `DwmRegisterThumbnail` — and the four rules that make a resize at pointer rate impossible to get wrong. The roads that lost here are recorded with their symptoms, so the next one is recognised rather than argued about.

**The problem, in what a user sees.** A pin (a hover preview promoted to a pinned window) shows a film, and dragging the pin's resize bar must keep that film filling the box at the film's own aspect while the box changes size at pointer rate. Every road that resized the film per step failed in one of a few ways: judder inside a frame that was otherwise the right shape; a picture zoomed in (cropped) or zoomed out (a small film in a field of black); a bar of black — or of the desktop — inside the pin; and a flash at the press and again at the release. The report that put the second engine on this road is the same fault in its bluntest form: with FFmpeg's player drawing the film, resizing the pin, dragging it, changing the volume and even clicking the picture all paused it — *"Resizing it or doing anything has to pause the frame, this include, moving/dragging the window around, changing the volume, even clicking the video frame makes the video paused"*. That is the cross-process call below, made per step and synchronously, on the other engine.

**Why resizing the film per step cannot work.** The player is another process. Asking its window for a box is a cross-process `SetWindowPos` made asynchronous (`SWP_ASYNCWINDOWPOS`; a synchronous one waits on the other process's thread, which is the one thing a drag cannot do), so on every step the window's new geometry arrives before the pixels in it do. Anything that sizes the film per step is therefore racing the content: the strip the box gained has no new pixels and must be painted with something — a stretched frame grabbed at the drag's start, which is the double image, a big stale picture with the live one on top — and on a shrink the parent clips a stale child into a cropped picture. No ordering of window calls fixes this without blocking the drag on the other process, and a preview that blocks a drag is not a preview. The only way out is to stop resizing the film.

**What was tried, and what killed it.**

| the idea | what it looked like | why |
| --- | --- | --- |
| Freeze the film for the drag: capture the band's frame, paint it opaque and stretch it into each box | the pin resized smoothly and the film stopped — a still, soft in each new box, then a jump at the release when the player was shown again | it never raced the content, it stopped drawing it: every box was the same stale frame |
| Hide the film for the length of the resize | the band went empty for the whole drag, which reads as the film having died | nothing is drawn while the box changes |
| The film as a `--wid` child of the host, fitted asynchronously on every step | a residual bounce — the picture trailing the band by a presentation — with the strip a grow left uncovered filled by a stretched held frame (the double image), and a shrink clipping a stale child into a cropped picture | the child's geometry arrives before its pixels; nothing orders the two without blocking the drag on the other process |
| FFmpeg's player as a disabled `WS_CHILD` of the host, fitted to the host's client on every step | the film kept the right shape and the box was never wrong, and every gesture paused it — a resize, a move, a volume change and a click on the picture alike | the fit was a synchronous `SetWindowPos` into the player's own thread, which is the drag blocked on SDL reconfiguring its swapchain: the race above, measured rather than argued about |
| A generous frozen source at the drag's start, then catch-up and settle asks | flicker and blur, with a flash still at both ends; the 3× cap was silently clamped in practice to the window system's maximum tracking size (`SM_CXMAXTRACK`/`SM_CYMAXTRACK`, about a screen plus 20 px), so a pin near the screen's own size got little more than the box it already had | every catch-up is still a resize of the source, which is the race again; a bigger box only makes the miss rarer |

| A thumbnail that stretches the source's whole client, margins included | zoomed out: the picture small in a field of black (measured `client 916x515 … picture 2595x1460 margins l311t0r311b0`, 311 px a side), and a source smaller than the box as the upscale that reads as zoomed in | mpv's own letterbox margins are inside its client, so stretching the client stretches them too |

| A host that painted the bars and trusted the thumbnail for the rest | a band of desktop inside the pin, standing after the drag | a DWM thumbnail composes **over** the destination's content, and `SWP_NOCOPYBITS` hands the host a client it has never painted, which the Shell shows through |
| A rectangle pair built from cached or planned geometry | at each settle the Shell sampled past the source's surface and drew nothing | the source's client and the picture's shape both change under a cached pair; the pair has to be read at the call |
| One source per film, placed once at the film's own size; the destination the whole box; the crop `cover` | the film fills the box through the drag, no flash at either end, no zoom either way | nothing moves but the box, so the road has no moment of its own to be wrong at |

**The road as it stands.** Four rules, each of which exists because of a row above:

- **One source per film, placed once, at the film's own picture size.** The player's window is given one box, once — at adoption, or by the pass that watches the player when it has not opened the file yet — at the size the film would be drawn at were it not fitted to a window, clamped to what a window may be, and never resized for the pin's life. **Where that number comes from is the one thing an engine answers differently**: mpv is asked for its own `video-params` (`dw`/`dh`, so a turned film's shape is the shape it draws), and FFmpeg's player, which is told nothing after its launch and answers nothing at all, is given the size the probe measured the same film at before the launch — *the probe's measurement is what FFmpeg's player contributes to this road*. A player that has not answered yet is waited for rather than guessed at. A resize changes the content geometry under the thumbnail; a move does not. The picture's shape is therefore a constant for the pin's life, and it is invalidated with the film: teardown forgets it, adopting another window resets it, and every frame checks the record belongs to the source it was placed for — so the film that follows can never be cropped by the shape of the one that ended. **The client is not a constant, and is not assumed to be one**: nothing this app does resizes the source, but Windows rescales a window carried to a display of another scale and mpv takes the suggested rectangle as it stands (see `video_launch::mpv_box_size`), so the crop is fitted into the client the window answers with now. A pair built for the placed client was a crop of the top-left quarter of the rescaled surface, stretched into the band — the pin that read as zoomed in (measured: `cli 3840x2160 pic 1920x1080 asked 1920x1080`, with no `thumbnail update` after it). A window that answers nothing is cropped by the placed client, so a failed read is the pair that already stands.
- **The destination is always the whole box, never a fitted sub-rect.** A destination smaller than the client leaves a rectangle over, and no ordering of the two shapes keeps it from showing; a destination that is the client leaves nothing to get wrong. The host erases that same client under the picture, because a DWM thumbnail composes over the destination's content — the host's own black is what a client the Shell has not composed yet shows instead of the desktop.
- **The crop is `cover`, from the centre, and a pure function of three numbers**: the source's live client, the film's constant picture shape, and the box. It is the largest rectangle of the picture that has the box's shape, centred in it — so a box of another shape crops the film instead of letterboxing it, and a box larger than the picture on an axis is the picture whole, upscaled by the Shell from the film's own pixels. Nothing in the crop reads a window or a player, so a frame can only change with the box or with a source resized under it.
- **A resize gesture may move nothing but the box and the source's position.** The source is native-sized and does not follow the pin, so a pin at an edge or a corner of the desktop would have the piece of the source the Shell samples hanging off it: the source is slid the shortest way back onto the monitor's work area, and that slide is `SWP_NOSIZE` and snaps to a 64 px grid, so a slow drag at an edge moves it once every 64 px rather than on every frame. A source whose crop already fits is not touched, which is every ordinary centred drag.

**The pin's band is a hole over a host that has a picture and black over one that does not, and every change of that owes exactly one paint** (`pin_film_host::the_band_is_a_standing_host`, `the_band_owes_a_repaint`). Nothing else paints a pinned film's band: no frame of this app's advances behind a player's film, so a paint written during a wait used to be the last word on it — a band filled black over a host whose registration had been let go for a swap stayed on the screen over the picture that arrived after it. So the handover, the host being shown again, a registration taking the picture and the registration being forgotten each leave the band's repaint owed, and the pinned tick spends it. A host that has been *taken off the band* (`take_the_film_off_the_band`, the film leaving the pin) is no claim on the pixel at all: a band still filled black for one would be a black rectangle standing where the film was, with nothing behind it, for the rest of the run.

**A new source may not take over before it is ready — and no player may go before it does.** A relaunch is another window, and its order is one rule: the replacement is begun, its source adopted and placed once, the registration handed over in one step, and only then is the player it replaced ended. **A picture already in the host is what covers a relaunch** — the standing registration, or the frame this app took out of the source's own window for it (see the paragraph below) — and it is the whole of the cover there is: nothing parks, hides or clears the film for a seek, a subtitle copy, a level change, a file step or any other player change, so the host is shown once and stays shown, and what covers the wait goes on drawing while the replacement opens its file. The film is thus never blanked by a handover — what changes hands is one rectangle, on the pass the new source can draw. That is a rule about the host as much as about the registration: nothing may take the film host off the screen with a pin standing over it, which is why `film host hidden while a pin lives` is a line a run must never contain — the only hide is the film leaving the pin altogether. The picture the pin is showing is the one the standing registration draws, so it keeps drawing until the new source's live client is the client the one placement asked for **and** it can show a frame: its player's video output is configured for one where the player answers over a pipe (the presented predicate without the second, which a replacement begun on a seek's second cannot supply), and where it answers nothing — FFmpeg's player — a few points of its own window have been read and at least one is not black. **A window at the asked client is not a picture**: it is the right size and empty for the whole of a decode, which is the band a seek and a subtitle copy were measured with. That sample is one `GetDC`/`GetPixel` pass per `SOURCE_DREW_EVERY` (64 ms) on the monitor that already watches the player, latched once the source has drawn, and never taken on a frame or under a drag — so readiness costs a handful of pixels a pass rather than a cross-process read per frame. Until then nothing is unregistered — the host's black erase is never exposed for a handover — and the pin's box is not re-pointed at the unready source. A source that never reaches its asked client is traced as `thumbnail source not ready` and waited for; a source at the right client that never draws is traced as `thumbnail source never drew after …ms, swapping anyway` and the picture is handed over at the player-start bound regardless (a film whose opening frame is black is that case, not a failure), so the pin is not blanked by a handover and the one before it is not left to a player that is ending. A source that does draw is written once as `thumbnail source drew after …ms`. The swap itself is one step, and its line carries both players — `thumbnail swapped old … pid N new … pid M after …ms` — so a handover onto a dead window cannot pass unnoticed. **The player it replaced is ended only once that swap stands, or at once where a still of its own picture stands instead**: `player retired after the swap pid N` is the line the loop leaves, `outgoing player ended at once pid N` is the cover's, and `player ended while standing …` is one a run must never contain. **A relaunch superseded before it stood is dropped rather than played out**: a newer seek or step kills the earlier replacement before it can publish, the player the host is drawing is never the one killed, and the drop is one line — `relaunch superseded before it stood pid N`.

**A relaunch covers the picture with a frame of this app's own and ends the old player at once.** The `dc` road — the only cover road this build carries, and what `RHP_FREEZE` means when it is unset or unknown — takes the outgoing source's own client with one `BitBlt(SRCCOPY)` at the release, about a millisecond, and there is no decode, no worker, no deadline and no race: the source's own DC is the one surface that holds the picture for the whole of the gap (the readiness sample reads it lit twenty times a second through the very black the pin shows), and `PrintWindow` of the same window answers black because the source wears `WS_EX_LAYERED` at alpha 1/255. The frame is sampled on a 16×16 grid over its inner half before it is offered as a picture — **a frame under 2% lit is never painted**, so this road can lose a cover but cannot paint a black one — and the lines are `still captured from the source dc pid N WxH lit=<pct>% in <N>ms`, the size, checksum and dumped PNG of `still captured frame pid N …` (trace builds only), and `placeholder painted from a still pid N at S`. The order from there is the whole correctness: the frame into the host's **retained cover**, one repaint without an erase, `DwmFlush`, the registration let go, and only then the outgoing player ended — freeing its file, its sound device and its GPU device before the replacement is spawned. `placeholder unavailable pid N: the old picture plays on` is the rejection: nothing painted, nothing unregistered and nothing ended, which is the `off` road for that one relaunch. The cover is retained rather than painted once (`pin_film_host::put_the_cover_in`), so the host's own erase and paint re-crop it to the client as it is at that moment rather than going black. **The pin's band over a cover is a hole** (`fill_band_opaque` asks `the_cover_stands`), because the pin's next repaint — ~70 ms after a seek — is what filled that band black over the host's frame and kept every cover off the screen past it; that band is the defect the seek road table below records, and 81bb408 is its fix. The swap is the one step it always was: the replacement is adopted, placed once, waited for until it has drawn, and its registration takes the whole box over the cover, which goes with it. A rejected capture, and the `off` arm itself, are the road before there was a cover at all: the registration goes on drawing the old picture, which plays forward until the replacement takes it over. **`dc` is the default and `off` is the only other arm**, both read once per run from `RHP_FREEZE`; a film mpv draws never comes here at all: its seek is a command down its pipe and it never relaunches. The tracker and the z-order follow the source that registration *draws* rather than the newest pid, so a host with a cover in it is never a pin declared empty. A film's late copied subtitles do not swap the picture at all: where the player has no command channel the copy is preloaded for the film and rides the next relaunch the user asks for — a seek, a level, a track, an engine — which names it in its filter chain anyway, while mpv keeps its instant `sub-add`, since it never restarts and never flashes.

A seek on FFmpeg's player is a relaunch, and the outgoing player's window is what the pin's registration draws until the replacement draws its own — so every row below is a statement about what that registration was left showing.

**A pin the desk reads black says nothing about which of the two things stopped, so the outgoing window's own client is sampled beside it.** A run of `still` on glass went black 72 ms after the release with every record this app keeps saying nothing had changed — the player alive, the registration standing, the still not painted — and that black has two possible causes that are indistinguishable from the pin's side: the player stopped drawing its own window, or the window still draws and the compositor stopped drawing it. So each `still probe` sample carries the same moment's reading of the source's own client through `the_sources_picture_is_lit` (the call the suspend road already uses) with the window's `vis`/`layered`/`topmost` beside it and the player the standing registration draws as `z`, and the result line carries `src_first_black_at` and `src_lit_at_swap`: a source that stays lit under a black pin is a composition or registration failure, and a source that goes black with it is the player itself. The registration is written down as this app believes it at the release (`covering registration: source … dest=… visible=… standing=…`).

**The order a cover is put up in is the correctness, not a tip.** A DWM thumbnail composes *above* the host's own GDI content, so the four steps are mandatory and no other order works: (1) paint the still into the host's client — or, as this build does, put it in the host's retained cover and repaint without an erase; (2) `DwmFlush`, so the paint and the composition are committed; (3) unregister the thumbnail; (4) end the outgoing player. **A paint under a standing registration shows nothing at all**, and **an unregister before the paint has committed exposes the host's black erase** — the two black bands every failed cover road in the table above ended in. The steps are written down one line each (`still painted pid N`, `dwm flushed`, `thumbnail let go for a still pid N`) so a wrong order is a line in the run rather than a frame nobody can explain. **And the host must not erase under a cover**: `WM_ERASEBKGND` fills nothing while a cover stands, and `WM_PAINT` draws the retained frame re-cropped to the current client, or every invalidation and resize in the gap would blank the picture the cover exists for.

**Three engines are on this road, and there is no other.** mpv and FFmpeg's player each make a window of the desktop's — one is launched with no `--wid`, the other has no embed switch to pass — and an installed f3d makes one too, because a model is a scene its renderer draws and this app has no reader for one; the host shows whichever it is through the Shell's thumbnail. **A model's band is the pin's, and the first press in it is handed over**: a film's band and a model's both answer `HTTRANSPARENT`, so a hand on the band is the pin's press — and where a film's press carries the pin, a model's is given to f3d's own window: it is placed in the band, raised over the pin's window and below its chrome, its `WS_EX_TRANSPARENT` and `WS_EX_LAYERED` off and its activation allowed, and a real left press is injected at the cursor, so the scene orbits and zooms from the engine's own capture (see `f3d_player::hand_the_band_over`). The band is the Shell's thumbnail again the moment the pair is not what the user is in. The gates that told them apart are gone with the roads they opened: there is no child host, no per-engine adoption and no per-engine style of pin. **A window that replaces itself is a new source**: a player that makes its window again — every relaunch of FFmpeg's player is another process with another window, and so is one relaunch for a seek, for a copy of the film's subtitles, or for the next file of a walk — is adopted by the pass that watches it and placed once. **It takes the picture over only when it is ready to draw**, which is the readiness rule above, so it is registered once, at that swap, and the registration the old window had is let go of only after the new one is in the host. The trace's `source adopted` line names the engine, and everything after it is the same for every engine.

**The rules have teeth in code.** Two calls touch the source window's geometry and no others: `size_the_source` is the one placement, reached only through `place_the_source`, and it alone may change the source's size (once); `move_the_source` carries `SWP_NOSIZE` and may change its position and nothing else. A third call, `lower_the_source`, carries `SWP_NOMOVE | SWP_NOSIZE` and only changes the z-order. A second placement is refused out loud and counted rather than swallowed, so a path that reaches one is a line in the trace: **`source re-placed` is a line a run must never contain.**

**The source is invisible rather than merely covered, whichever engine made it.** It wears `WS_EX_LAYERED` at alpha 1 of 255 (`RHP_THUMBNAIL_INVISIBLE`, on unless it says `0`), because a native-sized source may be larger than the pin and nothing of it may reach the screen — while a window the Shell is not drawing has no picture to thumbnail at all: a `SW_HIDE`n source's thumbnail is **not** frozen at its last frame — measured, it goes black 18-71 ms after the hide and stays black until something draws over it (see the seek road table above), which is what killed every road that freezes the outgoing player and why the cover that ships is a picture of this app's own. The bet is that the Shell draws the window's own surface and not the blended 1/255 result, and a run says which by whether the player is still alive when the pin goes black.

**Hover and pin are one film, for either engine.** A hovered film is drawn on this road too: one source and one registration per live film, with the hover's own host as the destination. A take-up promotes the hover's host into the pin's — the same window, the same player, the same registration — so it launches no player, asks the source for nothing, and re-crops like any other box change. A hover that is never pinned takes its source and its registration down with it. FFmpeg's player's hover is begun at the film's own size on the desktop and the pin promotes that same host, which is what keeps a take-up from relaunching a player that cannot be told where to start.

**A hover's film is loaded on one mpv kept warm between hovers** (`mpv_resident::serve`), begun idle from the hover's own argv with no file and parked off every display at 1×1, and a resident begun under a signature a hover cannot change is ended and begun again rather than reused. A resident serves only while no pin stands, and it is the pin's from the moment a pin takes the hover's player over — which leaves a fresh one owed, begun by the tick once no pin stands and none is held; only a standby resident whose **MPV TTL** has run out is ever reaped. The pipe is waited on only for a resident this hover began, and a file that has not answered `video-params` inside `FILE_LOADED_WAIT` is stopped and left warming rather than ended.

**A level is coalesced rather than written per message.** The popup is drawn at the level at once and the engine is told the latest one at most once a preview tick (`flush_pin_volume_level`), and FFmpeg's player takes it through a single slot that keeps only the last request, on the thread that holds the mixer's apartment. A level of nothing is a slider at `0.0` and never a mute. **Every level this app gives a player is written to the trace** — `volume takeup`, `volume press`/ `volume drag`, `volume set`/`volume target`, `volume ramp applied`, and `volume settle … playing_at`, which says whether the level is one a player was told or one still owed, so a knob a hand turned is told apart from a film born quiet.

**A film pin put away into the taskbar is its host minimized, and the hover of that button is a still this app takes itself.** The host is the window Windows lists on this road — it owns the pin's chrome (`own_the_pin_window`), so the Shell's button belongs to it and not to the pin, and a minimize is `ShowWindow(host, SW_MINIMIZE)` after the source the Shell draws through it is hidden (`put_the_pins_window_in_the_taskbar`, `hide_pinned_siblings`). **A still of the host's own rows would be the black it erases to**: the film in it is a DWM thumbnail composed *over* the host's client, so what the button holds is a picture of the host's *client as the desktop shows it* — the film and the chrome strips drawn over it — taken before the pin leaves the screen (`keep_the_pins_picture_for_the_taskbar`, `pin_taskbar_mirror::take_the_picture_of`). **A pin that stands in a window of its own has no host to be pictured of, and its own window is the button** (`pin_is_its_own_window`, `real_pin_window`), so the same picture is taken of that window at the same moment and held for the same button. **It is taken at every collapse and not only at a put-away into the taskbar**, because the collapse is the last moment the window on the button is on the screen: a pin that goes away into the bubble and is then asked for the taskbar from the bubble's own row has had no window of its own on the screen since, so the frame composed at that collapse — the last one the user saw — is what its button is handed (`take_the_pins_picture`, `collapse_pin_to`), and the row that puts a pin away forces the app's own still and invalidates it whether or not it could take a new picture. **The direct minimize takes nothing over that picture**: its window is still on the screen when the row runs, and the Shell's own freeze of it is what that road's hover has always been. `SW_MINIMIZE` from a hidden window is a *visible* iconic one — measured, `IsWindowVisible && IsIconic` — so the row leaves a real taskbar button behind the bubble either way. Every window that can wear the button is made supplying its own stills (`DWMWA_HAS_ICONIC_BITMAP`, `supply_the_stills_of_this_window`), the app's own bitmap is forced for as long as the pin is away (`DWMWA_FORCE_ICONIC_REPRESENTATION`, `the_buttons_still_is_the_apps_own`), the Shell's `WM_DWMSENDICONICTHUMBNAIL` is answered with it in that window's own procedure (`answer_a_thumbnail_ask` — the pin's own window answers it in `window_proc`, where an ask with no picture held is the hover's and answers nothing), and the picture is forgotten when the pin ends, the host goes, or the pin is up again. Both classes a host can be made from answer the same things, because a hover's host a pin took up *is* the pin's host from then on (`answer_a_host`).

**And the Shell's restore of that button is the pin's restore.** The window coming back is one message on both roads a pin is put away as a window — the pin's own window and the host that owns its chrome — so the size gate and the ask are one function (`the_pin_came_back`, `WM_SIZE`+`SIZE_RESTORED`+collapsed+not-this-app's-own-minimize), and the restore shows the host *and* the source the Shell draws through it again: a minimize takes both off the screen, and `place_the_pin_film_host` only moves a window (`bring_the_film_back`). A host that answered nothing there came back as a pin that still believed it was away — drag, resize, chrome and playback refused, the band black, and a second minimize answered by nothing. **Three things that road must not wait on.** The size the Shell sends is the window coming back *even while it is still iconic*, so the gate asks whether the window is hidden and not whether the restore has finished — a `SIZE_RESTORED` read as "not restored yet" left the pin on the screen and away for the rest of the run, with every seek refused. A host the size arrived for is asked back up by the restore itself rather than left to a later pass (`ShowWindow(SW_SHOWNOACTIVATE)`, which restores without activating), because the pin the user asked for is up with its film. And the show of the source is a *post* to another process, so the restore compares its ask against the last one it made rather than against `IsWindowVisible` — a hide still in flight would otherwise be read as "already up", the restore would ask for nothing, and the queued hide would land last: the host on the screen, the source down, and the band black under a film that is playing (`pin_film_thumbnail::set_the_source_visible`). The button's own **Close** is the pin's end rather than the window's destruction (`answer_the_hosts_close` → `request_pin_end`), so the teardown that takes the host down is the one that runs.

- **FFmpeg's player's road has no such run yet.** It is the same road, on a player the Shell draws the same way, and the report above is what it is for; what it has not had is a session traced for the counters the two runs above are read from. **The test suite measures none of this.** The suite holds the functions — a matrix of boxes and shapes that must fill the destination and stay inside the picture, one placement and no second, a press/drag/release/settle that asks the source for no box on *either* engine's route, a source that replaced itself adopted once and registered once, the host a take-up promotes — and that is all it can hold. Only an installed player, a compositing desktop and a hand on the resize bar show whether the film actually filled the pin: the Shell's thumbnail, the player's own window and the asynchronous geometry are all outside the process the tests run in.

**Diagnosing a run.** `RHP_PIN_TRACE` (presence is enough) writes the pin's road to `%TEMP%\rhp-pin-trace.log`, one timestamped line each; `RHP_RESIZE_TRACE` adds one line per resize step with the chrome's paint and the host's placement. A clean session contains almost nothing but `thumbnail update` lines — plus one `thumbnail held heartbeat` a second and one `thumbnail held` summary at each settle, both counted rather than printed per frame — so any other line is worth reading. The rectangles in the `thumbnail update` line are the whole diagnosis:

| the trace says | what it means | what to suspect |
| --- | --- | --- |
| `thumbnail source resized cli … placed …` | the source is not at the box the one placement asked for, and the crop is fitted into the client it is in now | something outside this app resized it — Windows rescaling mpv on a display change is expected at a seam, anything else is a path that resizes the source |
| `pic` ≠ `cli` | nothing: the crop is fitted into the source's live client, so the two are one number | a pair built by something other than `settle_the_registration` |
| `src` not inside `cli` or `pic` | the crop samples past the surface | the pair was built for another client, another film's shape, or a geometry that has moved |
| `dest` ≠ the host's client, or `dest` not at `0,0` | the destination is not the whole box | a fitted destination is back, or the pair was built from a box that has since moved |
| `host` ≠ `box`, or the host's place not the pin's band | the film is drawn at a size or place that is not the box | the host was not placed at the band this frame, or the band and the film are two windows again |
| `src` covering the whole `cli` while `pic` is smaller | a stretched frame inside a correct box | the crop is of the whole client, mpv's letterbox margins included |
| `source re-placed` | a second placement was refused | a path that resizes the source; the invariant is broken even though the frame was saved |
| `box 0x0` or `src 0x0`, or `thumbnail register failed` / `thumbnail properties failed` | a pair with no rectangle, or one the Shell refused | a window that has gone, a source not drawing, or a pair built before the host had a client |
| `thumbnail source not ready cli … asked …` | a source adopted to replace the picture cannot draw yet | a player that has not taken the box it was placed at, or an output not configured for a frame; the picture before it is still drawing, and this is the wait the swap is bounded by |
| `thumbnail swapped old … new … after …ms` | the picture changed hands in one step | clean, one per replacement; a swap with no not-ready line before it is a source that was ready at once |
| `seek picture cli … pic … asked … source …` | the frame a seek landed on, and what it is drawn from | `cli != asked` is the source away from the box the one placement put it at — a window Windows rescaled on a display change, which the crop follows (see `thumbnail source resized`); `pic != asked` is a film the player is fitting inside its own window, which the crop was not built for; `pic none` is a player that reports no picture at all, which is nothing read rather than a mismatch; three equal numbers say the flash is not in the geometry |

`thumbnail source moved` is not a fault — it is the slide at an edge — and `thumbnail source cannot hold the crop on screen` names the one case no position can fix (a crop longer than the work area). `thumbnail source native unknown`, `late` and `unobtainable` say which of the placement roads a film got.

**Where a window ended up, and who was in front.** Every line that reads the front carries `above=`, the window directly over it in the z-order, and most carry `foreground=`, the window holding the front: `band placed`, `band taken and given back: <why>` — with the road that asked for the flip, `a press`, `a preview update`, `a press on a running page`, `the pin appeared`, `a box change`, `the setting named the ordinary band` or `the setting was turned off` — the host's show, `pin above:` after a show, the keyboard hand-back at a collapse and at an end, `set_foreground … -> foreground=… pin above=…`, and the player's topmost show. The `Always On Top` road is read on its own lines as well: `setting names <band>: … holds-band …`, `appwindow <0|1> of <window>: the user is in it, read at its next show`, `settle after the setting moved: caret in … stands-over … raisable …` and `settled: …`. Every message a pin's window is handed carries an `above=` beside its `foreground=` and `focus=`. Both readings are described rather than left as `other`: `class:pid (image)` for any window Windows can still be asked about, this app's own by the word `window_name` gives them (`pin`, `host`, `preview`, `bubble`, `stand-in`), `none` for a handle that names no window at all, and `invalid` for one that names none any more (`a_window_description`, `what_is_above`). A pin with `none` above it is a pin at the front of its band; a listing's class above one, after a box change, is the whole of what "it put itself behind the listing" is read from.

**Watching a film's sound.** `RHP_PLAYBACK_TRACE` (presence is enough) writes `%TEMP%\rhp-playback-trace.log`: one `launch` line per engine start (engine, kind, the level the launch resolved to, and the form that level was given the player in — `aid=no`/`-an` or `volume=N gain=…`), one `engine truth` line per mpv start (the `aid`, `audio-device`, `current-ao`, `audio-out-params`, `volume` and `mute` the player itself reports, and the verdict they come to — the device that was asked for beside the driver in use, and that driver rather than the `ao` option this app never passes, which answers an empty list rather than a driver), every line either player writes on its own stream, and a `kill` line per player ended with whether a zero-timeout wait confirmed the process gone. **The level the launch asked for and the level the player is at are two words on that line** — `asked 100` beside `volume 0 mute no` — because they are two facts: a player that says all of a track, a driver and params while its own level stands at nothing, or its own mute is on, is a film that plays with no sound and every one of those answers calls it sound. It answers one question that nothing else on the machine can: a film that plays with no sound and no entry in Windows' Volume Mixer is either a launch that gave the player no track at all (the launch line says so), a player that could not open a device from the track it had (the player says so, and FFmpeg's player only says anything at all under this switch — its stderr is otherwise `-loglevel quiet` into a null stream), or that player told to be quiet (the level and the mute beside the level asked for). Unset, nothing is written and no thread is spawned; a launch that is neither traced nor guarded builds the command line it always did (`playback_trace`). **A traced launch is read at a level that names a device**: `--msg-level=all=warn,ao=v,audio=v` — `all=warn` still the ceiling, and the two modules an audio output speaks through raised past it — because a device that refuses is reported at `ao` and `audio` verbosity and nowhere else, and `all=warn` above them is a run that plays silently with the state written down and no reason beside it (`video_launch::mpv_args`).

**The player's opinion is not the only one, so the OS is asked as well.** A `session` line per launch, on the same trace, is what Windows' own mixer says about that player's pid: whether a session exists for it at all on the machine's render endpoints, the mixer's state for it (`active`/`inactive`/**`expired`**), the executable its session identifier names, the mixer's own slider and mute beside the player's, the stream's own per-channel volumes, and the endpoint it is on against the default endpoint read at that same instant (`audio_session`). **It exists because a captured run left every answer the player had exhausted**: mpv logged a device selected, a stereo float buffer opened and no error after it, reported `aid`, `wasapi` and params, `volume 100 mute no` — the six answers of twelve launches the user did hear — and played silently with no session in the Volume Mixer. **The four words a line is read for**: `expired` is the OS saying the stream is over under a player still writing to it, which nothing on the player's pipe can say; `session none` is the mixer answering and the player not in it, qualified by `children` — the sessions its own child processes made, since the mixer groups a child under its parent — so a miss is never ambiguous between nothing started and something started where nobody looked; `mixer 0.000` or `mute yes` is a silence of the mixer's own, at any level the player reports; and `channels` is the per-stream level, which is where a handover to the driver lands — mpv's default `--softvol=no` means the level this app gave it is applied by the driver, not inside the player, and neither `volume` nor the slider is that number. **The line states its own gaps**: `-` for a value the OS would not give, `unknown` for a state with no word, `refused` for an interface that would not be had (say `IChannelAudioVolume`), `none` for a session with no channel, and `session refused` with the part of the walk that failed — a silent probe would read as `session none`, which is a finding about the player rather than about this question. **Who a session is, and who stood beside it, is on the same line**: `session-id` and `instance-id` are `GetSessionIdentifier` and `GetSessionInstanceIdentifier` entire — the two strings Windows keys its remembered per-app volume and mute by, and the reason two sessions of one `mpv.exe` can be remembered differently — with the image the pid really runs beside them, and `neighbours` naming the sessions the endpoints listed beside the player's: their pid, image, state, mute and slider, the first eight of them with the count of what there was (`neighbours 8 of 14`), and **`dead` on a session whose process has ended** — the carrier this was added for, a lingering muted session a new one inherits from, and never dropped from the list. A cure's own line carries the same identity and neighbours, so a victim and a clean film are compared field for field inside one run. None of it is read where no trace asked for it: a guarded look on a run nobody is diagnosing walks exactly the walk it always did. **And the run it was built to describe proved a fault it now cures**: of eighteen players in one captured run, two had a session whose mute switch was on at `mixer 1.000` with its channels at `1.000 1.000`, under a player that reported `volume 94 mute no` — two mute switches, and the player can see only its own. So a **guarded** player's session is looked at for every read the guard already makes (`audio_session::look_and_cure`, on the guard's probe thread and straight after the engine ask), and a mute found on is taken off with one write — `ISimpleAudioVolume::SetMute(false)` — **whether or not `RHP_PLAYBACK_TRACE` is set**, because the trace is the recorder and the cure is the fix. **Nothing else is written by the cure**: not the master volume, not a per-channel volume, not `IAudioEndpointVolume` — the master volume is the app's own level and is written only by `set_the_mixer_level` for a film's knob, on the same walk and the same apartment (see `ask_the_ffplay_its_level`). **A session muted with its slider at nothing is a hand in Windows' own mixer**, so it is written down and left as it is (`session turned down … left alone`), because putting it back would overwrite a deliberate setting; and a mute the mixer refused, or a walk that could not be made, is written as a failure rather than swallowed (`session unmute failed …`). **COM is taken on that thread's own apartment** (`COINIT_MULTITHREADED`, given back at the end) and nowhere near the preview loop, which holds one for the engines that draw into it; the wait for a player's session to exist and every call after it are on the thread, bounded the way the pipe reads are. Unset, the trace spawns no thread and writes no line of its own; a player this app did not begin and is not guarding is never looked at at all.

**Healing a film's sound.** The trace describes the roads to a silent film; `audio_guard` walks back down them. It asks the same six questions (`aid`, `audio-device`, `current-ao`, `audio-out-params`, `volume`, `mute`), **and the machine's own look at that pid's session beside them**, and reads one verdict out of the two — a player whose every answer is sound and whose session is still muted is `session-muted`, the fourth road, and one whose mute the look took off is `heard` (see `audio_session`). Then it climbs a ladder, each rung taken at most once: a track asked back for with `set_property aid auto` — the launch's own road, healed; `audio-device` handed its own `auto`, which is mpv reloading its audio output, so a device refused while the film was starting gets one more attempt at it; the level this app last asked that player for asserted again with the player's own `mute` taken off beside it, which is the cure for a verdict of `silent` — a track selected, an output open and a player told to be quiet; and, if none of those was heard, **one** new player at the second and the pause the old one had, read once, and then the ladder ends. Each rung is entered on what the read-back said and never on a write having landed, and a player that answered **nothing at all** is asked again every half second for the half minute it is given, and not once more the moment it says anything — heard, no track, no device or silent. **That retry is bounded by the player's own readiness rather than by a schedule**, because a player is not ready at a wall clock: a 4 GB file off a slow disk can spend several seconds before mpv has created its audio client at all, and a read that gave up on such a player would never see the session that client owns. A player that has said nothing is not a film without sound and is never begun again: the one verdict the guard may not act on is the one it never got. **The same goes for a driver named with nothing playing through it** — `current-ao wasapi` and no `audio-out-params`, which a captured run read 548 ms after its launch and which is a player still opening its output as readily as a film that lost it — so that shape is read once more and the device cure is written on its second consecutive read; `aid=no` and a driver of `null` are answers, and each takes its rung on the first read. **A `session-muted` read climbs nothing**: the player's answers are the ones a working film gives, so a track, a device or a level asserted again would be writes to a film that is not what is muted, and the cure was the session's and was taken where the read was made. **Every read writes a line** (`audio guard`, `audio read-back`, `audio step`), so a field log carries the ladder's whole evidence even where it healed silently: the session clause is the last word on the read-back, and a read that was `session-muted` is a fault found rather than a film with its sound. **A cure that worked reads back as `heard`**, which is why it has a line of its own (`session unmuted pid … mixer 1.000 was mute`) — a cure nobody wrote down is one nobody can tell from a fault that never happened, and a cure the mixer refused is written as `session unmute failed …` rather than swallowed. **A ladder that ends is written once, and its last rung is written whole**: one `audio gave up` line carrying the launch's form and the level it asked for, the six answers of the read that reached it (`-` for the player with no pipe), and the verdict they come to — because a film nothing could cure is the case a log is read from with no reproducer behind it (`audio_guard::a_give_up`).

**The guard stands behind both roads, and a hover's ladder is the in-place rungs and nothing else.** A pin's film is cured where it stands and begun again once; a hover's — on a cold launch and on the resident's serve alike — is cured where it stands and then left, because the resident is the one player where a stale audio decision lives longest (one process handed file after file, begun at whatever level the first hover had) and because a hover that began a player again would pay the very wait the resident exists to save. **A serve is a new episode of the same pid**, so it arms a ladder of its own: the file before it spent nothing of this one's, and the `REBIRTH` record a pin's relaunch leaves behind is not a hover's to consume. A film the level itself gave no track is nobody's business on either road, and FFmpeg's player is guarded on a pin's road only — its ladder has no in-place rung at all, so a hover's guard on it could only ever give up. **A pin that takes a hover's player over gets the pin's road** — the same process and the same reads, with the rungs a hover stops short of from that moment (`audio_guard::a_pin_took_it_over`).

**The level a `silent` player is taken back up to is the level this app last asked for, not the one the film began at** (`audio_guard::the_level_moved`). A hand moves the level while the film plays, and mpv keeps its track at `volume 0`, so a pin dragged to the bottom of its knob answers exactly as a film something else silenced does — and the launch's level put back over that hand is the bug this closes. A level of nothing is the silence the setting chose, which the verdict already exempts, so no rung fires; a level moved to 60 makes the level rung assert 60. **The roads call the seam, and `mpv_ipc::set_volume` does not**: the guard's own rung writes through that function with its lock held, so a seam inside it would be the guard feeding its own record — a level it wrote taken for a level a hand had moved, on a lock it already holds. So a write the guard makes moves nothing, and the app's own writes move it where each of them landed: the pin's knob and the wheel and press behind it, the release's re-assertion and a row moved in the tray (which is the knob's road, `pin_chrome_layout::set_the_pin_players_level`), and a pin taking a hover's player over at the pin's own level (`pin_playback::adopt_the_hovered_film_in_the_host`). A hover's per-serve level needs no second write: the serve's caller arms the guard with that very level the moment the serve returns, so the arming is the record.

**The resident can be taken out of a run without a rebuild, which is the one A/B this fault needs.** A hover's film is loaded on the one mpv kept warm between hovers unless `RHP_NO_RESIDENT` is in the environment — presence is enough, and the value is not read. With it set no resident is begun at all: every hover begins a player of its own and ends it with the hover, and a pin adopts that player as it adopted one before the resident existed, which is the road `v0.4.5` had (`mpv_resident::keeping_a_resident`). It is a prototype's knob and not a setting, and not one the tray can reach: it is there because a film that plays with **no sound at all and no session in the mixer** is intermittent on the resident's road and was never seen on the tag before it, so the two architectures are run against each other on one machine rather than argued about. Unset, the resident road is the run, byte for byte.

**A player that answered `heard` is asked nothing further, and the sparse schedule that used to keep asking is gone.** `Heard` is where a guard ends: the one read `AUDIO_SETTLING` after the player comes up, the asks a player that has said nothing is owed, and the read-back of every rung the ladder took are the whole of what it asks a film, and a read that comes back heard clears it. The schedule it replaced — `+2 s`, `+4 s`, `+8 s`, then one every ~10 s for as long as the player lived, sampled on the probe thread and with it the late failure that climbed the in-place rungs a second time — sampled for a failure mode never once observed: a player heard at its first read that went silent later. Every muted film captured was **born** muted and caught by that first read, so the price was a poll for the length of a film for a case that has not happened. **Every read that remains asks the machine as well as the player**, so a session muted under a player whose own answers are sound is caught, written and taken off at whichever read finds it — and the asks of a player that has said nothing are reads like any other, which is what lets a 4 GB file that spends six seconds opening still be cured on the ask after it. What ends a guard besides `heard` is the ladder's own: a give-up and a session the mixer would not unmute are written once and the player is let go of, `a_player_ended` clears it (and a hover's serve is the end of its episode, whether the player is killed or left standing by), and a probe that wakes to a guard that is not its own reads no pipe and reports nothing. The player a spent ladder began (the `REBIRTH` record, `SPENT`) is given its one read and no rung at all, and the relaunch stays a player's own — **at most once in its whole life**, not once per episode — so a device that is genuinely gone is never begun again for.

**mpv has a pipe, and FFmpeg's player does not**, so the second one's ladder is one rung. An ffplay launch is piped on the standard error, and drained, on exactly the launches that have a use for a line — the trace, or a guard standing behind the film — because a pipe nobody empties blocks the child: the pipe is only ever there with its reader. A traced launch is played at `verbose` rather than `warning`, because SDL's own reason for refusing an endpoint is a `verbose` line, and `-nostats` is asked for beside it on exactly those launches: `verbose` otherwise turns on the status line — one `\r`-updated stream with no newline in it that would swallow the lines written after it (see `video_playback`). A launch a guard alone stands behind keeps `warning`, which is where its own cure is read from, and a run nobody asked for a trace of keeps the argv it had. A match against four strict fragments (`Could not open audio device`, `Failed to initialize the SDL audio`, `Failed to initialize audio`, `Could not initialize audio`) begins that player again once; an ordinary warning is not a signature, and a line the stream never carried is not one either. **The pipe and the thread that empties it are one contract** (`player_logs`): a pipe nobody reads fills, and a player blocked on a full pipe stops playing, so the drain starts with the player, keeps no more than one line, and ends when the pipe closes with the process — nothing on the UI thread, and no lock the paint wants. What that buys is the one account a hung player or a film with no sound is diagnosed from: the player's own lines, at the level the launch asked for, in `playback_trace`.

**Nothing here waits on the preview loop.** A player that has only just been begun has no pipe yet, so a thread asks and leaves the answer where the tick finds it, and the tick is what writes and decides. Its last rung is the pin's own swap path (`pin_playback::begin_the_pinned_film_again_for_its_sound` → `restart_pinned_player`), so the picture is kept exactly as a seek keeps it. **The guard moves no picture and no clock**: no pause is toggled, no second is asked for, and the only level it ever writes is the one the launch already asked for, put back on a player that had been silenced under it — a film the handover left held is begun again held. The rung waits for a tick with no swap and no handover in flight, because a picture changing hands is not a player to be begun under it.

**What this means for another player engine.** The road is engine-agnostic, and every engine this app has is on it — the two players and the viewer that draws a model: it needs a player that draws into a window of its own, whose picture size is known before anything else asks it for a box (so the source can be placed at it), and that is happy to render at that size while the pin is any size — the Shell does the scaling from there. The engine must never be asked to change that size while a pin is alive, and any engine whose film is sized per step, whichever it is, reintroduces the race described above. **What an engine cannot do decides how the road gets its two numbers, and nothing else.** FFmpeg's player has no API to answer with, so its picture size comes from the probe and a seek or a late subtitle copy is a relaunch — which the road takes as a new window and therefore a new source, adopted and placed once, with the picture before it kept until the new one can draw. A level is the one thing that reaches it while it runs, at its Windows mixer session (see `audio_session`), so changing the sound never relaunches a film. mpv answers over its pipe, so its size is its own answer, a seek is a line down that pipe, and its level is a property. An engine that could do neither would need a third: a size known at launch and a window that outlives the film.

## Kind notes (reader → engine, gate, scale, backdrop)

> Per-format specifics sharing one pattern: what draws it, which tray gate/scale/backdrop applies, and the one quirk that decides correctness (printer for Excel, flat-cover skip for books, first-plate rule for comics, dual-play alpha for metafiles).

Every kind answers the same six questions: who draws it, which tray gate turns it on, which scale function sizes it, what it composites over, what cache it uses, and what one quirk will make it wrong if ignored. Read this section as a checklist rather than a list of trivia.

- Picture/WIC/DDS/ToneMap: above. `image_background`, `preview_scale`. The default kind, and the one everything else falls back to. It has no engine in front of it, no probe, and no quirk beyond the header-size trust described under Read guards — and the one engine behind it: the image converter, for a name a codec Windows ships is asked about (`routing::chain`: `Native`, `ImageMagick`).

- Design (`psd_image/project_image/eps_image/cdr_image`): never composite; shipped preview (`mergedimage.png`, ORaster `Thumbnails/`, Procreate `QuickLook/Thumbnail.png`, CDR `metadata/thumbnails|previews/`, RIFF chunks; PSD planar+box-filter stream, 4 compressions, no Lab/multichannel/no-compat); `.ai`=PDF if `%PDF-` else EPS; `design_scale/fit`, `design_background`, `design_extensions`, `Design` gate.

A design file's own preview is read from inside the file rather than composed by this app, because Photoshop documents have no meaningful flattened form without the layer stack. The readers read a shipped thumbnail where one exists and otherwise stream the flattened composite — PSD is planar, so it is box-filtered on the fly, and three of the four compressions are supported. `.ai` is genuinely two formats in one extension: a PDF if the first bytes say so, an EPS otherwise.

- Libre (`libreoffice_render`): `[libre]` + Office-no-install fallback; `page_engine` (tray `Engine→Office Engine` + `app_installed` ProgID); headless w/ own doc, `--accept/--invisible` = no-hold; 1.2s cold/0.2s warm; TTL/`warm`; give-up by name+id; `swf` excluded (video). Shares `Document` gate/scale/cache w/ Office.

The second spelling of the same job as the Office engine, for machines with LibreOffice instead of Office. The user picks one in the tray, and the choice is a ProgID registration check, not a path search. LibreOffice is driven headlessly with its own throwaway user profile so a running instance is never disturbed; `--accept` / `--invisible` mean the converter will not block waiting for a dialog. Cold start is a second and a half, warm is a fifth of that, which is why it is kept warm under a TTL.

- Magick (`imagemagick_render`): `[magick]` second spellings+nothing-else-opens; and the fallback behind the picture readers for the names a codec Windows ships decodes (`[image]`'s raws, HEIF, JPEG XL, WebP, icons/cursors) — asked only where they came back with nothing (`magick_render_is_due` ∧ `measured_as_nothing`, `magick_fallback_is_due` for the loader); `-auto-orient` (only rotation applied anywhere); box=room ceiling, 8bpc; 1st picture only; raw-dump size via filesize÷px-weight proportions (`-size/-depth`); stdout→frame+disk page; refused remembered run-long; no TTL. `Images` gate.

ImageMagick is the picture kind's second half and the only reader of what nothing else opens. Two constraints drive everything: the box is the _room ceiling_, because the size is unknown until ImageMagick says, and there is no TTL, because the process is cheap and warm enough to keep. For a raw dump the dimensions are not in the file, so they are computed from the file size and the bytes-per-pixel implied by the requested `-depth` — a proportion, not a fact, which is why the preview may be right in shape and approximate in scale. `routing::chain` puts it behind `Native` for `Images` and alone for `Magick`: a camera raw, a `.heic` or a `.cur` is read here first, and the engine is asked about one only where that read answered nothing — which on a machine missing that codec package is every raw there is.

- PeaZip (`peazip_render`): `[peazip]` no-reader formats; `Backend::of` (7z console/FreeArc/zpaq/zstd; `.br/.bcm/.lpaq8` name-only); own thread, 1 queued, `CREATE_NO_WINDOW`+null stdin, adopted-not-recorded, give-up→unlistable; same `Listing`+cache. `Archives` gate.

For archive formats nothing in-process can open. `Backend::of` picks which PEaZip executable handles a given extension, and for the most obscure formats it can only guess from the name. One process is queued at a time and started with `CREATE_NO_WINDOW` and a null stdin, because these console tools will otherwise flash a window and wait for a keypress.

- Calibre (`calibre_render`): `[calibre]` azw/mobi/epub/fb2/djvu/lrf/pml/snb/tcr/htmlz; `ebook-convert` → PDF → first-non-flat of 8 (`book_page`); keyed (book,ver,engine); 2× render bound + hover cap; recorded, no TTL. `Ebook` gate, `ebook_scale`, `image_background`.

Calibre converts a book to PDF, and this app then renders the PDF. The one correctness rule is `book_page`: a converted book's pages are not all real content — the cover is a flat image, and several other pages are boilerplate — so the app walks the eight candidates and takes the first that is not flat. Without that a book opens to a blank or a copyright page.

- Comic (`comic_preview`): cbz/cbr/cbc via `[ebook]` + `page_spelling`; headers-only walk, `entry_bytes` single plate (`jpg/jpeg/jpe/jfif/png/gif/bmp/tif/tiff`, skip `__MACOSX`/meta), natural-numeric first, no spread cut, size off-tick, size-only cache; WebP/AVIF plates = none. Same `ebook_scale`/bg/gate.

A comic archive is a zip of images, and it goes through the book gate because it is the same user mental model. The rule that decides correctness is that panels are not pages: the first image in natural numeric order is shown whole, and a two-page spread is never cut in half.

- PDF (`pdf_preview`): `Windows.Data.Pdf` page 1, MTA threads; `%PDF-` in 1KB; `SHCreateStreamOnFileEx` + `CreateRandomAccessStreamOverStream` (verbatim-safe); measure-then-render-at-box (`ebook_scale`, ≥100%=fit); BMP encoder, white-opaque; size-only cache.

The OS PDF API needs a WinRT stream, and WinRT will not open a `\\?\` path — hence `SHCreateStreamOnFileEx` wrapped and converted, which is the "verbatim-safe" note. `MTA` here is the opposite of STA: WinRT streams are free-threaded, so these readers must _not_ be STA. Only page one is rendered, and the render is asked for at the final box size so the bitmap is never oversized.

- Vector (`metafile_image` + `svg_preview`): `Vector` gate/scale/backdrop (`vector_background`; checkerboard in-page). WMF/EMF `PlayEnhMetaFile` into own DIB + dual black/white coverage recovery; EPS preview-only (WIN header or `%BeginPreview`, budget-checked; 8b-index+alpha here). SVG: `svg_preview` (doc?+size via width/height→viewBox→300×150, `.svgz` inflate, verdict cached) → WebView2 image-page (`NO_INTERACTION_STYLE`, mtime URL); `vector_scale`.

A **DIB** (device-independent bitmap) is a plain array of pixels in memory that a program can fill in directly, which is why it is the target here: GDI metafiles are draw-command streams, so `PlayEnhMetaFile` executes them into a memory device context holding one of this app's own DIBs. That produces a bitmap with no alpha, which is why the same drawing is played a second time in white to recover coverage and get a clean edge. EPS is preview-only — this app never implements a PostScript interpreter, it reads the preview bitmap Adobe embedded.

- WebView2 (`webview_preview/{engine,host,environment,pages}`): newest-`want` only (wake, drop supplanted nav); `place` moves; `cursor_preview_hover` close rule; `file://` via `plain_path`; per-run profile; `webview_idle` (`Until away` = AFK); `NAVIGATION/HOST_CREATION_TIMEOUT`, 4× controller retries, `note_unanswered`; `RHP_WEBVIEW_TRACE/RHP_WEBVIEW_PROFILE`. Draws SVG, font specimens, HTML pages. A pin adds the source half: `ex_style_for(style, runs, source)` + `put_the_page_style` on every placement, `put_window`'s one placement and moves after it, and `the_window_takes_the_area` for the client the band samples.

WebView2 is a whole Chromium instance embedded for the three things GDI and WIC cannot do: SVG layout, font glyph rendering, and HTML. It is the most expensive thing in the app, which is why it is newest-wins — a second navigation request supersedes the first and the first is dropped rather than queued. It runs on a per-run profile directory (see Temp sweep) so no state carries between runs, and a `NAVIGATION` or `HOST_CREATION_TIMEOUT` that expires is recorded via `note_unanswered` so the same dead document does not time out on every hover.

The engine is told to stop whenever its window is not on screen (`Command::Hide`) and to start again before the next document, because a hidden window used to say nothing to the browser and a page went on running behind something nobody could see — an animated one on a `requestAnimationFrame` loop kept the GPU busy at a high rate until the app was restarted. An animated SVG is asked the same question, being a compositor working just as hard. On a machine whose runtime is too old to be asked, the window is hidden as before and the frames stop on that alone.

A page that runs is the one preview a pointer and a keyboard reach: the page's own rectangle is a place the hand is held — a drag that began on the page survives the pointer leaving it, an orbit carrying the pointer well outside the box the page was drawn in — and a click into the page gives it the keyboard (`engine_owns_the_keyboard`), where a document, a specimen and every other preview still refuse it, since showing a page is not a click and the page takes the keyboard only where the user clicked. What a page still cannot have: sound of its own, the files beside it, fullscreen, a right-click menu, the tools or a find bar. A picture or a video is dismissed by the pointer exactly as before, and this applies only to a page that runs. **Inside a pin only a page that runs is reached at all**: every other page is lowered, invisible and click-through, and the press that lands on its band is the pin's (see "The page road").

- Font (`font_preview/{font_tables,specimen}`): WebView2 `@font-face` page, `cmap`-gated lines (all-or-nothing + own-chars fallback), `name` (en pref), viewport units, per-bg ink, `direction` per line; `font_scale` (½ room), `font_background`, `[font]` list, own kind slot.

The app reads the font's tables; the browser renders the glyphs. ## Config / tray / processes / build

> Persistence and packaging. The app is the sole writer of `config.ini` (self-repairing + ordered), but a _read_ never writes it — only a start and a save do; tray is the UI onto it; every child process is tracked by job object + disk record so a crash still cleans up; installers build from the `github` profile.

`config.ini` is the entire user-facing state, and the app treats rewriting it as routine rather than exceptional. The tray menu is not a UI over a fixed struct — it is generated from `SETTING_GROUPS`, so adding a setting makes it appear in the right place automatically and it is impossible for the menu and the file to disagree about what exists.

the third is the picture's own — the one kind with a next file and no end of file to jump from, so the anchor's kind of the list is the pool all three draw from rather than two hard-coded kinds), `video_loop`/`audio_loop` (whether a hovered one goes round, default `true`; renamed once from `video_jump_enabled`/`audio_jump_enabled`, and a file holding the era's `pin_mode_*_jump_enabled = false`, `pin_mode_*_jump = shuffle` or `pin_mode_*_loop` is seeded once into the two that replaced them), `mpv_path` (empty default = first install found; read at launch), `f3d_path` (the same, for the viewer that draws a model), `html_background` (white/black/checkerboard only — a page is drawn on a page, so transparency is not one of the backdrops it is offered; any other value reads as `white`), `video_subtitles`, `theme` (read in the `General` group, since the look is the app's own rather than a text preview's), `video_hw_accel` (mpv's switch alone — what it reaches is mpv's own `--hwdec=auto`, FFmpeg's player is given no decode device, and a machine with no `mpv.exe` reads whatever the file says as off). Lists: missing key→restore+rewrite; empty=none; edited kept+ordered; `repair_older_lists` (row `before`) adopts added formats (image/vector/design/video/libre/archive/calibre/peazip/magick; `[ffmpeg]` order-only); `save` drops unknown. The video lists are two — `[video]` is what the media engine is asked to play, `[ffmpeg]` is what only FFmpeg's player reads; an existing `config.ini` is divided between the two on the next run, and a list you have edited is left as it is. Themes `%APPDATA%\...\theme\*.tmTheme` (`custom:<name>`, listed not read, re-read per menu).

- A read writes nothing — `reload_from_disk` takes what the file says and puts right what it has wrong or missing in what the app is using (`lists::repair_older_lists` read through rather than written back, a `video_engine` choice naming a player this machine has not got answered with `Best`), and the file keeps what it had; a start (`load`) and a `save` are the only two things that write it, and a read is neither. A write here would be a write the watcher sees, and the file is the one the user is holding open in the editor `Edit Config.ini` put them in: an editor writes it in place, so a read a second later took half of what they were writing and put the whole of the app's own view back over the rest of it. It is also what made an outside write stay — the app read what some other writer had put there, and the next thing on disk was the app's own agreeing with it. `differs` is therefore no longer consulted on the read path at all. A reload keeps a volume level this process last wrote — `save` records what it put on disk, and a reload that finds the file still holding that level keeps the level in hand, so a knob a hand has turned past it is not snapped back; a level the file holds at anything else is a hand edit and is taken whole.

Each list row records five things about itself — the built-ins it shipped with, how a name is matched, how it is normalised, which field it holds, and what it was `before` the user last edited it. That last one is what makes self-repair possible: on load, `repair_older_lists` compares the user's edited list against `before`, and any format the app added in a later version is inserted into the user's list rather than being silently absent, while `[ffmpeg]` is order-only because its order _is_ its meaning. A list that is present but empty means "none", which is different from a missing key, which means "restore the built-ins and rewrite the file". Retired keys are dropped rather than ignored, so an old install's file converges to the current shape on first save. Two match rules: an entry with a dot, like `tar.gz`, matches the end of the file's whole name rather than an extension; and a name two sections hold belongs to the earlier kind, so the kind decides which switch applies to it. No `ImageMagick TTL`, `PeaZip TTL` or `Calibre TTL`: those tools run once and exit, so idle time cannot bound them — a second hover is a cache hit. Nothing bounds `ffplay`, which lives exactly as long as the preview it draws; the mpv every hover is shown through is one resident kept between films (see **The film road**), and `MPV TTL` (`video_engine_idle`, default `away`) is the whole of what ends it.

Every start reads what the startup entry names against the path this process is running from and rewrites it where the two are not the same file, so the machine starts the copy you launched — not a portable copy unpacked in a folder, an older version still installed where it put itself, or a path that has moved since. The comparison is honest about spelling: a path in another case, or holding the `\\?\` prefix the Shell canonicalizes to, is the same file and the entry is left alone, and so is one that already names this copy with arguments of your own after it, while a short name for a folder or a junction is resolved rather than written over. Nothing else changes: whether this app starts at all is still the user's choice, an entry that is gone is not written back, and `config.ini` is untouched.

- Tray (`shell/tray/{menus,submenus,commands,ids,event_loop}`): icon/menu/exit/`TaskbarCreated`; rows: Preview Types, **Preview Settings** (Image / Video / Audio / Text — one half per kind that has settings beyond whether it previews at all), Timing, Placement, Scaling, Background, **Volume** (a `Video` half and an `Audio` half, each half's `Normalize`/`Remember Level` above its levels — what a film and a sound are heard at, hung from the tray rather than from either kind), Performance, Engines+TTL (one nine-item list per engine, longest first: `Indefinitely`, the times, `Never`, `Until Away` (default)), Pin Mode, Codecs (stateless, presence-checked), System. `Preview Settings → Video` carries the film's own `Subtitles` row, `Loop`, and a `Pin Mode` submenu (`Pause on Minimize`, `Shuffle`, `End of File`); `Audio` the same with two `Seek` rows, one outside `Pin Mode` for a hovered sound and one inside for a pinned one; `Image` a `Pin Mode` submenu with the picture's `Shuffle` and its `Zoom Background` (the band a zoom opens behind an opaque picture; a transparent one keeps its own kind's backdrop, `image_background`); `Text` the font size, Markdown mode, Render HTML, and the two gates — **Preview All Extensionless** and **Don't Preview Secret Files**. `Pin Mode → Navigation` is the four walk anchors, `Image` first. Gate/type change rebuilds that kind (`Refresh` recomposites others, text rebuilds frame).

The tray is generated from the config rather than written against it, which is what makes a restructure like `Preview Settings` a change to one builder: the halves a kind has are the rows appended to its own submenu (`append_pin_mode_menu`, `append_pause_minimized_item`, `append_shuffle_item`, `append_end_of_file_menu`), and one row answering the same question for a second kind is the same call with that kind's id. The one place the restructure had to reach past that is the flyout's geometry, which the pinned sound card's menu and the tray's own flyouts share (`menu_flyout_tier`) — and the second is the level lists, which are the one question asked of two kinds and therefore the one submenu built once and hung from the tray rather than from either kind's half (`volume_menu`).

Changing a gate does not restart anything; it rebuilds the affected kind in place. `Refresh` — a recomposite for most kinds, a full frame rebuild for text — is the operation the tray calls, and it is why a settings change is instantly visible rather than applied at the next hover.

- Started Processes (`app/engine_processes.rs`): Office app + `msedgewebview2.exe` (parent=us, by pre/post walk) + `ffplay`/`mpv` players + probes. Job `KILL_ON_JOB_CLOSE` (handle never closed) + `%LOCALAPPDATA%\...\engines\<pid>.state` + profile dirs; PID+image+start-time check (no bare-PID kill); startup sweep first; probes adopted-not-recorded; player recorded but exempt from tier wholesale ends.

The discipline here is _never kill by PID alone_: a bare PID can have been recycled between the record being written and the sweep running, and killing an unrelated process is unrecoverable. Every record carries the image name and the process start time, and a kill is refused unless all three match. The `KILL_ON_JOB_CLOSE` job is the belt to the disk record's braces — the handle is deliberately never closed while the app runs, so only a crash closes it and lets the OS reap everything in the set. Startup sweep runs first because whatever the last run left behind must be gone before this run registers anything of its own.

- Updates: see Runtime table. Checks at start + menu build, six-hour mem-only throttle, installer handover.

An update is an installer, not a patch: the running copy is handed over via `/S /R`, which means silent install plus relaunch, so the check verifies the downloaded file is a PE image (`MZ`) of a plausible length before it is trusted at all.

- Build: MSVC + `rust-lld` (`.cargo/config.toml`); `build.rs` + `winres` — the icon, the version block and a manifest declaring Windows 8 and later (the declaration is what stops `CreateWindowExW` refusing `WS_CHILD` with `WS_EX_LAYERED`), a failure rather than a warning where they do not compile, and the resource archive named as the binary's own link argument because a build script's `rustc-link-lib` reaches the library target (`tests/executable_icon` asks the linked executable); release kills running copy (src-watch; debug exempt); `cargo packager` NSIS from `packaging/nsis/installer.nsi` (silent uninstall, close running); `github` profile (`target/github`, `build-installers.ps1` pinned packager) vs `release` thin-LTO loop.

Two build profiles, two jobs. `release` is the fast inner loop: thin-LTO for quick incremental builds, no installer, and it kills the running copy first because the linker cannot overwrite an executable that is mapped. The `github` profile is the one that produces an artifact: a different target directory so it never collides with the inner loop, and `build-installers.ps1` driving `cargo packager` with a pinned version. NSIS handles the uninstall path, which has to close the running app before it can remove it. The target directory is the machine's rather than the checkout's where the machine says so: `.cargo/config.toml` includes an optional, git-ignored `target-dir.local.toml` (`[build] target-dir`), which the `post-checkout` hook writes from `git config rhp.targetDir` — and `git worktree add` runs that hook, so a new worktree shares the build cache with no manual step — one directory for every checkout on the machine, so a dependency is compiled and stored once. What one directory cannot share is this package: cargo's artifact and fingerprint names carry no part of a checkout's path, and cargo never looks at the artifact's own mtime, so a build in one checkout can be called fresh against another's recorded inputs and do nothing at all, leaving that tree's binary behind. The hook therefore touches `src/main.rs`, which dirties the package through the `cargo:rerun-if-changed=src` `build.rs` prints, and the next build relinks this package — and nothing else — where the two differ. With nothing set the hook writes nothing and cargo uses the checkout's own `target/`, which is what CI and every other clone get; the setting lives in git config rather than in a committed file so no machine's drive letter leaks into a clone.

## Test isolation (the app's own folders under `#[cfg(test)]`)

> Three folders of the machine's own are reached by process-wide code with no argument, and a test build of the app has a folder of its own for each of them instead — so a `cargo test` run cannot change what an app somebody is actually running has, and cannot read its records as its own.

The same rule in all three places: an environment variable names a folder for one run (`RHP_ENGINE_STATE`, `RHP_WEBVIEW_PROFILE`) and is read first, so a test that wants a folder of its own can name one; a build with nothing named falls back to `%TEMP%\rust-hover-preview-tests` (with `engines` and `webview` beneath it for the two process folders) rather than to the machine's own; and the fallback is `#[cfg(test)]`, so a release build is reached by none of it.

- `config.ini` — `settings_io::AppConfig::folder` → `test_folder` / `HELD_FOLDER`; the guard a test holds is `ConfigFolderOfItsOwn` (re-exported `config::config::ConfigFolderOfItsOwn` for the preview window's own tests).
- Engine state records — `app::engine_processes::state_folder` / `run_file`; a test that asserts a file's *absence* stands a folder in on its own thread (`StateFolderOfItsOwn`), because `RHP_ENGINE_STATE` names one folder for every thread and a test recording a player beside it would otherwise write the very file being asserted about.
- Browser profiles — `webview_preview::environment::profile_root` / `user_data_folder`.

Why this is not tidiness. The machine's own `config.ini` is the one file a run of the app reads every second and writes back what it took, so a test that read or wrote it changed what that run had: a whole default configuration was put over it while the app stood, and a hover delay of `137` a test left behind was taken up by the watcher and written back, so the one setting a hand had left clear held a number no menu offers. The engine records and the profile root are reaped and swept by the next start of the app, so a test writing there either has what it wrote taken away by a run that is not testing, or reads another run's records as its own.

`ConfigFolderOfItsOwn` is a guard rather than a variable because the file is one file: it takes a turn (`FILE_TURN`) _before_ it makes the folder — a test whose guard went away while another still had the app pointed at its folder would clear it out from under it — points the app at that folder for as long as it lives, and takes the folder away, and whatever the app wrote in it, when it drops. The turn is taken even where a test that panicked left it poisoned, so one panic does not take the tests after it down with it. Each guard makes one folder of its own rather than sharing one, so two tests running beside each other are not answered with each other's file. The two guards that used to reach the machine's file — a `CONFIG_FILE_TURN` mutex in `main` that the config module's and the card menu's tests queued on, and the card menu's own save-and-restore of the bytes it found — are gone with it, which is the point: a seam only holds while nothing reaches past it.
