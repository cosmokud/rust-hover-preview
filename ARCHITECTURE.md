# Architecture

## Overview

Windows 11 tray app. Watches Explorer's hover and focus state; renders a non-activating preview window near the cursor or focused item. Three parts over shared state and message passing: tray UI, Explorer hook, preview renderer.

## Runtime Topology

- **Main** — claims the single-instance mutex; initializes COM, config, DPI awareness; reaps engines and browsers a killed run left behind (Started Processes); starts the threads below; runs the tray event loop. Temp clearing runs on its own thread beside the others, not ahead of the tray. The two process-ending sweeps stay before the hook. `RHP_STARTUP_TRACE` writes each start step to `%TEMP%\rhp-startup-trace.log`.
- **Preview** — owns the layered window and all decoding/rendering. Idles on its own channel, not a tick; the wait interval is a ceiling on how long a window message (resume, display change) goes unnoticed. While a preview is up it keeps a 60 s tick servicing animation frames, the streaming overlay and the pointer region.
- **Explorer hook** — polls Explorer via UI Automation and Shell COM. `EnumWindows` with CabinetWClass/ExplorerWClass matching counts Explorer browser windows, how many show, and how many the front window's region leaves reachable, so a maximized window on one display is not read as hiding an Explorer window on another. Not joined at exit: every probe crosses into Explorer and a hung shell holds one indefinitely, as with the Office engine thread. Dies with the process.
- **Wheel watcher** — `WH_MOUSE_LL` hook publishing a wheel-tick counter the hook consumes to refresh the hovered item.
- **Config watcher** — reloads `config.ini` on change.
- **Update check** — spawned by start and by opening the tray menu; ends with its answer.
- **Office engine** — spawned by the first render request; ends once every family it holds is idle. The one apartment-threaded, pumped thread: OLE automation marshals calls back to the calling thread, so a thread that does not pump deadlocks. Nothing waits on it.

## Single Instance

One per user session. `main` claims `Local\rust-hover-preview-single-instance` as its first step, before DPI awareness, COM, config and any thread. A second launch finds the name taken, closes its handle, returns without tray icon, hook or window. The handle is held for the process lifetime, so a crash or kill still releases the name. `Local\` scopes the guard to the signed-in session.

## Update Checks

Asked by app start and by tray menu build, each on its own thread. The row above **Run at Startup** reports the last answer, so a menu-found update is offered on the *next* opening. Nothing is checked on a tick. Rate-limited to one request per hour however often asked; the hour counts however the check ended (found, nothing, GitHub unreachable). The hour is run memory only — no file records a check, so every run makes one at start.

Fetches one file: `version.txt` at `releases/latest/download`. The installer is fetched only from the release that version names (by tag and packager filename `rust-hover-preview_<version>_x64-setup.exe`) and only on click. A pre-workflow release answers `404`, read as nothing to offer. HTTPS via WinHTTP (system cert store, configured proxy, `WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY`) — no HTTP client or certificate list is compiled in. Offerable when the version is newer than running; a pre-release build reads as older than the stable release its own version names.

On click a dialog asks first: **`Auto`** (fetch, run, restart), **`Manual`** (open the release page, fetch nothing), **`Cancel`**. A message box with `Yes`→`Auto` and `No`→`Manual` renamed at creation by a `WH_CBT` hook on the asking thread for the life of that dialog. On `Auto` the installer is fetched into the app's own temp folder and checked against the promised length plus the two `MZ` bytes every Windows executable opens with; a failure is deleted and the click told so. A pass runs silently (`/S`) with `/R` to relaunch, and the app ends itself as it hands over. No signature is claimed.

What earlier versions left under `%LOCALAPPDATA%\rust-hover-preview\update` is removed at start, and the folder with it once empty.

## Source Layout

- `src/main.rs` — entry point, the two globals every thread reads, `RUNNING` and `CONFIG`.
- `src/app/` — `single_instance`, `startup`, `updates`, `engine_processes`, `afk`.
- `src/config/` — `config` (settings, defaults, sanitization), `theme_files`.
- `src/shell/` — `explorer_hook`, `wheel_input`, `key_input`, `cloud_files`, `pin_navigation`, `tray`.
- `src/ui/` — `preview_window`.
- `src/formats/` — `routing` (the one order every side asks a file's kind in: hook, loader, layout; plus the reader chain per kind), `native_formats` (which in-app reader takes a kind), `content_type`, `codecs`, and thirteen per-kind gates: `image_formats`, `video_formats`, `text_formats`, `archive_formats`, `office_formats`, `design_formats`, `vector_formats`, `font_formats`, `ebook_formats`, `libre_formats`, `magick_formats`, `peazip_formats`, `calibre_formats`.
- `src/readers/` — `wic_image`, `dds_image`, `bcn`, `webp_image`, `jxl_image`, `heif_sequence`, `tone_map`, `psd_image`, `project_image`, `eps_image`, `metafile_image`, `pdf_preview`, `comic_preview`, `svg_preview`, `font_preview`, `archive_listing`, `office_preview`, `audio_track`, `video_player`.
- `src/engines/` — `office_render`, `libreoffice_render`, `imagemagick_render`, `peazip_render`, `calibre_render`, `webview_preview`, plus `document_cache` (the pages those renderers draw, kept as files under the temp folder, keyed by the engine that drew each).
- `src/text/` — `text_preview`, `text_paint`, `text_theme`, `archive_preview`, `audio_preview`, `pin_chrome` (pinned caption and round bubble).

Module names are unchanged, only the path in front of them: `crate::text::text_preview`, `crate::engines::office_render`.

## Core Modules

- `main.rs`: single-instance guard, startup, COM lifecycle, DPI awareness, thread orchestration.
- `single_instance.rs`: the named-mutex guard.
- `engine_processes.rs`: every process started whose lifetime the app does not own. Each goes in a job object so whatever ends the app ends it; all but the probes and the image converter are also written to a run's own state file so the next run answers for it. See Started Processes.
- `explorer_hook.rs`: resolves hovered/focused Explorer items, normalizes paths, sends preview messages, and remembers what order each folder's view was last seen in (`note_view_sort`, `view_sort_of`, `ViewSort`/`SortKey`).
- `cloud_files.rs`: whether a file's content is on this machine, so a preview never starts a syncing provider's download.
- `pin_navigation.rs`: the list a pinned window's own **Previous**/**Next** buttons step through — a folder's files, filtered to what this build could preview, in the order the listing was showing them (see Pin Mode).
- `content_type.rs`: what a file's bytes say it is, where that differs from its name. No engine is ever handed content it cannot draw. Three tables. **1 — `infer`**: common formats by agreed signatures, no dependencies. **2 — this app's own**, in the shapes the rest of the app asks signatures in (`container_kind`, `has_mpegts_packets`): FFmpeg's transports and raw streams by start code/codec header; containers no file manager names (ISO base media family onward, games', cameras', recorders'); documents the render engine imports by nineties-era magic; pictures read for themselves (`.dds`, `.qoi`, `.exr`, `.pcx`, metafile) and those the image converter develops (`.xcf`, `.miff`); formats FFmpeg scores by shape rather than magic. The one box answered for is a package declaring its own type in the head (OpenDocument, StarOffice XML, Krita project) — the document's answer, not the box's. **3 — the name the file carries**, for a container silent inside the probe, a format whose signature is its own text, a name no FFmpeg demuxer reads; a name that is two formats is asked about its bytes first (`.pdb` is the Palm OS ebook, not the Microsoft program database). Left to the name deliberately on both sides: **a box is not a kind** — a zip (iWork and Office packages arrive in one) and the OLE compound file behind every `.doc`/`.xls`/`.ppt`; a format whose signature is its own text or whose marker sits past the probe (`.tga` footer, `.flm` trailer). A camera raw is the other edge: `.nef`, `.cr2`, `.arw`, `.dng`, `.pef` are TIFFs, so the bytes name the container and the camera's name settles it. Read cost is the front of the file, one 4 KB probe; a cloud file is not opened; an unpreviewed format starts no engine. Hook, loader, layout and every engine tier's pre-flight questions classify by it.
- `wheel_input.rs`: wheel hook thread publishing a tick counter.
- `key_input.rs`: keyboard watcher and key-name spelling. A low-level hook on a thread that only pumps its messages, publishing a press counter the preview loop drains once a tick; also what the pin key is watched by — a press, not a state; never swallowed (`Space` is Explorer's own). Watches a virtual-key number rather than a setting (`refresh`; a hook procedure may not take a lock); names (`alt`, `f8`, a letter) resolve through `key_to_vk`.
- `preview_window.rs`: layered window rendering, scale-aware sizing, GIF/WebP animation streaming, video previews (FFmpeg `ffplay` with verified-PID supervision where installed, media engine drawn by this window where not), monitor-bounded placement with paint-before-show, the pinned window, display-change and WM_POWERBROADCAST handling.
- `pdf_preview.rs`: first-page PDF via `Windows.Data.Pdf`; page size cached per file, nothing drawn held; file header confirmed before a path reaches the OS renderer.
- `image_formats.rs`: image gate — built-in list written to `config.ini` and read back, plus normalization. Nothing probed; the decoder has the last word. `svg`/`svgz` were entries here and are vector-list entries now (what draws them is the browser engine); files the app wrote before that are brought over (`config::configured_list_over_history`).
- `svg_preview.rs`: SVG, for two questions only — is this a document, and what size does it ask to be drawn at. Root `width`/`height`, `viewBox` answering relative-or-missing, 300x150 the browser assumes for a replaced element when neither is named; `.svgz` inflated on this side; unparseable file gets no preview. Measurements held between hovers by file and version; the drawing is `webview_preview`'s.
- `metafile_image.rs`: `.wmf`/`.emf` read as records handed to `PlayEnhMetaFile` — the placeable header, conversion of old-style into enhanced form, the DIB surface played into, and the two plays (black page, white page) that recover coverage. Nothing rasterized; a preview is the drawing replayed at the size shown.
- `eps_image.rs`: the preview an encapsulated PostScript carries of itself — no PostScript is parsed, evaluated or run. Two shapes: the Windows container whose header names its metafile and TIFF previews, and the Mac comment block between `%BeginPreview` and `%EndPreview`. A drawing goes to `metafile_image`, a picture to the common decoder; a program with neither shows nothing. One picture shape is read here because the decoder refuses it whole: a colour table with an alpha sample beside its index, read by walking the picture's directory for table, strips and alpha.
- `vector_formats.rs`: vector gate — built-in list plus normalization. The kind holds both browser-drawn documents and replayed drawings, so callers must ask the document half first; a hover reaching the drawing half with a document shows nothing.
- `font_formats.rs`: font gate — built-in list plus normalization. Nothing probed; the reader has the last word.
- `font_preview.rs`: fonts, for three questions before a specimen is drawn — is this a describable font, which lines its `cmap` covers, and what file the browser is pointed at. Reads `cmap` and `name` from whichever container it is (sfnt, one face of a collection, WOFF per-table zlib, WOFF2's single Brotli stream) under the global read budget; answers held per file version and per face. A line is drawn only where the font covers every character. A collection is answered with the face `ttc_face` names, written out as a font of its own.
- `wic_image.rs`: formats with no in-app decoder — HEIF (`.heic`, `.heif`), AVIF, JPEG XL, still WebP, `.dds` — read by the machine's codec. One imaging factory per decoding thread; the decoder is asked for a file, not a format; the layout's box is handed over, so the codec's scaling transform (or WIC's scaler) plus its format converter produce the BGRA a frame is composed in. Missing codec or undecodable file = no preview; the packages are named in the README. Nothing probed, nothing held. A `.dds` is the one format here also decoded in-app, and the codec is still asked first (BC1/2/3, at the preview's box rather than the file's texels); the rest go to `dds_image`.
- `dds_image.rs`: DDS formats the Windows codec refuses — every uncompressed one (classic and `DX10` headers alike) and every block format from BC4 up. Header for shape and format; one mip level of the first face, the level nearest the drawn size; blocks turned into BGRA and resampled there, since a block decodes to a 4x4 square. Format names read as written: four-character code, `D3DFMT` number, or DXGI format. BC1/2/3 are left to the codec; BC4-7 are `bcn`'s. Both BC6H variants read, the signed one drawn as light; likewise packed HDR and depth buffers.
- `design_formats.rs`: design gate — built-in list plus normalization. `ai` is in it although Illustrator documents are usually PDFs: the PDF gate is asked first and claims every one saved with PDF compatibility, so this list catches the PostScript ones read by `eps_image`.
- `bcn.rs`: block formats as functions over a 4x4 block (16 bytes, self-contained) — BC1/2/3 with the alpha their later variants carry, BC4/BC5 for one- and two-channel data, BC6H for light in both variants, BC7's eight modes. Verified block-for-block against the machine's decoder and two independent ones.
- `tone_map.rs`: the curve bringing light-valued samples (EXR, Radiance HDR, float textures) into eight bits, as `hdr_tone_map` and `hdr_exposure` name it: exposure in stops, a curve, the transfer. The only place those files pass through.
- `webview_preview.rs`: the WebView2 browser that draws every SVG and every font specimen, held warm on its own thread and window (a layered window has no child tree, as with the video path where the player's window is the preview). Hands over one *want*, not a queue: newest file wins, each want carries its generation, a superseded want is dropped without navigating or showing. Navigation bounded (`NAVIGATION_TIMEOUT`): the hover answered with nothing and the engine let go, browser and all. A landing names the file it was drawn for, so a page for an abandoned hover ends nothing (`showing_path`). The page is this app's own per file and backdrop: document as an image filling the box, font via `@font-face`. One engine per app, released after `webview_idle` (10 min) where `Persistent`, by the AFK timer otherwise, or as soon as both kinds it draws are off. Settings: script off, nothing fetched (resolver answers for no host), no context menus, devtools, accelerator keys or zoom. Profile folder under the local profile, also where a collection's extracted face is written. The browser process is adopted like an Office engine.
- `codecs.rs`: what this machine has — FFmpeg's player installed, media stack up, registered video/audio decoders, codec extensions claiming a picture format, applications and runtimes answering for a document/specimen/page. Starts nothing: an Office engine is asked by ProgID, a decoder by enumerating registrations. Callers: the tray's `Codecs` submenu (whole list, once per menu build) and the video path (one question per hover, the one cached answer). Engine tiers ask a third thing — whether LibreOffice, ImageMagick, PeaZip or WebView2 is installed at all, asked once when wanted, never started to find out.
- `video_player.rs`: the Windows media engine for the two kinds it plays — a video on a machine without FFmpeg, and a sound wherever its decoders reach the format. Frame-server mode with a video-made bitmap; the same object plays a sound, costing an engine with no surface plus two numbers (position, duration) the card's clock is drawn from. Who scales a frame depends on the size it is drawn at: at or below the picture's own size the engine is asked for the box and scales into it, and above it — `video_scale` past 100%, a pinned window dragged or maximized past the file's own size — the frame is asked for at the picture's size and resampled here (`scale_rows`, bilinear and separable, fused with the copy), because the engine's filter is not a question this app can ask it. A pinned window dragged across that size is where the scaling is handed over or taken back, and the one case that pays for a second surface. Also where "can this machine play this file" is answered for a sound (source reader asked for decoded PCM) and the length comes from. Seeking is deferred: the engine only takes it after reading the header, so the session keeps the request and makes it on the first ready tick (`apply_seek`). The file arrives as a stream over the Shell's verbatim path with the *plain* form as the name the source resolves by — a media source resolves by the name it is handed and a verbatim path is not a URL (`plain_name`).
- `video_formats.rs`: video gate with two built-in lists in `config.ini` and the MPEG-TS sync-byte probe settling the `.ts`/`.mts` the text lists share. `[video]` is what the Windows engine is asked to play, `[ffmpeg]` is what only FFmpeg reaches; they partition the one list they were, so an older `config.ini` is divided as it is read (`VIDEO_EXTENSIONS_BEFORE_THE_SPLIT`, `config::repair_older_lists`) without touching a user-edited list. The two decide which engine is asked first, never which one plays — the file's own answer is last word. Everything but the engine asks them together (router, layout, five engine gates).
- `audio_formats.rs`: sound gate with the `[audio]` list, plus the one verdict a list cannot give: containers a video's name carries (`.mp4`, `.mka`, `.ogg`) whose streams hold a sound and no picture, remembered per file and version (`remember_audio_only`) so the router answers them as the sound they are.
- `audio_track.rs`: what a sound is and which engine plays it — codec, rate, channels, bitrate, length — plus whether this machine plays it, held per file and version as one of three: not asked, a track, or nothing playable. Playback position is deliberately absent (the player's own).
- `audio_seek.rs`: where a sound starts. Everything but the memory is arithmetic on the probed length; the memory — last position per file, one line a file under `%TEMP%\rust-hover-preview\audio\seek.txt`, keyed by a hash of the path, LRU — is the only thing kept across runs, bounded by a 1 GB ceiling in code rather than in `config.ini` or the tray. Read on first use, written only while the tray is on the mode that reads it.
- `archive_formats.rs`: archive gate — built-in list, the dotted-tail rule making `tar.gz` a tarball, plus normalization.
- `archive_listing.rs`: reading an archive's table of contents — zip central directory, 7z header block, RAR header walk, tar 512-byte headers — into one entry list, with the entry cap, name cap, cancel flag and listing cache. Formats with no reader here are covered by an installed PeaZip's listing read into the same list by `engine_listing` (one field per line: path, size, packed size, is-folder, is-encrypted) under the same file key, so measure and render read one answer and a second hover is a cache read (`remember_engine_listing`). An encrypted table the engine will not list gets no listing rather than an empty one. `entry_bytes` reads one member for a comic plate.
- `archive_preview.rs`: listing into a page — implied tree, single-child collapse, sort, capped rows, the password mark, the summary line, painted through the text layer.
- `audio_preview.rs`: the sound card — bullet, name, probed facts, hairline, bar, and the player's clock, all painted by the text layer and themed. `measure` gives the box, `render` fills it, a clock repaint is a re-layout of the same page. Unknown length draws a block crossing the bar. An overlong name is drawn whole, clipped to the card, and scrolled under it by a preview-loop state (`NameScroll`).
- `office_formats.rs`: Office gate — built-in list, normalization, the container probe (OOXML package vs OLE compound file from the header), the engine per family, which engine a document is asked of (`page_engine`, `app_installed`), the waiting box (`default_page_size`), and `engine_page_kind`.
- `office_preview.rs`: measuring and drawing the page an Office document is previewed from — the render tier's page, or the render engine's where that engine is the one that draws it. How large the source may be drawn (`source_kind`) and the frame it is drawn into. Nothing held in memory; only the size is read once.
- `office_render.rs`: the render tier — the apartment-threaded engine thread and its recovery, the engine per family, late-bound automation exporting page 1 and taking a workbook's picture (decoded and re-encoded as a PNG) where no page can be exported, temp-copy hygiene for zone identifiers and long paths, the scratch file, the page cache, `hover_ended`, `excel_calculation_probe`, `page_is_workbook_picture`, and the diagnostic test driving one document of each family when one refuses.
- `libre_formats.rs`: gate for what an installed render engine draws — CorelDRAW above all — holding the `[libre]` list plus normalization. Deliberately narrower than the engine's reach: no name another kind already reads, no human-readable text document, none of the imports holding nothing to preview (palettes, extension packages, a theme, a web query). Membership settled by the engine's own filter registry, not advertised support: a name is in only where an import filter declares that exact extension. `swf` failed worst (its filters spin rather than fail); an earlier list held 24 more failures (PageMaker <6, older QuarkXPress, Visio stencils/templates, EPUB, a dozen no filter declares), each a launch answering nothing; the shipped list is kept beside the built-in one to strip them from existing files. An Office document the engine is the one that draws (own app not installed, or `Engine → Select Engine → Office`) is answered by `engine_page_kind` without consulting the list.
- `libreoffice_render.rs`: the engine those documents are drawn by. Conversion through the engine's own import filters (Document Liberation Project libraries) into a PDF under the app folder named for the document and version; the PDF path draws page 1. Conversion on its own thread: hover asks, waits as the spinner, replays when the page lands. One conversion at a time (one profile, one seat), queue keeps the newest. Process adopted into the job and recorded. A conversion outlasting any document is an engine that stopped answering: ended by name and id from both sides (the engine thread gives up; a document asked meanwhile ends that same process rather than queueing). Refusals remembered so a wrong list entry costs one launch. Pages bounded by `document_cache_mb`, LRU. Under `LibreOffice TTL` the engine is kept: started headless with a document of this app's own open (which is what makes an instance take the next conversion rather than a second instance starting beside it), released engine and launcher together on idle expiry or a conversion outrunning its bound. `warm` pre-launches. Nothing bundled, nothing linked.
- `magick_formats.rs`: gate for pictures the image converter develops — camera raws above all — holding the `[magick]` list plus normalization. Narrower than the engine's reach, settled from `magick -list format` one name at a time. Left out and named in the module: headless raw sample dumps (`rgb`, `rgba`, `gray`, …), Ghostscript/DjVu-dependent documents (`.ps`, `.xps`, `.djvu`), engine pseudo-formats (`xc`, `canvas`, `label`), names another list claimed (`sti`, `cin`), and `xwd` (coder module the Windows installers leave out). `is_engine_picture` is asked before the engine starts — bytes first, name after.
- `imagemagick_render.rs`: the engine those pictures are developed by. A raw is a sensor reading, so the file goes over and a PNG comes back: auto-oriented, resized to the box, eight bits per channel, metadata dropped, first picture of a multi-picture file kept (`.fits`, multi-page `.dcx`, `.mng`). **What the engine writes is read as it is written**: it goes to the engine's stdout on a thread of its own (a picture larger than the pipe would otherwise block on a write nobody reads) and comes back decoded into the hover's frame and written down as a page. Conversion on its own thread, one at a time, newest queued. Started `CREATE_NO_WINDOW` and adopted into the job rather than recorded, since a conversion lives a second. A run outrunning any bound is ended where it stands and the file remembered as undrawable. Nothing bundled, nothing linked. Per run it holds the picture, each file's developed size, and refusals; between hovers the frame sits in the image cache and the page under `image_disk_cache_mb`. No TTL. A cached frame costs no engine; a given-up frame is a page read or a fresh develop.
- `peazip_formats.rs`: gate for archives the listing engine reads — cabinets, isos, disk images, installers, Linux packages, single-stream compressors — holding the `[peazip]` list plus normalization. Built from what the installation's tools can be asked about. The console archiver's own table settled most of it: a name is in only where that table declares a *format* for it, so codecs with no format and no executable beside them (`lz4`, `lz5`, `lizard`, `flzma2`) are out. Names the sibling backends read are in for the opposite reason (the archiver refuses `arc`, `zpaq`, `br`; FreeArc's archiver, zpaq and `brotli.exe` read them). `Backend::of` routes a name to its tool; `has_a_listing` says which tools print nothing. Left out and named in the module: programs listed as resources (`exe`, `dll`, `sys`, `obj`, `elf`, `macho`), names another list claimed (`7z`, `zip`, `rar`, `tar`, `zipx`, `pmd`, `swf`, `flv`, `doc`, `xls`, `ppt`), and words rather than formats (`img`, `ext`, `fat`, `mbr`, `gpt`). `gz` is claimed twice and the archive list wins the dotted `tar.gz`. `is_engine_archive` is asked before the engine starts — bytes first, name after.
- `peazip_render.rs`: the listing engine's tools, never `peazip.exe` (a windowed frontend whose `-ext2list` *shows* a listing). The tool is chosen by the file's name: the console archiver at `res\bin\7z` for most, FreeArc's archiver, zpaq, Zstandard's tool for what that one cannot open, nothing for the three single-stream names with no listing. Each report has its own parser (`engine_listing`, `arc_listing`, `zpaq_listing`, `zstd_listing`) and produces the same `Listing` — same page, cache and key. `.br`, `.bcm`, `.lpaq8` are answered without a launch, showing the single member an extraction would write, derived from the file's own name. Runs on its own thread, one at a time, newest queued; adopted into the job, `CREATE_NO_WINDOW`, input closed so an encrypted table cannot leave the tool asking for a password. A run outrunning its give-up is ended and the file remembered as unlistable. No TTL: the second hover is a listing-cache lookup.
- `project_image.rs`: the picture a project container holds of the whole document — `mergedimage.png`, OpenRaster's `Thumbnails/`, Procreate's `QuickLook/Thumbnail.png`, CorelDRAW's newer `metadata/thumbnails/` and `previews/` — asked in order of worth, not container order, so a file holding both document and thumbnail previews from the document. Nothing unpacked to disk: a member is inflated into memory under `decode_budget_gb`, decoded and resampled into the planned box, its size read from the member header and held per file version. Names compared case-insensitively.
- `psd_image.rs`: the merged picture at the end of a Photoshop document, read past the layers — colour mode, image resources and layer/mask sections each stepped over by declared length, then the planar picture decoded into the planned box. Each channel reduced on the way past, one row at a time, so a hover holds the preview plus a row of source whatever the document size, and a document smaller than its box can be enlarged. All four compressions read; 16- and 32-bit depths and every answered colour mode brought into screen values. Lab, multichannel and a document saved without `Maximize Compatibility` (no merged picture) get no preview.
- `text_formats.rs`: text gate — built-in extension and file-name lists, the dot-file rule making `gitignore` mean `.gitignore`, plus normalization. Also holds `is_text_file`, which checks `text_preview_enabled` ahead of both lists.
- `text_preview.rs`: reading and decoding a text file, styling a window of it on demand (`styled_window`), laying it out and painting it (with a scrollbar when longer) into the same BGRA frame an image arrives in. Keeps the decoded document and styled windows, never a painted frame.
- `text_paint.rs`: the painting both painted previews share — top-down 32-bit DIB surface, font metrics and fonts grown from them, colour helpers the themes are read through, and `paint_run`, the one function placing a run of text, drawn from an origin its box need not share so the one scrolling run can be clipped by the box it moves under.
- `text_theme.rs`: the two bundled TextMate themes and the user's `.tmTheme` files, each parsed once and kept; scope lookups; the fallback keeping a broken file from taking the preview with it; the reading counter telling a cached document which version of a file it was coloured against.
- `pin_chrome.rs`: chrome a pinned preview wears — the caption above the media (theme-coloured bar, ellipsised name, six glyphs drawn as strokes: the pin's own previous, next and hand-off packed to the left of the window's minimize, maximize/restore and close, the three new ones dropped whole where the caption is too narrow to carry them — one row of one size, every mark centred in its own button and no mark taller than the glyph square it was asked for, which is why the walk arrows part half a span and the hand-off box is drawn full height about its own centre), the transport bar below (button, track with played part, two clocks, and the volume button, whose speaker is the same kind of stroke drawing), and the round bubble a collapsed pin becomes (circle with the pin's picture or a mark, plus a soft shadow). The volume popup is the one piece of chrome that is not a strip: a rounded panel with a groove and a knob, written straight into the window's own surface because what it floats over is the media. Writes premultiplied pixels into a surface the window copies onto its own; GDI knows no alpha, so a caption closes by handing every pixel its coverage back.
- `theme_files.rs`: the `theme` folder beside `config.ini` — which files are themes, the names they are listed and written under, the path a name resolves to.
- `tray.rs`: tray icon and menu, configuration toggles, exit flow, re-adding the icon on `WM_POWERBROADCAST`/DWM-Explorer restart, and the `TaskbarCreated` broadcast that signals the Explorer restart the hook is told about.
- `config.rs`: INI-backed configuration with defaults and input sanitization.
- `startup.rs`: registry integration for the run-at-startup setting (`sync_startup_setting`).
- `updates.rs`: the only network question in the app.

## Media Pipeline

- What a file is, is asked of its content before its name. `routing` is the table hook, loader and layout all ask, and `native_formats` says which in-app reader takes a kind — so a name two lists hold is one kind everywhere.
- Images (static, GIF, WebP) decode in the preview thread; animated formats stream into a shared queue. Still-vs-animated is answered from the head of the file without decoding (`head`): GIF frame blocks, WebP `ANIM`, PNG `acTL`, the `ftyp` brand list of an ISO base media file, and — the one that cannot be read from a byte pattern — the image header of a JPEG XL codestream, asked of a decoder. A one-frame GIF is drawn by the still path. Formats with no in-app decoder go to the Windows codec at the planned box. `.dds` is the one such format with an in-app decoder behind the codec's.
- A picture whose samples are light (`.exr`, Radiance `.hdr`, float texture) is tone mapped into eight bits first, with `hdr_tone_map` and `hdr_exposure`.
- A decoded still is kept between hovers keyed by file, version and pixel size decoded at, LRU-dropped to fit `image_cache_mb`.
- An animated preview opens on its first frames, not a startup buffer; the decoder then runs ahead of playback.
- An animation is held whole where it fits the per-animation decode budget; what does not fit plays through a sliding window, frames behind the playhead returned and the decoder restarting the file. Both sides settle under the one lock the frames are shared through, so a release and the end of a decode cannot pass each other.
- A frame's own delay is the playhead's unit: a frame held a second or more is waiting, not drift; only lateness past that delay is snapped forward.
- The window uses GDI and `UpdateLayeredWindow` on a topmost no-activate surface. A frame opaque everywhere is *copied* rather than composited (the blend is the identity in every backdrop kind). Opacity is asked where pixels are made (off the drawing thread, once per frame); a frame whose producer has not asked keeps the blend. The corner spinner is drawn into the box it sits in, so an overlay repaint touches kilobytes rather than thirty megabytes every 80 ms.
- Video is played by the Windows media engine wherever it can decode the file and by FFmpeg's `ffplay` where it cannot — two engines, one preview, decided once per file by which list the name is in and by the engine's own answer. FFmpeg is the fallback because a player window cannot be resized, seeked or paused, while the engine's frames are drawn by the app. The FFmpeg path launches `ffplay` and runs `ffprobe` geometry and an `ffmpeg` cropdetect pass at once, each with a deadline, and the hover waits for the slower. The media engine's path measures with a source reader, draws the frames in this app's window, and scales them itself wherever the preview is larger than the file's own picture (see `video_player.rs`).
- A hover's box is measured off the preview thread wherever measuring is a felt read — a PDF page opened, an archive's TOC walked, a document/specimen parsed, a comic's first plate read — and the hover is laid out as the spinner and replayed when the answer lands, like a video's geometry probe. What is measured is held by file, version and what it was measured against (a listing's page is wrapped to the room it is drawn in). "This reader has nothing for this file" is held the same way and is the one answer a wait comes down on rather than being replayed (`measured_off_the_tick`). A read that came apart is answered as that same "nothing", sent through `catch_unwind`: a thread unwinding past the notify would leave the file on the list of reads running, and every later hover of it a spinner nothing ends.
- PDF previews render page 1 through `Windows.Data.Pdf`.
- SVG is measured in-process and drawn by the browser engine in a window of its own.
- Fonts are described in-process and drawn by the same engine under those lines.
- Text is read, decoded, highlighted and painted in-process.
- Archives read their own table of contents and paint a page from it. An archive no reader has is listed by an installed PeaZip into the same listing and drawn as the same page.
- Office documents are previewed from the page the render tier produced, or from the page the render engine drew.
- A picture the image converter develops is previewed from the PNG it wrote, under the `Magick` kind, decoded and composited like any picture, and written down as a page under `Cache → Image (Disk)`.
- A book nothing here opens is converted by an installed Calibre into a PDF and previewed as the first page that says anything, under the `Calibre` kind.
- A comic is previewed from its first plate, read out of the container by this app and drawn as a page of the `Ebook` kind; no engine, nothing unpacked to disk.
- A sound is previewed as a card of the file's facts with the sound behind it, the card painted by the text layer, playback by the Windows engine where its decoders reach the format and `ffplay -nodisp` where they do not. Which engine, and whether one plays it at all, is an off-thread probe; the same probe answers what an `.mp4`/`.mka` holding only a sound is. Start position is `Volume → Audio Seek`, read as a player starts. End of file is 0:00 under both engines: the engine is asked to loop, the player — whose loop returns to the second it was started at — is given no loop and restarted at the beginning. A hover costs the card's layout and, once playing, a clock repaint 4x/second (30x/second while a name scrolls).

## What A Hover Is Allowed To Read

Bounds sit at the two places a read can start: the hook's resolution gate and the loader. Both ask the same questions, so a file one refuses cannot be reached through the other. The ceiling on any read is one number — `decode_budget_gb` (1 GB default, tray `Performance → Decode Budget`) — handed to every reader before it allocates.

**Cloud placeholders.** A file whose content is not on this machine is refused before anything opens it. `cloud_files.rs` asks the file's _attributes_ — a directory-entry question that, unlike opening, does not start the download. The entry is the one the gate already read (present, a file, version, content-here), taken once and handed to every question after.

**Kind probe.** One probe at the hook's gate, shared with loader and layout, so one hover pays once. Reads the first sixteen bytes and extends to the full 4 KB only when that settles nothing. The answer is held as the facts themselves (`head`), not as one question's answer, so kind and reader come out of one read. A cloud file is not opened at all. A path reaches an engine only when its content belongs there.

**Images** are bounded by what decoding may ask for, not by shape. The header is read first, but for the box the frame decodes into, and the budget is handed over before anything is allocated, so a 7000x10000 illustration decodes at its own size while a file asking for more than a preview could justify gets none. `catch_unwind` turns a decoder error into a missing preview, while a huge allocation is an abort that takes the tray icon with it — so every reader gets the budget first, the decoders through `image`'s limits and the three canvas allocators (GIF, animated WebP, the Windows codec) through the same check. A header that will not report dimensions is not a refusal: decoded as always, simply not cached. A texture is bounded the same way and more narrowly: a `.dds` hover is a 148-byte header plus the first mip level of the first face, and a file claiming more than it holds is answered by a short read.

**Archives** are bounded by their table of contents, the only part a listing reads. Nothing is decompressed: a zip's central directory and a 7z's header are one read at the end, RAR's headers walk from the front, tar's are the 512-byte blocks between the data. A scan stops at 20,000 entries, cuts names past 300 characters, and every loop asks the same cancel flag. A `.tar.gz` must be inflated to be walked, so its stream is capped at 64 MB and past that the page says the listing stopped early.

**Office documents** are not read by this app at all. This side only asks the header whether the file is an OOXML package or an OLE compound file, from eight bytes, before handing a path to an engine. The engine's process is bounded on this side instead: a cloud document is never handed over (the engine's open would be the download); a zone identifier (Protected View) or an over-long path is rendered from a temp copy, which also keeps the engine from locking a file the user is working in; documents open read-only, without touching the recent-files list, hidden, and close unsaved; a page is asked for the moment a hover exists rather than after the pointer rests.

**UI Automation** is bounded by a client timeout set at creation, because every probe crosses into the shell's thread. The bound lives on the client, so the client must be `CUIAutomation8` (created, not the legacy `CUIAutomation`, which does not answer for `IUIAutomation2`). A client that cannot be bounded is still used, with the legacy object behind it: refusing the client leaves the resolver with no automation at all rather than a slower one. A probe that times out found nothing, which the rest of the hook already handles.

**SVG** is read whole only to measure, under the global budget including inflated size (which `.svgz` needs — sizes asked before allocation); what the drawing costs is the engine's, bounded by the rules the engine is given.

**Fonts** are read whole under the same budget, but only two tables parsed: `cmap` and `name`. Webfont containers inflate under the budget: a WOFF's tables are deflated one at a time, a WOFF2's single Brotli stream is decompressed only as far as the last table a specimen needs and only up to the same ceiling that stops a picture or an `.svgz`. A collection is the one file this app writes: one face — `ttc_face`, first by default — is copied out as a font of its own into the browser's profile folder, named for file, version and face, cleared at next start.

**HTML** is the one previewed file this app does not read, and the one place the budget does not reach. A page handed to the browser while `render_html` is on is read by the browser, not by this side: nothing is opened, measured or parsed here, so there is no read for `decode_budget_gb` to bound, and the browser's read of the file — of the page and of whatever it pulls beside it — is unbounded by it. That is deliberate, and it is the same bargain the SVG and font paths already make about what the drawing costs, taken one step further because a page is not a document this app can hold in memory in the first place. The other bounds still stand: a cloud placeholder is refused before anything opens the file, the frame may not navigate out of itself, and scripts, popups, forms and context menus are off. What is given up is a ceiling this app could not have enforced on a browser anyway; what is kept is that the file was a file the user pointed at.

## Image Previews

A still is decoded, resampled to the size the layout asked for, converted twice (RGBA then BGRA) and handed back rather than rebuilt on the next hover. A held frame is valid for file, version and pixel size decoded at: the version because an edited file is decoded again, the size because frames are stored decoded and scaled. A header that will not report dimensions cannot name that size, so such a file is decoded and simply not held.

The cache is bounded by bytes, not entries: `image_cache_mb` (64 MB default, cap 2048, `0` holds nothing), read from configuration on each use so an edit applies without a restart. The default is one full-screen frame at 4K (~33 MB BGRA at display size). A frame larger than the whole budget is not held at all rather than trimmed. The rest is trimmed on every use, LRU by counter rather than clock; trimming on use is what makes lowering the setting, `0` included, release what it no longer covers. The cache is consulted *before* the decode, so a hit never pays for a decoder.

## Tone Mapped Previews

A picture whose samples are light needs the transfer function saying how a light is written down and a curve bringing a wider range into the display's instead of clipping it. Measured, not assumed: the `image` crate's conversion is a bare clamp, so a linear 0.5 (188 as a level) was drawn as 128 and everything from 1.0 up as white; on files written as the format is, `[0.25, 0.5, 1.0, 4.0]` came out `[64, 128, 255, 255]` and now comes out `[124, 156, 188, 231]`.

`tone_map` is exposure in stops, a curve, then the sRGB transfer. `hdr_tone_map` is a setting: `reinhard` (default, `x / (1 + x)`), `aces` (filmic), `srgb` (transfer alone), `off` (bare clamp). `hdr_exposure` shifts before any curve; an unknown name takes the default. Applied at the one place both kinds pass through, before anything else: in `load_static_image` at the top before the resample (cheapest order — an 8-bit buffer is a quarter of the memory and resamples faster), and in `dds_image` sample by sample. Alpha is not curved (coverage is not light). A picture already holding levels is not touched.

## DDS Previews

A `.dds` holds S3TC blocks (BC1/2/3, called DXT1/3/5 by older files) or the formats joined to them (BC4/BC5, BC6H, BC7, uncompressed). Two readers, ordered by cost.

The Windows codec is asked first and reads less than the format: BC1/2/3 behind classic and `DX10` headers alike; every DXGI format from BC4 up and every uncompressed one refused as "image header unrecognized". What it gives in exchange, and the reason to ask, is the size — a texture handed to it at the planned box, so a 4000-square texture costs the preview rather than 64 MB of texels and a resample.

`dds_image` reads the rest. Uncompressed channels come out of the masks a classic header declares or the DXGI format a `DX10` header names; BC4-7 come from `bcn`. A block decodes to a 4x4 square, so the level is decoded whole and resampled after. Both BC6H variants are read. What neither reader has — the integer formats and the 64-bit-per-texel depth-stencil pair — gets no preview.

Data rather than colour: a `_SNORM` channel is a signed number either side of zero, six uncompressed (R8, R8G8, R8G8B8A8, R16, R16G16, R16G16B16A16) and two blocked (BC4/BC5, the unsigned blocks read the other way). What is drawn is the remap every tool draws: the sample's range stretched over the display's, negative dark, zero middle, positive light, no curve. A two-channel signed format's missing channel is drawn at the mid-range, not black. A four-channel signed format is drawn opaque, its fourth sample another signed number rather than coverage. A signed BC6H is light and goes through the curve like every other light. Packed HDR (`R11G11B10_FLOAT`, `R9G9B9E5_SHAREDEXP`) holds light, so it takes the curve. A depth buffer is read as its single channel and drawn as the colour format with the same packing is: `D16_UNORM` a level, `D32_FLOAT` light, `D24_UNORM_S8_UINT`'s low twenty-four bits a level; the stencil is left out and stencil-only views are not read at all.

All eight were settled against `image_dds` on random data at whole and ragged shapes; the signed codebook's arithmetic is that reference's, which is why it rounds where the unsigned codebook truncates.

A hover reads the header and one mip level of the first face and nothing after: a cubemap is six faces, a texture array however many slices the header declares, a preview shows the first. Which level is the one still at least as large as the box, so a 4000-texel texture at 800 wide uses a sixteenth of the blocks. A file declaring a chain it does not carry is read from its first level. The header is at most 148 bytes; the level's size is worked out from the header, checked against the budget and the file's own length. A file that is not a DDS, a format neither reader has, and a short read are one answer: no preview.

A `DX10` header can say what alpha is _for_; the one thing acted on is `DDS_ALPHA_MODE_OPAQUE`, drawn as any other opaque picture. A straight or premultiplied channel is composited as always; a file declaring nothing is drawn exactly as its texels have it.

Backdrop is a setting of its own — `dds_background` — not a picture's, so a `.dds` is a kind of its own under `MediaType`: a texture's alpha is very often a mask, a height, a roughness, or a channel a tool never filled.

## Codec Previews

Formats with no in-app decoder — HEIF (`.heic`, `.heif`), AVIF, JPEG XL, still WebP, `.dds` — are decoded by the codec Windows has. Nothing is bundled; the packages are named in the README, and a missing one simply means no preview. A missing `Codecs` row offers the page it is installed from and opens nothing by itself. Two exceptions: a still WebP the codec cannot read is decoded by libwebp (`webp_image`) where the codec is missing; and a `.dds` the codec cannot fully read falls to `dds_image` rather than to nothing. The DDS codec is Windows' own, so it is the one codec here not named in the README.

**This is a statement about stills, and it is now the only half of the three that is true.** A file that moves is not a still of a format the codec has, and the same codec cannot be the answer for it, which is why `head` asks a `.jxl` a decoder and an ISO base media file its brand list before this section is reached at all (see Media Pipeline). Two readers sit behind that, and they are not the same kind of thing:

- **An animated JPEG XL is decoded by a decoder compiled into the app** (`jxl_image`, `jxl-oxide`), and that is not a fallback — it is the whole of the answer, and the codec is still asked first for a *still* `.jxl`, which is a different question and still needs the Store package. The reason is the flag rather than the pixels: whether a `.jxl` is a sequence is not written anywhere a byte pattern can be read, since it sits in the codestream's own image header behind whatever container box the file carries in front of it, so a file whose name says nothing has to be opened before it can be said what it is. A JPEG XL is a sequence of frames in time — the format's own answer to a GIF, a WebP and an APNG alike — and a codec that reads one of them as a still has already thrown away half of what the file is. A frame's duration is in ticks and is converted through the file's own timebase, in 128 bits because `ticks * denominator * 1000` is about three orders of magnitude past what 64 bits carry.
- **An AVIF or HEIF image sequence is read by the media engine Windows has, as a decode engine and not as this app's video path** (`heif_sequence`): an `IMFSourceReader` on the file, pulled synchronously, each sample wrapped as BGRA and pushed into the same `Vec<ImageFrame>` queue a GIF feeds. The app's own video path — the media engine in frame-server mode, `MediaType::NativeVideo` — is deliberately not used, because a moving picture is a moving GIF in a fancier container and the whole point of the queue is that the drawing code does not know the difference. The engine was chosen because HEVC and AV1 have no decoder of their own in this graph, and libheif and libde265 were rejected for a reason that is about the tree rather than the formats: this app compiles zero C/C++. **It does not work, and this was measured rather than suspected.** Asked directly about an `avis` AVIF and an `msf1` HEIC, `MFCreateSourceReaderFromByteStream` refuses both with `0x80004005`; the same calls against an AV1 `.mp4` and an HEVC `.mp4` return frames at 100 ms and 33 ms on the same machine. So the codecs are installed and the engine demuxes both of them — what it has is no demuxer for the image-sequence brands, and no configuration of this app changes that. Every failure path returns `None` and none of them panic, and a `None` means the still path draws the first frame, which is what this app did before any of it existed. The reader stays wired in and is simply never given a file it can open, so a future container reader needs no routing change: it is one function returning what `heif_sequence` would have. A file with fewer than two frames is a still by the same argument and is drawn as one.

Both produce `Vec<ImageFrame>` through the same `StreamedFrames` queue a GIF, a WebP or an APNG feeds, which is what is meant by reused rather than duplicated: they get `animated_scale`, the sliding window, the opaque memcpy fast path and the pictures gate for free, and `MediaType` gained `AnimatedHeif` and `AnimatedJxl` beside `AnimatedGif`. Only the JPEG XL of the two is given a file it can open today, and the other is what a container reader would be wired into in its place. What a decoder here is not is a video: a file that starts moving is a picture that moves, not a video, and the gates and the scaling follow that rather than changing kind on the file.

The codec is asked for the planned box rather than the file's size — the reason this path exists instead of a compiled-in decoder: a phone's photograph is 40 MP and a preview a fraction of one, and a codec that scales as it decodes decodes the fraction. Where a codec cannot, WIC's scaler takes the size the rest of the way, and the format converter turns whatever came out (10-bit, wide-gamut, no alpha) into the 32-bit BGRA a frame is composed in, so the resample and the RGBA/BGRA conversions every other picture pays are not paid at all.

Bounded by the same number: the frame's own size is read before allocation and handed to `decode_budget_gb` in `u64` so a shape overflowing `u32` cannot wrap into a size that would pass. A missing codec, a file the codec will not open, and a frame that will not decode are one answer: no preview.

The picture is held in the image cache keyed by file, version and pixel size. What is not done is orientation: a phone photograph carries the rotation it is to be shown at, in its container or its EXIF and sometimes both, and this app applies one to no format yet.

## Design Previews

A layered design document is not composited — no blend mode, mask, clip, group or effect is implemented anywhere — and does not need to be: every one of these formats keeps a picture of the whole document inside itself, and the preview _is_ that picture, decoded into the planned box. Which reader is asked is settled by the file's header, not its extension — `psd_image`, `project_image`, `eps_image`, behind the `design_formats` gate. CorelDRAW is the exception: all this app can read by itself is the picture its program kept for a file browser, 96-256 px across, so `.cdr` lives in `[libre]` and an engine draws it.

A Photoshop document is its own merged image: the colour mode, image resources and layer/mask sections are each stepped over by declared length, and the planar picture after them is decoded straight into the preview's box, never at the document's size (a `.psb` allows 300,000 px a side). Each channel is reduced into the target as it streams past by a box filter averaging every source pixel into the pixel it belongs to, so a hover holds the preview plus a row of source whatever the document's size — which is what lets a document smaller than its box be enlarged. All four compressions are read: raw; PackBits (bounded so a count is never an allocation); and the two zipped forms, the predicted one unwinding each row's difference byte by byte at 8-bit, as whole samples at 16-bit, and at 32-bit through the gathered byte order the form writes a row in. Screen values: 8-bit as it is, 16-bit by its high byte, 32-bit by its clamp; RGB, CMYK (four inks read as the light they leave), grayscale, duotone (read as the gray it is built on), indexed (palette averaged, not the indices), bitmap. Each channel is averaged on its own, the same reading of straight alpha a PNG gets. Refused whole: Lab, multichannel, and a document saved without `Maximize Compatibility`.

A project container is a zip with the finished picture in it, so the preview is a member read: `mergedimage.png`, OpenRaster's `Thumbnails/`, Procreate's `QuickLook/Thumbnail.png`, and CorelDRAW's newer `metadata/thumbnails/` and `previews/`, in that order of worth rather than the container's — a CorelDRAW file whose drawing sits on a master page writes a blank-white page 1, and the thumbnail beside it is the drawing. `mergedimage.png` is the document at the size the work was made at; a thumbnail is a small picture enlarged, which is why the document is preferred whenever it is there. A member is inflated into memory under `decode_budget_gb` and decoded from there, nothing written to disk; its size is read from the member header and held per file version. Names are compared case-insensitively. CorelDRAW also writes an older shape, a RIFF container (versions 6-12, what most `.cdr` files in the wild are), read by `cdr_image`, where the picture is a chunk rather than a member.

An `.ai` needs no reader of its own: saved with `Create PDF Compatible File` it _is_ a PDF, drawn by the PDF path under `ebook_scale`, asked for the `%PDF-` signature the name `.ai` alone carries. What that leaves — a document saved as PostScript — is claimed by the design list and read by `eps_image`.

Everywhere else a design preview is a frame of this app's own: composed like a picture's, held in the image cache under file/version/size, composited over `design_background`. Its size is a share of the _display_ — `design_scale`, `fit` by default — separated from a picture's because a hover is given a document's own picture at whatever size it happens to be (`effective_preview_scale` answers `fit_reduced` as for a page or specimen). The gate is its own under `Preview Types` (`Design`); the list is `design_extensions`.

## Libre Previews

Documents with no in-app reader are drawn by an installed LibreOffice, whose import filters read CorelDRAW above all and the older office formats. Those names are the `[libre]` list — the other half of the `Document` kind under `Preview Types`, with `Document Scaling` and a `Cache → Document` budget shared by both engines' pages — and what comes back is a PDF drawn by the PDF path's first page. Read by this app alone a `.cdr` shows nothing rather than a thumbnail stretched to fill the screen. The Office kind leans the same way: a machine with no Office has its documents drawn by the engine and they stay Office documents, same gate, scale and backdrop.

Which of the two engines a document is asked of is one question with one answer, through `office_formats::page_engine`, reading the tray's `Engine → Select Engine → Office` choice and the machine together: the engine where the choice names it and it is installed, otherwise the application that owns the format (`app_installed` reads the family's ProgID — a registry read, the same test the render tier makes before driving one). The engine's page is a page like any other, measured from its own first page, laid out beside the cursor, drawn at the Office kind's share of the room and waited for in the spinner's box until it lands. A document whose content the engine reads is asked of the engine whatever its name says. A conversion is seconds, so it happens once per document and the page is kept as the same kind of page an export is, one conversion at a time, a refusal remembered two minutes.

The wait is the same one an Office document has: the page is measured as the spinner's own box and placed flush at the pointer, and the loop asks for the page the moment there is a hover. The conversion runs on the engine's thread, not the preview loop's: a launch held on that loop is a hover that never comes up, a tray that does not answer and a pointer that cannot leave the file. When the page lands the hover is replayed and measured from it; when the engine marks that it will not draw the document the spinner comes down. The wait is capped like an Office render's, and a page landing after its hover has gone is kept. The engine can be launched before the page is asked for (`warm`).

The engine is kept under `Engine → LibreOffice TTL` (released by the AFK timer where not `Persistent`): a launch is an application start, and an instance already running can be handed the next document instead — started headless with a document of this app's own open, which is what makes it take the work; started with `--accept` or `--invisible` and nothing to hold it answers nothing and is evicted. A `--convert-to` issued beside a running instance is drawn inside it and the asking process does nothing and exits. Measured 1.2 s cold against 0.2 s handed to a warm engine. A kept engine is waited for before the conversion is asked for and not after: a request issued while the instance is still opening its document starts a second engine beside it. What keeping it costs is the application — a few hundred MB with a document open — which the idle time bounds: the engine thread looks once a second, an instance idle past the time is ended engine and launcher together, and `0 seconds` keeps none, a launch per document. An instance let go of is one this app started; a LibreOffice the user has open is another instance entirely.

An engine that has stopped answering is what the give-up is for. A document a filter cannot read does not always fail: on a Flash file the filters spin at a core of 100% and never write a page, and a document still being drawn and an engine that has stopped drawing look the same from outside. A conversion past the bound is ended by name and id from whichever thread asks next: the seat and core come back, the conversion is remembered as one the engine will not draw, and the document behind it is drawn — what is ended is the engine, not the asking process, because a page handed to a kept engine is drawn inside it. That is why `swf` is not in `[libre]`: it is a video FFmpeg reads and the engine spins on.

## Magick Previews

The pictures nothing else on a Windows machine opens are developed by an installed ImageMagick. Those names are the `[magick]` list — the other half of the picture kind under `Preview Types`, with the `Images` gate and no engine TTL — and what comes back is a PNG drawn by this app like any picture. A raw is a sensor reading with a recipe for turning it into a picture, and a hover onto one was the case the app had nothing to say about. A raw is also the format whose orientation is always written and never applied by this app — `-auto-orient` is asked of the engine here, the one place in the preview path where a file's own rotation is applied.

The engine is asked for a picture at the room the display has — the largest box the file can be drawn in, since such a file cannot be measured until converted and that box is a ceiling on its size — so a 40 MP raw costs the preview rather than the sensor; eight bits per channel and dropped metadata are the engine's to give up. The first picture of a multi-picture file is kept, since a `.fits`, a multi-page `.dcx` and an animated `.mng` are several pictures in one file and a hover has one place to put one.

The list is not only the raws: every name the engine draws when forced is in, including second spellings of formats another list holds (`pict` beside `pct`, `sun` beside `ras`, `pcds` beside `pcd`, `dxt1`/`dxt5` beside `dds`) and formats no picture preview was ever asked for (a fax page, a slow-scan television frame, a console texture, an Amiga icon). Left out and named in the module: a font (the font kind's), pages needing an uninstalled Ghostscript or DjVuLibre, the engine's own notation, and names whose coder this build does not ship.

A raw sample dump is the one kind the engine cannot measure: the samples are the file and width/height/depth live wherever it was made, so forcing the engine answers `must specify image size`. A hover works the shape out arithmetically from the file's length and the weight of one pixel of the name: the proportions pictures are written in are tried in turn, commonest first, and the first dividing the pixel count exactly is the size, handed over as `-size` and `-depth` before the file is named. Two things are not knowable and are not guessed: a shape and its transpose are the same pixel count, so a portrait dump is read as the landscape shape; and a landscape photograph's worth of pixels is a square's from time to time (1920x1080 is also 1440x1440's worth), which the order of proportions settles toward the common shape. A length fitting none of them is a file with no preview, answered by the layout without starting anything.

A hover waits for one process as every engine-drawn preview does: the spinner in the box the picture will fill, placed at the pointer, replayed when the engine answers. The answer comes back through the preview channel rather than a watched folder, because the engine is a converter rather than an application: a message says the picture is in hand, or that the file is one the engine will not draw, remembered for the run so a wrong list entry costs one launch. A conversion that outruns a bound no readable picture reaches is ended where it stands and its file remembered as refused. An engine answering inside `spinner_delay_ms` clears the pending load with the answer rather than leaving a spinner armed over a picture already refused.

The engine's output goes to its stdout, so there is no scratch file and nothing for a bad run to leave — and the bytes are used twice: decoded into the frame the hover is drawn from, held in the image cache; and written down as a page under `%TEMP%\rust-hover-preview\image` bounded by `image_disk_cache_mb` (`Cache → Image (Disk)`). So a hover whose frame is cached is an ordinary cache hit — no engine, no decode, as fast as a JPEG. A hover the frame cannot answer is a page read, in three cases: the budget gave the frame up, the picture is larger than the whole frame budget, and the first hover after a restart.

Two limits: a page's name cannot carry the box the develop was asked for, so a picture developed into a room a smaller display had is served at that size until a develop overwrites it — a display or scale change costs one develop, not one per hover. And every reader of a page tolerates one that is not there, because a temp cleaner may take one between hovers: a page that cannot be read is given up and the file developed again.

The picture itself is the read the app has always done — decoded from the engine's bytes rather than the source, resampled into the planned box, cached under file/version/box, composited over `image_background` at the share `preview_scale` names. The switch over it is the picture switch; what a user who wants raws left alone edits is `[magick] extensions`.

Nothing is bundled or linked: the engine is the user's own installation, found in the versioned `ImageMagick-*` folders of both program directories, beside `config.ini`, or beside the app — and the older name is only ever taken from one of those folders, because a `convert.exe` on the `PATH` is Windows' own file system converter. There is no TTL: this one exits with the file. What a user wanting faster raws changes is `image_cache_mb` or `image_disk_cache_mb`; `0` in either keeps nothing between hovers.

## PeaZip Previews

A zip, 7z, rar, tar and `.tar.gz` are read from their own table of contents and produce the same page for all five. An arj, `lzh`, cab, iso, wim, vhd, `.deb`, `.rpm` and the single-stream `.gz`, `.bz2`, `.xz`, `.zst` have no reader here and a hover shows nothing. Those names are the `[peazip]` list, the other half of the `Archives` kind under `Preview Types`. A single-stream format is one member whose name need not be in the stream: a `.bz2` of `notes.txt` shows `notes.txt`, the name an extraction writes. A cab or iso shows nothing where a raw shows the thumbnail the camera left in it. A name the engine will not list is remembered — one launch, never another. Without PeaZip installed these names show nothing.

Nothing is bundled or linked: the tools are the user's own PeaZip, found where it installs and beside `config.ini`. Not `peazip.exe`, whose `-ext2list` has the windowed frontend *show* a listing. What runs is chosen by the file's name (`Backend::of`): the console archiver at `res\bin\7z` for most, FreeArc's archiver, zpaq, Zstandard's own tool for a `.zst` (which the archiver also reads but without the pre-compression size a hover is for), and nothing for the three single-stream names. A `.br`, `.bcm` and `.lpaq8` have no tool and show the member an extraction would write — its name from the file's own, and the file's weight — starting nothing. The extra codecs make it PeaZip's build rather than stock: a `.zst` lists through it, a `.br` does not. What the archiver opens but this app has no business showing (programs as resources, extensions that are words) is left out on purpose.

A hover waits on a launch the preview loop cannot wait on, so the listing runs on its own thread: the spinner at the pointer, replayed when the answer lands. One listing at a time, newest queued. The process is adopted into the job rather than recorded (a listing lives a fraction of a second), started `CREATE_NO_WINDOW`, and given its input closed (`Stdio::null()`) — the one flag about safety rather than looks, since an encrypted TOC would otherwise leave the tool asking for a password nobody can answer.

An engine that stopped answering is the other half. A damaged archive, or one read through something this machine was not given, can outrun any bound (measured: the zpaq PeaZip 10.9.0 ships is zpaqfranz, which does not come back at all from a file that is not a zpaq). A run past its give-up is ended where it stands, the file remembered as unlistable and the hover answered. The listing comes back as the same `Listing` every other archive's is, under the same cache key. There is no TTL: a user wanting faster archives changes the cache.

## Calibre Previews

The one thing this app draws as a book by itself is a PDF. Everything a person buys or borrows is a format that renderer does not open — Kindle/Mobipocket (`.azw`, `.azw3`, `.azw4`, `.mobi`, `.prc`), `.epub`, `.fb2`, scanned `.djvu`, Sony `.lrf`, and the `.pml`, `.snb`, `.tcr` of the 2000s readers. Calibre's pipeline reads every format above and writes a PDF. Those names are the `[calibre]` list, the other half of the `Ebook` kind under `Preview Types`; a name the engine cannot read is answered with no preview once and then remembered.

What comes back is a PDF handled as a page an installed render engine drew: read from the page cache, drawn into the same BGRA frame by the same first-page renderer, at the share `ebook_scale` names, over `image_background`, sharp at whatever size because it is a page and not a picture. One thing differs, and it is what a book has that a document does not: **a page is chosen rather than taken.** An EPub, Kindle or Mobipocket file puts the cover first, and a cover is as likely to be one flat colour as artwork — the quick start guide inside Calibre's own installation carries a single-pixel cover — so the opening pages are looked at, small, until one holds more than one colour, and that page's size is the layout and whose pixels are drawn (`pdf_preview::book_page`). A page with anything on it is never skipped and the walk stops after eight, so a book of blank leaves still shows its first page; a self-read PDF is still page 1. The cache is named for the book, its version and the engine that converted it, so a book and a document that happen to be the same file cannot be handed each other's page. A page that is there is a read; a page that is not is the wait for a conversion.

What a book _is_ is asked of its bytes before its name: a Mobipocket file by the type `BOOK` and creator `MOBI` (which tells it from the Palm ebook the render engine's filters read, under the same header), an EPub by its declared type, a FictionBook by its root element, a DjVu by its opening chunk, a BBeB book by its letters with zero bytes between. A `.snb` (SQLite), `.tcr` and `.pml` (text) and `.htmlz` (zip) have no head to ask about, so those four are answered by name alone.

Nothing bundled or linked: the engine is the user's own Calibre at `Calibre2`, beside `config.ini`, or beside the app. What runs is `ebook-convert`, handed a book and a path to write; the windowed `calibre.exe` is never opened, and the book is named by its whole path so nothing about the file's own name can move a file of this app's or be read as a switch. The process goes in the job and is *recorded* (a conversion is seconds, and a bad run's process is worth answering for), `CREATE_NO_WINDOW`, standard streams closed.

A conversion past its give-up is ended where it stands, the book marked unconvertible and the hover answered. Here that is the ordinary case rather than the exception: DRM the engine will not open, or a scan it cannot decode, can take minutes to say so and some never do. The bound is twice the render engine's, a reason that is the format's: a document is converted *from* one document, a book from every page of a book. The first hover of a large one is bounded too — it stops waiting after the app's own cap whatever the engine is doing and the conversion runs on, so a thousand pages is drawn for the next hover.

There is no TTL: handed a book it boots a whole Python application, writes the PDF and exits. It is the engine a TTL suits best on paper and the one with nothing to hold; what a user wanting faster books changes is the page cache.

## Comic Previews

A `.cbz` is a zip of plates, a `.cbr` a rar, a `.cbc` a zip of several comics' pages under a folder each with a `comics.txt`; what they share is the answer to a hover, the first plate inside, as a page. The names are the `[ebook]` list's, which is also where the PDF's spellings live (`ebook_formats`): the list says which names are books, the _file_ decides which reader answers. Drawn as a PDF page is — `ebook_scale`, `image_background`, the `Ebook` switch, a frame of this app's own.

The plate is read rather than converted, which is the whole design: the engine that reads comics unpacks the archive, decodes *every* plate, rewrites each (trims borders, adjusts levels, resizes to a device profile, converts to greyscale unless told not to) and builds a document of the lot — a hundred megabytes and minutes — where a hover needs one picture, which the container hands over directly. The headers are walked for the **names** (inflating nothing), and only the entry that is the page is read, decoded and drawn (`archive_listing::entry_bytes`, whose whole point is the one entry). Nothing is written to disk — the plate is inflated into memory under the decode budget and decoded from there, as `project_image` does — and nothing is cached in front of the decode: what is held between hovers is the plate's *size*, so a second hover costs the same decode.

Which plate is first is a question about names, by the rules comic readers and the engine agree on. A plate is a picture — `jpg`, `jpeg`, `jpe`, `jfif`, `png`, `gif`, `bmp`, `tif`, `tiff` — and anything else (`ComicInfo.xml`, `comics.txt`, a readme) is not. A zip written on macOS carries a `__MACOSX` folder of resource forks shadowing real members, which is not a plate either. The first plate is the first **by name, counting the digits**: writers pad numbers to different widths, so `2.jpg`, `02.jpg` and `10.jpg` order by the number, which is what makes a chaptered comic come out in reading order too, the folder's number compared before the plate's. What is _not_ done is as deliberate: a two-page spread is drawn as the one page it is rather than cut in half. Its size is the one thing read before the preview is placed, both off the preview thread, so a first hover on a comic is the wait for the size, and the plate is read for the frame once the box is known.

The plate is decoded from **bytes out of a member** rather than from a file, so a container of WebP or AVIF plates (much digital manga) gets no preview rather than a page, and what it would take is a stream over memory for a codec handed a path (see TODO.md). And a comic's page is *not* chosen the way a converted book's is: an engine's page is walked for the first that says anything, skipping a flat cover, while a comic's first plate is taken by name and shown as it is.

## PDF Previews

A PDF preview shows page 1 rendered by `Windows.Data.Pdf`, so the app bundles no renderer. Two threads do the work and both `CoInitializeEx(COINIT_MULTITHREADED)` first, as WinRT requires.

The preview thread measures the page before anything decodes, because the preview is positioned and sized first: the engine's page size in DIPs (96/inch) is what the layout is computed from, as video geometry is resolved up front. That probe is cached per path, failures included. Measuring is off the preview thread, so the hover is laid out as the spinner and replayed with the answer. The render records the page size it read in the same cache. Before a path reaches the renderer it must carry a `%PDF-` header in its first kilobyte.

The document is opened from a stream over the file itself — not a copy read into memory, and not through `StorageFile`. `StorageFile.GetFileFromPathAsync` rejects the verbatim `\\?\` form the hook canonicalizes shell paths to, failing with `ERROR_BAD_PATHNAME` while the same file opens through a plain path, which is why a PDF previewed from a search result but not from a folder view. A PDF is read by seeking anyway — the object graph is found from a table at the end, and a page's content and resources can be anywhere — so memory bought nothing a seek could not and cost the whole file held, twice over. `SHCreateStreamOnFileEx` is handed the path directly rather than the WinRT broker resolving it, so it accepts every path form the rest of the app produces (long and UNC included), and `CreateRandomAccessStreamOverStream` wraps that COM stream as the `IRandomAccessStream` the engine asks for. A hover onto a large PDF costs what the page costs, not the file.

The decode worker then renders page 1 into exactly the pixel size the layout asked for, after fitting the page's own aspect ratio into that box, so a page not the shape the layout assumed is letterboxed rather than stretched. Rendering at the target size keeps a scaled-up preview sharp. A PDF is laid out as a share of the room the display has: `ebook_scale` starts at the whole of the room, every value at or above `100%` reads as that fit, and a value below `100%` is a size the user picked that reduces the fitted size. `effective_preview_scale` is the single place deciding it, so layout and render cannot disagree. The renderer is asked for its BMP encoder (a header parse instead of a PNG inflate), and the page is painted on opaque white so its text stays readable over any `image_background` mode. The result is an ordinary static frame: the existing spinner covers the wait and a render finishing after the cursor moved on is dropped by the same generation check as every other load.

Nothing drawn is kept. A page is a screenful of pixels rather than the document — about six MB at fit-to-screen on a 1440p display, over thirteen at `100%` on 4K, against a file usually a fraction of a megabyte. What is remembered is the page's size, read once per file and version; the render is paid again on the next hover. The `Ebook` gate is the switch, and no size means "draw nothing".

## Vector Previews

A vector drawing is not decoded, it is _drawn_, and this app carries no rasterizer and no vector parser. It carries two ways of asking something else to draw one, and the **Vector** kind holds both: an SVG document, drawn by the browser engine (see SVG Previews), and a Windows metafile, played by the drawing layer. All of it is one tray setting — one gate, one scaling, one background. The two halves are asked apart, in one order: the document first, because the one list names both and neither reader of the drawing half would take a document.

A `.wmf` and `.emf` are lists of drawing records rather than pictures, and Windows ships the player: `PlayEnhMetaFile` draws the records into any device context, and a memory context holding one of this app's own DIB sections is one — the same 32-bit BGRA surface every other frame is composed in. Nothing is rasterized; a preview is the drawing replayed at the planned box, which is why a metafile stays sharp at any size. The older form is read for its placeable header first (the one place a `.wmf` declares its drawing's size and twips per inch), and a file without one is handed to the layer as it comes, the layer working the bounds out from the records; either way records are converted to the enhanced form the layer plays, which is also how a headerless file is measured.

Two plays are made for every frame, over black and over white, and the coverage the device context never writes is recovered from what the two disagree about: a pixel the drawing touched is the same colour over either page, a pixel it left alone is the page itself, so the difference between the plays _is_ how much of the page the drawing covered. That is what lets a drawing stand on whatever the tray says is behind it — including nothing — and why a metafile whose marks are black on white need not be given a white page to be legible.

An encapsulated PostScript file is the other half and the more awkward one, because an `.eps` is a PostScript _program_ and this app has no interpreter — nothing is parsed, evaluated or run. What is read is the preview the format exists to carry, in two shapes: the Windows container, opening with a signature no PostScript file does and a header naming where the program starts and where two previews may be (a metafile and a TIFF, either possibly missing), or the comment block where a Mac writer puts the same picture as hexadecimal between `%BeginPreview` and `%EndPreview`. Each is read for what it holds rather than for what it says: every offset is measured against the file's own length and the decode budget before a byte is read, so a hover onto a `.wmf` costs a header before this reader gives up. A drawing is handed to the drawing layer, a picture to the decoder, the drawing preferred where a file carries both. One picture shape is read here rather than by the decoder, which refuses it whole: an eight-bit index into a colour table with eight bits of alpha beside it, read by walking the picture's directory and looking the table up here, with the alpha the decoder would have ignored kept and an associated (premultiplied) one divided back out of the colour it was multiplied into. A program with neither shape shows nothing.

## SVG Previews

An SVG is a document of shapes, gradients, texts and images, and this app does not draw one. What draws a document is the WebView2 runtime Windows 11 ships with, in a window of its own — the PDF path's shape with the renderer moved out of the process: `svg_preview` answers the two questions asked before handover (is it a document, what size does it ask to be drawn at), the layout places that size, and the box that comes out is the box the engine's window is given. What it is asked for is a share of the room the display has — `vector_scale`, whole of the room by default, `100%` or more read as that whole room too. A page follows the same rule at a share of its own (`ebook_scale`, `document_scale`). What a document is drawn over is `vector_background` — a document is drawn on a page where a picture's transparency is the picture's — shared with the metafiles. Three of the four backdrops are the controller's to apply; the checkerboard is the page's own, since the engine composites its own.

Nothing is rasterized here, and the sentence is about drawing a vector rather than about decoding a picture — a distinction the release binary keeps by a different route than the one it used to. It still carries no rasterizer (no `usvg`, no `tiny-skia`, none of the font and shaping stack), and what a document is drawn by is the one renderer implementing the whole of SVG, SMIL and CSS animation. A pixel decoder was added beside it — `jxl-oxide`, for an animated JPEG XL (see Codec Previews) — and that is a decoder of a raster format, not a rasterizer: there is still nothing here that turns vector outlines into a bitmap. The cost is the runtime being there: without it there is no SVG preview, and `Engine → WebView2 TTL` is greyed. There is no "does it move?" question: a still document and one that moves are drawn the same way.

A measurement is all this app does with a document. The size is the root element's own `width`/`height`, with `viewBox` answering where they are relative or missing, and 300x150 the browser assumes for a replaced element where a document names neither; a `.svgz` is inflated here rather than by the browser. The answer is held between hovers, keyed by file and version; a version that is not a document is remembered as that. Reading is the measure, and a document of any size is read and parsed whole, so that read is off the preview thread and a first hover is the wait for it. Nothing drawn is held. A file that will not parse as XML, or whose root is not an `svg`, gets no preview, which also keeps a box the engine would draw nothing in from opening.

What a document may reach is bounded, though not by its size: this side reads a file whole under the global budget, and the browser reads the document under rules the engine is given — script off, a resolver answering for no host, no context menus, no devtools, no accelerator keys, no zoom. The engine is pointed at a page of this app's own with the document in it as an image, and that is what makes the document the size of the preview box: a browser lays a standalone SVG out at the size the document asks for and does not stretch it to the window, so a 120-pixel document in a display-sized window is a 120-pixel picture with the rest of the window empty. An image, on the other hand, is drawn to the box it is given whatever its own size, by layout rather than magnification. Nothing is given up and something is gained: an SVG drawn as an image is animated and not scripted, cannot take the pointer, and cannot reach anything outside itself — not a file beside it, not a URL — so the engine's rules are the image's rules, which is why the page is written rather than the document put in as markup. The page is a few hundred bytes in the run's own folder, rewritten per document, pointing at the document through a URL versioned by the file's modification time so an edited file is never answered from the browser's cache.

A page of HTML, drawn by the same engine while `Text Preview → Render HTML` is on, is written the same way and with one difference worth stating: the wrapper embeds the file itself in a full-bleed `<iframe sandbox="allow-same-origin">` rather than as an image, because a page is asked for at the size of the box it is given — a browser shows a page in a frame and lets it scroll, so the same layout a drawing needs is what keeps a page from showing only its first screenful in a display-sized window. The single sandbox allowance is the page's own origin, without which its relative stylesheets and pictures would not load; everything else is withheld, exactly as it is for a document drawn as an image, and the links a page keeps are reached from outside by `BROWSER_ARGUMENTS`. The page is named for the backdrop and the file as well, so two pages are two pages the browser has not seen, and both URLs carry the version.

A hover shows the engine's window and nothing else: what stands in for one while a browser starts is the waiting spinner, and a document whose page never arrives leaves nothing on screen. Beginning the engine costs a browser start (~250 ms measured, nearly all of it the controller), so the first hover of a while pays it: one engine is kept warm, let go by the `Persistent` toggle at the top of the same submenu — persistent kept for `webview_idle` (10 min), non-persistent by the AFK timer. A wait that follows the pointer takes the engine's window with it, so the document is drawn where the wait ended up rather than where the hover began. What the engine is handed is one document rather than a list: each ask publishes the *want* (file, backdrop, box, generation), so the engine takes the newest want and what was asked for after it is not drawn at all — not navigated to, and a navigation already running for it dropped rather than put up, its thread *woken* for the question rather than left finishing a page nobody waits for, the same way the page's own arrival wakes it, so nothing is polled. The window holds the document before the next one, and a document the pointer has left takes the window down without waiting for the navigation. A document that lands names the file it was drawn for, and that name is what the loop ends its wait on: a page arriving for an abandoned hover ends nothing. A document is closed the way a picture is: the pointer arriving at the engine's window is the pointer arriving at the preview (`cursor_preview_hover`), and what the pointer is over _inside_ it is a browser child window one or two levels down, so the question is whether the window under the pointer is the engine's or one inside it — comparing the two handles alone never answers yes.

The page and its image are pointed at by URL, and the path a hover carries is the Shell's — the verbatim `\\?\…` form, which no browser will open and which is refused silently — so the prefix comes off and a share keeps its server (`file:///C:/…`, `file://server/share/…`).

The engine's state lives in one user data folder and one folder is one browser at a time: an environment pointed at a folder another browser holds answers `ERROR_INVALID_STATE` for its controller. That other browser can be a leftover from a run that ended badly, so the folder is a _folder per run_ (`%LOCALAPPDATA%\rust-hover-preview\webview\<pid>`) and earlier runs' folders are cleared at startup, best effort, since one still held cannot be removed.

Defence in depth: the controller is asked for four times over a couple of seconds before the attempt is given up, and a failure is remembered for a minute, during which an SVG hover opens nothing at all rather than a box nothing would be drawn into — there is no reader behind the engine to fall back to. A document the engine could not put up, whose page could not be written, or which it did not arrive at, costs that hover and nothing else. A navigation given longer than any document takes to be laid out is the one failure the engine cannot report for itself: what it waits on is an event that may never come, and the thread waiting on it is the thread the idle timeout lives in, so every document after it would wait behind a wait that never ends, with the previous file standing in its window. The wait is bounded (`NAVIGATION_TIMEOUT`), past which the engine is let go, browser and all. Being had at all is bounded the same way (`HOST_CREATION_TIMEOUT`): the environment and the controller are asynchronous calls whose completion handlers are the runtime's to fire, and both were waited on until they did. They are now asked inside one shared deadline, so a browser which is *silent* rather than refusing spends the attempt instead of being asked again on a fresh clock; and a host that stopped answering is ended rather than closed when let go, its browser ended first by the id it was recorded under. Because a thread that has stopped answering posts nothing, the wait is bounded on the waiting side too: a hover whose document has not arrived in the time any document takes has its spinner taken down and the engine stood down for a while (`note_unanswered`). A tracer (`RHP_WEBVIEW_TRACE`) and a folder override (`RHP_WEBVIEW_PROFILE`) exist for the same reason the other probes do: an engine that does not come up says nothing by itself.

## Font Previews

A hover on a font shows a specimen: the name the font calls itself, the pangram _The quick brown fox jumps over the lazy dog._, and a line each for as many of Japanese, Chinese, Korean, Cyrillic, Greek, Arabic, Hebrew, Thai and Devanagari as the font's `cmap` covers. It is drawn by the engine the SVG path uses — nothing on this side rasterizes, shapes, or carries a font parser of the kind that draws text — and the page is this app's own, with the font through `@font-face`. That engine reads all five formats a font goes by, so the drawing costs no reader; without WebView2 there is no font preview.

The one question a browser cannot be asked is what a font _covers_. It falls back per glyph and says nothing: a page drawing 「いろは」 in a Latin-only font draws it in a system font, at the same size and layout, so a preview showing it would claim something untrue. Coverage is therefore parsed here, from `cmap`, all or nothing: a line is drawn where every character of it is in the font, and the space between two words is not a character a font must have. Each line is the closest thing its script has to a pangram (the Arabic and Hebrew pangrams those scripts are sampled with, the Thai and Devanagari openings, the rest words a font is as likely to be asked for as to have), drawn whole or not at all, so a font of a script there is no line for is drawn from the characters its own map holds; a file with no character map at all gets no preview rather than a page of another font's text.

What that costs is one read of the file and a parse of two tables: `cmap` and `name` (family and style, a Windows English record preferred, the file's own name where the font names itself nothing). Both webfont containers are read as well as the two open formats and a collection: a WOFF's tables are deflated one at a time with the reader the archives use, and a WOFF2's are one Brotli stream, decompressed only as far as the last table a specimen needs and only up to the global budget. The parse is held between hovers, keyed by file, version and face, so the two faces of one collection are two answers and a file that turned out not to be a font is remembered as that. The parse reads the whole file, so it is off the preview thread: a first hover is the wait for it, and a file that will not parse is answered with the wait coming down rather than a spinner over nothing.

A font has no size it asks to be drawn at — what a file holds is outlines — so the box the layout places is this app's own: the shape a specimen wants, and the share of the room `font_scale` names, half the display by default (a drawing's starts at the whole of the room). Every size in the page is a viewport unit, so the window that comes out of the layout _is_ the size the type is drawn at, and a font covering more lines than the box was shaped for is drawn at smaller type rather than past the bottom. The page carries its own colours rather than getting them from the controller, because a specimen is a page of text and not a picture with transparency: light ink on the black backdrop, dark on the white one and on the checkerboard's squares, and light ink with a soft dark shadow where there is no backdrop to read against. What it is drawn over is `font_background`. Each line carries its own direction, which is what a browser settles from anyway: a right-to-left line is laid out from the right so its punctuation ends it where the script ends it.

A collection is the one case the engine cannot be handed the file for. A `.ttc` holds several faces sharing one table pool, found by offsets, and a page has no syntax for naming a face inside one, so one face is written out as a font of its own — a header and a directory of that face's tables, copied where the new offsets say — beside the browser's profile folder, named for the file, version and face. Which face is a choice rather than a property: `ttc_face` names it, first to tenth, and a collection with fewer faces than the setting names is drawn from the last one it has. The heading carries both halves — the face's own name and `(2 of 4)` — and the page is named for the face as well, so switching faces is a page the browser has not seen rather than the one before it out of cache.

A font is its own kind under `Preview Types` — a gate of its own, a list of its own in `config.ini` (`[font]`, `otf,ttc,ttf,woff,woff2`) — and both halves of the app ask in the same order: the hook's media gate asks the font list after the text lists and before the image list, and the renderer asks the same place in the same order.

## Text Previews

A text preview shows the first screenful of a text file, colored by the syntax definition its extension names. Which files those are lives in `config.ini`, written from the built-in lists on first run and read back, so a user can add a format without a rebuild; `text_formats.rs` owns both lists and the normalization that keeps a hand-edited entry from matching anything but a bare extension. Both the Explorer hook's previewable gate and the renderer consult it.

There are two lists because one cannot reach the files a repository is recognized by. Extensions are matched the way the filesystem reads them, which leaves out `LICENSE` and `Makefile` (no dot at all) and, less obviously, `.gitignore` — a leading dot begins a _name_, not an extension, so `Path::extension` reports none. The extension lookup therefore falls back to the name minus a leading dot, which is what makes a `gitignore` entry mean `.gitignore`; and a second list of names carries the extensionless files, matched whole, case-insensitively, with the same dropping of a leading dot on both sides. A file is in when either list claims it, so `.eslintrc.json` is read by its extension while `.eslintrc` is read by its name. The one gate both sides ask is `routing::kind_of`, so a file the hook offers is one the renderer can draw.

Text has no size of its own, so the PDF path's two-step shape is repeated with a different measurement: `measure` resolves the box the first screenful wants, bounded by the display, the layout fits that box beside the cursor or focused item, and `render` is handed the box that came out. A PDF page is a vector drawn at whatever size is asked for; text is drawn at a fixed font size scaled by the display's DPI (`GetDpiForMonitor` on the monitor under the hover, falling back to 96), so scaling the box would only stretch the window around text that stays the same size. `effective_preview_scale` therefore answers `100%` for text — never enlarged, reduced only when the space beside the cursor cannot hold it — and the renderer reads the box as "as many lines and columns as fit". What the fit must not do is shrink the box whole: lines wrap at the width the box ends up with, and a narrower box needs more rows than the proportional height leaves, so the document is measured again at the width the box came out with and that box placed again from the measurement. A two-line file gets a two-line window — more when lines wrap — and a long file takes the largest box the display allows. That largest box is the display's work area cut down to the share `text_scale` names (`text_box_room`): the setting is the room a page is *measured in*, not a zoom over a size the file holds, since a page of text has no size of its own — `fit` is the whole work area, which is the room this kind was given before the setting existed, and a share past the whole is the whole, so a page is never measured in more display than the display has. It is a ceiling rather than a share of the result: a page taking less room than the share allows keeps the room it takes, which is what keeps a short file's small box, and a `Text Size` large enough to fill the share cannot grow the page past it. The re-measure for a narrower width is clamped to the same room, because wrapping at that width takes *more* rows, and a page measured at a share of the display and again at the width the layout handed it would otherwise come back taller than the share allows; at `fit` the room is the whole work area, which is wider and taller than the layout is, so nothing is clamped at the setting's own start. Only the text kind is measured this way — an archive listing, a PeaZip page and every other kind is measured against the work area itself.

`Text Preview → Font Size` multiplies into that: `TextMetrics` scales the display DPI by the configured percentage into one scale, so glyphs, line spacing and page margin grow together and a preview at 200% is the same page twice the size. The size is deliberately not part of the parsed document's cache key — styled lines are identical at any scale and only layout changes, so changing the size repaints from cache instead of re-reading. The combined scale is bounded (0.25x-16x), so a hand-edited `text_font_scale` cannot ask GDI for a glyph taller than the screen. It is the scale of the glyphs and nothing else: it never widens the box, and it is the room above rather than the size in it that `text_scale` names, so the two are set for different wants and a large font size can no longer carry the page past the share the box was given.

Previews are gated by kind from `Preview Types`: `image_preview_enabled`, `video_preview_enabled`, `text_preview_enabled`, `ebook_preview_enabled`, `archive_preview_enabled`, `document_preview_enabled`, `design_preview_enabled`, `vector_preview_enabled`, `font_preview_enabled`, all on, switched through `config::PreviewType`. Five kinds an engine or reader draws are not switches of their own: a picture the image converter develops answers to `image_preview_enabled`, a document the render engine draws to `document_preview_enabled`, an archive the listing engine reads to `archive_preview_enabled`, a book the ebook engine converts to `ebook_preview_enabled`, and a comic to that same `ebook_preview_enabled`. A gate is only whether previews of that kind may be shown at all — the lists and settings deciding which files are previewed are untouched, so a kind switched off and back on restores what was configured. Both halves of the app ask: the hook's media gate asks the kind of a file — video first (only content settles the `.ts`/`.mts` the text list shares), then a PDF, a comic, an archive, an archive no reader has, a book the ebook engine converts, an Office document, a document the render engine draws, a picture the image converter develops, a design document, a vector drawing, the text lists, the font list and the image extensions last — and the renderer asks the same question when it measures, in the same order. A name two lists hold is the kind the earlier list makes it, which is what keeps a `.swf` from being measured as a page and drawn as a video. A document is asked about in the same order and by both halves — the vector list first, and within it whether the file is one — so `svg`/`svgz` are under `Vector` rather than `Images`: pictures switched off leave a document previewing, and drawings switched off leave pictures alone. `text_preview_enabled` is checked in `text_formats::is_text_file` ahead of both lists. A kind switched off takes the preview of that kind with it: the tray hands the preview thread a type change and a preview whose own kind is the one that changed is rebuilt from the hover it came from, which drops it because the layout finds no size for a file whose kind is off — a preview of any other kind is left alone, so a running video is not restarted by a toggle it has nothing to do with. The engine behind a kind goes with it: `Document` ends the Office processes, and `Vector` or `Fonts` lets the browser go. The Office ones are ended from the tray rather than asked of the worker (a worker inside an uncancellable COM call would hold one for good, and the tray may not wait on one), while the browser is let go by its own thread. A gate written into `config.ini` rather than clicked in the tray is answered the same way, by each engine's own thread.

Colours come from the theme selection, which can be a file the user wrote: `text_theme` answers from one of the two bundled TextMate themes or from the `.tmTheme` a selection names in the `theme` folder beside `config.ini`. A file is read when it is asked for rather than when the folder is listed, the menu is what lists the folder, and opening it drops the parsed files so the next preview reads them again. A file that is missing, unreadable or not a theme is answered with the default (Atom One Light) rather than nothing: the renderer is handed a theme it can paint with, the item keeps its place in the menu, and the selection stays in `config.ini` until another is chosen, so a repaired file is used as soon as the menu is opened again.

The parsed document is cached per path, modification time, length, theme and Markdown mode — plus, for a file theme, the reading of it the document was coloured against, since a file can be edited under a name that does not change — so a second hover, a repaint or a theme switch costs a layout rather than a parse. What is cached is the _text and where its lines start_ (eight bytes per line, no parsing), which is what lets a preview know how tall a document is and how far it can scroll before anything is coloured. Styled lines are built per window by `styled_window`, kept in a small per-document cache and indexed by absolute line number, so a window covering a scroll position costs nothing. For a source file the parser runs from wherever it left off, or from the nearest checkpoint taken every few dozen lines, and only the requested lines are kept: nothing past the window is ever styled and a jump in either direction is bounded by the checkpoint spacing. The parse state cannot live in the shared cache — syntect's `ParseState` holds pointers into Oniguruma's match regions and is not `Send` — so it is kept per thread in a `thread_local`, while the windows, being plain data, are shared between the measuring and painting threads. Four producers: `syntect`, with the syntax definitions `two-face` adds on top of the ones it bundles, colors source and markup files; `pulldown-cmark` turns a `.md` into the document it describes, handing fenced code back to `syntect` and asking the theme for the colour of a heading, a quote or a link by scope, so a rendered document and a highlighted source share one palette — the one producer that reads all of its input, because a rendered line's place is only known once the block before it has been walked, and it keeps only the window's lines as it goes; an RTF control-word stripper reduces a `.rtf` to the text it carries, skipping Word's own tables, once at load; and an NFO reader decodes CP437 art and consumes its ANSI escapes into colors toned toward the page. The one producer whose lines are not the file's own is rendered Markdown: a paragraph is one line, a heading is one, and the blank line between two blocks is one the source does not have, so the walk that renders the document also counts what it drew — once, when the document is built — and the scroll range, the scrollbar and the lines said to be left out are all measured in those lines. Reading is bounded (2 MB, 2000-line scroll range) and decoding decides the encoding from the file: BOMs first, then UTF-8, then the legacy code page CP437 belongs to. Two guards keep non-text out: NUL bytes mean the file is not UTF-8 text (a UTF-16 file is recognized from where its NULs fall, anything else is binary), and a decode that is mostly control characters is a binary file that happened to pass.

What is painted is kept too, keyed by the file and version, the options it was painted with (theme, Markdown mode, font scale, full mode), the box, the DPI and the starting line: a frame is pixels, so unlike a parsed document the font scale really is part of what makes it and a scroll position really is a different frame. `text_cache_mb` is the budget — `0` by default, cap 2048, and `0` means a cache holding nothing rather than a preview switched off — read from configuration each time, trimmed LRU by counter on every use, and a frame larger than the whole budget not held at all. The cache is consulted before the document is even looked up, so a hit costs a clone rather than a layout and a paint. A frame a selection was painted into is never held.

Layout keeps a document readable inside the box rather than filling it. A line wider than the page continues on the next, wrapped between words, and a word wider than the page (a URL, a hash) is cut at the edge, because nothing in a text preview scrolls sideways. The wrap goes only as far as the frame could draw — the lines it has room for, and no scroll position reaches past them, because a position is a document line and a frame always starts at a line's own first visual line — so a minified file costs a frame's worth of wrapping rather than the whole file's. A frame is pulled back until it can be filled from where it starts, so the last screenful is full: the lines above a frame that would end early are walked backwards from its top while the box has room, which measures the pull-back in the document's own lines rather than in the lines that fit — one line can take two of the box's, and a pull-back by the number of lines that fit left the end of the document out of reach, both as a wall a few lines too high and, past the end, as a frame that painted nothing. One rule follows for the end of a document: the frame whose tail fills the box is the last one, its last line is on screen, and a position past it resolves to that same screenful rather than to an empty box. A line is kept at the end for a note whenever the frame cannot show everything and no scrollbar will say so.

A document longer than its frame gets a scrollbar, drawn into the same frame: a groove and a thumb whose length is the share of the document the frame shows and whose position the share above it. The bar's geometry comes from one function used by both painter and hit test, so what is drawn and what a drag lands on cannot drift apart. The wheel reaches the preview through the low-level mouse hook rather than the window, because the preview never has focus and Windows delivers wheel messages to the focused window (Explorer) instead; the hook asks the preview for the pointer region, swallows the message when the pointer is inside it, and leaves the notches for the preview thread. The delta comes from the hook structure's `mouseData` — a low-level hook is handed the message identifier and a pointer to that structure, and the delta a window would find in the high word of `wParam` is not filled in there. Dragging the thumb is ordinary mouse input, which the layered window does receive: a press starts a drag with capture, a move maps the pointer back to a document line in the range the bar was drawn for (the lines the preview can reach, not every line the file holds), and a release ends it.

The same messages carry a selection. A press not on the bar starts one, a drag extends it, and both ends are places in the text rather than points on the screen: the frame hands back the lines it painted with where each run landed, and a point is turned into a (line, character) against those, so a selection survives a repaint and a point running off the text takes the nearest end of the line. The selection is painted into the frame rather than drawn over it — the run under it is split and drawn in up to three pieces, the middle over the theme's highlight — so changing a selection costs a re-render of the window, which by then is a repaint rather than a re-parse. Copying reads the same painted runs, so what is copied is what was on screen, and the lines a selection touches are joined with Windows line endings. The clipboard is the system one: a movable block of UTF-16 via `SetClipboardData`. Keyboard copy is the one piece of text editing that cannot arrive as a message — the preview never takes focus — so it is polled like the rest of the app's key reading: `Ctrl+C` only while there is a selection to copy, and `Ctrl+A`, which selects the whole frame, only while the preview is pinned. Selecting everything is otherwise the menu's `Select All`, taking the same range. The right-click menu is asked for its command rather than posting one, so it needs no message loop and the preview never has to activate.

All of it is full mode's, and full mode is what being *pinned* means for a text preview. A hover is a preview to read and then leave: the renderer is handed a frame that does not scroll (text a box cannot hold is said in a line on the end of it), the preview keeps no state to select into, and the pointer over it closes it the way it closes any other preview. A preview the pin key turns into a window is handed full mode instead, and the media is laid out again when taken up, because the mode is read from the pin being up rather than from the configuration (`current_text_options`). That is also why the same file can be two frames: what a hover showed and what the pin shows are built from different options, and the painted-frame cache is keyed by them.

What makes all of that possible is one published pair of regions: the journey from the point a text preview was opened from (the cursor that hovered the file, or the middle of the focused item) to the preview, and the preview itself, both in screen coordinates, with the margin a hand that overshoots needs beyond the preview's far edge. Their shape is the point. A preview is placed _beside_ what it belongs to rather than over it, so the pointer has to travel to reach it, and the journey is that crossing: it reaches the preview's _nearest_ point and stops, so everything it covers away from the preview is the row of the file list the pointer crosses, and it is as tall as the crossing rather than as tall as the preview. Reaching across to the far corner instead covers the whole column of the list between pointer and preview, and inside the region nothing under the pointer is resolved: a text preview as tall as the display put every file in that column out of reach for as long as it was up, which read as previews failing at random in a list beside a text preview and never in one beside an image. The one place the pair reaches past the preview is the edge the journey ends at (the right edge for a preview placed right, the left for one placed left), because the pointer is still moving when it arrives and what waits there is usually the scrollbar, a thin target at the very edge of the frame: `text_scroll_far_edge_grace_pixels` (40 logical pixels at the display's DPI, read from configuration each time the regions are published rather than baked in) keeps a hand that overshoots from taking the preview down with it. Nothing past the near edge is added. The pair is published for any text preview in full mode, scrollable or not — resting on a preview is how it is selected from — recomputed from the preview loop on every tick so it tracks the window as it is moved, and two flags published beside it say whether the preview on screen can scroll and whether the pointer is being held at all. Both are atomic reads, so the hook's check costs nothing until a text preview is up.

The Explorer hook asks whether the pointer is inside that region and answers exactly one question: whether the pointer is on its way to the preview. A move is normally what resolves the item under the pointer and drops a preview whose file is no longer under it, and on the way to a preview the item under the pointer is the preview rather than a file, so while the pointer is inside the region and over no file the preview stays and the mouse-delay path that would raise a preview for nothing is skipped. It does not decide what is _under_ the pointer: another file takes the preview over the moment one is under it, inside the region or out. Nothing is held over from one tick to the next — the answer is read from the region as published, so a pointer outside it is treated as it was before the pointer ever touched the preview — and a pointer over the preview rather than over Explorer is not read as the user having left Explorer, since a preview is drawn on top of the window it belongs to and the check cannot see under it. The wheel hook asks for the preview's own region before deciding whose wheel it is: it belongs to the preview while the pointer is on it or just past its edge, not while the pointer is still crossing the row in front of it. The regions are withdrawn when the preview is hidden, so nothing else has to know which previews scroll.

A theme or Markdown-mode change is different from a background change: a text preview's colours and glyphs are in its painted frame, so `Refresh` rebuilds the visible preview from the hover it came from (recorded when it was shown) instead of recompositing the frame it already has, while every other format only needs the recomposite.

Painting goes through GDI into a surface of its own: a memory DC with a top-down 32-bit DIB section, filled with the theme's background, block decorations written directly into the pixels, and every run drawn with `ExtTextOutW` against an opaque background rectangle — which is also how a code block's band and an inline code span get their fill. Fonts are created per style and size, once per paint, and the DC is handed back its original object before they are deleted, so a hover leaves no GDI objects behind. The frame is forced opaque on the alpha byte on its way out: a text preview is a page, not a cut-out.

**HTML.** One kind of text file is a document a browser can already draw, and the tray's `Text Preview → Render HTML` (off where the app starts, `render_html` in `config.ini`) is what asks for it to be shown that way rather than as its markup. The question is the name alone — `htm` and `html`, read through the same `lookup_extension` every list reads, so `.HTML` and `.html` are one name and `.xhtml` is left alone with every other text file — and the answer is the configuration's rather than the name's, which is what lets the same file be a page of text with the switch off and a page on screen with it on. The kind does not change: `.htm`/`.html` keep riding `PreviewType::Text`, no kind is added and no extension routing moves, so the gate, the lists and `text_preview_enabled` all mean what they meant. What changes is who draws it — the file goes to the WebView2 engine the SVG and font paths already use, in the wrapper page described under **SVG Previews**: a full-bleed frame of the file itself, sandboxed to its own origin, in a page named for the backdrop and the file and pointed at by both URLs versioned by the file's modification time. Scripts, context menus, devtools, zoom and name resolution are the engine's own standing rules (`configure()` and `BROWSER_ARGUMENTS`), so a page is previewed under the same rules a drawing is.

A page asks for no size of its own, so the box is this app's own: a nominal 1280x800 page box scaled by `document_scale`, the same rule `PreviewType::Document` uses, which is what makes a page drawn here the size of a page drawn by an Office app. The scaling is settled in the layout, before a browser is asked for anything. A machine with no WebView2 runtime is answered with the text preview instead, as it already is for drawings and specimens, and there is no third answer: `draws` is the one place the switch is read, and it is read there rather than in routing so that the two engines ask the same question. Switching follows the rule every other rendering setting follows and does not rebuild what is already up — a pin showing a page keeps it, and the next hover is drawn the new way (`refresh_render_html`).

## Archive Previews

A hover on an archive shows a summary line, a hairline and a tree of the archive's own entries — folders first, each row indented by depth, every file's size right-aligned, and a note at the end when the page could not hold everything. The page is painted rather than composited, through the same GDI layer a text preview uses, which is what gives it the same font, margins and theme, and no syntax highlighter anywhere in the path.

The page is built from the table of contents and nothing else, so no member is ever decompressed. `archive_listing` reads it per format — zip through the `zip` crate's central-directory view, 7z through `sevenz-rust2`'s header parse, RAR through RARLAB's official UnRAR sources compiled in by `unrar_sys`, tar through the `tar` crate and `flate2` — and answers one shape for all: names, sizes, whether each is a directory, and whether the archive could be read to the end. A name is cleaned up to be drawn and nothing else: separators normalized, control characters dropped, the whole thing cut to 300 characters. It is never resolved, joined or opened, so an archive cannot use its own contents to reach anything.

Which reader opens a file is settled by the file's own header first and its name second. The gate a hover passes (`archive_formats`) asks only what the file is called, because it asks it of every item the pointer touches and a syncing provider's placeholder is a directory entry that can be answered for but a file that must not be opened. Which reader can open it is a question for the loader, already past the cloud gate: a `.jar` is a zip under a name the zip crate has never heard of, and a `.zip` that turns out to hold a 7z is still a 7z. An archive whose own file table is encrypted is answered with a page that says so rather than nothing, and one whose entries are encrypted but listed is marked as such.

The tree is built from the entries' paths rather than their order. A folder that exists only as a prefix (a zip written without a directory entry for `docs/`, holding `docs/report.pdf`) is still a folder, which is why the header counts folders the way a file manager would. Children sort folders first then by name, case-insensitively with digit runs compared as numbers, so `report2` sits before `report10`. A folder holding nothing but the next folder collapses with it into a single row. The rows carry a glyph from the icon face Windows ships — Segoe Fluent Icons on Windows 11, the MDL2 set it replaced on Windows 10 — chosen by what an entry is and what it is called: a folder, a page, a picture, a film, a note, a brace for code, a zipped folder for an archive, and the archive's own glyph in the summary line. The face is asked for once, and a machine that has neither is drawn without icons rather than in a face that does not exist.

The page is drawn to a cap. A hundred rows are laid out, the box the display allows may show fewer, and the rest is said in one muted line — `… and 46 more items`, or `… and at least 46 more items (the listing stopped early)` when the scan rather than the page ran out.

Nothing about the page is interactive. It does not scroll, nothing in it can be selected, and the pointer resting on it closes it the way the pointer resting on an image does. The listing is cached by path, modification time and length, so the measure pass, the render pass and a second hover read the archive once between them, and the frame is rebuilt from the hover it came from when the theme, font size or `Archives` gate changes. Reading that table is the measure, and it is the one measure here that can be felt, so it is off the preview thread and a first hover is the wait for it. An archive an *engine* lists is not read this way: what that side waits for is the engine's own listing, and a listing already remembered is a page measured out of memory.

## Office Previews

A hover onto a Word, Excel or PowerPoint document shows a page of it, drawn from the one source there is: the page the render tier produced and is holding in memory — or, where the render engine is the one that draws the document, the page that engine drew. Which is decided by `office_formats::page_engine`. What a document saves inside itself — the `docProps/thumbnail.*` metafile or bitmap an OOXML package carries, the summary information stream a legacy compound file keeps — is deliberately not read: it is a thumbnail a couple of hundred pixels across, and it costs a zip or a compound-file parse to reach. A workbook is the one page that is not simply read out of the file: Excel lays a sheet out for printing from the values in it, and works those values out again as it opens the workbook — so a page of a workbook is the page its values come out as. Holding Excel in manual calculation first does not prevent that (measured, not assumed), and setting the mode at all costs a workbook opened and closed for the asking, since Excel answers for neither reading nor writing while none is open.

`office_preview::measure` reads the source's own size (a PDF page's DIPs from the PDF engine, an image's pixels from its header, both read out of the file the render tier kept) and `render` draws it into the planned box. The size is remembered by the document and version, so the layout's several questions in one hover cost one parse; it is not remembered on the page's own file, because that file's place in the budget's order is kept beside it rather than written onto it. A size cannot outlive the page it belongs to. Shrinking a picture far larger than its box uses the box filter (the fast one) and enlarging the smooth one. What is drawn is checked before it is used: a page that will not give up its size (bytes a render cut short, or bytes something else corrupted) is dropped and the document rendered again, because a page that cannot be drawn would otherwise be handed to every later hover and each would blink. That check lives on this side rather than where the page is held because it is the side that may ask the PDF engine: these threads are multithreaded apartments, while the engine thread is not.

What a render produces is kept as a page on disk, where both engines' pages live. `document_cache` names a page for the document, the version of it that was drawn and the engine that drew it: `<key>.pdf`, `<key>.png` and the `<key>.bmp` a workbook's picture used to be written as — no longer written, still read and still cleared away, so a page a run before this one left keeps working until a new one replaces it — with `<key>.none` for a document an engine would not draw, all under `%TEMP%\rust-hover-preview\document`. The image converter's pictures are kept in `%TEMP%\rust-hover-preview\image` against a budget of their own: the two are folders rather than one because a run seeds its table from the names a folder holds, and a hashed name cannot say which budget it was written under, so one folder would make both budgets unenforceable across a restart. The engine is part of the name because the two do not draw the same page — LibreOffice's rendering of a `.docx` is not Word's. `document_cache_mb` is the budget: 256 MB default, cap 2048, and the pages least recently *read* are given up first, read off a table the run keeps beside the pages, so neither a read nor a trim is a question for the disk. A page's file used to carry its own last-read stamp, and what that cost was a write to the volume for every read of every page and a walk of the folder with a timestamp per file, on the thread that draws the hover, every time a document's hover ended. `0` is a cache holding nothing rather than a tier switched off: at nothing a page lives from the moment it is drawn until the moment the hover that asked for it ends (`hover_ended`), and the next hover draws it again. The budget is not a switch either way — an Office document has no other source for its preview, and the `Document` gate is the switch. Office's export calls take a file name rather than a stream (`ExportAsFixedFormat`, `Presentation.Export` and `CopyPicture` all write to a path), so one render does pass through a file: a scratch name of its own in the temp folder (`page-<pid>-<n>.<ext>`, which is what keeps a file left by a process ended mid-render from being mistaken for a page this one wrote), read back and deleted in the same breath, with every candidate extension removed whether or not it was the one written. The temp folder is cleaned at startup and the pages inside it are not: a scratch file a killed process left is not one the next attempt may find, while a page drawn before this run is one this run can read.

Which shape the source is decides how large it may be drawn. A page Office exported and a slide's PNG are vector or near enough, so they take the room the display has at the share `document_scale` names, the rule a PDF follows, a share below `100%` included. The picture a workbook is answered with where no printer can export a page is the exception: it is only as good as the pixels it holds, so a share of the display is read for it as the same share of its own size, and a fit is the bitmap at its size rather than an enlargement to fill the screen. It is a PNG — the same kind a slide's export is — so which of the two a page is cannot be asked of the file it is kept as, and is asked of the document's family instead (`page_is_workbook_picture`); the same question keeps the picture from being rendered again for a display larger than it. That decision is `effective_preview_scale`'s office arm, which is why `office_preview::source_kind` exists.

While a page is on its way there is nothing to measure, so the preview is the spinner's own box — `office_preview::WAITING_BOX`, the size of the arc and the halo that fades past it — placed at the size it is rather than fitted to the display, and flush at the pointer's own corner (the one of the four quadrants the display has room for the spinner in) and a pixel off the pointer, because the preview window is what a mouse message at the pointer lands on and the pointer has to keep clicking and probing the file it is waiting on rather than the spinner waiting on it. Every kind of wait is placed that way (`waiting_placement`) — the arc's own box at the pointer's corner, a decode's and a browser's as much as a page's — so what stands in for a preview that is not ready is one thing to read wherever it appears, and the box the preview will arrive in is kept for the preview. The spinner is the arc and nothing else: its frame is transparent, so what is behind it is the desktop rather than a backdrop, and its composition skips the backdrop setting (`image_background` and `vector_background` alike). The arc carries a soft dark halo so it reads over a light file list as well as a dark one. The spinner goes up once the wait has run past `spinner_delay_ms` (a quarter of a second by default), the one delay every kind of preview is answered by, a page Office is rendering included — for the load that may be about to finish: the window is hidden while one runs, so a decode taking a few milliseconds goes straight from nothing to the preview rather than flashing a spinner, while a page is an Office start away and is never that load. A preview still on its way follows the pointer: the spinner is placed again as the cursor moves along the item, and the page that arrives replaces it where the pointer is. Moving within the item never reaches the load at all — the hook answers a move over the file it is already showing with nothing but a fresh hover delay, so no `Show` is sent, no generation moves and nothing is cancelled while a cursor keeps moving over the file it is waiting on. A pointer that moves _onto_ the spinner is the same case the other way round: the box sits a pixel off the hand and follows it, so a hand settling into it puts the pointer over this app's own window, where the file under it cannot be read at all. The spinner therefore publishes the region it occupies as one that holds the pointer, the way a scrollable text preview does, so a hover is not dismissed from there and the page it is waiting for not thrown away with it: dismissed, the render still finishes but lands for a hover that is gone. Leaving the item and coming back is a `Hide` (which cancels the load, not the render) and a re-show the same-file rehover latch holds off; a render still running is never abandoned by either, and a request arriving for a document whose page landed while it waited is answered from the cache rather than by Office again. Only the place is recomputed — the size the hover measured, its `Avoid Filename` region and its scale — so a tick of following costs a cursor read and a placement, and the window is moved only when the place it comes out at has changed. A keyboard hover's preview is the item's own and follows nothing. The page is asked for in the box that family's pages have (`default_page_size`), which is what a slide's export width comes from.

The render tier is asked for by the preview loop rather than by a hover, because the loop is what knows which hover is on screen: a request is made the moment a document is missed, so what a page costs is its render and not a wait in front of it, and the tier drops a superseded request rather than rendering every one asked for. When the page exists, `OfficeRenderReady` arrives through the same channel every other message does and the hover is replayed — the measure now finds the page, the load draws it, and the window is given the page's own box and frame by the one `UpdateLayeredWindow` that paints it, never resized ahead of that paint: a layered window shows the frame it already holds stretched into whatever box the window has, so a spinner resized into the page's box first would be a bar across the screen until the page landed. That replay is an _upgrade_, not a new preview: what is on screen stays while the page is loaded, because hiding the spinner for the second a large picture takes to decode is a blink the user reads as the preview failing. A render that lands after its hover has gone is dropped, and the page it produced is released with the hover it was meant for — kept only as far as the budget allows. The wait is capped at twenty-five seconds from the hover: past that the preview comes down rather than spinning for good, and the file is left alone for two minutes so it is not asked for again on every pass.

A rendered page is drawn by the existing PDF path — Word and Excel export page 1 to PDF, and `pdf_preview` renders it — so a rendered document and a PDF preview are the same picture drawn by the same code. PowerPoint is the exception and exports slide 1 as a PNG, because the alternative is a PDF of every slide in the deck; it is exported at the width the preview asked for, bounded between 640 and 1920 pixels.

Two members of the object model are not what their VBA spelling suggests: a slide is reached through the collection's item, `Slides.Item(1)`, because asking `Slides` itself for one is answered with "member not found"; and Excel's export needs a printer, because what a workbook's page is is what it prints. Where there is no printer, `printer_installed` says so up front — Excel answers `ActivePrinter` with "unknown printer (check your Control Panel)" — and the workbook is answered with `CopyPicture` of the used range's top-left instead, written out as a PNG: the clipboard's bitmap is decoded and re-encoded, which costs one decode and one encode on the engine's own thread for a picture of flat-coloured cells that is several times smaller as a PNG than as the bitmap it arrived as. Writing the DIB out raw as a BMP was what this was, and what that cost was a page of five to forty megabytes for the same picture. A refused copy is asked for again a moment later, because the first ask of a workbook Excel has just opened is regularly refused ("unable to get the CopyPicture property of the Range class") while the sheet is still being laid out, and the next ask is answered. The picture is taken off the clipboard rather than left on it, because leaving it there makes Excel ask, on its way out, whether a large amount of information should stay on the clipboard — a dialog no one is present to answer. What it shows is the corner of the sheet rather than its printed layout, which is the most a machine without a printer can produce, and it is copied only as far as a preview could ever show it: the window is cut down in proportion until what it would draw fits a budget smaller than any display (900x700 pixels, because a picture is shown at its own size rather than fitted to the screen) so tall rows keep as many of them as the budget allows instead of being halved until only a sliver is left. Only the range's own measurements are asked for to cut it down, never its cells. On a machine that has a printer, an export that comes to nothing is taken as the instance declining rather than the document failing — the instance a retry is about to replace — so no picture is asked for there until an attempt is already a retry, where it is the last thing tried before the document is given up on. Copying out of an instance that has just refused to export is a detour of its own: the copy is refused by the same instance, after the retries the clipboard needs, and what the first attempt should be is the fresh instance the retry is going to ask anyway.

## Engine Lifetimes

Three engines driven out of process can be kept warm between previews — the Office application a family's page was rendered by, the browser that draws every SVG and font specimen, and the LibreOffice instance — and what bounds each is one of two rules, chosen per engine by the `Persistent` toggle at the top of that engine's TTL submenu (`Engine → Microsoft Office TTL`, `LibreOffice TTL`, `WebView2 TTL`).

Marked persistent, an engine is kept for its idle time whatever the user is doing: the clock runs from the last page or document it drew whether Explorer is in front or not, and `Indefinitely` is never let go of at all. `0 seconds`, the bottom of the list, is the other end — an engine let go the moment it has drawn a page.

Not marked persistent — how every one of them starts, and how all three are bounded unless someone says otherwise — an engine is kept while the user is anywhere near Explorer and let go once they are not, and its idle time is not consulted at all. What keeping an engine buys is the wait a hover would otherwise pay, which is only worth anything while a hover can be made: with every Explorer window minimized, or every one behind the region a maximized or fullscreen window in front covers on any display, there is nothing on screen for a preview to be about. `Engine → AFK Timer` is how long that state has to last (an hour down to a quarter of a minute, a minute by default) and it counts the whole time nothing has been reachable rather than one engine's last page, so a fullscreen application entered for a minute costs the engines their warmth and nothing else, while stepping back into Explorer a second before that costs nothing.

What decides it is the Explorer hook and nothing else. `ExplorerState` is already worked out for the loop's own sleeps — reachable is a window that is showing and out from behind whatever is in front of it, which is where the multimonitor rule lives — and each read of it publishes the answer into `app::afk`, whose clock is the whole of the state either rule needs. What counts as an Explorer window is the browser frame's class and nothing else (`cabinetwclass`, `explorerwclass`, the same test the window walk is made with): the rest of the shell is explorer.exe too (the desktop `Progman`/`WorkerW`, the taskbar, the Start menu, the search box), and reading one of those as Explorer left the state on `ActiveFocus` with the desktop in front, which is what Show Desktop leaves there. The engines ask that clock on the look they already take for their idle times — the Office worker twice a second, the LibreOffice thread once a second, the browser every quarter of one while up — so nothing polls, wakes a sleeping thread, or costs a hover anything, and an engine is never let go of while something it drew is in front of the user: a preview is only up while Explorer is, and the pages an engine drew are kept apart from the engine that drew them.

An engine can also be asked for before a preview needs it, and it is the hover that asks rather than the setting: once the pointer has settled on a document whose page an engine draws — a sixth of a second, `WARM_SETTLE_MS` — the preview loop asks that engine's tier to come up, which is the launch a conversion begins with and no conversion at all. What that overlaps is the rest of the wait for the page: a launch is a second or more, and the alternative is paying it after the pointer has stopped. It is asked once per run and only where a page is actually owed (a document the engine has already drawn, one it has turned down, and a kind switched off are not asked about) and is a no-op for an engine already up. A setting that keeps no engine is answered with nothing, and the rules above still decide when what was started is let go of. LibreOffice is the engine warmed that way (`warm`). Office is not, and that is its tier's shape: its worker is handed a document to render (the slot it takes is a `RenderRequest`, and the application is created inside the render that uses it), so "start the application with nothing open" is not a request that tier can be given without taking it apart, and the two converters have nothing to warm, since neither keeps an instance between files.

Nothing is let go of mid-work either. The Office worker asks only with no request pending, the LibreOffice thread between documents, the browser with nothing on screen. What each does to be let go of is unchanged — a `Quit` and a verified termination for an Office engine, the engine and its launcher ended together for LibreOffice, the controller closed and the window destroyed for the browser — so nothing on the release path is new, and every process ended is still one this app started and confirmed the identity of.

## Office Render Engine

The engine is the Office application itself, driven late-bound through `IDispatch` and called by name, so nothing depends on a type library, a build step, or the installed version. One engine is created per family on the first render that needs it and kept for `office_engine_idle` after that family's last one (10 min default, `0` for one let go as soon as it has drawn a page, or `indefinitely`), then quit; a family never has two, because an engine is started only once no process this app began for that family is still running, and a replacement waits for the process it replaces to be gone before it is asked for. The families are held side by side rather than one at a time, so a folder holding a document, a workbook and a deck costs one Office start each rather than one every time the pointer crosses between them, and each is let go on its own clock. The thread that owns them ends with the last one, so an app left alone ends up with neither an Office process nor a polling thread — an engine kept indefinitely being the one setting asking for both. That thread is apartment-threaded and pumped: OLE automation marshals its calls back into the thread that made them, and a thread not retrieving messages deadlocks.

Automation may attach to an instance the user already has running (these applications are registered for multiple use), so the engine is careful with what it touches. Whether the instance was already visible is read first: a visible one is the user's, and is neither hidden, quit nor ended, while the settings it is given (dialogs suppressed, macros switched off) are taken for each render and put back the moment that render is over. Only an instance this app created is hidden and quit, and the process it started is recorded (the process list is walked before and after creation, and the one that appeared is the app's) so a render which never returns can end every engine the worker was holding. Documents are opened read-only, without touching the recent-files list, in a hidden window all three support even in a visible application, and are closed without saving.

None of those calls can be cancelled or bounded: a modal dialog inside Office holds the COM call for as long as it is up. What that costs is one render, never the tier. Ending an engine counts as work like any other, so it happens inside the same marker, and a worker inside one piece of work longer than any of them take is given up on when the next hover arrives — every Office process this app started is ended, the worker generation moves on, and a fresh worker takes the request. The abandoned thread is left where it is, since nothing in user mode can end a call it is inside, and everything it does on the way out is conditional on it still being the current worker: it can neither clear the live worker's thread id nor end an engine the new worker is using. A panic is contained the same way — one document's failure is that document's, and the thread goes on — and the thread id is handed back however the thread ends, because losing it would leave every later request posted to a thread that is gone.

Letting an engine go is a call of its own, and an Office application finishes quitting while its automation client is pumping: one told to quit and then abandoned can sit there for good, which is what a left-behind Excel instance looks like. So the quit is given a moment of pumping on the worker thread, and a process still there after it — one this app started, verified as still being that application — is ended rather than left running. That is the idle path: an engine being let go because it has refused a page is not asked to quit at all. A quit is another call into the instance that refused, and one that is not answered is pumped for seconds before the process is ended anyway. An instance that is the user's own is never ended by this, whatever it answered: `attached` is what stops it, the same as everywhere else. A superseded request is dropped rather than queued behind, and the newest hover is the one that runs.

A render is not quite invisible either: Office shows a progress window of its own while a page is exported — the wide, short "Publishing…" bar — and none of the settings an engine holds keeps it off the screen; it is shown whether or not the application it belongs to is visible. It is a progress bar, so a render watches that process for the window being _shown_ — `EVENT_OBJECT_SHOW`, filtered to the process, with the class as the check, since a window's title is the machine's language and this is not — and hides it the moment it is put up; a sweep of the process's windows runs beside the hook as the half that does not depend on an event arriving. Only a process this app started is watched.

## Video Preview Engines

A video is played by one of two engines, decided once per file, in three parts (`media_engine_plays`). Whether there is anything of FFmpeg's to fall back *to* comes first (`codecs::plays_video_natively`): on a machine with no `ffplay` the engine is the only player there is, the file is never opened for the question, and everything below is skipped. Then the name — which of the two lists in `config.ini` carries it; `[ffmpeg]` is not put to the engine at all. Last is the file's own answer: the engine is asked whether it can decode *this* file as a source reader over it whose first video stream can be handed back as frames at all (`video_player::plays`, held per file and version, so a hover, a layout and a pin after it pay for one probe). That probe asks the engine's own two parts — a decoder for the stream, and a converter into the format this app composes in, the video processor, which a source reader has only where it has been told to insert one (`MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING`): asked without it the reader is asking every codec to deliver RGB32 on its own, which no H.264 decoder does, and every film of every kind is answered no for a reason that has nothing to do with the file. What the probe still cannot answer for is the pipeline the engine plays through, which can have no mode for a file both parts accept — an H.264 film in 4:2:2 or 4:4:4 chroma is decoded and converted by a reader and never drawn by the engine — so the last word about a file is the app's own: a session with a surface over the file that has handed over no frame at all after `FIRST_FRAME_GIVE_UP` is a session failing at the file (`failing_path`), a file written down that way (`mark_unplayable`) is FFmpeg's player's from then on — in the same map, read out by the same question, so the routing, the layout and the load agree — and the hover is replayed for the player to take what the engine made an empty box of. That is what makes the lists safe to be wrong about: they decide which engine is asked and never which one ends up playing. The engine is preferred because of what only it can be told: a pause, a seek and a position that are real rather than a player ended and begun again at a second, and frames this app draws itself — which is what lets a pinned window of one be resized, and dragged by its picture. The two are the same preview to the user (same box, placement, backdrop, spinner) because they are the same preview to the app: what differs is only which side of the window the picture comes from. Whether the file is played here at all is asked of the file itself before either engine is reached: a video is a video by what it holds rather than by what it is called.

Measuring a video is a probe, and the probe is the one thing about a video done off the preview thread. It is `ffprobe` and an `ffmpeg` cropdetect pass — two external processes run at once, the hover waiting for the slower — so a hover that read it would spend that time inside the layout with nothing it could draw. What is done instead is what a document with no page rendered for it does: `get_media_dimensions` answers the waiting box for a video it has no probed answer for, the hover is laid out as the wait, and the probe runs on its own thread. When it answers, the hover is replayed from the message it came from (`VideoProbed`, `replay_where_the_pointer_is`), and that second pass finds the geometry in the cache. The replay is a continuation rather than a new preview, so the spinner stays up — the same clock, so a probe answered inside `spinner_delay_ms` does not restart the delay, and the same frame on screen. The answer is held whether or not anything is waiting for it: a geometry and the lack of one are both answers, and holding the lack keeps a file neither reader will open from being probed on every hover (`ProbedGeometry`). Each child is given `VIDEO_PROBE_TIMEOUT_SECS` and killed when it outruns it, a bound the wait did not have: the hover waiting on a probe is not waiting on an engine. A file slower than that is answered with a video placed without its crop while a file neither child says anything about is answered as unmeasurable and kept that way. The hover is answered whatever became of the probe, a panic included: the notify is reached through a `catch_unwind`, because a thread that unwound past it would leave the spinner standing over a file it had finished with. What is left on the preview thread is a cache lookup, which is what `start_video_playback` reads its crop filter from — the one thread that must not wait for two processes never does.

How large a video is shown is `video_scale`, a share of the file's own size, and it is a size for the waiting box and the player's window alike, because what the layout places is one box that both are put in. The share is the rule a picture follows rather than a page's, for the reason the probe exists: what a video preview is measured and placed by is a frame of it, a bitmap, so a percentage of it is a percentage of its pixels and a fit is the largest size the room beside the pointer allows. `effective_preview_scale` decides it, so measure and render cannot disagree. The one case it is not asked about is the hover still waiting for the probe: there is no video to place yet, so what is on screen is the spinner's own box, and the setting is read when the replay lays the measured video out.

An animated picture has a size of its own the same way, and the one thing that cannot be read from its name. `animated_scale` is asked for a GIF, a WebP or a PNG holding more than one frame, and `preview_scale` for one that does not — a still GIF and an animated PNG are both files a name cannot settle — so `image_is_animated` walks the file's own structure without decoding anything: GIF frame blocks, the WebP `ANIM` chunk, the PNG `acTL` chunk, the same things the loader insists on before it calls a file an animation at all (a GIF whose second frame never arrives is loaded as a still, and the setting follows the loader rather than the name). It is asked from `effective_preview_scale`'s picture arm, and the frames are decoded at the size it answers, because the loader is handed the same scale the layout was. Where the two settings name the same share, which is a fresh install's state because both start at `100%`, nothing is read at all: a file is only opened for this when the answer could change what is drawn.

**FFmpeg's.** `ffplay` is started per hover and its own window _is_ the preview, the layered window staying hidden while it is up (see Video Process Lifecycle). It plays what the engine cannot open, and its geometry comes from `ffprobe` and a cropdetect pass, so a video letterboxed inside its own frame is cropped to what is in it.

**The media engine's.** Drawn by the app. `video_player` creates the engine in _frame-server mode_ — the mode it is in when no playback window or visual is named, rendering mode having to be asked for by naming a playback window — and then asks it for frames rather than letting it draw: it decodes, paces itself, plays the audio and loops (the engine's own `SetLoop`) while this side calls `OnVideoStreamTick` once a tick and takes the frame it says is due with `TransferVideoFrame`, into a bitmap of this app's own. That frame is then an ordinary one, composed and drawn by the same code every other frame goes through, which is why a video the engine plays lands in `Follow Cursor`, `Best Position`, each `Avoid` mode, the keyboard path and the backdrop setting for free rather than through a second implementation of each. The crop is FFmpeg's other half here rather than a filter of its own: the rectangle cropdetect settled on is handed to the engine as the _source_ rectangle of its frame transfer — `MFVideoNormalizedRect`, a share of the frame rather than pixels (see `video_player::Crop`) — so a video letterboxed inside its own frame is cropped here as it is there, and the box, which is placed at that crop's shape, is filled by the picture rather than by the engine's black border around a whole frame fitted inside it. Frame-server mode is the _default_, and what the engine requires of a frame-server caller is an event sink (`MF_MEDIA_ENGINE_CALLBACK`) and the frame format (`MF_MEDIA_ENGINE_VIDEO_OUTPUT_FORMAT`), the format being the one this app composes in, a D3D `A8R8G8B8`, whose bytes are the same in the same order as the BGRA the rest of the app works in. A frame is only there to be taken once the engine has current data: `OnVideoStreamTick` reports a frame as due some while before one is queued, and a transfer asked for in that window is _failed_ rather than answered late, so the session asks `GetReadyState` first — without it an `.mp4` never plays at all.

Nothing about it is a process: no player to start, no window of its own, no PID to record, no job object to adopt it into, no style monitor — every one of those belongs to the FFmpeg path because a player is a separate program drawing in a window this app does not own. What it costs instead is one copy of each frame into the bitmap the engine delivers into, the one thing per frame that is not free, and what it is bounded by is the same rule as everything else: the file is opened as a stream rather than read into memory, and the source reader that measures it is dropped before anything is played.

Measuring is a question of its own, asked of the _source reader_ rather than of the engine, because the layout must know a video's size before it can place one and because the answer is also what decides whether there is a preview at all: a file the engine is the one for and no reader claims — an `.mkv` whose codec this machine has no decoder for, a container whose handler Windows does not ship — is answered with no size, which is how the layout drops it rather than opening a box nothing would be drawn into. A file FFmpeg's player would try is placed at a 16:9 default instead, because `ffplay` will play it anyway, and the two are told apart by the engine's own question rather than by the name. Where FFmpeg is the one installed, a probe that comes back empty falls through to the engine's own measurement rather than to the default.

The engine's frames come back into the load the ordinary way, so a video preview is installed like any other: it is the media kind that is new (`NativeVideo` rather than `Video`), and the two kinds are what tell `render_layered_preview_at` whether the frame it is holding is one this window draws or one a player is drawing over it. What ends a video is unchanged either way — the pointer leaving the file, another preview taking its place, the `Videos` gate closing, a display change, a resume from sleep, the app exiting — through the same call, and the media engine is let go there rather than killed there. Its shutdown asks nothing of an outside process, so it needs none of the kill-only discipline stopping `ffplay` does. It is let go by the thread that started it and by no other — a session belongs to the thread that made it — so the take-down that runs when the pointer leaves the file, which is the Explorer hook's and not the preview loop's, kills the player process and leaves the engine to the loop's own take-down: an ending asked for from the wrong thread is a call that does nothing while the sound goes on playing (`hide_preview`, `kill_player_process`, `stop_video_playback`).

A video the engine plays lands with a frame of the layout's own box and nothing drawn into it, and the difference between that and every other load is that the frame is not a picture of the file: what its load carries is the placeholder the engine's own frames are written into, and the engine has only been *asked* to play — `Load` and `Play` answer before the file's header has been read, and the first frame arrives on a tick of its own (`take_native_video_frame`). Opening the window on that placeholder is a flash of the backdrop at the start of a hover: its pixels are mostly transparent, so composed over the backdrop the tray keeps for pictures it *is* that backdrop — the checkerboard by default — and what the eye catches is the backdrop alone until a frame lands. So the install holds the window back rather than putting it up: `FirstFrameWait` keeps the box the hover's layout came out at and the hide count the install was under, and the tick that takes the first frame is what puts the preview up — the frame painted at that box, and the window shown after it. Either answer moving on drops the wait rather than revealing it: a newer hover installs its own media and puts its own window up, and a hide is the pointer having left the file (`HIDDEN_EPOCH`). A session that already has a frame in hand is not held back at all — the frame is taken where the media is installed — so a hover that lands back on a file that is playing, or on one that was taken down and asked for again, is a preview at once. A hover left waiting is nothing on screen rather than something wrong: an engine that never hands a frame over is a failure `failing_path` already answers, three seconds in, by handing the file to FFmpeg's player.

Which files the engine will play is a property of the machine: whatever Windows 11 decodes out of the box plus whatever a codec extension from the Microsoft Store has added. That is what the tray's `Codecs` submenu is for, and why the app names no codec of its own here and bundles no decoder.

## Sound Previews

A sound is the one kind of preview that is not the file: what a hover shows is a card of what the file holds — its name, format, sample rate, channel count, and how much room a second of it takes — and the sound itself plays behind it. The card is a page of this app's own, painted by the text layer like an archive's listing and coloured by the same theme, so a sound is a painted preview in every way that matters. What is heard is played by one of two engines, and which one is the machine's answer rather than a setting: the Windows media engine where its own decoders reach the format, and FFmpeg's `ffplay` where they do not. The engine plays inside this app's process, with no window, no process to supervise and a clock that can be read back out of it, while `ffplay -nodisp` is a process that has to be started and killed; so the answer that starts nothing at all is asked first. The file reaches the engine as a stream over the Shell's verbatim path with the *plain* form of that path beside it as the name the source is resolved by — a media source is resolved by the name it is handed, a verbatim path is not a URL, and the refusal arrives on the engine's notify callback *after* `Play` has already answered, which is a sound that probes as playable, draws its card, and then sits with a clock that never moves (`plain_name`).

Which engine a file is played by is one probe, run off the preview thread, asked in the same place and the same way a video's geometry is. On the engine's side it is a source reader over the file: the first audio stream's own media type is read for the facts the card is drawn with, and then the reader is asked for *decoded* PCM on that stream — the whole of "can this machine play this file", because a reader can only hand back what a registered decoder produces. On FFmpeg's side it is an `ffprobe` pass over the container, read for the audio stream's codec, rate, channels, bitrate and length, and whether there is an audio stream at all; the same `AUDIO_PROBE_TIMEOUT_SECS` bound and after-the-fact kill the video's two probes get are what keep a file that never answers from holding a hover. Neither engine answering is a hover answered with nothing: no card is painted for a file nothing will ever play.

The answer is held per file and per version in three states rather than two — not asked, a track, or nothing to play — because a hover waits on one of them and is dropped for the other. The wait is the same one every measured preview has: `audio_box` answers the waiting box for a file no probe has read, the hover is laid out as the spinner at the pointer, the probe runs on its own thread and replays the hover when it answers, with the card's own layout measured on the same thread and held under the same room-and-settings key an archive's page is (`measured_off_the_tick`). And it is the same probe that settles the containers a name cannot: an `.mp4`, `.mka` or `.ogg` whose bytes hold a sound and no picture is a file the video probe finds no shape for, and what that arm of the video probe does now is hand the file to the sound probe — a sound it can play is remembered as one (`remember_audio_only`), and the router, which asks that verdict before it asks the video list, answers the replayed hover as the sound it is.

How far the sound is and how long it is is the player's own answer, in the two forms the two engines give it. The Windows engine reports position and duration directly, and that is what the card's clock is drawn from; FFmpeg's player reports nothing at all, so its position is this app's clock over the moment the player was started and the length is the probe's. Either way the card is repainted while the sound plays, at `AUDIO_CARD_REPAINT`, four times a second: the page is laid out again into the box it was already drawn at, the clock and the bar under it are what differ. A file that does not say how long it is gets a block crossing the bar instead of a filled part of it.

The card's own name is the other thing that moves, and it moves only where the card has no room for it. A name is not part of what a card asks the display for — the width is the facts line with the clock beside it, or the narrowest bar, whichever asks for more — so a name longer than that is drawn *whole* and clipped to the card instead of being cut short with an ellipsis, and no card is ever wider for what it is called. What moves it is a scroll the preview loop owns (`NameScroll`), put up with the card the moment it is installed and advanced by the repaints that follow: the name rests at its beginning for a second, travels left at about one advance of its own font a 100 ms — a speed every card is scrolled at, however large it is drawn, because the advance is the font's and not a number of pixels — until the end of it is in sight, rests a second more, and comes back the way it went, ping-ponging for as long as the card is up. The page is handed how far the name has gone and nothing else: the name's box does not move, its origin does, and the box is what clips it, so a repaint is the same page laid out again rather than a scrolled surface blitted somewhere (`paint_run`). And the cadence follows from the motion: a card whose name is being scrolled is repainted at `AUDIO_NAME_REPAINT`, thirty times a second, while a card whose whole name fits keeps the clock's own cadence.

How loud it is, is two settings rather than one. `Volume → Video` is the soundtrack of a video, silent by default, and `Volume → Audio` is a sound file, quiet by default — a video is looked at and its soundtrack is as likely a distraction as anything, while a sound file *is* the sound, so one setting for both would mean turning a film up to hear a song. Both offer the same ten levels and both are read at the moment a player is started, which is also the moment the next hover is answered with: a level at `0%` starts no player at all — the card is drawn, its clock still and its bar empty. What ends a sound is what ends a video, through the same call: the pointer leaving the file, another preview taking its place, the `Audio` gate closing, a display change, a resume from sleep, and the app exiting, with the engine let go of in this process and FFmpeg's player killed as the process it is.

Normalize is the one thing a level is read against that is a property of the file rather than of the app: a file's loudest sample is measured — FFmpeg's `volumedetect` decodes every sample and reports the peak in dB relative to full scale — and what brings that peak to full scale is a gain the file is played at, multiplied into the level. The measurement is the one read of a sound that is not a header: asked beside the probe, on the same off-the-tick thread and under a bounded wait of its own (`AUDIO_GAIN_TIMEOUT_SECS`), and held per file and version next to the track (`audio_track::gain`). A file that cannot be measured (no meter, a read past its cap, no sound stream) is held as a gain of one, so it is played as it holds and not measured again; a file of *silence* is that same answer, its peak being `-inf dB`. Which player starts follows from that answer rather than from the machine's decoders: the Windows engine can only be handed a level (`SetVolume` is attenuation where `1.0` is the whole of it), so a file with a gain to apply is started in FFmpeg's player, whose gain is a filter (`-af volume=…`) and whose level is folded into it — the two multiply, and a normalized file at `Volume → Audio` 10% is heard at a tenth of full scale rather than at ten times it. The card's clock follows the player that was *started* rather than the engine the machine's decoders would have made of the file, which is what `audio_clock` reads `started` for. The setting is read where a player is started, so it reaches the next hover — with one exception that is a file rather than a hover: a file probed while the setting was off has no gain and is played as it holds, and what measures it is a read on its own thread, so the hover that asked for it is answered the old way and the one after it is not (`spawn_gain_scan`). On a machine without FFmpeg there is nothing to measure a peak with and nothing to apply one with, and the row is greyed in the tray. A video's soundtrack is offered the same switch and the same measurement as a setting of its own that starts off: `Volume → Video → Normalize` is read where the video's player is started, its peak measured beside the geometry probe — the same read of the same file on the same thread a hover is waiting on (`measure_video_gain`) — and the gain folded into the `-af` filter the film's level was already carried by. What the default buys is what a hover pays: a film's audio is a decode of the film, and one is asked for only where the switch was thrown.

Where in the file it starts is the third question the `Volume` submenu answers and the one only a sound is asked — `Volume → Audio Seek`, a submenu of its own below the two halves, because a file met again is as often wanted from where it was left as from its beginning. The four answers are the memory, the beginning, the middle and anywhere at all, each read at the same moment the volume beside it is: as a player is started, so a click reaches the next hover rather than moving the sound on screen. Two are arithmetic on the file's own length — the beginning needs nothing known, and the middle and anywhere are shares of a length read where the file is probed, the reader's presentation on Windows' side and `ffprobe`'s report on FFmpeg's — because a share of a length nothing has read is not a place, and a hover whose file says nothing about its length plays from the beginning. The third is the memory, the one thing this app keeps anything for: the position each file was last left at, held per run and written under `%TEMP%\rust-hover-preview\audio\seek.txt` across runs, keyed by a hash of the path, and bounded at a gigabyte by a ceiling in the code and in neither `config.ini` nor the tray — an entry is a few dozen bytes, and what a memory at the ceiling gives up is the sounds nothing has listened to in the longest time. The position is that of the player — the engine's own clock, or this app's over FFmpeg's start plus the second it was put in at — and it is written down as the card is repainted, the only moment this side knows it, with the end of a hover writing what it has whatever the interval says (`audio_seek::flush`). Nothing is written while the tray is on any of the other three answers.

Being taken to that second is each engine's own arrangement. The Windows engine is *told* — `SetCurrentTime`, a number of seconds — but not before it has read the file's own header, and the header is not there the instant `Load` answers, so a session asked to start somewhere keeps the request and makes it on the first tick that finds the engine loaded: the tick a sound's own preview runs at, a sixtieth of a second, which is what makes what is heard of the file's beginning the time a header takes to read rather than the quarter of a second until the card's clock is next looked at. A seek the engine never becomes ready for is given up on after a few seconds and the sound plays from its beginning. FFmpeg's player is *launched* at the second instead — `-ss`, an option of its input rather than of the player — which is a file read from that point rather than one played towards it; what the card's clock is counted from there is the moment the player was started *and* the second it was put in at. The two engines therefore agree about what is heard without agreeing about how they got there.

Where a sound goes when it reaches the end of the file is the beginning of it — 0:00, whatever the file and whatever the setting started it at — and the two engines get there differently. The Windows engine is asked to loop the presentation (`SetLoop`), and what that restarts is the file rather than the second the engine was taken to. FFmpeg's player cannot be asked for that and is not: the position `ffplay`'s loop seeks back to *is* the position it was started at — `-ss` is the one value that seek-back reads — so a sound dropped half way into a file would go round the second half of it for as long as it was hovered. What plays a sound given a start position is therefore a player handed the second and no loop, which `-autoexit` ends where the file ends, and what the preview loop starts in its place is a player of the whole file that loops from the beginning (`wrap_audio_player`): every pass but the first goes back to 0:00, and what lies between two passes is the time it takes to start a player — the reason the pass after the first is started on the tick the player's exit is found rather than at the next card repaint. The clock moves with the player, since it is this app's own over the moment a player started and the second it was put in at. A player that stopped before it had played anything (no output device, a decoder that will not have the file) is not started again, and the card behind it is left with no clock at all. What separates the end of a file from a failure is time, and the length a file says it has bounds the pass that time is measured against rather than deciding it, because a container's own length is a header's reading of itself and is a little out for some formats.

## The `Codecs` Submenu

The tray's `Codecs` submenu lists the engines and codec extensions a preview can lean on, grouped as `Videos`, `Audio`, `Images` and `Engines`, with a row that is present carrying a check glyph and a row that is missing carrying a cross. There is no `config.ini` key behind it and nothing to configure — what it reports is what the machine has. A missing row that has a page to be got from is pickable, and picking one asks whether to open that page; a missing row with nowhere to send anyone is greyed; a present row is inert.

What it is for is the question a user asks when a preview does not appear: a `.heic` with no preview is a greyed `HEIF (HEIC)`, and an `.mp4` with no preview on a machine that has neither engine is both rows greyed. It is also how the app can name a codec it does not carry and send a user to where that codec is installed from without installing or fetching anything itself: the pages it opens are the ones the README names, handed to the browser the user already has, and only after they have said yes.

Each row is asked of the place the thing would be used from rather than of a package list, so a row is checked only where the capability really is there. A video decoder is asked of the media stack's own registry of decoders (`MFTEnumEx`, filtered to the compressed format that decoder takes as input), the same question the engine answers when handed a file — so a codec extension installed but not registered answers honestly as missing; an audio codec is asked of the same registry under the audio category, the one row in that group that is a package rather than something Windows ships (Vorbis and Opus are the Ogg family's audio half and arrive with the extension that carries Theora). A picture format is asked of the imaging factory's own components (`IWICBitmapCodecInfo` and the MIME types it claims), which is how a `.heic` is found to need _two_ packages: the HEIF extension carries the container and the HEVC or AV1 decoder carries what is inside it, so the `HEIF (HEIC)` row is the container and its decoder together — and the page a missing one opens is that same two-package answer read once more. An application that draws a page is asked for by its ProgID, the same test the render tier makes before driving one, and it does not start it; the browser is asked through the loader's own version query; and the PDF engine is asked whether its WinRT class is registered at all, because it is opened with a stream rather than with nothing and there is no cheaper way to ask it something.

The answers that are kept are FFmpeg's own — whether its player is installed, which is asked on every video hover because it is what routes a video to one engine or the other, and whether the player *and* the meter a sound's peak needs are installed, which is what the tray's `Normalize` row is read against. A hover must not go looking through the `PATH` for either, so both are read from a cache the tray's menu build clears. That is also what makes installing FFmpeg take effect without a restart.

## Video Process Lifecycle

`ffplay` is the only long-lived external process the app starts itself — an Office engine is another, but COM is what starts it and its discipline is its own. It is started per hover, its own window is the preview surface while the layered window stays hidden, and it is stopped when the hover ends — switching to another video, switching to an image, leaving the file, disabling previews, a display change, or system suspend.

A player is a process, and a process has a window to create before anything of the file is on screen — so what stands in for the video while it starts is the waiting spinner, at the pointer every other wait is shown at (`VideoStart`). The frame the player was started for is held until its window is there rather than handed to `CURRENT_MEDIA` with the process: a wait is what this app's window is, and the frame would be what the spinner was showing instead of the arc. The handover happens on the first tick the player's own window is up — `VIDEO_HWND`, the handle the no-activate monitor already finds and styles — and this app's window goes with it. A player that never puts a window up is not waited for forever: one that has exited, or one whose hover has moved on before its window was there, is ended where it stands — `kill_stray_video_process`, the job object and the record the player is written down in are what answer for a process this app started — and one that outlives `VIDEO_START_WAIT_SECS` without a window is given up on (`player_wait`).

Stopping is kill-only: the app requests termination and never waits for exit, because a process stuck in kernel I/O cannot be terminated by anyone in user mode, and an unbounded `wait` on the Explorer hook thread would freeze hover tracking for good. The PID of the last spawned player is therefore kept until the process is confirmed gone rather than cleared on the spot, and two checks recover a player that survived its stop: the Explorer hook re-checks the recorded PID once a second while no file is hovered and no keyboard preview is up, and the preview thread re-checks it before spawning a new `ffplay`, so a new preview cannot stack a second player next to a stalled one. Both checks terminate only when the recorded PID still belongs to `ffplay.exe`, read from the same process handle that is terminated, so a recycled PID can never hit an unrelated process; the record is cleared only after the process is gone, through a compare-exchange so a freshly spawned player's PID cannot be wiped by a stale check.

## Started Processes

Three things this app starts are not its own to keep: the Office application that draws a document's page, the browser that plays an animated document, and the `ffplay` a video preview runs in. Each is ended where it is ended deliberately — an idle engine let go, a player stopped — and what `engine_processes.rs` is for is the ways an app does not get to choose: ended from Task Manager, taken down by a crash, closed by a logoff. A process that outlives the app that started it holds a profile folder, an Office licence seat or a file handle, and a leftover Office engine is also the thing a new engine would be a duplicate of. The two probes a video's geometry is read by are shorter-lived than any of them and are adopted for the same reason: one left behind by a crash would go on reading a file nobody is waiting for.

Two mechanisms cover that, and they cover different halves. A job object with `KILL_ON_JOB_CLOSE` holds every process this app adopts, and its handle is deliberately never closed by the app: what closes it is this process ending, however it ends, and the system ends everything in the job with it — the only mechanism that asks nothing of a process that is dying, which is exactly what a crash is. What the job cannot take — a process already inside a job that will not nest is how that happens — is covered by a record on disk: each run writes what it started to `%LOCALAPPDATA%\rust-hover-preview\engines\<pid>.state`, and the next run reads every file there and ends what the runs that are gone left behind. A run still alive is another session of the same user and its engines are its own; a browser left by a version that wrote no record is reached the same way, through the profile folders a run leaves, each named for the run that made it. The player is written down with the engines and is not one of them: it is the picture the user is watching, so the wholesale ending a tier is let go of with — a preview type switched off in the tray, a worker given up on — is not its to receive, and a video that is playing is not taken off the screen by a setting that has nothing to do with it. What ends a player is its hover ending; what answers for one this app never got to end is the record, and the record is held until the process is confirmed gone rather than being struck off when the kill is requested, because a terminate is a request. The file is written when something is started and not when something ends, so a line may name a process already gone: a line is acted on only where the image and the start time still match, so a line whose process has ended is inert by construction, and the next record rewrites the file whole. The probes are the one thing adopted without a record: a process that lives a few dozen milliseconds would be written down and struck off again inside the hover that started it.

Finding each of them is its own question, and every answer rests on something the runtime guarantees rather than on a name. An Office engine is the process that appeared across `CoCreateInstance` (the same walk that tells an instance this app created from one the user already had open), and the browser is the `msedgewebview2.exe` whose parent is this process, because the WebView2 loader starts it from here; a browser another app started is a child of that app. The player and the probes need no finding at all: each is this app's own child, held by the handle it was spawned with and recorded under the id that handle names.

What is never done is acting on a process id by itself. An id recorded hours ago may belong to something else by now, so a record is acted on only when the process still runs the image the record names _and_ started when the record says it did — a creation time is what the checks that hold a process in hand never needed and a file cannot do without. The sweep runs at startup before anything else, so a leftover engine is gone before this run can start a process of its own, and never beside one.

## Explorer Hook Flow

1. Detect the active Explorer window and the focused or hovered item via HWND/class matching and UI Automation, with input-grace helpers (`should_probe_keyboard_focus`, `should_probe_hover_resolver`, `should_probe_stationary_hover`) throttling probes to recent user activity and a `stationary_hover_probe_done` latch capping stationary-hover work to a single probe per parked cursor. An item is found by the box the view gives it rather than by the text drawn inside it, and that box is kept to the part of it the view is showing: a provider reports an item's box at the place its content is drawn however far the view has been scrolled, so in a view larger than its window the box of a clipped item carries on behind the toolbar and past the bottom edge, where the pointer is on the search bar or off the window rather than on the item. The container the view draws its items in is read in the same walk and the two are clipped together (`view_bounds`), so what answers for an item is the part of its box that exists on screen. The box is what says the pointer is inside the item, so the metadata line a Content row writes is not what answers for that row: the name is consulted afterwards, as the check that position and file agree, and only when the name could be one of the files this app previews. A view reports a row's metadata exactly as it reports a name, and a name like that is passed over rather than taken for the file. A cursor probe that comes back slowly is not answered with a pause: what it costs is the tick it took, and the next tick asks again. The only pause the pointer probes still wait out is the one a restart or a display change arms, where what is wrong is the windows rather than the speed of the answer. The keyboard's item is one too: the focused element, or the item its list has selected when the view reports the list itself as focused (the search results view does), read from that element and walked up to the item that holds it exactly as the pointer's is. One batched UI Automation read gives the item's box, the name the view shows it under, its position in the view and the value its accessible pattern carries, and the position is turned into a path by the same view lookup the pointer uses, tab rules and all. No name is looked up for either path and nothing is walked: a search result whose file lives in another folder is answered by the item itself, and two results sharing a name are told apart by where they are. `tick_ms` (15 ms default — one system tick, the shortest wait the system honours, since a wait is served on the system's clock and a number between two ticks spends the same time as the one below it; the menu offers up to five) sets how fast the loop runs while Explorer has focus, and the same number gates the stationary probe. It is the app's one rate that is about itself rather than about a hover, trading how soon a move is answered against what the app costs while it works — every look is a crossing into Explorer, and while a preview is up and the hand is moving, one item is resolved per tick. The keyboard's own probe keeps its own rate, being the heaviest of them and one the keyboard asks for only while a key is driving.
2. Treat a wheel tick as input when the wheel is driving Explorer (the pointer is over it, or over a preview window that covers the pointer while Explorer still receives the wheel). The wheel moves the list under a stationary cursor, which changes the hovered item without any mouse movement: every tick reopens the probe latch and restarts the hover clock, so the item the list brings under the cursor is resolved and previewed as the wheel turns rather than once it stops, and an item that is not media takes the preview away with it. What that gives up is the second look a scroll used to get: a list still animating can be read mid-flight, so a fast flick may preview an item the list was passing on its way. A scroll also ends keyboard ownership: the keyboard preview is closed, the pointer freeze released, and the recent-keyboard-input window ends.
3. Treat clicks, Enter, the navigation keys and the keys a file name is typed with as user navigation. A folder probe runs at the active cadence for a moment after such a press, so a folder that press opens is recognized before the user's next key press rather than up to a full idle interval later. Once the new view has settled the post-folder-change suspension lifts on its own, so the item that landed under a parked cursor previews without a mouse move, and the first navigation key press after the change previews the item it selects — the gate lifts on a fresh press transition (never on key-down state left over from the navigation that opened the folder), so that press is no longer swallowed as a focus baseline. A hover is not spared a place change by the box it was resolved from either: that box belongs to the listing that has been left, so a look under the pointer that answers nothing after the change is a file that is not there any more rather than a read that failed (`read_failure_is_the_same_item`), which is what used to leave the preview of the old file on screen over an empty folder. A folder change that no input precedes (a programmatic renavigation, a network refresh) still waits for user input, and the auto-focused first item still never previews without a key press. What the probe found is kept as facts rather than as one written key (`HoverLocation`): the folder behind a view is a walk out through the shell to a filesystem path, and a share, a slow disk or a library answers nothing to it on some looks and a path on others, so keyed by the first fact that answered, the same place read as `folder:…` and then `url:…` — each a change to act on, which took the preview down and put it back a moment later. A fact is compared only where both looks answered it, and a look that answered nothing is a look to repeat rather than a change. What is compared is the fact in the form it is compared in (`location_fact_key`): the folder a view has open is canonicalized where that succeeds — which is where the verbatim `\\?\` form comes from — and left as the view reported it where it does not, so one place answers two spellings on the volumes where canonicalizing is what fails from time to time, and case and a trailing separator are the same difference. And one look answering what the last one did not is not taken as the user having left: what a change is still not allowed to do is take down the preview of the *file* the pointer is on — the place is recorded, the view's caches and the tick's own answer go with it, and the item under the pointer is read again, so a change of place that leaves the same file under the pointer is a view that re-answered rather than the user leaving, and the preview stands with the question asked again, while a file this view does not hold takes the preview down and arms the gate as it always did.
4. Read the file's own directory entry once and answer every question about its presence from that one reading — present, a file, version, content-here — rather than asking the volume once per question; then normalize the resolved path and validate the file extension. The `.ts` and `.mts` extensions are shared with TypeScript sources, so those two are additionally confirmed by a short MPEG-TS sync-byte probe before a video preview is started. The gate is what the file _is_, asked the way the renderer asks it — video first, then PDF, archive, Office document, design document, vector drawing, text lists, font list, image extensions last — with that kind's `Preview Types` gate applied on top, so a file whose kind is switched off resolves to nothing rather than to another kind's preview. Every question the renderer asks about a file is asked in that order as well — which reader draws it, what size it is, what share of the display it takes, what it is drawn over — so a name written into two lists belongs to the earlier of them wherever it is asked about, and the tray's switch for that kind is the switch that applies to it. That is the rule the move of a format from one list to another has to keep: the kind a name is moved to is asked in a new place, and every caller that asks a list question has to ask it there too.
5. Send `Show` or `Hide` messages to the preview thread via channel.
6. Resolve a file from the item that stands for it, and read nothing else. The folder index, the down-the-tree descent, the search-root index and the Shell view name index that stood here are gone: a name is looked up nowhere, and the hook never touches the filesystem to find a file. What is cached about a view is only what answers a question a view has already been asked — the folder a window remembered, which window is one of Explorer's, and the views the window last resolved in, read from the Shell window collection once for the window rather than once per probe — and it is dropped when the location changes.
7. Keep keyboard and mouse precedence explicit: an arrow-key preview owns the screen and is never dismissed by the parked pointer (a wheel scroll does end it, handing the screen back to the mouse), while a mouse preview is still dismissed the moment the cursor touches it. Each keyboard spawn measures the preview's own on-screen box (`preview_screen_rect`) and, when that box covers the cursor, freezes the pointer-driven triggers — `should_probe_preview_hover`, the hover resolver/folder probe, and mouse hover previews — until the cursor is moved more than the pointer tolerance (20 px), so jitter cannot end a keyboard preview. That tolerance is what a move has to clear for the whole of the keyboard's turn, not only while the box happens to cover the cursor: a navigation key press — or the first character of a name being typed, which is the same press — puts the keyboard in charge of the screen (`keyboard_screen_owner`), and the state survives the keyboard previews it opens and closes. What the state holds back — and this is what `Prioritize Keyboard` is, on by default — is the parked pointer: while the keyboard drives, the file the pointer is sitting on does not preview, so a key pressed onto an item with no preview of its own (a file whose kind is switched off, a result whose path could not be resolved) reads exactly as a key pressed onto one that has a preview, instead of handing the screen to whatever the pointer happens to rest on. That is what keeps the two previews from trading the screen on a large search-result view, where the items the keyboard walks are the ones still being resolved. With the setting off, none of that is asked of the pointer: a key pressed onto an item with no preview to give leaves the pointer's own hover standing rather than taking it down and putting it straight back up — there is no keyboard preview to put in its place, so what is on screen changes only when the keyboard reaches an item that has one. The turn ends on deliberate pointer input: a move past the tolerance or a wheel tick gives the pointer the screen back (the wheel closing whatever keyboard preview was up, or merely ending a turn that had nothing to close), and a folder change hands it back as well, so the item that lands under a parked cursor previews in the new listing without a move, with the user's own next key press taking the screen for the keyboard again. A press ends a hover by itself, which is the other half of the rule and not the setting's: Enter hides what is on screen at once, the way Backspace already did — a press that opens an item is the view changing, and a preview of the file that was hovered is not left over the listing it belongs to — and a click ends a keyboard preview where the pointer is not on the preview itself, because a click is the one press that can navigate a folder without the pointer moving: the address bar's breadcrumbs are clicked where the pointer already is, and the folder probe cannot notice that change for it, being the pointer's own and skipped for as long as a keyboard preview is up. The focused-item baseline — its name _and_ its box, so two results sharing a name are two items — is cleared on mouse movement, and the focus observed after that acts immediately, so the first navigation key switches to the keyboard preview instead of being swallowed as a fresh baseline. When the mouse does take over, the file that was shown is latched (`SuppressedHover`) the way any dismissed hover is: held off the mouse path for the same-file rehover delay — long enough that the hand-over cannot flash it straight back — and released sooner when the cursor resolves a different file. A probe that meets the latch stays open instead of being spent, so a pointer left parked on that file previews it as soon as the delay has passed. A move is also what the settling delay is measured from: the clock a hover is timed against is restarted by every move, so the file under a pointer that has not stopped is one the hand is crossing rather than asking about. `settling_delay_ms` is how long that pointer must have been still before the hover below previews anything — the pointer is the whole of its subject, and a keyboard preview is not gated by it — `0`, where the app starts, switches the requirement off, so a move onto a new file falls through to the hover and has its preview put up while the hand is still on its way, while any other value holds the pointer's previews back to a pointer settled for that long, a floor under the hover delay rather than a replacement for it. A tick that fell through this way is still a moving one, so the keyboard-focus probe stays with the stationary ticks: a move has just handed the screen to the mouse and dropped the focus baseline, and the item the keyboard is on is not read until the pointer has stopped.

Explorer restarting is the one thing the hook cannot recover from by itself. Every Shell object it resolves items through — the window collection it asks which views a window holds, and the view that answered for one — is served by explorer.exe, and a proxy into a process that is gone does not reconnect: it answers no call for the rest of the run. That is what left every hover after a restart with nothing while the app looked alive, since the tray icon was re-added and the window counting that decides whether Explorer is up never used the shell's objects at all. A restart is therefore counted where it is already noticed: the tray window is sent `TaskbarCreated` when the shell builds its taskbar again — the same broadcast its icon is re-added on — and the hook builds the collection again when that count has moved, dropping the view that answered through it and the caches keyed by window handles that belonged to the gone process, hiding whatever preview was up, and re-arming the folder-change gate the way a folder change does. A collection that came out missing when it was asked for is built again on a slow retry rather than kept missing for the rest of the run: it is asked for while the shell may still be coming up — the tray retries its own icon for that same reason — and a missing collection answers exactly as a dead one does.

What a tick costs is its own rate and its own readings, and neither is one number. The rate is the state's: a tick every `tick_ms` while Explorer has focus, and a wake every 150 ms, 500 ms or a second while it is visible-but-unfocused, minimized or absent — so a machine whose Explorer is behind another application is not paid for at the rate of one being used, and a desktop with no Explorer window up is asked about twice a second rather than sixty times (`ExplorerState`). The keyboard is polled only inside the active path, and in one pass: the navigation keys, the letters and digits a file name is typed with (Explorer's own type-ahead moves the selection with none of the navigation keys touched, so the keys a name is typed with are what opens the window the focus is probed in, and they are read only where neither Ctrl nor Alt is held, a letter under one of those being a command rather than a name), the arrows and letters a shortcut is made of, the modifiers and the keys that are not navigation keys at all are one `GetAsyncKeyState` apiece, read together because a key read twice in a tick is not the same answer twice — the press bit it reports is consumed by whoever reads it first (`navigation_input`). And one reading of the pointer is taken per tick — its position, the scale of the display it is on, and the window under it — with everything the tick asks about the pointer asked of that one reading: the item, the place, the move threshold, the wheel's own question and the preview's hold are questions about one instant, and a caller that reads the cursor for itself mid-tick is asking about a later one (`PointerTick`). The one read that is deliberately fresh is the preview loop's own, taken a step before a hover is laid out, because that one is about where the preview goes.

Nothing else in the app polls. The tray waits on its own window's messages — the icon, the menu, Explorer restarting, the system coming back from sleep and the quit the exit paths post are every wake it has, so a wait finds them all and a poll would find none — and the thread that keeps a player's window from taking focus waits on an event between videos rather than waking every eighty milliseconds to re-assert a window no player is holding: the event is signalled by the hand-over a new player makes, and the timeout behind it is the cadence the window is kept in step at while one is playing (`ensure_noactivate_monitor`).

## Item Resolution

Both paths resolve a file the same way: from the _item_ that stands for it rather than from its name. The item is read with one batched UI Automation request — its box, the name the view shows it under, Explorer's own `ItemIndex` (the position it holds in the view), and the value its legacy accessible pattern carries — and the position is turned into a path by the view showing it. A pointer takes its item from the point, walking up from the element under the cursor to the nearest list row or data item whose box holds it (the whole row is the target, which is what Explorer itself highlights when an item is selected); a keyboard preview takes it from the focused element, or from the item its list has selected when the view reports the list itself as focused, walking up the same way because what a view says about an item is kept on the item and not on the text it draws inside it. A keyboard item is asked one thing more, because its preview is placed from the item alone with no cursor to measure from: the boxes each piece of its own text is drawn in — one read, from the item's children in one more batched call. Those boxes are what the `Avoid` setting keeps a preview off — the leftmost piece of the text, which is the `Name` column of `Details` and the name above the path of `Content`, for `Avoid Filename Column`, that same piece narrowed to the name's own width for `Avoid Filename`, and every piece of it together for `Avoid Details` — and, with the item's shape, what says whether the item is a row of its view at all: a row is one by the columns it draws _beside_ its name, not by how wide its box comes out against the display, since a `Details` or `Content` row writes its text into the left end of a box as wide as the view and the empty tail past the region a preview is kept off is the only room it leaves a keyboard preview. They are read for an item of any shape whenever the caller has a region to measure: the label under an icon is a box of its own, and the name of the item the keyboard is on is the file the preview is about. A keyboard item is one such caller every time it is resolved, `Avoid Nothing` included, since the region a keyboard preview is placed from is never absent — the setting is read there as `Avoid Filename` — while the pointer's item is asked the same question at the moment a preview is about to be shown for it, and not with every probe. Nothing is looked up by name on either path and nothing is walked: a name is the one thing a search across folders shares between files, and two results sharing one are told apart by where they are.

The view is found by the window first: the Shell windows are matched against the frame the item's window belongs to — the root window under the pointer, or the frame of the window the focused item is drawn in — rather than against focus or a rectangle, so a background Explorer window and another application's window are excluded by that one comparison. What the window names is not always a single view. A window that holds tabs registers one Shell window per tab and every one answers with the frame's own window, so the frame names a _set_ of views; and the tabs not showing cannot be told from the showing one by their windows — the Windows 11 frame reports both of its views as visible — so what settles which of them it is, is the window the item is _drawn in_: the window under the pointer, or the window the item's own provider reports for the keyboard's, is a window of exactly one of the frame's views, and that view (the showing tab) is asked alone. A view answers about its own folder's items whether it is showing or not, so the tab the item is not in is one whose answer is about something else: it is not asked, and its agreement is not waited for. A pointer in none of them — over the navigation pane, the toolbar, the details pane, none of which belongs to a tab — is answered the way every window was before that window was read: each view is asked for the item at its position under the item's name, and what two of them answer has to agree, because two tabs showing the same folder are one answer and either is right, while two tabs whose items differ are a question the item cannot settle — and no answer is better than the wrong tab's file. What the frame's views _are_ is read from the Shell window collection once for the window rather than once per probe, and read again only where it cannot describe the window any more: the window gone, hidden or minimized, or the desktop holding a different number of Shell windows than it did when the set was read.

The file itself is the one the Shell hands over for that item's position (`IFolderView2::GetItem` → `GetDisplayName(SIGDN_FILESYSPATH)`) — for a search result, the real file wherever it lives — but the two questions are asked in order and are not the same question, and the item at that position is fetched once for both rather than once for each: the name it is shown under and the path it stands for are two reads of one item object. First, which view holds the item: a candidate claims it when the item at that position goes by the name the accessibility tree reported, and a folder claims it exactly as a file does, because what an item _is_ says nothing about which view is showing it. Then, and only of the views that claimed it, the file: the path the Shell hands over, gated to a file this app previews. A view that holds the item but has nothing to show for it (a folder, an executable, an archive) is a _match with no file_, not a view that failed to match, and that distinction is the whole of it: read the other way, the tab that owns the item abstains, the other tab's media file is the only answer left, and hovering a folder previews another tab's picture. Tabs that disagree — about the file, or about whether there is one — are a question the item cannot settle, and no answer is better than the wrong tab's file. A pointer asks the view twice and takes the answer only when both looks found the same item, which keeps a list that scrolled under a parked cursor from answering with its neighbour's file. An answer is kept between probes while the pointer stays inside the item — and the window — it was read in, so a hand sweeping along one row of a list is many points and one question: what clears it is the pointer leaving that item, a wheel turning the list under it, a press, a navigation, or the window's views being read again. Each path has one other witness: the item's own accessible value, when that value is a whole path — which is where a search result states its file, and what answers when no position is reported at all. Nothing else is tried: an item no witness can vouch for is left without a preview rather than guessed at, which is why a search of several hundred results costs both paths the same work a folder does.

The place a view is showing is read the same way as the item, and out of the same set: the folder a view has open and the URL it was opened with are the facts the hook compares to notice that a place has changed, and they are asked of the view the pointer is in rather than of every Shell window the desktop holds. What the hints used to be: a walk of the whole collection on every folder probe, bounded by 64 registrations, with each one crossed into for the view it holds, and the window it settled on was whichever of a frame's tabs answered with the frame's own window first — which for a window holding tabs is not the tab the pointer is in. What is read now is the frame's own set of views, kept for the window, and the one view of it the point is drawn inside; where a pointer is inside none of them the answer is the view the pointer was last inside of that frame (the tab the hand was last working in), and the frame's first view where it has never been inside one. Which of a frame's views is showing is not something a pointer over chrome can say; what the rule buys is an answer that does not move while the pointer does not, so one place is read as one place rather than two. The fresh search check the miss path makes is the same call on the same view, so the two cannot disagree about which view they are asking (`anchored_view_context`).

## DPI Awareness

Per-monitor DPI awareness v2 on startup, with a fallback to per-monitor DPI awareness if v2 is unavailable, which avoids scaling artifacts on layered windows when Windows UI scaling is above 100%.

## Preview Window Placement

The preview is bounded to the display nearest the hovered cursor or focused item rather than the whole virtual desktop, resolved through `MonitorFromPoint`/`GetMonitorInfoW` and falling back to the virtual screen when the monitor lookup fails, so the window does not spill onto a neighbouring display.

Each update repositions the window before installing the new frame or spinner. Crossing between displays of different scale raises `WM_DPICHANGED`, which discards the frame that was on screen — one composed for the display the window has left, wrong in size and scale for the one it is on now — so installing the content first would leave the previous display's image stranded; the window proc can only throw the frame away, so it raises a flag the loop reads, and the loop replays the hover the frame came from, which lays it out again at the scale of the display the pointer is on now. For the same reason the layered surface is painted before the window is revealed.

Taking the window down and putting it up are two threads' work, made one step rather than two: `hide_preview` runs where the Explorer hook decides the pointer has left, because a preview that waited for a channel to be read would linger after the hand had gone, while what puts the window up is installed on the preview thread when a load lands. Under one lock the hide moves a count, and a load is checked against the count it was started under — so a frame that arrives in the moment after the pointer left is dropped instead of revealing the window, which is the preview that blinks: closed and back a few milliseconds later for a file nothing is on any more. It is a comparison and not a wait; nothing in it holds a preview back from going up, and the load a dismissed hover was waiting on is dropped where it stands — no frame installed, no engine window put up, no player started. The wait is held to the same rule: a spinner for a hover the pointer has left is not built at all. What a show replaces is stopped by the show itself rather than by the `Hide` that may have arrived with it: the messages are drained newest-wins — a hover already stale is not worth a layout — so a `Hide` and the show that follows it in the same breath are one message by the time they are read, which is how a keyboard preview takes the screen from a hovered file. Every branch that puts a preview up ends what was up before it (`stop_video_playback`), and for a sound that is the difference between a card that goes and a sound that plays on with nothing on screen to stop it. The window's own take-down is posted to the loop that owns it rather than sent (`ShowWindowAsync`), so a busy — or wholly unresponsive — preview loop is never a thread the hook waits on. A loop that is not running cannot let go of anything, so what it was holding is ended from the hook instead: a preview loop that has not ticked for `PREVIEW_STALL_MS` has the engines it keeps warm ended where it stands, non-blocking and engines only, with the player left to its dismissal and a browser's document left alone because that window *is* the preview while it is up. Nothing waits on the loop to recover, and the next hover starts engines again as though the stall had not happened.

The count covers a hide that has been *sent*, and a hide is only sent once the hook has noticed — a tick of its own, while the frame lands on a tick of the preview loop's, and a pointer can cross a whole row of the list between them. That moment is answered by the pointer itself. The item the hook last read under the pointer is published as the box the view draws it in (`publish_pointer_item_box`), withdrawn with the window in the same lock as the count, and a reveal is held to it: a frame or a spinner is put up only while the pointer is still inside that box, and one that lands for a hover that has moved on is dropped where it stands. The same box is what says the mouse has moved at all, which is not a distance to measure: the threshold the loop compares against is a hand's own jitter, and one that grows while the keyboard drives so a pointer at rest cannot end a keyboard preview, so a pointer could cross to the row below, and another file, without counting as a move at all — and the preview of the file it had left stayed on screen, since the stationary probe closes behind its first answer. A pointer outside the item the preview on screen is about has left it, and is treated as the move it is. A look that answers *nothing* is not that verdict on its own, because nothing is two different things: a read that failed at the item the preview is about (the walk out through the shell that answers nothing on a volume slow to answer) and an item that is not a file this app previews at all, an application or a folder, where the look answered properly and there is nothing to show for it. What tells them apart is the item rather than the answer, since every look publishes the box of the item it found: the preview is spared only where the box under the pointer is the box this hover's preview was resolved from _and_ still holds the pointer (`read_failure_is_the_same_item`). Another item is another box — an item with no preview of its own being an item all the same — so a preview can no longer be spared for an application the pointer has moved onto and stay there until the pointer leaves the item or touches the preview. Neither question is a wait, and neither is timed: a preview goes up and comes down the moment its answer changes, at any `Timing → Delay` the user picks, including the 0 ms the app starts at.

Preview size is derived from the media's native dimensions and the `preview_scale` setting, either a percentage of the native size or `fit` for the largest size the display area allows. The requested scale is always capped by the free space on the chosen side or quadrant, so a preview can never be clipped by the display edge — a large image at a small scale shrinks to fit, and a small image at 400% or fit-to-screen is reduced to whatever the display can hold. The same scaling is applied to the decode request, so image, GIF/WebP and video previews all land at the computed size. The one rule a size can come from besides those is a reduction of the fit itself, which is what a preview drawn at whatever size it is asked for follows below `100%`: the room the display has, reduced to the configured share of it. Which share that is belongs to the kind: `vector_scale`, `ebook_scale`, `document_scale`, `font_scale` and `design_scale` each name their own, so a picture's scale leaves every drawing, page, specimen and design document alone, and what a specimen's share is of is the box `font_preview` measures a font at. `scale_in_room` is the one place that answers it, for the size a preview is given and for the room a position mode chooses between, so the size the layout plans and the size the renderer draws at cannot come apart.

Where the preview lands on that side differs between the two position modes. `Follow Cursor` fills the roomiest quadrant around the cursor, growing away from it in both axes. `Best Position` places the preview beside the cursor or the focused item — on whichever side has more room for it — and centers it on the same line: `centered_top` puts the preview's middle on the cursor's own row (or the focused item's) and clamps that to the display. The rule is shared by every format — image, GIF/WebP, video, PDF and text — because it is part of the layout both mouse and keyboard previews are computed from. It is also what a preview still on its way follows the pointer with: `compute_mouse_layout` is asked again for the cursor as it moves, at the hover's own size and `Avoid` region, which is where the media is placed when it arrives. A text preview's own size is the one its document was measured again at, not the display's own measurement: the wait re-places from the re-measured size (`text_preview_layout`). The wait itself follows a place of its own, and no position mode decides it: a waiting spinner carries `flush_at_cursor` and is placed by it at the pointer's own corner — a pixel off it, so the pointer's own messages stay with the file it is waiting on — at the arc's own size in whichever quadrant the display has room for it, rather than at the size the preview will be and in the quadrant the mode would have filled (`waiting_placement`).

One rule is applied on top of whichever placement a mode chose, for the `Avoid` setting: a placement that came out over the region its own item draws — the name the file is listed under at `Avoid Filename` (the default), the box the view gives that name at `Avoid Filename Column`, and that box with the columns a row writes beside it at `Avoid Details` — is moved by the shortest step that clears that region, past its right edge, past its left, under it or over it, and a step is only taken where the display has room for the preview it moves. The last two of those ways name a *column* rather than one item's own text, and a column is a region the view draws every row's text in: a preview stepped off the item's own row and left at the column's width covers the rows beside it — in a `Details` or `Content` view, a preview above or below the hovered row covers its neighbours' names exactly as one placed over it would — which is the whole of what those two ways of avoiding exist to keep a preview off. The ways out of a column are therefore the two to its sides, and the ways under and over the row are taken only where the display leaves no room in either: a preview over the neighbours' names is then the lesser thing, because the item the preview describes is the one it would cover instead. Which of the two a region is comes from the hook with the region itself (`AvoidRegion`), since it is what measured it and only it knows whether the item draws columns beside its name at all. A mouse hover's step is also held to the pointer, the fourth thing a way out has to satisfy: a mouse preview is dismissed the moment the cursor touches it, so one placed _under_ the cursor is dismissed the instant it appears and put back the same way a moment later, for as long as the pointer sits there. The reach of it is the tile: the pointer on a thumbnail with the label beneath it, where the shortest step that clears the label rises over it, onto the thumbnail the pointer is standing on. So a way out that keeps the pointer clear of the preview is preferred over one that does not, whatever size the two offer, and one that covers it is still taken where no other way out is left. The keyboard's placements carry no pointer: what they clear is the focused item, and a preview over a parked pointer is allowed for them.

Keyboard previews are placed next to the focused item, which can put them over a parked pointer, and that is allowed: while a keyboard preview is up it stays topmost and the pointer is not treated as hovering it, so it cannot be cancelled or made to blink by a cursor that happens to sit underneath. The placement anchors on the item's own edges — which is what keeps a preview off the file it describes — because that reading holds for an item that is a box. An item far wider than it is tall that draws columns beside its name is not one: a `Details` or `Content` row is a box as wide as the view with its name and its columns written into the left end of it, so the row's own right edge _is_ the view's, and what lies beside it is the space the view is not using, a sliver at the window's edge. The columns are what says the item is a row — the label under an icon, a tile's stacked lines and a name on its own have none — and not the item's own width against the display, which reads the row of a window narrower than half the display as a box however that row is drawn. What such a row does leave is the empty tail past the region the `Avoid` setting keeps a preview off — at `Avoid Filename` that region is the name alone, so the columns drawn after it are the room the preview takes, while at `Avoid Details` it is the whole of what the row draws, which is the tail the placement has always been measured from — and that region is what the keyboard's placement is measured from, since it is the hook's own read of the row's text elements: the preview takes its place and its size from the tail, `Best Position` centring it on the row's own line just past that edge and `Follow Cursor` growing it from the row's corner. A row with no tail to place a preview in (a narrow view, a name long enough to fill it) is anchored at its _middle_ instead, the way the mouse path anchors on the cursor, and is allowed to cover the rest of the row. A keyboard preview is never placed from no region at all: `Avoid Nothing` is read there as `Avoid Filename`, since a placement by the position mode alone is one read from a cursor and the keyboard has none — its item is a box as wide as the view, which the mode alone would put the preview on the middle of, over the file it describes — and the name, the one line a preview can be put beside, is what that setting keeps off instead. The hook confirms this from the preview's own box (`preview_screen_rect`, taken from the layered window or the `ffplay` window once visible) rather than from a cursor position test, and holds the pointer off until the mouse is moved on purpose.

At `Avoid Filename` the region is cut to the width the name itself is drawn at, because a view reports the room a name is _given_ — one width for every row of a `Details` folder, a long name and a short one alike — so the name is measured where it is drawn, extension and all: the icon font the shell gives folder views, scaled to the display the item is on (the display of the region itself, since a view need not report a window for an item) and taken at the larger of the two sizes a view draws a name at (the font itself in `Details`, 125% of it in `Content`), with a font and a memory DC made for the one call and let go again. The larger size is what makes one measurement serve both views; a `Details` row is left keeping a quarter more room than its name takes. `Avoid Filename Column` is that room as the view reported it, without the cut. The cut only ever narrows the box, so a name that fills the room it was given, or is drawn truncated to it, is left as the view reported it. The text is a region the Explorer hook measured, so it comes with the hover rather than being anything the preview thread can see: for the pointer's own item it is read at the moment a preview is about to be shown, once per preview rather than with every probe, and a keyboard hover carries the box the walk already measured. A view that reports no text for an item leaves the item's own box as the region, since the name is drawn inside that box whatever the view says about it. The distance the placement keeps from whatever it is beside is what the text is cleared by, so it is stepped off rather than touched at its edge. A room too small to be worth having — the sliver of tail past a name that fills its row, the last strip of a display under a row at its bottom — is not taken at all, so a preview is never squeezed into a sliver to get off a name it would have covered anyway. The waiting spinner is the one placement the rule passes over: it is put at the pointer's own corner by its flush rule and left there, over the name, rather than stepped a margin off the file whose page it is waiting on.

## Pin Mode

A preview is a hover: it is placed at the pointer, follows it, and goes when the pointer does. Pressing the pin key while one is up — `Space` by default, `pin_key` in `config.ini`, the row named for it under **Pin Mode → Enable** in the tray — stops all of that and turns what is on screen into a window of its own: captioned, movable, always on top, still there until it is closed. The key is watched the way the trigger key is watched and by a sibling of the same machinery: a low-level keyboard hook of its own in `key_input`, installed on a thread that does nothing but pump its messages, publishing a press counter the preview loop drains once a tick — counting a press rather than a state, and never swallowing the key. The watch is bound to a number rather than to the configuration (`refresh`), and what re-reads the setting is the config watcher thread and the tray's own row.

Taking a pin back *down* is what that same key does, and it is the one thing the key cannot decide for itself: what it is answered by is a count of presses made anywhere on the desktop, so a `Space` typed into a text editor is the same press as one made in Explorer, and used to take a pin down with it. What a press does is therefore settled by three facts, in a small pure function beside `pin_command_request` (`pin_press_action`, answering `Unpin`, `Swap` or `Nothing`), and the hand is asked first because it is the only one of the three that cannot be a coincidence: a mouse press that has landed on the pinned window or on the bubble and has not been taken off it since (`PIN_HAND`, set by the two window procedures' `WM_LBUTTONDOWN` and read as `PIN_HAND && pointer_on_a_pin_window()`) is the pin being touched whatever the keyboard is doing, and it is what a drag of the bubble leaves behind. The second is whether Explorer holds the keyboard (`explorer_hook::is_foreground_explorer`, which the preview loop asks as well as the hook), for a pin never takes focus: a press with another program in front is that program's and does nothing at all, since a window lost that way is a window nothing asked to be lost. With the keyboard in Explorer and the hand elsewhere, a window that is up is what stands between the tree and the files in it, so the press is about the pin and takes it down — one gesture for the whole of it, which is what a key Explorer also owns has to be. None of the three is asked of Windows, and that is not an oversight: the pinned window and the bubble are both created `WS_EX_NOACTIVATE`, so a question one call would settle for an ordinary window — is this the window the user is in — cannot be settled at all for these two, and the keyboard and the app's own record of a press are what is left.

What a pin does to the hover machinery is refuse it, in both directions and at the one place each direction passes through: `show_preview` and `show_preview_keyboard` answer nothing while a pin is up, because a hover raised beside one is a second thing on screen, and `hide_preview` — the door every one of the hook's twenty-odd dismissals goes through — comes down on the pin's behalf rather than the pointer's, which is also what leaves the player process and the media engine behind it alone. The preview loop keeps a gate of its own at the door it shows a hover by, and it is a different door: what is on screen is recorded as a hover message whoever put it there, so an answer that lands for the file a *pin* is showing — a box measured off the preview thread, a video's probe, an engine's page, a setting changed in the tray, a hover that was in flight when the pin came up — would be replayed out of that record as a hover, and acted on it would stop the pin's media and put a hover where the window was, which is the one thing a pin is there to refuse. So a hover message is dropped while a pin is up (see the loop's own gate before its message match), and an answer the pin has taken for a wait of its own is spent on the pin rather than replayed for a hover as well; the messages the pin answers for itself — a take-up, a box, a take-down — are not hovers and go on as they always did. Nothing of it moves the window: a hover is not *composited* on a pin, and the repaint a tray setting asks for is the pin's own band and chrome drawn again rather than anything laid out beside it. So the pointer may cross a folder, the wheel may turn, a name may be typed, and nothing spawns and nothing despawns, which is the whole of what "the preview mode is paused" means here. The hook stops _resolving_ as well as showing: one tick past the trigger gate it reads what the notification area says and sleeps, so a pin costs the shell nothing — nothing except what `Pin Mode → Update Preview` asks of it, and only where that setting asks (see below) — and the pause is bounded by a flag rather than by the pointer, since what ends it is the pin and not a move: the close button, the key again, the kind of what is pinned being switched off in `Preview Types` (a pin is not a hover, so there is nothing to rebuild it from and it comes down instead), previews themselves being turned off, the trigger key gating them away where `Timing → Trigger Key → Affect Pin Mode` says the key is the pin's business — off where the app starts, in which case a pin is a window the key is not read for, up or collapsed into its bubble, and `Hold to Disable Preview` is the mode the row speaks for — the machine suspending, or the thing the pin was a window onto going away — a player's process ending, the browser's window closing, the media session falling over. A pin that has come down raises `PIN_RESUMED` once, and the hook spends that one reading to clear what a hover leaves behind — the file it was last about, the latch that holds a re-hover back, the gate a folder change raises — so the first hover after a pin is answered at once rather than after the delay a file the pointer had left and come back to would be given.

What a pin does with _another_ file is the tray's `Pin Mode → Update Preview`, and it is the one thing a pin does that the hover machinery behind it is not able to: with `Enabled` on, which is where it starts, a pin is shown the file the user picks while it is up, which is what makes it a window that reads one file after another rather than one that is closed and taken up again for each — and a pin that is only a bubble is the one thing that is *not* shown one, for the same reason it is not ended by the key: a pick made behind a bubble is the file the user is walking to rather than one they have asked to be shown, so the last one is held in the loop (`pin_bubble_pick`) and offered to the key above, and a click on the bubble still brings the window back on the file it was showing, as it always did. Three things count as picking a file, and they are the three ways one is picked in Explorer: a click, which is the pointer acting on the view; the move of the keyboard's focus, which is what the arrows, the page keys and a name being typed move, probed through the same `get_focused_explorer_item` the keyboard hover's own path probes and at the same rate, compared as a `FocusedItemKey` — a name and a box — so that "another file" is a file and not a spelling, and counted only where the item was read in the place the watch was already watching — a folder opened, another tab, another window and a folder pressed into with Enter move that focus as well, and an item the focus has *landed* on is the baseline the next key is measured against rather than a file anybody picked; and, only where the submenu's second row `Update on Hover` is switched on, the file the pointer settles on, at the delay and the settling a hover of it would have been given, with a pointer nobody has moved since the pin went up counting as having hovered nothing. The place is the view's own answer — the window the view is drawn in and the URL it was opened with — read once per item the focus lands on rather than once per tick, since it is a crossing into the shell, and two places are told apart by the facts both looks answered, the rule the hover machinery reads its own place by. What a place cannot answer is asked of the keys themselves, and a focus that has moved counts as a pick only where *both* say the keyboard is what moved it: the watch keeps the one fact the input already tells it — whether the last thing to move the focus was a key that walks a listing, an arrow, Home, End, a page key or a name being typed, which lands on the user's own choice, or something that moves the focus without a walk, which is an Enter, a Delete, a Tab, a shortcut of Explorer's own, a click, a button of the mouse's own, or any key held with Ctrl, Alt or Windows down — and a walk is only good for as long as a key press is given to have moved something, so that a witness nothing made good on cannot outlive the press that gave it. The place cannot be the whole of it because the view a *focused* item is read in is not the item's own: an item's provider reports no window for a frame's views to be told apart by, so what answers is the remembered view — the tab the pointer was last seen working in — and a tab switched or a folder opened under the keyboard then reads as the place the watch was already watching. The keys are read by the hook on the pinned tick itself (`focus_move_input`), once a tick and once only, the way every other read of them is, and only while a pin is up: nothing is asked while none is, and what a walk costs is a press the user has already made. What that comes to is the line the setting promises — a file a click, a hover or a key the user pressed picked, and never a file a listing that changed under the keyboard put under the focus — and where the two witnesses disagree the cost is one press: the next arrow is a walk again, and the item it lands on is offered as it would have been. The folder a view *has open* is deliberately not read: walking it out of the shell's objects and stat-ing what comes back is a price a key being held down would pay two or three dozen times a second, where the URL names the same place for a folder view and is answered every time, and the window the view is drawn in is what tells two tabs showing one folder apart. The second row is greyed while `Enabled` is off, because a pin that follows nothing does not follow a hover either. What all of it is gated behind is the pin itself: the watch is a branch of the hook's tick that only a pin reaches, nothing of it is read while no pin is up, and nothing of the hover machinery's own state is touched by it.

The work is the preview loop's. What the hook does is ask the pin what it is showing (`pinned_path`) and offer it a file when one is picked — never the file it is already showing, and never a name no kind of this app previews — and what the loop does with the offer is a swap rather than a second preview: the media is loaded for the box the pin has, on the loop's own thread and synchronously, at the price a pin's own box change already pays, and the window is then taken up again by the path a first pin takes, with what belongs to the window rather than to the file — the box a maximized pin restores to, the level its own volume control was moved to, chrome that is already showing — carried over. What a swap measures the box against is a bound the pin carries rather than the box the file it is showing came out at, and that is the whole of why a pin that follows a listing does not walk its way down: `PinnedPreview::bound` is the longest side of the box the window went up with, of the one a manual resize last left it at, or of the one the first file with a shape of its own was given where the pin has none — taken at that file's take-up, and the only bound a swap can ever add — since a move, a swap, a maximize and a display change all leave it as it is — and fitting one shape into the box another came out at can only ever take a side off it, which is a window walking its way down to nothing file by file. A pin that went up on a file *drawn* to its own box — a page of text, a listing either reader produces, a sound's card — carries no bound at all: that box is a size the file was drawn to rather than one the user gave the pin, and a two-line file's window or a four-hundred-pixel card is no ceiling for what follows it. What a swap into such a pin is laid out against is the room the display has, at the scale the tray names for the new file's kind, and the box that comes out is where the bound is taken from — the same box a first pin on a picture takes its own from. It is a side rather than the box itself because a box is a shape and the files that follow have shapes of their own: the room a swap is fitted into is that side square, cut to the room of the display the pin is on, so a pin taken up as a portrait leaves the whole of its long side for the widescreen file that follows it, where the portrait's own box would have shown that file at a fraction of the size for no reason the user could see. Inside that room the file is laid out at the scale the tray names for its kind, which is the scale a hover of the same file would take: a fit fills the room's side, a percentage takes the file's own pixels and is reduced only where the room cannot hold them, so what a swap promises is the window's place and its ceiling rather than its exact size, and the window is centred where it stands, so a hand that has moved it is not moved back. A window that is maximized stays maximized, fitted to the display's room the way the maximize itself was, a sound's card excepted, which is given the maximize up as it arrives (`pin_restore_after`): a card offers no maximize to stay in — nothing to fill, so no button to reach the state by — and a restore carried onto one would leave the file after the card measured by a maximum that is no longer standing. "Fitted to the display's room" is the whole of it, and it is the same bound rule stated for a second kind of box: the room is read once in `pin_swap_space` and carried on `PinSwapSpace` as `room`, because a maximize is a statement about the room rather than about the window's current box, and so the box the file before this one came out at is not a thing a swap into a maximized pin measures against — 16:9 fitted into a 16:9 box, then 4:3 fitted into that, then 1:1 fitted into that, is a running intersection rather than a walk, and it converges on the smallest shape in the folder, monotonically, while the caption goes on drawing the restore glyph the entire way because the maximize was never given up. Measured against the room every time, a walk through shapes is a window of one size showing something else, which is the promise every other swap in this file keeps; `a_maximized_pin_walks_its_files_against_the_room_and_not_the_last_box` carries the box forward across three continuous laps and asserts every lap equals the last, which is the assertion that fails when the window ratchets. And the bound outlives the display it was measured on: it is capped by the room of the display the pin is on now, so a window carried to a smaller screen is fitted into what is there rather than into what was. A kind with no shape of its own — a page of text, a listing either reader produces — keeps the box exactly, because the box is what that kind is drawn into rather than a room it is fitted to and the scaling rules say nothing about a size it does not have. A sound's card is the one drawn kind that does not keep it, and is the one card measure is a size rather than a room: a swap lays it out at the box `audio_box` came out at, centred on the box the pin has now, and the box the file before it left is not a size a card is drawn to or fitted into — so a card a listing is followed into is the card a hover of the same file would have drawn, rather than one cut to whatever box was standing there. What every other wait has in common is that the pin keeps the file it is showing and the pick is made again, by name, from the answer itself: a file whose _box_ is still being read (a page measured off the preview thread, a video nobody has probed, a sound nothing has probed) answers with a square placeholder while the read runs, and a window laid out at that placeholder is a 16:9 file in a 1:1 box — and a page, a picture or a listing an engine has not produced yet is the same deferral, asked for on the pick rather than refused by it, because a swap is not a wait and a pin has nowhere to put a spinner. Each wait is *started* where that pick is deferred, since nothing else asks for one while a pin holds the hovers back: a video's geometry probe, a sound's track probe (the measure a card is built from, `audio_box`, taken the way a hover takes it, off the preview thread), and the page, developed picture or listing of an engine the file's own kind names (`request_engine_render`, asked for the room the display has rather than the pin's own box, which is the room a hover of the same file asks for and the page the two share). A landing is taken as the pin's own answer where it arrives — a message for Office, the image converter and the listing engine, the page itself for the two engines that write one into the app's own folder — rather than as a hover's replay, which would be a second preview on screen beside a window that is not one; a file the engine turns down ends the wait with the pin keeping what it has.

A document the browser engine draws is the one kind shown as it is *asked for* rather than after it lands: the media arrives at once — there is no frame of this app's in it — so the band is empty for as long as the browser takes, which for the first document of a run is the browser being started. What that costs is the liveness rule rather than the preview: a pin is a window onto something the engine *stands behind*, which is a document it holds or one it still owes and has not failed at, because reading the window alone takes a browser that is starting as a pin that has come apart and closes the window before the drawing appears. An engine that fails is where a pin of one does come down, by the engine's own failure notice, which is the same notice a hover's wait is answered with. And a box that changes under a document — resized, maximized, restored, carried to another display — *moves* the engine's window with it (`webview_preview::place`), where a hover is only ever told where a wait has ended up, and where the browser's own window is the band and the chrome is this app's.

The window it happens in is the preview's own, which is why there is one of it and not two: `WS_EX_LAYERED | WS_EX_TOOLWINDOW | WS_EX_TOPMOST | WS_EX_NOACTIVATE` at `WS_POPUP`, painted with `UpdateLayeredWindow`, exactly as before. What changes is what the box means. A hover's window _is_ its frame (the layout measures a box and the media is loaded at it) and a pinned window's is the media plus two bands: the caption above it, and the transport bar below it for a kind that plays — or the media and nothing else, for a kind whose chrome is drawn _over_ it (`pin_overlay_chrome`). Pinning is therefore not a reload and nothing about the picture moves: the media keeps the box it had, and the window grows around it — upward for the caption, downward for the bar, or not at all for a kind whose chrome is drawn over its media, whose window _is_ the media's box. `PinnedPreview` is that state — the media's box, the longest side a swap may give it, the box a maximized one goes back to, the scale of the display it was put up on, and what the pointer is doing on it — held in a global because three sides ask it: the loop that takes it up and puts it down, the window procedure that reads the captions' buttons and the drag, and every repaint. What the repaint composes is the media band at its own row offset, the caption, and the bar, in one surface, which is `render_pinned_preview_at` beside the hover's own painter. The band is filled from the frame the media holds, and a frame is the size its pixels were written at: a band of another size — which is every band while an edge is under the hand, and the band a resize has just been let go of — is that frame _scaled_ into it, never a frame redeclared to be the size of the box while the pixels of the old one are still in it, which is a picture sheared a row at a time. Three kinds leave the media band empty on purpose — a video FFmpeg's player is playing, an SVG document, a font specimen — because the thing drawn there is a window of somebody else's, and a band of alpha-zero pixels is a band those windows keep: hit testing a layered window is answered by the shape of its own pixels, so the player keeps the mouse and the caption keeps the pointer. For the two of them the placement is a tiling: the player's window, or the browser's, is put at the media band's box and travels with it — and is not re-asserted while a pin is collapsed, since a bubble is nobody's backdrop.

The caption is drawn by `pin_chrome`, which is GDI and the text painting layer and no window at all: a bar in the colours of the theme the text previews are painted with, the file's name measured and cut with an ellipsis where the room runs out, and up to three glyphs drawn as strokes rather than taken from an icon font: minimize, maximize or restore, and close, washed with Windows' red whoever is looking at it — and, on a caption that carries the pin's own three, two more in the theme's ink, each a chevron whose vertex is at the end it points at and whose arms open away from it (`draw_chevron`), so the two point opposite ways rather than the same way.

The six glyphs are one row, and a row is judged as a row: none of them is twice the height of the rest, and each sits in the middle of its own button. Two things follow from that which a test on one mark at a time cannot see. A chevron's arms part *half* a span either side of the middle row — the close cross, the maximize box and the restore pair are all the glyph square, and arms reaching as far as the mark is walked are drawn a span either side of the middle, which is twice that — and the two arms are taken in *opposite* directions as they thicken, so they are each other turned about the mark's own middle row at any stroke width, where a stroke run the same way on both sides closes the arms into a blob on the row where they meet and the point stops being a point above 100%. The chevron is walked in whole pixels rather than through `stroke_segment`, deliberately, because the single row at the end the arms part from *is* the mark and an anti-aliased stroke a pixel wide rounds its own point off; the close cross is walked the same way for the same reason. The hand-off glyph was redrawn from that same row: as a full-height box with its top-right corner left off and an arrow leaving that corner, laid out about the mark's own centre and then with the stroke's half-width taken out of the layout, because a stroke is drawn about the line it is given and not inside it — a mark a stroke and a half past the size it was asked for is a mark off its own button. It is `stroke_segment` (the primitive the volume arcs use) rather than `put`, which is what puts the arrow's taper in it. Its first draft was rejected in design review for reading as the upload mark — a box too small to read as a box, with a large arrow standing on top of it — and a button that means "hand this to another program" must not be drawn as one that means "send this away"; that reading is a constraint on the drawing, not on the code, and it is the reason the box is full height and the corner is open. The maximize is not offered where there is nothing to maximize (a sound's card is its own size; a video FFmpeg's player has is a window this app does not own) and the buttons that are offered keep their places against the right edge when one is missing, because a close button is found by knowing where it is rather than by looking. A press on the caption begins a _move_ rather than a modal drag loop: `SetCapture` and a delta per mouse message, because the preview loop has to keep ticking (a video's frames come through it) and the player's window has to travel with ours. The body of the window is a handle for the same reason a title bar is one: a press anywhere on the media moves the window, with two exceptions — the parts of a text preview that are the text preview's own business (the scrollbar, and the text itself, where a press begins a selection; the margins around the text are the handle there), and a video FFmpeg's player has, whose band is a window of somebody else's and belongs to that player's own clicks.

Three more buttons sit on that caption, and they are a pin's rather than a window's, which is why they are measured separately and packed to the left of the window's group rather than inside it (`button_boxes`): the file before the one pinned, the file after it, and the hand-off of the pinned file to whatever program this machine has filed it under. Minimize, maximize and close keep the exact pixel slots they have always had, because those are the buttons a hand has been reaching for on every window on the desktop and a close button that moved because this build was updated would be a close button in a new place; the three new ones are packed off the group's own left edge at the same size and in the written order — previous, next, then the hand-off — so that a caption which cannot carry all three of them drops them whole and keeps the window's three exactly where they would have been. Which of the two is given up is not a question: the walk is a thing a window only has once it is a pin, and closing a pin is not.

The walk those two buttons step is `shell::pin_navigation`, and it is a list of names rather than a read of what they hold. One flat `read_dir`, no recursion — the folder the pinned file is in and not a subfolder of it — and no file opened: the kind is asked of the name alone (`routing::kind_of_name`, deliberately rather than `routing::kind_of`, since the content-reading form is what settles the two names the video list shares with the text lists, a `.ts` being either an MPEG transport stream or TypeScript, and paying for that on every file in a folder is thousands of opens and, on a cloud-synced folder, the whole folder downloaded). What that costs is that a transport stream is walked as the TypeScript it shares its name with, which is the right way round because a file walked onto is loaded whole and answers for itself. Whether a file is a file at all is `DirEntry::file_type()` — data the OS returned with the name, with no stat — and a reparse point is never asked for `metadata()` after it, for the same reason the folder walk never is: hydrating a OneDrive placeholder downloads the file, and `metadata()` is read only where the order is a Date or a Size walk and only of a file that has already passed the type check. Whether a reader is installed is asked once per kind per scan and remembered rather than per file, or a folder of Word documents is a registry lookup each. What a scan is held as is each entry's kind beside its path, so switching `Pin Mode → Nav File Types` re-filters what is already in hand rather than reading the folder again, and the map is capped, because a hand that pins files in a thousand folders should not leave a thousand folders behind it. The folder is read on the first press and not when the pin is taken up, and what it is read under is the configuration — which is why the walk is asked of a switch that exists by the time somebody presses a button. The switch is `Pin Mode → Nav File Types` (`PinNavFileTypes`, `pin_nav_file_types` in the file's **General** heading, `all` by default and the answer for every file written before it existed), and it narrows the walk from every file the build could preview to those of the pinned file's own category. The categories are a fold of the kinds, not the kinds themselves (`routing::nav_category`): a `PreviewType` is a claim and claims are per reader, while what a caption's button is asking is whether a file is worth stepping onto from the one on screen, so the engine-backed kinds are folded in with the ones they share a switch with — images with the image converter's, documents with the ebook's, archives with the listing engine's, design with the vector's — and the fold is exhaustive, so a kind this app grows has to be told where it goes rather than defaulted into a category by omission. A camera raw is therefore walked as a picture and a book as a document, which is what a user walking a folder would call them.

The order of the walk is the listing's own where the listing can name one. `IFolderView2::GetSortColumnCount` and `GetSortColumns` are asked of the view the app already holds, off the folder view each resolved item came from, and the column is matched on its system property key (`sort_key_of`) rather than on a name a locale prints, so a folder sorted by name, date modified, size or type — either way round — is walked the way the window beside it is showing it, in any language. A descending column reverses the column alone: the name beneath it is a tie-break, and a listing sorted newest-first still reads its equal dates the same way round. The four keys are written out by `fmtid`/`pid` rather than imported, because the `windows` crate binds that property set's keys only behind a further feature this app has no other use for and does not bind the `Type` key at all — which is the whole of what this feature adds to `Cargo.toml`. Where there is no order to reproduce the walk falls back to natural name order, and the same answer covers an icon or tile view, a view whose items the user has dragged, a `search-ms:` results view (a search holds results across folders, ordered by relevance, and no sort is remembered for one at all), and a view that cannot be asked; natural name order is also what Explorer shows for `Name` ascending, and it is a comparison of the digits as numbers, so `img2` comes before `img10`. The ends wrap: the first file's previous is the last and the last file's next is the first. A pinned file the walk does not have — its kind switched off since the pin was taken up, or nothing on the machine that can read it — has no position to step from, so the step is taken from the end it points at (`step_to`): next to the first file, previous to the last, with the pinned file left exactly where it is rather than lost.

A step is a **pick**, handed to the loop through the same slot a file picked in the Explorer listing uses (`pin_swap_requested`), and that is what makes the button, the listing and the keyboard one gesture. It is deliberately not a `PreviewMessage::PinUpdate`: that message is the Explorer's half of the question and the loop's own match for one is a no-op, while `Pin Mode → Update Preview` gates whether a pick is acted on at all — the right answer for a file the user picked behind a window, and the wrong one for a button they pressed, which is a thing they did and is asked for by no setting. `step_pinned_file` takes the configuration by copy and lets the lock go before the walk: the walk reads a folder, and `CONFIG` is app-global, so a lock held across a folder read is a lock every other thread waits on for as long as the disk takes, the preview thread included. What the swap behind it is, and what it measures the box against, is the pin-follows-a-listing machinery described above, unchanged: **Open With** is the only one of the three that is not a swap. It hands the pinned path to `ShellExecuteW` and comes straight back (`open_path_with_default_app`), with the verbatim `\\?\` prefix taken off first — the same adjustment `webview_preview` and `office_render` already make, and a file handed to the Shell in that form is a file it cannot find, so the button would do nothing at all. The handle it returns is read and deliberately not asserted: a format with no registered association is an ordinary machine rather than a fault in this one, and a pin has nowhere to put an error, so a button that did not work says so by having not worked.

The two arrows are a third way of asking for the same step, and the only one of the three that is read on the hook thread rather than in the window procedure — which is not a choice: `GetAsyncKeyState`'s press bit is consumed by whoever reads the key first, so a second reader in the same tick finds it already taken and answers nothing at all, and polling the keys from the preview loop could therefore never see a press that `navigation_input` had already read. It has to come out of the one pass the hook already makes on every tick a pin is up, whether or not the pin follows anything, since spending those bits is what the pass is for as much as watching anything is (see `focus_move_input` above). `NavigationInput` and `FocusMoveInput` each carry the direction as a `step`, and only a fresh press of it counts: the walk is one file at a time, so a key left down is a key held and not a folder walked end to end. An arrow under Alt or Ctrl is Explorer's own back and forward and is not a step, and the modifier is settled before the arrow is read as one. What decides whether a step is a step at all is Explorer itself, asked of the foreground window the same way `pin_press_action` asks it of a pin key (`pin_navigation_step`): with a listing in the keyboard the arrow moves that listing's selection and the pin follows the file that lands under the pointer as it follows any other pick, and with none in the keyboard there is no listing for the key to move, so the walk the pin is already showing is what the arrow is left to mean — a listing minimized is in the keyboard no more than a listing behind another window is, so the one test covers both and no second question is asked. The gate is a pure function over the direction and that one fact, and the step it lets through is posted as the same `PinCommand::Previous` or `PinCommand::Next` a click posts, which is why `PinCommand` and `ask_pin` are crate-visible: one door, whichever side of the app the gesture came from. Nothing asks for it — `Pin Mode → Update Preview` is about the Explorer half of the question, and where Explorer is not in front there is no Explorer half to be about.

For the kinds this app draws itself — a picture, a texture, an animation, a drawing, a page of a document or a book, and the video the media engine decodes — the caption and the bar are not bands the media gives up room to but strips drawn _over_ it: the window is the media's box, the caption is its first rows and the bar its last, and what that buys is the whole of the display for the media rather than the display less two bars. What a strip over a picture is, is a strip of the picture nobody can see, so it is there when the hand asks for that _strip_ — the pointer near the caption's rows or near the bar's, from either side of the window's edge — and gone otherwise, and the two are asked about apart, because they are two different things a hand reaches for: a pointer at the bottom of a video has not asked for its title bar, and a bar drawn across the picture for a hand that was at the other end of the window is the very thing this arrangement is for. A pin shows the whole of its chrome as it comes up and puts it away a moment later (`PIN_CHROME_ARRIVAL_SECONDS`), because coming up is one of the moments a hand is looking for the buttons. There is no fade between those two states, and none is wanted: a strip is drawn into the window's own rows, the media having been composed there, so a half-shown caption would be a strip with the picture gone behind it rather than a fainter strip — and what a strip costs is the one repaint that notices it has changed, a press being answered by whether the hand is _asking_ for the strip rather than by whether the paint has caught up with the question. What asks is where the cursor _is_ and nothing else: a press or a drag on the media is a hand on the picture rather than a hand looking for a title bar, and a drag that began on the caption keeps its caption because the pointer under it is on the caption still, the window having followed it. The question is asked of the cursor on the loop's own tick rather than waited for as a message, because a strip that has gone is not a region a mouse can be over — the window would be waiting to be told about a place only it could have known to make. The kinds whose band is a window of somebody else's (the video FFmpeg's player has, and the page an SVG or a font is drawn on) are not among them, and neither are the two that carry a page instead of a picture: a text preview and a sound keep their caption and their bar where they have always been, in bands around the media, always there.

What a resize does with the box is a question about the kind of thing inside it, and it is one question with three answers (`PinFrame`). A picture, a video the engine draws, and a page an engine rendered have a shape of their own, so every edge and every corner scales both sides by what the hand asked for: what the window is given is always a box the media fills exactly. A drag is arithmetic in the media's box from beginning to end and what it hands back is the _window's_, which is the same box for a kind whose chrome is drawn over its media and the media's grown by the two bands otherwise — leaving that last step out is a window a caption taller than the picture it is showing, which the paint stretches into the band, and a caption taller again at the next drag. A page that is _laid out_ to its box (a document, a listing) takes the drag one edge at a time, because any box it is handed is a box it draws text into and a wider window is a longer line rather than a bigger letter. And two kinds are not framed at all: a sound's card is its own size, and a video FFmpeg's player has is a window this app does not own, so neither is resized and neither offers a maximize. A resize writes the bound a swap is measured against as well — the one the hand makes, where the other is taken by the first shaped file a pin without one is shown — so the side a hand leaves a window at is the side every file picked after it may use (see `PinnedPreview::bound`). The eight places a framed window is resized from are the four bands along its sides and the four where two of them meet, and a corner's band is wider than a side's: a corner is the smallest target of the eight, and the top-right one shares its place with the caption's buttons. The bands are asked about _before_ the caption, and that order is the whole of why the top edge and the two corners at the top of a window work at all: the top band lies over the strip the caption is painted in, so a caption asked about first is a window whose title bar covers three of its eight resize targets. The pointer is told where it is rather than left to find out — a side names the side, a corner names the diagonal it lies on, and a pointer on none of them is put back to the arrow — which means the position is read from the cursor and not from `WM_SETCURSOR`, whose `lParam` is a hit-test code with a mouse message above it rather than a point in screen coordinates. The drag itself is measured from the box the press began on rather than from the box the last message left, so that a long drag cannot drift: the edge opposite the one under the hand is nailed down, a side whose other axis is not being dragged keeps that axis centered on the line it was on, and a corner, where the hand asks for both sides at once and the shape allows one of the two answers, takes whichever of them is nearer to what the hand asked for. What the box is applied _by_ is the paint rather than a placement ahead of it: a carried window is a `SetWindowPos`, since what a layered window is drawn from is the surface it already has and moving the window moves that surface with it, while a resized one is an `UpdateLayeredWindow`, which stands the frame, its place and the window's size up in one call — applying the box first and painting after it is a moment per pointer move in which the surface of the previous box stands at the place of the next one, and it is read as the whole of the window's contents shaking, from every edge and corner but the bottom-right one. What a drag may never do is take the box off the display it is on or below the size a hand can still take hold of (`PIN_MIN_MEDIA_PIXELS`), and it is _stopped_ by that limit rather than cut by the placement afterwards: a box asked for past the display and trimmed back to it would be a box one of whose sides was held while the other grew. Maximize is Fit to Screen, centered in the work area: the media is given the largest box of its own shape the room has — scaled _up_ to it as well as down, so a small picture fills the display rather than sitting at its own size in the middle of it — and a page laid out to its box is given the room itself. What *of* is fitted is the file's own shape as `media_dimensions` measured it, never `pin.content`, and that is the second half of why: `pin.content` is already a fitted box, so its aspect is its container's and not the file's, and maximizing to it maximizes to whatever the window happened to be standing in. The decision itself is `pin_maximize_decided`, told apart from the reading and the writing around it because a toggle is a state machine and this is its only transition: a window with a restore put aside is put back and gives it up, one without is maximized to the room and remembers the box it had. Which of the two it is must be read from the restore that came *in* and never from the one going out, because the two are never the same value — a maximize remembers a box and a restore gives it up, so they cannot agree — and a button that checked its answer against itself would do nothing at all, in both directions, forever, which nothing else about the pin would say; `a_maximize_button_answers_in_both_directions` asserts the structural property directly rather than the symptom, that a press never leaves the pin in the state it was handed. A wait shape (`box_is_the_wait`) is filtered out of the measured shape in both arms, since a square placeholder is not the file's aspect either and fitting to it is the stretch under another name. Around the decision is the lock rule every other reader of a pin keeps: `pin_maximize_inputs` reads the path, the dpi, the frame and the two boxes in one look and the lock is let go of before anything is measured, because `media_dimensions` takes other locks, reads the file and can spawn threads, and this is the thread that pumps the pinned window's own messages — a read held under the lock is a window that stops answering for as long as the file takes (the same rule `pin_swap_space` and `pin_update_plan` keep). The write is then re-taken under the lock and guarded on the state that was read — same path, same restore — so a walk that has landed elsewhere in between discards the result rather than laying a box decided for the old file over the new one; the tick answering that walk is already queued, so the right answer there is to let it have it, which is a decision not to write and is therefore made beside the write rather than before it. Restoring down puts back the box the window had before it was maximized, place and size alike, which is the plain undo of the maximize for as long as no hand has moved the window; a window that _has_ been moved is not a maximized window at all any more, and which way it was moved makes no difference: that maximize is given up as the drag is made, whether the hand carried it to another place or pulled it to a size of its own, which puts a maximize back in the caption and makes the button maximize the box the hand left behind (`pin_restore_box` keeps the box a restore puts back exactly so long as no drag has changed the window, and gives it up on the first one that does — a press that changes nothing, a box already against the room's own edge, is not a drag and leaves the maximize standing). The rule is one rather than two on purpose: a carry that used to keep the size a restore remembers and take only the place was answering a question the resize already answered, and what the hand has taken hold of is a window there is no longer a way back from. The box that is put back is a box for a file, not a rectangle: it belongs to whatever was on screen when the maximize was pressed, and a window that has since walked along the pin to a file of another shape and then restores down is drawn into it stretched. So the size stays the user's — a restore undoes a maximize, it does not resize — while the shape is the file's, fitted into that size by `pin_restored_box`, which is `pinned_media_box` asked of a chosen box rather than of a display; the file is the ceiling and not the shape, so a file taller than the size is given the full height and a width of its own rather than squashed. A file with no measured shape at all — a measure still running, a kind with no shape of its own — falls back to the remembered box verbatim, which is the only answer there is and the user's own. `a_restore_down_gives_the_file_on_screen_a_box_of_its_own_shape` asserts the aspect that comes back is the file's, that the box is never larger than the size chosen, and that a file whose shape *is* the box's shape comes back at that size in the middle of the room — which is what makes the rule a fit rather than a guess at some smaller box. A window dragged past an edge keeps a caption's worth of itself on the display, so it can always be dragged back — and so does one that is _taken up_ at an edge, which is where a hover placed beside a file near the top of the screen ends up: what is held to the display when a pin is created is the window rather than the media, so the caption and its buttons come back onto the screen and the media is given back the box they were taken from, shifted down by however much of them had fallen off it.

What a drag _draws_ while the hand is still moving is the frame scaled into the band as it stands at that moment — and a drag that changes no pixels draws nothing at all: a move is a `SetWindowPos` per pointer message and nothing else, because what a layered window is drawn from is the surface it already has and moving the window moves that surface with it, so the fill of the whole window, the composition of the media into it, the caption and the bar painted over it and the whole surface handed back to `UpdateLayeredWindow` that stood beside every one of those messages were a display's worth of pixels worked over for a picture that had not changed. A resize is the drag with something to draw, and a band that is not the frame's size is filled one of two ways. A frame whose pixels are opaque everywhere is _stretched_ into it by GDI: the frame is copied into a surface of its own — kept between messages, and the frame's size rather than the window's — and `StretchBlt` at `HALFTONE` scales it into the window's surface, which is the whole of what a still picture costs a step of the drag. The alpha byte is written back over the band afterwards rather than trusted to the stretch, because a 32-bit `BI_RGB` surface has no alpha channel as far as GDI is concerned and what `ULW_ALPHA` reads treats that byte as coverage. A frame that has an alpha channel is _sampled_ instead: the four source pixels around each destination pixel, weighted by how far into the square between them the point falls, composited over the backdrop where it lands rather than where it came from — GDI cannot be asked what is behind a pixel, and the squares of a checkerboard are placed by where a pixel is in the band rather than by where it came from. Either way the band is filled by the picture the hand is already holding, scaled the way an image viewer scales one. What it buys is the drag itself: a box changes on every pointer message, and a media decoded for each of them is a decode per message. What the media is drawn at when the box _stops_ changing is the other question a pinned re-layout asks, and it is answered properly there: the frame is loaded again at the size it is now shown at, on the preview thread, because a pin is not a hover and has no spinner to put up and no generation to match an answer against — and a frame the image cache already holds is handed back rather than decoded, so a box that changed once is paid for once. The kinds somebody else draws are cheaper: a player's window is resized, a browser is told the new bounds of the page it is already showing, and the media engine's surface is resized with the frames it hands back.

Minimize collapses the window into a round bubble: a window of its own, layered and topmost and never in the taskbar, painted by the same module as a circle in the theme's colours with the pin's own picture inside it where the kind has one — the frame already in memory, shrunk to cover the square and cropped to the middle of it — or a mark where it does not, and a soft shadow under it so it reads as lying over the desktop. It is put on the minimize button itself — that button's own box, centered on it, found in the caption's own layout rather than taken to be the window's corner, which is the close button's place and moves when a pin has nothing to maximize — and clicked to bring the window back, which goes up where a preview of it would have been placed at the bubble — the position mode the tray's `Placement → Position` asks for, made by the same algorithm every hover is placed by and asked for the box the window already has, so what the mode decides is _where_ the window goes rather than how big it is, with a pin collapsed while it was maximized the one box that is not placed at all — dragged by a capture of its own rather than left to the loop's ticks, which is the opposite of the bargain a pinned window's drag makes: a bubble that small is read against the pointer itself, so while the button is down the thread waits on its own message queue rather than on the loop's clock (`carry_bubble_drag`), and what puts the bubble where the hand is is the pointer's own place on the screen, less the offset the press took hold of it by — measured once, so taking hold of a bubble does not jump it by however far from its middle the press landed — rather than a delta between two mouse messages, because the coordinates a message carries are measured in the frame of the window the drag is moving: a delta taken from them is one this app has either already applied or never applied, and a window moved by its own messages chases the cursor instead of sitting under it. A press that has not moved past the drag slop places nothing, and a right click on it closes the pin, which is the one thing a collapsed pin can be asked for that has no other mouse route. A bubble is not a thing the pin key ends, either: it is a window the user put away on purpose and is working behind, so a press with Explorer in front brings the window back up on the file that has been picked since it went down, and a press with nothing picked does nothing at all — what is being asked for there is the file being walked through behind the bubble, and an end would lose the window rather than answer that. The window is put back up first (`restore_pin`) and the file is then swapped in by the path a pick takes (below), in the same tick and by the same rule, so the position and the scaling are the ones `Pin Mode → Update Preview` already produces rather than a rule of the key's own; the swap is held back to a tick with no load already in flight, since a window put back up without the file it was brought back for is a worse answer than the bubble it stayed in, and the file waits for the next press either way. A press on the bubble itself still closes the pin, and that is `PIN_HAND` doing it rather than a rule — a click and a drag are the same press to it. A collapsed pin is still a pin — previews stay held back, and what it was playing is held where it stands — so the bubble is the whole of what is on screen and the whole of what has to be clicked. What holds it is the tray's `Pin Mode → Pause Preview`, a sound and a video apart and both on: the media engine is paused where it stood and told to go on when the pin is put back up, while FFmpeg's player — which takes no pause at all — is ended with the second of the file it had reached, kept for the player begun in its place (for a video in the transport's own held second, for a sound in `BubblePause`). The park and its giving back are made on the loop's own tick (`settle_bubble_playback`), which is where a sound's clock lives — the moment its player was started and the second it was started at — and a park is not a player that came apart: `pin_media_is_alive` tells the two apart, or the pin would come down the moment it was minimized.

A video's transport is this app's own, because neither engine hands one over: FFmpeg's player draws no seek bar of its own, its keyboard controls need a focus this app's windows never take, and there is no way to ask it where it is. So the bar is drawn by `pin_chrome` — a play button, a track with the played part filled in, and the two clocks — and what is behind it is kept in `PinTransport`, which is what both engines can be asked: the length of the file, where this app's own clock says a player it started has got to, and whether that player is stopped. A video the media engine plays is asked directly: its position is its own, a seek is `SetCurrentTime` through the machinery a sound's seek already uses (a seek asked before the engine has read the file's header is kept until it has, and one asked of a session that is already playing is made where it is asked for — which is what makes a bar dragged a minute into a film the same thing as one dragged a second into it — and a seek made while the file is held moves the second the pause is drawn at with it, that second being this side's own rather than a clock that would follow the engine there), and a pause is the engine's own. A video FFmpeg plays is the other way round: the player can be told nothing once it is running, so the clock over its start is what the playhead is drawn from, and a seek would be that player ended and another begun at the second the bar was dragged to. What is _not_ done there is pretending otherwise: a bar whose player cannot be told anything is a read-out rather than a control — no button, nothing to drag, and the two clocks beginning where the strip does (`TransportState::interactive`) — because every control on it would be a question this engine cannot answer. The volume button is the one thing drawn on a read-out as well, because it is this app's control rather than the player's: the level a pin is given is the one `Volume → Video` names at the moment the pin is taken up — which is the level the preview was already playing at, both engines being started at that setting — and everything done to it afterwards belongs to that window alone (`PinVolume`), so a knob moved on a pin is a player begun at another level and never a write to the setting. The media engine takes a level while it plays, which is what makes a drag heard as it moves; FFmpeg's player takes one only by being started at it, so what a drag is owed is settled where the hand lets go — that player ended and begun again at the second its clock had reached — the same bargain a seek makes. The popup is the one piece of chrome drawn over the media band of a video FFmpeg plays, and that band is a window of somebody else's: while it is open the pin's window is put above that one and the tick's re-assertion of the player is held off (`pin_volume_open`), the panel being the only opaque pixels of ours in those rows. That is also why the caption of such a pin offers no maximize and its edges take no resize: the box would be a different one for a player's window to scale its picture into, and the picture it would show is a smaller one with bars around it. A paused picture keeps what the band was holding — the last frame the engine drew, and for a video FFmpeg plays it is empty where that player's window was, with no mark drawn in it at all — a drag shows where it is being taken rather than where the file is, and a file whose container says no length is a bar with no playhead to place — the two clocks read `--:--` — which is the truth about it.

## Configuration

Configuration lives at `%APPDATA%\rust-hover-preview\config.ini`. Changes are detected by the config watcher thread and applied without restarting. The app is the only writer of that file: the installer seeds nothing into it, so a fresh installation gets the settings of that build rather than the defaults of whenever the installer was packaged. The registry entry that runs the app at startup is written by the app on that same first run, from the setting that asks for it and at the path it is running from (`sync_startup_setting`), so the installer writes nothing there either. After that run the entry is what decides, and the setting follows it: the tray's item says whether the entry is there — asked of the registry rather than of the configuration, so one the user turned off in Task Manager reads as off — and that start brings the configuration into step with it.

The file is written in a fixed shape: the `[settings]` section first, under one heading per menu of the tray — a comment naming the menu, in the order the tray lists them, with the keys of a heading alphabetical — and then the sections that hold the file lists, in alphabetical order, keys alphabetical within them. A heading is a comment and nothing reads it back, which is what the grouping is for: the menu a setting is changed from is the menu it is found under. A menu renamed or moved is an edit to `SETTING_GROUPS` rather than a migration of every file that exists — the files are brought to it by the read instead, which writes a file again when it has not got a heading the table names, or lists them in another order (`headings_are_old`). The settings the tray has no item for (a decode curve, a face of a collection, the spinner's delay) are kept together under `Advanced`, and a setting `save` writes that the table does not name is written last of all under `; Ungrouped`. The INI reader the values are collected in keeps sections and keys in hash maps and writes them in whatever order those hand back, a different order on every write — so a file the user is meant to read and edit by hand was being reshuffled under them on each save. What `ordered_text` returns is the same text that writer produced, in an order that does not move, and a saved file read back and saved again is byte for byte the same.

What the file has wrong or missing is put right as it is read, and the file is written out again where it does not say what the app is using. One part is done before the read: the lists this app shipped and has since added to are brought up to the list of now (`repair_older_lists`), which gives an existing installation the formats added since — and divides the one video list of an older file into the two lists of this build, since a list holding exactly the entries the app shipped is the app's own and a list somebody edited is theirs. The rest is the read's own answer, asked of every file: what this app would write for what it has just read is held up against the file, key by key and both ways round (`differs`, over what `to_ini` holds) — every key the app writes has to be in the file holding what the app writes for it, and every key in the file has to be one the app writes. A file missing a setting (the line deleted, the whole section gone, a setting this build has that the file was written before it existed) is a file to write, and so is one holding a value the app does not read back as its own: a tone map that is not one of them, a delay past its ceiling, a face of a collection past the last one there is. A key the app does not write is a difference as well, and that is where the names this app has stopped writing go: `svg_scale`, `svg_background`, `off_trigger_key`, `transparent_background` and the rest are not names anything reads, so the setting they once named is at its default and their lines are dropped by the write. The names this build retired with the merged `Preview Types` gates are read the same way: `pdf_preview_enabled`, `pdf_scale` and `pdf_cache_mb` are `ebook_preview_enabled`, `ebook_scale` and `ebook_cache_mb` now; `office_preview_enabled`, `office_scale` and `libre_scale` are `document_preview_enabled` and `document_scale`; and `libre_preview_enabled`, `magick_preview_enabled` and `peazip_preview_enabled` are the gate of the kind each belongs to — so what those settings held starts at its default on the first read after an update, and their lines go with the first write. What is not compared is what is not a key — a comment, a blank line, the order the keys are written in — so a comment survives until a write happens for another reason, and goes with that write. A heading is the one comment that is read, and only whether it is there and where it comes in the run of them: a file grouped by an older arrangement holds the same keys as one grouped by this one, so the headings a file lists, and the order it lists them in, are the one sign of a file written before the settings moved or the menus were rearranged, and one write puts every heading back at once, in the order of the table (`headings_are_old`). Nothing here moves a value a user has: a default this app has changed its mind about is no reason to write anything, and a build that prefers another one writes it where there is nothing to overwrite, which is a fresh installation and nowhere else. A default that moves therefore reaches new installations only — a value in a file is read as a value somebody chose, and nothing in the file says who. Both are done at a start and on every reload of the file the watcher sees, so an edit that writes a value the app cannot read, adds a key of the user's own, or names a setting the way an older build named it, is put right where it is made rather than at the next start.

The tray and the file read one default each. A setting a menu offers values for starts at a `DEFAULT_*` constant in `config`, and what that constant names is read everywhere the value would otherwise be written out a second time: what an untouched setting is worth, what the tray's own item is marked `(Default)` for (`default_label`), and — for a value a setting no longer offers — what a file naming one is read as. The texture's half of the `Background` submenu is where the last of those is put to work: a texture is offered the two backdrops that are a page, black and white, because its alpha channel is as often a mask or a height as it is transparency, and a file naming one of the other two from before the half listed all four is read as `DEFAULT_DDS_BACKGROUND` (`sanitize_dds_background`). A default that moves is one edit, and the mark and the fallback move with it.

Which files each kind of preview covers is a list in the file, one section per kind — `[image]`, `[video]`, `[text]` (which carries the extensionless names beside its extensions), `[archive]`, `[office]`, `[font]` — written from the built-in list on first run and read back, so a format the app does not know is a file edit rather than a rebuild. The gate modules own them, each with the normalization that keeps a hand-edited entry safe to match against, and the hook and the renderer read the same lists rather than classifying a file twice.

A list is repaired rather than lost. A key that is gone comes back with the built-in entries and the file is written out again with them, which makes a hand-edit that removes too much recoverable: the reload that finds a key missing is also the write that puts it back. An empty value is not a missing one and is kept as written, because that is how a user asks for no files of that kind at all — the `Preview Types` gate is a switch over behavior, while an empty list is the kind configured away. What is read otherwise is exactly what the file says: a list anyone has edited keeps its own entries and its own order, and the entries a kind has gained since a file was written are the repair's business rather than the read's. That check writes a list only where the entries differ from the built-in list's, because a write moves the mtime, the watcher reloads, and a file written out for a change that was not one would keep the app writing for as long as it ran. Nothing else in the file is preserved across a write: `save` builds a fresh `Ini` from the known fields, so a hand-added section, key or comment is dropped the next time the app writes.

A list the app itself has changed is brought up by the repair rather than by the read. `svg` and `svgz` were added to the built-in image list, and a file holding exactly the entries the app shipped before they existed is the app's own older list rather than the user's, so the repair reads it as the current built-in list and the file is written again with the new entries in it. Without that, an entry added to a built-in list would reach a fresh installation only: every `config.ini` already written holds the list as it was, and a list that differs from the built-in one is otherwise taken for the user's own. A list with any one entry changed — added, removed or spelled differently — matches neither and is kept exactly as it is, and an empty value is kept empty. `IMAGE_EXTENSIONS_BEFORE_DDS`, `IMAGE_EXTENSIONS_BEFORE_CODEC_FORMATS`, `IMAGE_EXTENSIONS_BEFORE_SVG` and `IMAGE_EXTENSIONS_WITH_SVG` are those older lists and `repair_older_lists` is the check that reads them; the image, design and vector kinds are the ones with a history, and a kind whose built-in entries change again is added to it. Asking the question this way costs one thing, worth saying out loud: an entry a user took out can come back, because a list trimmed to exactly the entries this app shipped before that entry existed is this app's own as far as the check can tell. What that buys is the other half — the formats added since.

Themes the user adds live in `%APPDATA%\rust-hover-preview\theme`, beside `config.ini` and created on first run: a `.tmTheme` there is listed by the tray under its own file name (the stem, `atom-one-light` for `atom-one-light.tmTheme`), read from disk the first time a preview asks for it, and re-read whenever the tray menu is built, so a file added, edited or repaired is one menu-open away from taking effect rather than a restart. The folder itself is only ever listed — a file's contents are not touched until it is chosen — and it cannot shadow a bundled theme: a file theme is written `theme=custom:<name>`, while `light` and `dark` on their own always mean the bundled Atom One Light and One Dark Pro. A file that cannot be read or is not a theme is painted with the default, which is what the menu marks while the name it was chosen under stays in the file.

## Build And Packaging Notes

- The MSVC toolchain uses `rust-lld` via `.cargo/config.toml` for faster, more consistent linking.
- Windows resources are set in `build.rs` through `winres`.
- A release build ends a running copy of the app before the crate is linked, because Windows will not let the linker replace an open binary. `src` is watched so the rebuild an edit asks for is the one that gets it; debug builds are left alone.
- Release installers are produced by `cargo packager` (NSIS `.exe` setup).
- What the installers and the released `.exe` are built from is the `github` profile rather than `release`: `build-installers.ps1` packages with `--profile github` and the packaging metadata builds and reads that profile's output (`target/github`), so the artifact is optimized as one program over one codegen unit while `cargo build --release` keeps the thin-LTO profile the edit-build-test loop is short on.
- The NSIS setup is built from `packaging/nsis/installer.nsi`, cargo-packager's own template with its "Already Installed" page removed: an older installation is uninstalled silently before anything is copied, and a running copy of the app is closed without asking. The cargo-packager version the template was written against is pinned in `build-installers.ps1` and the deploy workflows, so moving to a newer one is a deliberate pin bump and a diff of that file.
