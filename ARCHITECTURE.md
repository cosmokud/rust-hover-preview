# Architecture

## Overview

Rust Hover Preview is a Windows 11 tray application that watches File Explorer focus and hover state, then renders a non-activating preview window near the cursor or focused item. It is split into a tray UI, an Explorer hook, and a preview renderer that communicate through lightweight shared state and message passing.

## Runtime Topology

- Main thread claims the single-instance mutex, initializes COM, config, DPI awareness, then runs the tray event loop.
- Preview thread owns the layered preview window and media decoding/rendering.
- The preview thread idles on its own channel rather than on a tick. While nothing is on screen there is nothing to animate, nothing to repaint and no pointer region to keep in step, so it waits on the preview channel itself and wakes when a hover arrives; the interval it waits on is only a ceiling on how long a window message — a resume, a display change — goes unnoticed. While a preview is up it keeps its sixty-a-second tick, which is what services animation frames, the streaming overlay and the pointer region.
- Explorer hook thread polls Explorer state with UI Automation and Shell COM APIs, and uses EnumWindows with CabinetWClass/ExplorerWClass class matching to count and classify Explorer browser windows so idle polling never spins up Explorer's shell automation providers.
- Wheel watcher thread installs a system-wide low-level mouse hook (`WH_MOUSE_LL`) and pumps the messages it needs, publishing a wheel-tick counter that the Explorer hook consumes so wheel scrolling refreshes the hovered item.
- Config watcher thread reloads `config.ini` when it changes on disk.
- Office engine thread is spawned by the first render request and ends itself once every engine it holds — one per family — has gone idle. It is the one apartment-threaded, pumped thread in the app — OLE automation marshals calls back into the thread that made them, and a thread that is not pumping them deadlocks — and nothing ever waits on it; see Office Render Engine.

## Single Instance

The app runs as a single instance per user session. `main` claims a session-local named mutex (`Local\rust-hover-preview-single-instance`) as its first step, before DPI awareness, COM initialization, config loading, and any thread is started. A second launch — from a desktop shortcut, the Start menu, the startup entry, or the `.exe` directly — finds the name already taken, closes its own handle, and returns from `main` without creating a tray icon, Explorer hook, or preview window. The guard handle is held for the lifetime of the process, so the name is released when the app exits, including after a crash or a forced kill, and the next launch becomes the primary instance. The `Local\` prefix scopes the guard to the signed-in session, so a second user signed in over Remote Desktop still gets their own instance and tray icon.

## Core Modules

- `main.rs`: single-instance guard, process startup, COM lifecycle, DPI awareness, thread orchestration.
- `single_instance.rs`: named-mutex guard that limits the app to one running instance per user session.
- `engine_processes.rs`: every process this app starts that it does not own the lifetime of — an Office engine, the browser that plays an animated document, the player a video preview runs in. Each is put in a job object, so that whatever ends the app ends it, and written down in a file of its own run, so that a run which never got to end them is answered for by the next one; see Started Processes.
- `explorer_hook.rs`: resolves hovered/focused Explorer items, handles path normalization, and sends preview messages.
- `cloud_files.rs`: whether a file's content is on this machine at all, so a preview never turns into the download a synchronizing provider would start.
- `wheel_input.rs`: system-wide mouse-wheel hook thread that publishes a tick counter, so a scroll that moves the list under a parked pointer is visible to the polling loop.
- `preview_window.rs`: layered window rendering, scale-aware sizing, animation streaming for GIF/WebP, FFmpeg-backed video playback with verified-PID process supervision (see Video Process Lifecycle), monitor-bounded placement with paint-before-show presentation, and the display-change and WM_POWERBROADCAST handling that resets state when the display under a preview changes, on system resume, and on suspend.
- `pdf_preview.rs`: first-page PDF rendering through the PDF engine that ships with Windows (`Windows.Data.Pdf`), with the page size cached per file, the page it drew held in memory up to `pdf_cache_mb`, and the file's own header confirmed before a path reaches the OS renderer.
- `image_formats.rs`: the gate for image previews, holding the built-in extension list that is written to `config.ini` and read back from there, and the normalization that keeps a hand-edited list safe to match against. Nothing is probed here: the decoder has the last word on whether a file is a picture at all, and it is handed one only after this gate has claimed it. `svg` and `svgz` are entries of this list and so sit behind the same gate, though what draws them is `svg_preview` rather than a decoder.
- `svg_preview.rs`: SVG previews — the size a document asks to be drawn at, the frame it is drawn into, and the parsed documents held in memory between hovers (a frame is never held, and never in the image cache). Nothing is decoded: a vector has no native size, so the document is rasterized at the box the layout planned, which is what makes a scaled-up preview sharp. A gzipped `.svgz` is inflated here rather than by the parser, text is drawn from the machine's font database read once, and a document cannot pull in a file beside it: `Tree::from_data_nested` ignores `<image>` elements linking to external files, and a document's own script is never run.
- `svg_animation.rs`: playing a document that moves, from either of the two ways it can say so — the declarations in its markup (`<animate>`, `<animateTransform>`, `<set>`) and the `@keyframes` its stylesheets name, matched to elements by selector — as the value each has at a moment, written back into the document per frame, since usvg drops animation entirely. Numbers and colors are interpolated, a transform is composed over whatever the element already had with CSS's own origin honored, and the two timings a keyframe block can carry are read for duration, delay, repeats and fill mode. Event-based timing, `additive`/`accumulate`, spline interpolation and easing curves are not, and a value that cannot be blended is held rather than guessed at; a declaration outside all of this is one animation fewer, and a document whose animations are all outside it is drawn as the still it is.
- `webview_preview.rs`: the browser engine that plays a document `svg_animation` cannot — the WebView2 runtime Windows 11 ships with — held warm on a thread of its own with a window of its own, because a layered window has no window tree to put a child in (the same shape as the video path, where the player's window is the preview). The preview loop asks whether a document moves and hands it over with the box the layout came out with, and the still frame this app drew stays underneath until the engine's window lands on top of it. One engine is kept per app and let go after `webview_idle`, ten minutes by default; its settings are the app's rules rather than a browser's — script off, nothing fetched from anywhere (a resolver rule that answers for no host), no context menus, devtools, accelerator keys or zoom — and it keeps a profile folder of this app's own under the local profile. The browser process it starts is adopted like an Office engine, so that neither a crash nor a kill can leave it running; see Started Processes.
- `video_formats.rs`: the gate for video previews, holding the built-in extension list that is written to `config.ini` and read back from there, and the MPEG-TS sync-byte probe that settles the `.ts` and `.mts` the text lists share — a list a user edits, so an extension added to it is a video from the next read, with only those two ambiguous names costing a probe.
- `archive_formats.rs`: the gate for archive previews, holding the built-in extension list that is written to `config.ini` and read back from there, the dotted-tail rule that makes a `tar.gz` entry mean a tarball, and the normalization that keeps a hand-edited list safe to match against.
- `archive_listing.rs`: reading an archive's own table of contents — zip's central directory, 7z's header block, RAR's header walk, tar's 512-byte headers — into one list of entries, with the entry cap, the name cap, the cancel flag every scan asks, and the listing cache.
- `archive_preview.rs`: turning a listing into a page — the tree the entries imply, the collapse of single-child folders, the sort, the capped rows, the summary line, and the paint through the text painting layer.
- `office_formats.rs`: the gate for Office previews, holding the built-in extension list that is written to `config.ini` and read back from there, the normalization that keeps a hand-edited list safe to match against, the container probe that asks a file's own header whether it is an OOXML package or an OLE compound file, the engine each family is rendered by, and the box a preview is placed for while its page is on the way.
- `office_preview.rs`: measuring and drawing the page the render tier produced — how large the source may be drawn, and the frame it is drawn into. Nothing is held in memory here: the page belongs to the render tier, and what this module does with it is read its size once and draw it.
- `office_render.rs`: the render tier — the apartment-threaded engine thread and its recovery, the engine it holds for each family, the late-bound automation that exports page 1 and takes a workbook's picture where no page can be exported, the temp-copy hygiene for the paths and zone identifiers Office will not open, the scratch file every render passes through, the in-memory cache the rendered pages live in, and the diagnostic test that drives one document of each family through the real path when one of them refuses.
- `text_formats.rs`: the gate for text previews, holding the built-in extension and file-name lists that are written to `config.ini` and read back from there, the dot-file rule that makes a `gitignore` entry mean `.gitignore`, and the normalization that makes a hand-edited list safe to match against.
- `text_preview.rs`: reading and decoding a text file, styling a window of it on demand, laying that window out, and painting it — with a scrollbar when the file is longer — into the same BGRA frame an image arrives in, and the cache those painted frames are held in.
- `text_paint.rs`: the painting both painted previews share — the top-down DIB surface, the font metrics and the fonts grown from them, the color helpers the themes are read through, and the one function that puts a run of text on the surface.
- `text_theme.rs`: the color themes — the two bundled TextMate themes and the user's own `.tmTheme` files, each parsed once and kept — plus the scope lookups that answer "what color is a heading in this theme?", the fallback that keeps a broken file from taking the preview with it, and the reading counter that tells a cached document which version of a file it was colored against.
- `theme_files.rs`: the `theme` folder beside `config.ini` — which of its files are themes, the names they are listed and written under, and the path a name resolves to.
- `tray.rs`: tray icon and menu, configuration toggles, exit flow, WM_POWERBROADCAST handling to re-add the icon after DWM/Explorer restart on resume, and the `TaskbarCreated` broadcast that re-adds it when Explorer itself restarts — the restart the Explorer hook is told about, since the Shell objects it resolves through belonged to the process that is gone.
- `config.rs`: INI-backed configuration with defaults and input sanitization.
- `startup.rs`: registry integration for the Run-at-startup setting.

## Media Pipeline

- Images (static, GIF, WebP) are decoded in the preview thread, with animated formats streaming frames into a shared queue.
- A decoded still image is kept between hovers, keyed by the file, the version of it that was read and the pixel size it was decoded at, and dropped least recently used first when it no longer fits `image_cache_mb`. See Image Previews.
- An animated preview opens on its first frames rather than on a startup buffer: the handover decides when the preview appears, not how much of the animation is played, and the decoder runs on ahead of playback once it has been handed over.
- The preview window uses GDI and `UpdateLayeredWindow` to draw to a topmost, no-activate surface.
- Video previews launch `ffplay` for playback and query `ffprobe` for video geometry at the same time as the cropdetect pass that finds the letterboxing: neither needs the other's answer until the crop is validated against the dimensions, so a hover waits for the slower of the two rather than for both in turn. The player's lifetime is supervised as described in Video Process Lifecycle.
- PDF previews render page 1 through `Windows.Data.Pdf`; see PDF Previews for the split between measuring a page and rendering it, and for the cache a rendered page is kept in.
- SVG previews are parsed and rasterized in-process at the box the layout planned, and a document that moves is played frame by frame through the same streaming queue the animated image formats use; see SVG Previews for what a document is not allowed to reach and for how much of SMIL is played.
- Text previews are read, decoded, highlighted and painted in-process; see Text Previews for the split between the document, the layout and the frame, and for the cache a painted frame is kept in.
- Archive previews read the archive's own table of contents and paint a page from it, on the same worker thread and into the same BGRA frame; see Archive Previews for what a scan is allowed to read and how far it goes.
- Office documents are previewed from the page the render tier produced — a PDF page, a slide's image or a workbook's picture, drawn into the same BGRA frame; see Office Previews.

## What A Hover Is Allowed To Read

Everything that reads a file's bytes is bounded, and the bounds sit at the two places a read can start: the hook's resolution gate, and the loader that actually opens the file. Both ask the same questions, the way both already ask what kind of file something is, so a file one of them refuses cannot be reached through the other. What the ceiling on any of those reads *is* is one number rather than one per format — `decode_budget_gb` in `config.ini`, a gigabyte by default, and the tray's `Performance → Decode Budget` — and every reader is handed it before it allocates, so what a hover may cost is bounded the same way whatever the file turned out to be.

A file whose content is not on this machine is refused before anything opens it. OneDrive, SharePoint, Dropbox and the other synchronizing providers leave a placeholder in the folder — a few kilobytes of metadata carrying the name, size and dates — and pull the content down the first time something reads it. Nothing about the file says so: an ordinary open is what starts the transfer and the reader simply waits for it. That wait is unbounded, it is a download the user never asked for, and on a metered connection it is a bill, so a placeholder is answered with no preview instead of with a read. `cloud_files.rs` asks the file's *attributes*, which is a question about its directory entry and is the same question the shell asks to draw the cloud state in a file's icon; unlike opening the file, it does not start the download.

An image is bounded by what decoding it may ask for rather than by its own shape. Its header is still read first, but for the box the frame is decoded into rather than for a yes or no: what a decoder is handed is that budget, and it is asked before anything is allocated, so a seven-thousand by ten-thousand illustration, which is an ordinary thing to hover, is decoded at its own size, while a file that asks for more memory than a preview could justify is answered with no preview. That is the shape a decompression bomb has, and it is the shape of this bound for a reason: `catch_unwind` turns a decoder that returns an error into a missing preview, while an allocation as large as a huge image asks for is an abort rather than an unwind, and an abort takes the tray icon with it. Every reader is therefore handed the budget before it allocates — the decoders through `image`'s own limits, and the two that allocate a canvas of their own, the GIF's and the animated WebP's, through the same check. A header that will not report its dimensions is not a reason to refuse the file — the decoder has the last word on whether it is an image at all — so those are decoded as they always were and simply are not held in the cache.

An archive is bounded by its own table of contents, which is the only part of it a listing reads. Nothing is decompressed: a zip's central directory is one read at the end of the file, a 7z's header is one read at its end, a RAR's headers walk from the front skipping each member's data, and a tar's headers are the 512-byte blocks between the data — so a hover onto an archive of five gigabytes costs what a hover onto a small one does. A scan stops at twenty thousand entries and cuts a name that has run past three hundred characters, and every loop asks the same cancel flag the load worker already holds, so a pointer that has moved on leaves the reading behind. The one format that cannot be read this way is a `.tar.gz`, whose table is not addressable at all: it has to be inflated to be walked, so its stream is capped at sixty-four megabytes, and past that the page says the listing stopped early rather than reading on.

An Office document is not read by this app at all. What a hover shows is the page Office drew for it, so the only thing this side does with the file is ask its own header what it is — an OOXML package or an OLE compound file, from eight bytes — before a path is handed to an engine, which is what keeps a file that is not a document at all from starting one. Everything a document holds is read by Word, Excel or PowerPoint, in its own process.

That process is bounded on this side instead. A document whose content is still in the cloud is never handed over, because the engine's open would be the download; a file carrying a zone identifier — the Protected View trigger — or a path longer than Office can take is rendered from a temp copy, which also keeps the engine from locking a file the user is working in; documents are opened read-only, without touching the recent-files list, in a hidden window; and a page is asked for the moment a hover exists rather than after the pointer has rested on the file, so the dwell a page waits for is the same hover delay every other preview waits for.

UI Automation is bounded by a timeout, set on the client when it is created. Every probe crosses into the shell's own thread, so a shell that has stopped answering would hold the hook inside a probe for as long as it likes, and the slow-probe backoff cannot see a probe that has not returned yet, which leaves an unbounded wait with nothing watching it.

The bound belongs to the client object rather than to the query, so the client has to be one that carries it: `CUIAutomation8` is created rather than the legacy `CUIAutomation`, which does not answer for `IUIAutomation2` at all. That distinction is not academic. Treating the missing interface as fatal — on the reasoning that a client which cannot be bounded looks bounded while able to block forever — is what answered every hover with no preview, because refusing the client left the resolver with no automation at all rather than with a slower one. A client that cannot be bounded is therefore still used, with the legacy object behind it as the fallback: what a client that ignored the timeouts costs is the wait this was meant to remove, which is the behavior the app had before, and not a dead app. A probe that times out is a probe that found nothing, which is what the rest of the hook already handles.

An SVG document has no cap of its own. A file is read whole and parsed whole, and what bounds it is the budget every other read is answered under, inflated size included — a `.svgz` is a few kilobytes that can inflate to a great many, and both counts are asked for before they are allocated — because a document's own size is what its visit costs, and a cap of its own would refuse documents the budget would have allowed. What is bounded here instead is what a document may *reach*: the nested parse ignores `<image>` elements linking to external files, the fonts are the machine's own database rather than any a document names, and a document's script is never run.

## Image Previews

A still image is decoded, resampled to the size the layout asked for and converted twice — to RGBA and then to BGRA — and a file list is a place a pointer is swept back and forth over, so the frame that was already built for a file is handed back rather than built again. What a held frame is valid for is the file, the version of it that was read, and the pixel size it was decoded at. The version is there because a file edited in place has to be decoded again, and the *size* is there because a frame is stored decoded and scaled: the same photo shown at 100% and at fit-to-screen really is different pixels, and only the size that was asked for can be handed back for it. A header that will not report its dimensions cannot name that size, so a file measured that way is decoded as it always was and simply not held.

The cache is bounded by bytes rather than by entries, because what a preview holds is its pixels and a folder of thumbnails and a folder of wallpapers are not the same number of files. `image_cache_mb` in `config.ini` is the budget — 32 MB by default, capped at 2048, and `0` for a cache that holds nothing — and it is read from the configuration each time the cache is used rather than captured, so an edit applies without a restart. It is trimmed to that budget on every use, least recently used first, with a counter for the order rather than a clock so the order cannot be changed by the system clock moving; trimming on use is also what makes lowering the setting, to zero included, release what it no longer covers instead of leaving it held until something else happens to be stored. A frame larger than the whole budget is not held at all, because it would evict everything else and still not fit.

The cache is consulted *before* the decode rather than after it, which is what the header read buys: the size the frame would be decoded into is known before anything is decoded, so a hit never pays for a decoder at all.

## PDF Previews

A PDF preview shows page 1, rendered by `Windows.Data.Pdf` — the PDF engine that ships with Windows — so the app bundles no renderer and the user installs nothing. Two threads do this work, and both initialize a multithreaded apartment (`CoInitializeEx(COINIT_MULTITHREADED)`) before their first call, which is what WinRT requires of the calling thread.

The preview thread measures the page before anything is decoded, because the preview is positioned and sized first: the page size the engine reports (DIPs, 96 per inch) is what the layout is computed from, the same way video geometry is resolved up front. That probe is cached per path, failures included, so a file is parsed once and an unreadable file is not re-parsed on every hover. The render records the page size it read in the same cache, because both steps open the document: what the render already read is what the next measure would otherwise have opened the file again to find. Before a path is handed to the renderer it has to carry a `%PDF-` header in its first kilobyte, which is what keeps a mislabeled file out of the OS parser.

The document is opened from a stream over the file itself — not from a copy of it read into memory first, and not through `StorageFile`. `StorageFile.GetFileFromPathAsync` rejects the verbatim `\\?\` form the hook canonicalizes shell paths to: it fails with `ERROR_BAD_PATHNAME` while the same file opens through a plain path, which is why a PDF previewed from a search result but not from a folder view. A PDF is read by seeking in any case — the object graph is found from a table at the end of the file, and a page's own content and the resources it names can be anywhere in it — so reading it into memory bought nothing a seek could not have, and what it cost was the whole file held, twice over, while the page was parsed. `SHCreateStreamOnFileEx` is handed the path directly rather than the WinRT broker being asked to resolve it, so it accepts every path form the rest of the app produces, long and UNC paths included, and `CreateRandomAccessStreamOverStream` wraps that COM stream as the `IRandomAccessStream` the engine asks for. What a hover onto a large PDF costs is now proportional to the page rather than to the file.

The decode worker then renders page 1 into exactly the pixel size the layout asked for, after fitting the page's own aspect ratio into that box, so a page that is not the shape the layout assumed is letterboxed instead of stretched. Rendering at the target size is also what keeps a scaled-up preview sharp: `100%` is a 96 DPI page, while 200% or fit-to-screen is rendered larger rather than enlarged afterwards. Because of that, a PDF is laid out at fit-to-screen rather than at the configured percentage — the largest size the display allows is also the most legible one, and every percentage at or above `100%` asks for at least that room — while a percentage below `100%` is a size the user picked, and reduces the fitted size rather than being ignored: `25%` shows a quarter of what fit-to-screen would. `effective_preview_scale` is the single place that decides it, so the layout and the render can never disagree about the size. The renderer is asked for its BMP encoder, which turns the decode on this side into a header parse instead of a PNG inflate, and the page is painted on an opaque white background so its text stays readable over any `image_background` mode. From there the result is an ordinary static frame: the existing spinner covers the wait, and a render that finishes after the cursor has moved on is dropped by the same generation check as every other load.

What was drawn is kept between hovers, keyed by the file, the version of it that was read and the box it was drawn into — a page is stored as the pixels it was rendered as, so the same PDF at fit-to-screen and at `25%` really is different pixels, and a file edited in place has to be drawn again. `pdf_cache_mb` is the budget — `32` by default, capped at `2048`, and `0` means a cache that holds nothing rather than a preview tier that is switched off, since the page is drawn for the hover that asks for it either way — read from the configuration each time the cache is used so an edit applies without a restart, trimmed to that budget least recently used first on every use, with a counter for the order rather than a clock, and a page larger than the whole budget is not held at all because it would evict everything else and still not fit. The cache is consulted before anything is opened, so a hit never pays for the engine, the header probe or the parse.

## SVG Previews

An SVG is not a picture to a decoder but a document of shapes, gradients, texts and images, so a preview of one takes the PDF path's shape rather than the image path's: the size the document asks to be drawn at is read from the document itself, the layout places that size, and the renderer draws the box that comes out. That is also what makes an enlarged preview sharp — a vector is rasterized at the size it is shown at, never decoded at a native size and resampled into the frame. Where it does *not* follow a page is the configured percentage, which means the document rather than the window: `100%` is the size the document asks for, `50%` is that at half, and fit-to-screen is the room the display has — the rule a picture follows, since a document is one that happens to be drawn rather than decoded. A document says how large it wants to be, and a preview that filled the display with a small document and left the rest of the window empty behind it was answering a question nobody asked. What it is drawn over is a setting of its own — `svg_background`, the tray's `Background → SVG Background` — rather than the backdrop a picture gets, because a document is drawn on a page where a picture's transparency is the picture's: the renderer tells the two apart by the kind of media a file became — `MediaType::StaticSvg` or `MediaType::AnimatedSvg` against every other kind — so a document drawn once, one this app plays, and the still frame that waits under the engine's window are all drawn over the document's backdrop.

A parsed document is held in memory between hovers, and a drawn frame is not. A hover meets the same document several times — the layout measures it for the box, the loader measures it again to scale that box, and the renderer parses it once more to draw it — and the parse is the cheap half of a vector to keep: a tree of paths and styles is small next to the frame it draws, and what a second hover of the same file would otherwise pay for is that parse all over again. Documents are therefore held, keyed by the file and the version of it that was read — a file edited in place is parsed again, and a version that turned out not to be a document is remembered as that rather than read on every pass — up to sixteen of them, dropped least recently used first, and the lock is never held across a parse, so the layout measuring on one thread and a load drawing on another do not wait for each other. A frame is never held: it is as large as the display's room, it can be drawn again from a tree already in hand, and an SVG frame has no business in the budget `image_cache_mb` counts for photos. Nothing is written to disk — what is held lives in the process and goes when it does.

What a document may reach is bounded, though not by its size: a file is read whole, and a gzipped `.svgz` is inflated on this side rather than by the parser. The parse is the nested one, which ignores `<image>` elements that link to external files, so a document cannot use a hover to have a file beside it — or anywhere else on the machine — opened and drawn; an embedded `data:` image is part of the document and is drawn. A document's script is not run at all, because this is a renderer and not a viewer. Text is the one thing a document asks for that comes from the machine, and it is drawn from the system font database, read once on the first SVG preview: usvg has no fonts of its own, and a document of nothing but text comes back blank without it.

A document that moves is played rather than drawn once. usvg drops animation altogether — "no events and no animations" is its own description of itself — so `svg_animation` reads the declarations the document carries, works out what each of them is at a moment, and writes the document out again with those values in it for the renderer to draw. Frames go into the same streaming queue a GIF or an animated WebP fills, one per thirty-third of a second, and the producer runs only as far ahead as the queue has room for: a pass that fits in the player's window is drawn once and looped from memory, and one that does not is drawn again for each loop. A pass that was cut short — the animations of a document whose own cycle is longer than the frames a preview plays of it, such as a clock whose hour hand takes twelve hours to come round — is not looped at all but played *forward*, so what a hover shows keeps time rather than jumping back when the ten seconds are up; that is the difference between a second hand that sweeps and one that snaps back every ten seconds. A frame costs a parse and a rasterization — about one to four milliseconds for an eight-hundred-pixel preview, depending on what the document draws — which leaves the cadence a wide margin.

Where the machine has the WebView2 runtime — Windows 11 ships it — a document that *declares* animation is handed to `webview_preview` instead, and this reader is what plays it on a machine that does not. The engine is Chromium, so it plays the whole of SMIL and CSS rather than the subset above, and what this app draws for such a document is the still first frame the engine's window lands on top of: a hover shows the document rather than a gap while a browser starts, and a document whose page never arrives simply stays still. The declaration is what decides whose it is, not this reader: a document that moves in a way the reader cannot follow is still one for the engine, and a document that does not move never starts a browser at all.

What the engine is pointed at is a page of this app's own with the document in it as an image, and that is what makes the document the size of the preview box. A browser lays a standalone SVG out at the size the document asks for and does not stretch it to the window — a 120-pixel document in a display-sized window is a 120-pixel picture with the rest of the window empty, and a document with no size of its own fills the window and is magnified by any factor put on top of that — so the two disagree at every scale except the one that happens to match. An image, on the other hand, is drawn to the box it is given whatever its own size is, by layout rather than by magnification: `100%` is the document at the size it asks for, `50%` is the whole of it at half size, fit-to-screen is the whole of it as large as the display allows, and what is on screen is a document and not a corner of one. Nothing is given up for it, and something is gained: an SVG drawn as an image is animated and not scripted, cannot take the pointer, and cannot reach anything outside itself, so the engine's rules are the image's rules — which is why the page is written rather than the document being put in it as markup. The page is a few hundred bytes in the run's own folder, rewritten for each document, pointing at the document through a URL versioned by the file's modification time so that an edited file is never answered out of the browser's cache.

What that page and its image are pointed at is a URL rather than a path, and the path a hover carries is the Shell's — the verbatim `\\?\…` form, which no browser will open and which a browser refuses silently — so the prefix comes off and a share keeps its server on the way (`file:///C:/…`, `file://server/share/…`). Beginning the engine costs a browser start — a quarter of a second measured on this machine, nearly all of it the controller — so getting there is not free either. `webview_preview` is where the accounting continues: the window, the warm holder, the idle timeout and the rules the engine runs under.

An engine that cannot be had does not cost a preview, and the first line of defence is that it is not asked to share anything. The engine's state lives in one user data folder, and one folder is one browser at a time: an environment pointed at a folder another browser is holding is answered with `ERROR_INVALID_STATE` when it asks for its controller. That other browser can be a leftover — one left by a run that ended badly, whose app is gone and which holds the folder for as long as it lives — so the folder is a *folder per run* (`%LOCALAPPDATA%\rust-hover-preview\webview\<pid>`), and the folders earlier runs left are cleared at startup, best effort, since one still held cannot be removed and is not this run's to insist on. No run can therefore be blocked by any other, and the worst a leftover costs is disk until the next start.

What remains is defence in depth for an engine that fails for any other reason, in three parts. The controller is asked for four times over a couple of seconds before the attempt is given up. A failure is remembered for five minutes, during which a document that moves is the reader's rather than the engine's, so the picture plays rather than sitting still. And the preview that was up is replayed through the same path a display change uses, so the still frame a hover opened on is replaced by the reader's own animation as soon as the engine has been found wanting — the first hover, not just the next one. A tracer (`RHP_WEBVIEW_TRACE`) and a folder override (`RHP_WEBVIEW_PROFILE`, which is what the probes use so they can run beside a running app) exist for the same reason the other probes do: an engine that does not come up says nothing by itself.

Two front ends feed that one model, because a document says what moves in either of two ways. The declarations in its markup — `<animate>`, `<animateTransform>`, `<set>` — are read from the element they animate, which is the one they sit inside or the one their `href` names: a document may keep a declaration apart from what it moves, and a clock does, putting its three hands at the end of the file and the three animations that turn them in `<defs>`, each pointing at a hand by id. Both spellings of the attribute are read, `href` and the `xlink:href` older documents use, and a name that resolves to nothing falls back to the element the declaration sits in. The stylesheets a document carries are read as stylesheets: `@keyframes` blocks by name, the rules that name them matched against the document by type, class, id and the descendant and child combinators, and the `animation` shorthand or its longhands read for the duration, delay, repeat count and fill mode. Inline `style` attributes are read the same way. Where both reach the same attribute of the same element the stylesheet is written last, so it is the one that shows, which is the order a browser's cascade puts them in.

The subset played is a real one rather than the whole specification. Numbers and colors are interpolated between the values a declaration names; a transform is composed over whatever the element already had, and a keyframe that says `transform: none` is the identity of the ones that do not, which is what makes a rotation from nothing play; a keyframe block that names only one end of an animation starts or ends at the value the element already carries; and `keyTimes`, `dur`, `repeatCount` and `fill="freeze"` are honored — as are a CSS pass's own timings and its `transform-origin`, percentages of the element's box under `transform-box: fill-box` included, which is what turns a spinner about its middle rather than about the corner of the canvas. What is not read is event-based timing, `additive` and `accumulate`, `calcMode="spline"`, and `direction` or `play-state`; timing functions are drawn linearly rather than eased; a percentage in a transform's own arguments is refused rather than resolved; and a value that cannot be blended is held until the next one instead of guessed at, which is what `calcMode="discrete"` means anyway. A declaration that asks for something outside all of this is one animation fewer, and a document whose animations are all outside it is simply the still document it was before any of this existed.

A document that will not parse, or whose size is not a size, is answered with no preview, which is the answer a file that will not decode gets. An SVG is its own kind under `Preview Types`: `svg` and `svgz` are entries of the image list, which is what gets a document past the gate that claims it, but what draws one is not a decoder and what plays one that moves is a browser, so the switch for them is not the switch for pictures.

## Text Previews

A text preview shows the first screenful of a text file, colored by the syntax definition its extension names. Which files those are lives in `config.ini`, written from the built-in lists on first run and read back from there, so a user can add a format or remove one without a rebuild; `text_formats.rs` owns both lists and the normalization that keeps a hand-edited entry from matching anything but a bare extension. Both the Explorer hook's "is this previewable" gate and the renderer consult it, so the two cannot disagree about what a file is.

There are two lists because one cannot reach the files a repository is recognized by. Extensions are matched the way the filesystem reads them, which leaves out `LICENSE` and `Makefile` (no dot at all) and, less obviously, `.gitignore` — a leading dot begins a *name*, not an extension, so `Path::extension` reports none for it. The extension lookup therefore falls back to the name minus a leading dot, which is what makes a `gitignore` entry mean `.gitignore`; and a second list of names carries the extensionless files, matched whole, case-insensitively, with the same dropping of a leading dot on both sides so that `gitignore` and `.gitignore` are one entry in either list. A file is in when either list claims it, so `.eslintrc.json` is still read by its extension while `.eslintrc` is read by its name. `is_text_file` is the one gate both sides ask, so a file the hook offers is a file the renderer can draw.

Text has no size of its own, so the two-step shape of the PDF path is repeated with a different measurement: `measure` resolves the box the first screenful wants, bounded by the display it will be shown on, the layout fits that box into the space beside the cursor or focused item, and `render` is handed the box that came out and fills it. What differs is what the box means. A PDF page is a vector and is drawn at whatever size the layout asks for; text is drawn at a fixed font size scaled by the display's DPI (`GetDpiForMonitor` on the monitor under the hover, falling back to 96), so scaling the box would only stretch the window around text that stays the same size. `effective_preview_scale` therefore answers `100%` for text — never enlarged, reduced only when the space beside the cursor cannot hold it — and the renderer reads the box it is given as "as many lines and columns as fit". What the fit must not do to a text box is shrink it whole: the lines wrap at the width the box ends up with, and a narrower box needs more rows than the proportional height leaves — a long line that took two rows at the display's width takes three in the box that comes back, and a frame sized for the two showed only the first of them, which is a long line that looks unwrapped. The document is therefore measured again at the width the box came out with, and that box is placed again from the measurement, so its height is the height the text really takes at the width it wraps in. A two-line file gets a two-line window — more when its lines wrap — and a long file takes the largest box the display allows, which is the same thing fit-to-screen does for a PDF.

The tray's `Text Preview → Font Size` setting multiplies into that: `TextMetrics` scales the display DPI by the configured percentage into one scale, so the glyphs, the line spacing and the page margin grow together and a preview at 200% is the same page twice the size rather than the same page in a larger box. The size is deliberately not part of the parsed document's cache key — the styled lines are identical at any scale, and only the layout changes, so changing the size repaints from the cache instead of re-reading the file. The combined scale is bounded (0.25x to 16x), which is what lets a hand-edited `text_font_scale` of any percentage be used as written without asking GDI for a glyph taller than the screen.

Previews are also gated by kind, from the tray's `Preview Types` submenu: `image_preview_enabled`, `video_preview_enabled`, `text_preview_enabled`, `pdf_preview_enabled`, `archive_preview_enabled`, `office_preview_enabled` and `svg_preview_enabled`, all on, switched through `config::PreviewType`. A gate is only whether previews of that kind may be shown at all — the lists and settings that decide which files of that kind are previewed are untouched, so a kind switched off and back on restores what was configured. Both halves of the app ask: the Explorer hook's media gate asks the kind of a file — video first, because only content settles the `.ts`/`.mts` the text list shares, then PDF, then the text lists, then the image list — and the renderer asks the same question when it measures a preview, so a preview cannot be laid out for a kind that is off. A document is asked about in the same order and by both halves — the image list first, then whether the file is one — so `svg` and `svgz` are under `SVG` rather than under `Images`: pictures switched off leave a document previewing, and a document switched off leaves pictures alone. `text_preview_enabled` is checked in `text_formats::is_text_file` ahead of both lists, so turning text previews off is one gate the hook and the renderer both already consult, and the lists survive for when it is turned back on. A kind switched off takes the preview of that kind with it: the tray hands the preview thread a type change, and a preview whose own kind is the one that changed is rebuilt from the hover it came from, which drops it because the layout finds no size for a file whose kind is off — a preview of any other kind is left as it is, so a running video is not restarted by a toggle it has nothing to do with. The engine behind a kind goes with it as well, since what an engine is for is previews of its own kind: `Office` ends the Office processes, and `SVG` lets the browser go. The Office ones are ended from the tray rather than asked of the worker — a worker inside a COM call it cannot cut short would hold one of them for good, and the tray may not wait on one — while the browser is let go by its own thread, which reads the gate rather than being told about it. A gate written into `config.ini` rather than clicked in the tray is answered the same way, by each engine's own thread, so the switch is the same switch however it is thrown.

The colors come from the theme selection, and the selection can be a file the user wrote: `text_theme` answers from one of the two bundled TextMate themes, or from the `.tmTheme` a selection names in the `theme` folder beside `config.ini` (see Configuration). Both are read by the same reader, and a file is read when it is asked for rather than when the folder is listed, so a folder of themes costs nothing until one is chosen; the menu is what lists the folder, and opening it is also what drops the parsed files so that the next preview reads them again. A file that is missing, unreadable, or not a theme is answered with the default — Atom One Light — instead of nothing: the renderer is handed a theme it can paint with, the item keeps its place in the menu, and the selection stays in `config.ini` until another theme is chosen, so a repaired file is used as soon as the menu is opened again.

The parsed document is cached per path, modification time, length, theme and Markdown mode — plus, for a theme that came from a file, the reading of it the document was colored against, since a file can be edited under a name that does not change — so a second hover, a repaint, or a theme switch costs a layout rather than a parse. What is cached is the *text and where its lines start*, not styled lines: the line table is eight bytes per line and no parsing at all, which is what lets a preview know how tall a document is — and how far it can scroll — before anything has been colored. Styled lines are built per window by `styled_window`, kept in a small per-document cache, and indexed by absolute line number, so a window that already covers a scroll position costs nothing and the window the layout asks for is sized from the box. For a source file the parser runs from wherever it left off, or from the nearest of the checkpoints taken every few dozen lines, and only the requested lines are kept: nothing past the window is ever styled, and a jump in either direction is bounded by the checkpoint spacing. The parse state itself cannot live in the shared cache — syntect's `ParseState` holds pointers into Oniguruma's match regions and is not `Send` — so it is kept per thread in a `thread_local`, and the windows, which are plain data, are shared between the threads that measure and paint. Four producers fill that model: `syntect`, with the syntax definitions `two-face` adds on top of the ones it bundles, colors source and markup files; `pulldown-cmark` turns a `.md` file into the document it describes, handing fenced code back to `syntect` and asking the theme for the color of a heading, a quote or a link by scope, so a rendered document and a highlighted source file share one palette — it is the one producer that reads all of its input, because a rendered line's place in the document is only known once the block before it has been walked, and it keeps only the window's lines as it goes; an RTF control-word stripper reduces a `.rtf` file to the text it carries, skipping Word's own tables, once, at load; and an NFO reader decodes CP437 art and consumes its ANSI escapes into colors toned toward the page they are drawn on. The one producer whose lines are not the file's own is the rendered Markdown document: a paragraph is one line, a heading is one, and the blank line between two blocks is one the source does not have, so the walk that renders the document is also what counts what it drew — once, when the document is built — and the preview's scroll range, its scrollbar and the lines it says are left out are all measured in those lines. Reading is bounded — 2 MB and a 2000-line scroll range — and decoding decides the encoding from the file: byte order marks first, then UTF-8, then the legacy code page CP437 belongs to. Two guards keep non-text out: NUL bytes mean the file is not UTF-8 text (a UTF-16 file is recognized from where its NULs fall, and anything else is binary), and a decode that is mostly control characters is a binary file that happened to pass.

What is painted is kept as well, keyed by the file and its version, the options a preview was painted with — theme, Markdown mode, font scale, full mode — the box and the DPI it was painted in, and the line it starts at: a frame is pixels, so unlike a parsed document the font scale really is part of what makes it, and a scroll position really is a different frame. `text_cache_mb` is the budget — `0` by default, capped at `2048`, and `0` means a cache that holds nothing rather than a preview that is switched off, since a frame is painted for the hover that asks for it either way — read from the configuration each time the cache is used so an edit applies without a restart, and trimmed to it least recently used first on every use, with a counter for the order rather than a clock. The cache is consulted before the document is even looked up, so a hit costs a clone rather than a layout and a paint, and a frame larger than the whole budget is not held at all because it would evict everything else and still not fit. A frame a selection was painted into is never held: that is a picture of a drag rather than of the file, and it is different for every one of them.

Layout keeps a document readable inside the box rather than filling it. A line wider than the page continues on the next one, wrapped between words, and a word wider than the page — a URL, a hash — is cut at the edge: nothing in a text preview scrolls sideways, so whatever ran past the right edge would be out of reach for good, and that is as true of a source file, a block of NFO art or a paragraph no grammar claims as it is of a rendered document. The wrap goes only as far as the frame could draw — the lines it has room for, and no scroll position reaches past them, because a position is a document line and a frame always starts at a line's own first visual line — so a minified file, one line of megabytes, costs a frame's worth of wrapping rather than the whole file's. A frame is pulled back until it can be filled from where it starts, so the last screenful of a document is full instead of showing two lines at the top of an otherwise empty box — the lines above a frame that would end early are walked backwards from its top while the box has room for another, which measures the pull-back in the document's own lines rather than in the lines that fit: one line can take two of the box's, and a pull-back by the number of lines that fit left the end of the document out of reach, both as a wall a few lines too high and, past the end, as a frame that painted nothing. What that leaves is one rule for the end of a document: the frame whose tail fills the box is the last one, its last line is on screen, and a position past it — a thumb dragged to the bottom of its track, a line left over from a file that was longer when the preview opened — resolves to that same screenful rather than to an empty box. A line is kept at the end for a note whenever the frame cannot show everything and no scrollbar is going to say so: a file that was cut at the read cap, whose remainder cannot be reached by scrolling either, or any document at all in a preview that does not scroll.

A document longer than its frame gets a scrollbar, drawn into the same frame the text is: a groove and a thumb whose length is the share of the document the frame shows and whose position is the share above it. The bar's geometry comes from one function used by both the painter and the hit test, so what is drawn and what a drag lands on cannot drift apart. The wheel reaches the preview through the low-level mouse hook rather than the window, because the preview never has focus and Windows delivers wheel messages to the focused window — Explorer — instead; the hook asks the preview for the pointer region, swallows the message when the pointer is inside it, and leaves the notches for the preview thread. The delta comes from the hook structure's `mouseData`: a low-level hook is handed the message identifier and a pointer to that structure, and the delta a window would find in the high word of `wParam` is not filled in there. Dragging the thumb is ordinary mouse input, which the layered window does receive: a press on the bar starts a drag with capture, a move maps the pointer back to a document line in the range the bar was drawn for — the lines the preview can reach, not every line the file holds — and a release ends it, so the bar and the thumb's drag cannot disagree about where the end of the document is.

The same messages carry a selection. A press that is not on the bar starts one, a drag extends it, and both ends of it are places in the text rather than points on the screen: the frame hands back the lines it painted with where each run of each line landed, and a point is turned into a (line, character) against those, so a selection survives the window being repainted and a point that runs off the text takes the nearest end of the line instead of being lost. The selection is painted into the frame rather than drawn over it — the run under it is split and drawn in up to three pieces, the middle one over the theme's own highlight colour — which means changing a selection costs a re-render of the window on screen; a screenful of lines is cached by then, so it is a repaint rather than a re-parse. Copying reads the same painted runs, so what is copied is what was on screen, and the lines a selection touches are joined with Windows line endings. The clipboard itself is the system one: a movable block of UTF-16 handed over with `SetClipboardData`. Keyboard copy is the piece of text editing that cannot arrive as a message — the preview never takes focus, so it would never receive the keystroke — so it is polled the way the rest of the app reads keys that belong to it: `Ctrl+C` only while there is a selection to copy. Selecting everything is the menu's `Select All` instead, which takes the whole frame, the range a Copy with nothing selected would have taken anyway. The right-click menu is asked for its command rather than posting one, so it needs no message loop and the preview never has to activate.

All of it is full mode's. With the tray's `Text Preview → Full Mode` off, the renderer is handed a frame that does not scroll — the text a box cannot hold is said in a line on the end of it, the way it was before any of this — the preview keeps no state to select into, and the pointer over it closes it the way it closes any other preview.

What makes all of that possible is one published pair of regions: the journey from the point a text preview was opened from — the cursor that hovered the file, or the middle of the focused item — to the preview, and the preview itself, both in screen coordinates, with the margin a hand that overshoots needs beyond the preview's far edge. Their shape is the point. A preview is placed *beside* what it belongs to rather than over it, so the pointer has to travel to reach it, across a gap and sometimes against the side the placement chose, and the journey is what that crossing is: it reaches the preview's *nearest* point and stops there, so everything it covers away from the preview is the row of the file list the pointer crosses, and it is as tall as the crossing rather than as tall as the preview. Reaching across to the preview's far corner instead — the box around both rectangles — covers the whole column of the list between the pointer and the preview, and inside the region nothing under the pointer is resolved: a text preview as tall as the display put every file in that column out of reach for as long as it was up, which read as previews failing at random in a list beside a text preview and never in one beside an image. The one place the pair reaches past the preview is the edge the journey ends at — the right edge for a preview placed to the right of the cursor, the left edge for one placed to the left — because the pointer is still moving when it arrives and what waits there is usually the scrollbar, a thin target at the very edge of the frame: the `text_scroll_far_edge_grace_pixels` setting is what keeps a hand that overshoots it from taking the preview down with it — forty logical pixels at the display's DPI, read from the configuration each time the regions are published rather than baked in, so the distance is a setting as well as a constant. Nothing past the near edge is added, since the pointer has already stopped there. The pair is published for any text preview in full mode, scrollable or not — resting on a preview is how it is selected from, and a document that happens to fit still needs that. It is recomputed from the preview loop on every tick, so it tracks the window as it is moved, and two flags published beside it say whether the preview on screen can scroll and whether the pointer is being held at all. Both are atomic reads, so the hook's check for them costs nothing until a text preview is actually up.

The Explorer hook asks whether the pointer is inside that region, and answers exactly one question with it: whether the pointer is on its way to the preview. A move is normally what resolves the item under the pointer and drops a preview whose file is no longer under it, and on the way to a preview the item under the pointer is the preview rather than a file, so while the pointer is inside the region and over no file the preview stays, and the sweep of the mouse-delay path that would raise a preview for nothing is skipped. It does not decide what is *under* the pointer: another file takes the preview over the moment one is under it, inside the region or out of it. Nothing is held over from one poll tick to the next either — the answer is read from the region as it is published, so a pointer outside it is treated as it was before the pointer ever touched the preview — and a pointer that is over the preview rather than over Explorer is not read as the user having left Explorer, since a preview is drawn on top of the window it belongs to and the check that asks whether the pointer is over Explorer cannot see under it. The wheel hook asks for the preview's own region before deciding whose wheel it is — the wheel belongs to the preview while the pointer is on it or just past its edge, not while the pointer is still crossing the row in front of it, where the wheel is Explorer's. The regions are withdrawn when the preview is hidden, so nothing else in the app has to know which previews scroll.

A theme or Markdown-mode change is different from a background change, and the preview loop treats it as such: a text preview's colors and glyphs are in its painted frame, so `Refresh` rebuilds the visible preview from the hover it came from (recorded when it was shown) instead of recompositing the frame it already has, while every other format only needs the recomposite.

Painting goes through GDI into a surface of its own: a memory DC with a top-down 32-bit DIB section, filled with the theme's background, block decorations written directly into the pixels, and every run drawn with `ExtTextOutW` against an opaque background rectangle — which is also how a code block's band and an inline code span get their fill. Fonts are created per style and size, once per paint, and the DC is handed back its original object before they are deleted, so a hover leaves no GDI objects behind. The frame that comes out is forced opaque on the alpha byte on its way out: a text preview is a page, not a cut-out, and the same composition path that paints a PDF's white page then composites it unchanged in every `image_background` mode.

## Archive Previews

A hover on an archive shows what is inside it: a summary line, a hairline, and a tree of the archive's own entries — folders first, each row indented by its depth, every file's size right-aligned, and a note at the end when the page could not hold everything. The page is painted rather than composited: it goes through the same GDI layer a text preview does (`text_paint`), which is what gives it the same font, the same margins and the same theme — the bundled One Dark Pro and Atom One Light, or a `.tmTheme` of the user's own — and no syntax highlighter anywhere in the path, because there is nothing in a listing to highlight.

What the page is built from is the archive's table of contents and nothing else, so no member of it is ever decompressed (see What A Hover Is Allowed To Read). `archive_listing` reads that table per format — zip through the `zip` crate's central-directory view, 7z through `sevenz-rust2`'s header parse, RAR through RARLAB's official UnRAR sources compiled in by `unrar_sys`, tar through the `tar` crate and `flate2` — and answers one shape for all of them: names, sizes, whether each is a directory, and whether the archive could be read to the end. A name is cleaned up to be drawn and nothing else: separators normalized, control characters dropped, the whole thing cut to three hundred characters. It is never resolved, joined or opened, so an archive cannot use its own contents to reach anything.

Which reader opens a file is settled by the file's own header first and by its name second, and the two answer different questions. The gate a hover passes — `archive_formats` — asks only what the file is called, because it asks it of every item the pointer touches and a synchronizing provider's placeholder is a directory entry that can be answered for but a file that must not be opened. Which of the readers can open it is a question for the loader, which is already past the cloud gate: a `.jar` is a zip under a name the zip crate has never heard of, and a `.zip` that turns out to hold a 7z is still a 7z. An archive whose own file table is encrypted is answered with a page that says so rather than with nothing, and one whose entries are encrypted but listed is marked as such.

The tree is built from the entries' paths rather than from the order they arrive in. A folder that exists only as a prefix — a zip written without a directory entry for `docs/`, holding `docs/report.pdf` — is still a folder, which is why the header counts folders the way a file manager would and not the way the archive happens to be stored. Children sort folders first and then by name, case-insensitively and with digit runs compared as numbers, so `report2` sits before `report10`. A folder holding nothing but the next folder collapses with it into a single row, `a/b/c/`, so a deep and narrow path costs one line instead of one per level. The rows carry a glyph from the icon face Windows ships — Segoe Fluent Icons on Windows 11, the MDL2 set it replaced on Windows 10 — chosen by what an entry is and what it is called: a folder, a page, a picture, a film, a note, a brace for code, a zipped folder for an archive, and the archive's own glyph in the summary line. The face is asked for once, and a machine that has neither is drawn without icons rather than in a face that does not exist, because a missing icon font is a row of boxes.

The page is drawn to a cap. A hundred rows are laid out, the box the display allows may show fewer, and the rest is said in one muted line at the end — `… and 46 more items`, or `… and at least 46 more items (the listing stopped early)` when the scan rather than the page is what ran out, because past that point everything counted is a floor and the page says so.

Nothing about the page is interactive. It does not scroll, nothing in it can be selected, and the pointer resting on it closes it the way the pointer resting on an image does: those are text full mode's, and a listing is a thing to glance at rather than a thing to work in. The listing is cached by the file's path, modification time and length, so the measure pass, the render pass and a second hover read the archive once between them, and the frame is rebuilt from the hover it came from when the theme, the font size or the `Archives` gate changes — a painted frame, like a text preview's.

## Office Previews

A hover onto a Word, Excel or PowerPoint document shows a page of it, drawn from the one source there is: the page the render tier produced and is holding in memory. What a document saves inside itself — the `docProps/thumbnail.*` metafile or bitmap an OOXML package carries, the summary information stream a legacy compound file keeps — is deliberately not read. It is a thumbnail, a couple of hundred pixels across: either tiny in a preview or an enlargement of something that small, and it costs a zip or a compound-file parse to reach. The page is the whole of it. A workbook is the one page that is not simply read out of the file: Excel lays a sheet out for printing from the values in it, and it works those values out again as it opens the workbook — so a page of a workbook is the page its values come out as, which is not necessarily the page the file was saved holding. Holding Excel in manual calculation first does not prevent that: a workbook is recalculated as it is opened whatever the application's calculation mode says, which is measured rather than assumed, and setting the mode at all costs a workbook opened and closed for the asking, since Excel answers for neither reading nor writing it while none is open. `office_render::excel_calculation_probe` measures both halves of that.

Everything a hover draws is held in memory. `office_preview::measure` reads the source's own size — a PDF page's DIPs from the PDF engine, an image's pixels from its header, both parsed out of the bytes the render tier is holding — and `office_preview::render` draws it into the box the layout planned. The size is kept on the page it was read from, so the layout's several questions in one hover cost one parse between them, and a size cannot outlive the page it belongs to: a document that is saved again is a different page, and its size is read from that one. What that costs is worth bounding, and a picture can be far larger than the box it is shown in — a worksheet's corner at screen resolution is millions of pixels — so shrinking one uses the box filter, which is the fast one, and enlarging the smooth one. What is drawn is checked before it is used, too: a page that will not give up its size — bytes a render cut short, or bytes something else has corrupted — is dropped and the document rendered again, because a page that cannot be drawn would otherwise be handed to every later hover, and each of them would blink. That check lives on this side rather than where the page is held because it is the side that may ask the PDF engine: these threads are multithreaded apartments, while the engine thread is not.

What the render tier keeps is memory, and only memory. `office_cache_mb` is the budget, pages are dropped least recently used first when it is exceeded, and the page a hover is waiting for is never one of them: a budget of nothing means nothing is kept *between* hovers, not that a page cannot be shown at all. It is `64 MB` by default — producing a page costs an Office start and an export, so a document that has been drawn comes back without another render — while `0` is the size for a machine that would rather keep nothing: at `0` a page lives from the moment the render produces it until the moment the hover that asked for it ends (`hover_ended`), and the next hover of that document renders it again. Nothing here switches the tier off either way: an Office document has no other source for its preview, and the `Office` gate under `Preview Types` is the switch. Office's export calls take a file name rather than a stream — `ExportAsFixedFormat`, `Presentation.Export` and `CopyPicture` all write to a path — so one render does pass through a file: a scratch name of this render's own in the temp folder (`page-<pid>-<n>.<ext>`, which is what keeps a file left behind by a process that was ended mid-render from being mistaken for a page this one wrote), read into memory and deleted in the same breath, with every candidate extension removed whether or not it was the one written, so a failed export leaves nothing behind for the next attempt to find. Nothing is ever read from that file twice. The user's own cache folder is not a cache location at all any more: what an earlier version left under `%LOCALAPPDATA%\rust-hover-preview\office` — and any scratch file a killed process left in the temp folder — is deleted at startup, before anything can write there again.

Which shape the source is decides how large it may be drawn. A page Office exported, and a slide's PNG, are vector or near enough, so they take the room the display has — the rule a PDF follows, a configured percentage below `100%` included. The bitmap a workbook is answered with where no printer can export a page is the exception: it is only as good as the pixels it holds, so it is scaled the way an image is, by the configured percentage, rather than enlarged to fit. That decision is `effective_preview_scale`'s office arm, which is why `office_preview::source_kind` exists — the layout has to know which kind of source it is placing before it places it.

While a page is on its way there is nothing to measure, so the preview is the spinner's own box — `office_preview::WAITING_BOX`, the size of the arc and the halo that fades past it — placed at the size it is rather than fitted to the display, which for a box of that size would be a screen-sized square with a spinner in the middle of it. The box is the spinner's frame and nothing more, and the wait is placed flush at the pointer's own corner — the one of the four quadrants the display has room for the spinner in, and a pixel off the pointer, because the preview window is what a mouse message at the pointer lands on and the pointer has to keep clicking and probing the file it is waiting on rather than the spinner that is waiting on it — rather than the margin every other preview keeps and the step off the name it covers: the spinner is the wait for the file under the hand, so it is the spinner at the hand, and one placed a cursor's width away from it, in a frame the arc floated in the middle of, said less about what was being waited on than the empty space it left. The spinner itself is the arc and nothing else: its frame is transparent, so what is behind it is the desktop rather than a backdrop, and its composition skips the backdrop setting — `image_background` and `svg_background` alike — for that reason: the configured backdrop would put back the square the transparent frame exists to avoid. The arc carries a soft dark halo so that it reads over a light file list as well as over a dark one. The spinner goes up as soon as the load has answered that it is waiting on a render, rather than after the moment a load that might be about to finish is given: nothing can be shown until the page lands and a page is an Office start away, so a hover that gave the load the moment every other load is given would spend the render showing nothing at all. Every other load keeps the moment — the window is hidden while one runs, so a decode that takes a few milliseconds goes straight from nothing to the preview rather than flashing a spinner on the way. A preview that is still on its way follows the pointer, so the wait stays with the hand instead of sitting behind: the spinner is placed again as the cursor moves along the item it belongs to, and the page that arrives replaces it where the pointer is. Moving within the item never reaches the load at all — the hook answers a move over the file it is already showing with nothing but a fresh hover delay, so no `Show` is sent, no generation moves and nothing is cancelled while a cursor keeps moving over the file it is waiting on. A pointer that moves *onto* the spinner is the same case reached the other way round: the box sits a pixel off the hand and follows it, so a hand that settles into it — or a move the box has not caught up with — puts the pointer over this app's own window, where the file under it cannot be read at all. The spinner therefore publishes the region it occupies as one that holds the pointer, the way a scrollable text preview does, so a hover is not dismissed from there and the page it is waiting for is not thrown away with it: dismissed, the render still finishes, but it lands for a hover that is gone, and what the user sees is a spinner that came to nothing and a preview that waits to be asked for a second time. Leaving the item and coming back is a `Hide` (which cancels the load, not the render) and a re-show the same-file rehover latch holds off; a render that is still running is never abandoned by either, and a request that arrives for a document whose page landed while it waited is answered from the cache rather than by Office again. Only the place is recomputed — the size the hover measured, its `Avoid Filename` region and its scale are what it is placed with — so a tick of following costs a cursor read and a placement, and the window is moved only when the place it comes out at has changed. A keyboard hover's preview is the item's own and follows nothing. The page is asked for in the box that family's pages have (`office_formats::default_page_size`), which is what a slide's export width comes from: the spinner's box says nothing about how large the page will be drawn, so it is not what the render is asked for.

The render tier is asked for by the preview loop rather than by a hover, because the loop is what knows which hover is on screen: a request is made the moment a document is missed, so what a page costs is its render and not a wait in front of it, and the tier drops a request that has been superseded rather than rendering every one asked for. When the page exists, `OfficeRenderReady` arrives through the same channel every other message does and the hover is replayed — the measure now finds the page, the load draws it, and the window is given the page's own box and frame by the one `UpdateLayeredWindow` that paints it, never resized ahead of that paint: a layered window shows the frame it already holds, stretched into whatever box the window has, so a spinner resized into the page's box first would be a bar across the screen until the page landed. That replay is an *upgrade*, not a new preview: what is on screen stays while the page is loaded, because hiding the spinner for the second a large picture takes to decode is a blink the user reads as the preview failing. A render that lands after its hover has gone is dropped, and the page it produced is released with the hover it was meant for — kept only as far as the budget allows, which at nothing is not at all. The wait is capped at twenty-five seconds from the hover: past that the preview comes down rather than spinning for good, and the file is left alone for two minutes so it is not asked for again on every pass.

A rendered page is drawn by the existing PDF path — Word and Excel export page 1 to PDF, and `pdf_preview` renders it — so a rendered document and a PDF preview are the same picture drawn by the same code. PowerPoint is the exception and exports slide 1 as a PNG, because the alternative is a PDF of every slide in the deck; it is exported at the width the preview asked for, bounded between 640 and 1920 pixels.

Two members of the object model are not what their VBA spelling suggests, and both were found by the diagnostic below rather than by reading: a slide is reached through the collection's item, `Slides.Item(1)`, because asking `Slides` itself for one is answered with "member not found"; and Excel's export needs a printer on the machine, because what a workbook's page is is what it prints. Where there is no printer, `printer_installed` says so up front — Excel answers `ActivePrinter` with the sentence "unknown printer (check your Control Panel)" — and the workbook is answered with `CopyPicture` of the used range's top-left instead, written out as a BMP: the one image format that is exactly the bytes the clipboard holds. A refused copy is asked for again a moment later, because the first ask of a workbook Excel has just opened is regularly refused — "unable to get the CopyPicture property of the Range class" — while the sheet is still being laid out, and the next ask is answered. The picture is taken off the clipboard rather than left on it, because leaving it there is what makes Excel ask, on its way out, whether a large amount of information should stay on the clipboard — a dialog no one is present to answer. What it shows is the corner of the sheet rather than its printed layout, which is the most a machine without a printer can produce, and it is copied only as far as a preview could ever show it: a report whose rows are tall — wrapped headings, merged cells — or whose columns are wide would otherwise be several million pixels, slow to copy, slow to write and slow to draw, all for a corner no preview can hold. The window is cut down in proportion until what it would draw fits a budget smaller than any display — 900 by 700 pixels, because a picture is shown at its own size rather than fitted to the screen the way a page is — so tall rows keep as many of them as the budget allows instead of being halved until only a sliver is left. Only the range's own measurements are asked for to cut it down, never its cells, so a sheet of a million rows costs the same as a small one. On a machine that has a printer, an export that comes to nothing is taken as the instance declining rather than the document failing — the instance a retry is about to replace — so no picture is asked for there until an attempt is already a retry, where it is the last thing tried before the document is given up on. Copying out of an instance that has just refused to export is a detour of its own: the copy is refused by the same instance, after the retries the clipboard needs, and what the first attempt should be is the fresh instance the retry is going to ask anyway.

## Office Render Engine

The engine is the Office application itself, driven late-bound through `IDispatch` and called by name, so nothing here depends on a type library, a build step, or the installed version. One engine is created per family on the first render that needs it and kept for `office_engine_idle` after that family's last one — ten minutes by default, `0` for one let go as soon as it has drawn a page, or `indefinitely` — then quit; a family never has two, because an engine is started only once no process this app began for that family is still running, and a replacement waits for the process it replaces to be gone before it is asked for; the families are held side by side rather than one at a time, so a folder holding a document, a workbook and a deck costs one Office start each rather than one every time the pointer crosses between them, and each is let go on its own clock, so the family asked for most recently is the one that outlives the others. The thread that owns them ends with the last one, so an app left alone ends up with neither an Office process nor a polling thread — an engine kept indefinitely being the one setting that is asking for both. That thread is apartment-threaded and pumped, which is the opposite of every other worker in the app: OLE automation marshals its calls back into the thread that made them, and a thread that is not retrieving messages deadlocks.

Automation may attach to an instance the user already has running — these applications are registered for multiple use — so the engine is careful with what it touches. Whether the instance was already visible is read first: a visible one is the user's, and is neither hidden, quit, nor ended, while the settings it is given (dialogs suppressed, macros switched off) are taken for each render and put back the moment that render is over, so an engine sitting warm between documents is holding nothing of the instance's own — which is what makes keeping one for an hour, or for as long as the app runs, safe to do to an instance that is the user's own Word or Excel. Only an instance this app created is hidden and quit, and the process it started is recorded — the process list is walked before and after creation, and the one that appeared is the app's — so that a render which never returns can end every engine the worker was holding. Documents are opened read-only, without touching the recent-files list, in a hidden window that Word, Excel and PowerPoint all support even in a visible application, and are closed without saving.

None of those calls can be cancelled or bounded: a modal dialog inside Office holds the COM call for as long as it is up. What that costs is one render, never the tier. Ending an engine counts as work like any other, so it happens inside the same marker, and a worker that has been inside one piece of work for longer than any of them takes is given up on when the next hover arrives — every Office process this app started is ended, since a worker being given up on is holding all of its engines, the worker generation moves on, and a fresh worker takes the request. The abandoned thread is left where it is, since nothing in user mode can end a call it is inside, and everything it does on the way out is conditional on it still being the current worker: it can neither clear the live worker's thread id nor end an engine the new worker is using. A panic is contained the same way — one document's failure is that document's, and the thread goes on to the next hover — and the thread id is handed back however the thread ends, because losing it would leave every later request posted to a thread that is gone.

Letting an engine go is a call of its own, and an Office application finishes quitting while its automation client is pumping: one that is told to quit and then abandoned can sit there for good, which is what a left-behind Excel instance looks like. So the quit is given a moment of pumping on the worker thread, and a process that is still there after it — one this app started, verified as still being that application — is ended rather than left running. That is the idle path: an engine being let go because it has refused a page is not asked to quit at all. A quit is another call into the instance that refused, and one that is not answered is pumped for seconds before the process is ended anyway, while a process about to be ended has nothing left that needs putting back — so the process this app started is ended where it stands, and the engine the retry asks is a new instance, which is the point of the retry. An instance that is the user's own is never ended by this, whatever it answered: `attached` is what stops it, the same as everywhere else. A superseded request is dropped rather than queued behind, and the newest hover is the one that runs.

A render is not quite invisible, either: Office shows a progress window of its own while a page is exported — the wide, short "Publishing…" bar — and none of the settings an engine holds keeps it off the screen. Alerts, screen updating and the automation security mode were each measured against it, and it is shown whether or not the application it belongs to is visible, so a hover used to see the bar for the whole of a slow export. What it is, though, is a progress bar: nothing about the export depends on it being seen, so a render watches that process for the window being *shown* — `EVENT_OBJECT_SHOW`, filtered to the process, with the class as the check, since a window's title is the machine's language and this is not — and hides it the moment it is put up, which is what keeps it out of a frame a display is drawing; a sweep of the process's windows runs beside the hook as the half that does not depend on an event arriving. Only a process this app started is watched: an instance the user is working in keeps every window it owns, the same as it keeps its dialogs and its macros.

## Video Process Lifecycle

`ffplay` is the only long-lived external process the app starts itself — an Office engine is another long-lived process, but COM is what starts it, and its discipline is its own (see Office Render Engine). It is started per hover, its own window is used as the preview surface while the layered window stays hidden, and it is stopped when the hover ends — switching to another video, switching to an image, leaving the file, disabling previews, a display change, or system suspend.

Stopping is kill-only: the app requests termination and never waits for exit, because a process stuck in kernel I/O cannot be terminated by anyone in user mode, and an unbounded `wait` on the Explorer hook thread would freeze hover tracking for good. The PID of the last spawned player is therefore kept until the process is confirmed gone rather than cleared on the spot, and two checks recover a player that survived its stop: the Explorer hook re-checks the recorded PID once a second while no file is hovered and no keyboard preview is up, and the preview thread re-checks it before spawning a new `ffplay`, so a new preview cannot stack a second player next to a stalled one. Both checks terminate only when the recorded PID still belongs to `ffplay.exe`, read from the same process handle that is terminated, so a recycled PID can never hit an unrelated process; the record is cleared only after the process is gone, through a compare-exchange so a freshly spawned player's PID cannot be wiped by a stale check.

## Started Processes

Three things this app starts are not its own to keep: the Office application that draws a document's page, the browser that plays an animated document, and the `ffplay` a video preview runs in. Each of them is ended where it is ended deliberately — an idle engine let go, a player stopped — and what `engine_processes.rs` is for is the ways an app does not get to choose: ended from Task Manager, taken down by a crash, closed by a logoff. A process that outlives the app that started it holds a profile folder, an Office licence seat or a file handle, and a leftover Office engine is also the thing a new engine would be a duplicate of.

Two mechanisms cover that, and they cover different halves of it. A job object with `KILL_ON_JOB_CLOSE` holds every process this app adopts, and its handle is deliberately never closed by the app: what closes it is this process ending, however it ends, and the system ends everything in the job with it. That is the only mechanism that asks nothing of a process that is dying, which is exactly what a crash is — and it is why the video player is adopted even though its own supervision already ends it while the app runs. What the job cannot take — a process already inside a job that will not nest is how that happens — is covered by a record on disk: each run writes what it started to `%LOCALAPPDATA%\rust-hover-preview\engines\<pid>.state`, and the next run reads every file there and ends what the runs that are gone left behind. A run that is still alive is another session of the same user, and its engines are its own; a browser left by a version of this app that wrote no record is reached the same way, through the profile folders a run leaves, each named for the run that made it.

Finding each of them is its own question, and all three answers rest on something the runtime guarantees rather than on a name. An Office engine is the process that appeared across `CoCreateInstance` — the same walk that tells an instance this app created from one the user already had open — and the browser is the `msedgewebview2.exe` whose parent is this process, because the WebView2 loader starts it from here; a browser another app started is a child of that app, which is what keeps the sweep from reaching past this app's own.

What is never done is acting on a process id by itself. An id recorded hours ago may belong to something else by now, so a record is acted on only when the process still runs the image the record names *and* started when the record says it did — a creation time is what the checks that hold a process in hand never needed and a file cannot do without. The sweep runs at startup before anything else, so a leftover engine is gone before this run can start a process of its own, and never beside one.

## Explorer Hook Flow

1. Detect active Explorer window and focused or hovered item via HWND/class matching and UI Automation, with input-grace helpers (should_probe_keyboard_focus, should_probe_hover_resolver, should_probe_stationary_hover) throttling probes to recent user activity and a stationary_hover_probe_done latch capping stationary-hover work to a single probe per parked cursor. An item is found by the box the view gives it rather than by the text drawn inside it, so the metadata line a Content row writes is not what answers for that row: the name is consulted afterwards, as the check that the position and the file agree, and only when the name could be one of the files this app previews. A view reports a row's metadata exactly as it reports a name, and a name like that is passed over rather than taken for the file. A shell that answers a cursor probe too slowly too often (three probes over 700 ms) puts the cursor probes on a pause — the pause stops the asking and nothing else: the preview that is up stays, because it belongs to the file the cursor was on, the keyboard's turn is left as it is, and the preview is withdrawn only when the cursor leaves that file, which would otherwise strand it on a file the pointer is no longer on. The keyboard's item is one too: the focused element, or the item its list has selected when the view reports the list itself as focused — the search results view does — read from that element and walked up to the item that holds it exactly as the pointer's is. One batched UI Automation read gives the item's box, the name the view shows it under, its position in the view and the value its accessible pattern carries, and the position is turned into a path by the same view lookup the pointer uses, tab rules and all. No name is looked up for either path and nothing is walked: a search result whose file lives in another folder is answered by the item itself, and two results that share a name are told apart by where they are, not what they are called.
2. Treat a wheel tick as input when the wheel is driving Explorer (the pointer is over it, or over a preview window that covers the pointer while Explorer still receives the wheel). The wheel moves the list under a stationary cursor, which changes the hovered item without any mouse movement: the stability window restarts while the wheel turns and the latch is reopened, so when the list settles the item that landed under the cursor is resolved and previewed (or the preview is dropped when that item is not media). A `ScrollSettleProbe` only acts on an item that survives two consecutive probes, because Explorer can still be animating the scroll. A scroll also ends keyboard ownership: the keyboard preview is closed, the pointer freeze is released, and the recent-keyboard-input window ends, so the mouse preview takes over the item under the cursor.
3. Treat clicks, Enter and the navigation keys as user navigation. A folder probe runs at the active cadence for a moment after such a press, so a folder that press opens is recognized before the user's next key press rather than up to a full idle interval later. Once the new view has settled the post-folder-change suspension lifts on its own, so the item that landed under a parked cursor previews without a mouse move, and the first navigation key press after the change previews the item it selects — the gate lifts on a fresh press transition (never on key-down state left over from the navigation that opened the folder), so that press is no longer swallowed as a focus baseline. A folder change that no input precedes (a programmatic renavigation, a network refresh) still waits for user input, and the auto-focused first item still never previews without a key press.
4. Normalize the resolved path and validate the file extension. The `.ts` and `.mts` extensions are shared with TypeScript sources, so those two are additionally confirmed by a short MPEG-TS sync-byte probe (`src/video_formats.rs`) before a video preview is started. The gate is what the file *is*, asked the way the renderer asks it — a video first, then a PDF, then the text lists, then the image extensions — with that kind's `Preview Types` gate applied on top, so a file whose kind is switched off resolves to nothing rather than to another kind's preview.
5. Send `Show` or `Hide` messages to the preview thread via channel.
6. Resolve a file from the item that stands for it, and read nothing else. The folder index, the down-the-tree descent, the search-root index and the Shell view name index that stood here are gone: a name is looked up nowhere, and the hook never touches the filesystem to find a file. What is cached about a view is only what answers a question a view has already been asked — the folder a window remembered, and which window is one of Explorer's — and it is dropped when the location changes, because both describe the place the window has left.
7. Keep keyboard and mouse precedence explicit: an arrow-key preview owns the screen and is never dismissed by the parked pointer (a wheel scroll does end it, handing the screen back to the mouse), while a mouse preview is still dismissed the moment the cursor touches it. Each keyboard spawn measures the preview's own on-screen box (`preview_screen_rect`) and, when that box covers the cursor, freezes the pointer-driven triggers — `should_probe_keyboard_focus`'s companion `should_probe_preview_hover`, the hover resolver/folder probe, and mouse hover previews — until the cursor is moved more than the pointer tolerance (20 px), so jitter cannot end a keyboard preview. That tolerance is what a move has to clear for the whole of the keyboard's turn, not only while the box happens to cover the cursor: a navigation key press puts the keyboard in charge of the screen (`keyboard_screen_owner`), the state survives the keyboard previews it opens and closes, and while it holds the pointer-driven hover path is skipped even with no preview on screen. Without it, a focused item that cannot produce a preview — a file whose kind is switched off, a result whose path could not be resolved — ended the keyboard preview and left the parked pointer free to raise a preview of whatever it sat on, which the next key press dismissed in turn: on a large search-result view, where the items the keyboard walks are the ones still being resolved, that read as the two previews fighting over the screen. The focused-item baseline — its name *and* its box, so two results that share a name are two items — is cleared on mouse movement, and the focus observed after that acts immediately, so the first navigation key switches to the keyboard preview instead of being swallowed as a fresh baseline. When the mouse does take over, the file that was shown is latched (`SuppressedHover`) the way any dismissed hover is: held off the mouse path for the same-file rehover delay — long enough that the hand-over cannot flash it straight back — and released sooner when the cursor resolves a different file. A probe that meets the latch stays open instead of being spent, so a pointer left parked on that file previews it as soon as the delay has passed.

Explorer restarting is the one thing the hook cannot recover from by itself. Every Shell object it resolves items through — the window collection it asks which views a window holds, and the view that answered for one — is served by explorer.exe, and a proxy into a process that is gone does not reconnect: it answers no call for the rest of the run. That is what left every hover after a restart with nothing while the app looked alive, since the tray icon was re-added and the window counting that decides whether Explorer is up never used the shell's objects at all. A restart is therefore counted where it is already noticed: the tray window is sent `TaskbarCreated` when the shell builds its taskbar again — the same broadcast its icon is re-added on — and the hook builds the collection again when that count has moved, dropping the view that answered through it and the caches keyed by window handles that belonged to the process that is gone, hiding whatever preview was up, and re-arming the folder-change gate the way a folder change does, so the probes wait for the windows the new shell is still putting up. A collection that came out missing when it was asked for is built again on a slow retry rather than kept missing for the rest of the run: it is asked for while the shell may still be coming up — the tray retries its own icon for that same reason — and a missing collection answers exactly as a dead one does.

## Item Resolution

Both paths resolve a file the same way: from the *item* that stands for it rather than from its name. The item is read with one batched UI Automation request — its box, the name the view shows it under, Explorer's own `ItemIndex` (the position it holds in the view), and the value its legacy accessible pattern carries — and the position is turned into a path by the view that is showing it. A pointer takes its item from the point, walking up from the element under the cursor to the nearest list row or data item whose box holds it (the whole row is the target, which is what Explorer itself highlights when an item is selected); a keyboard preview takes it from the focused element, or from the item its list has selected when the view reports the list itself as focused, walking up the same way because what a view says about an item is kept on the item and not on the text it draws inside it. A keyboard item is asked one thing more, because its preview is placed from the item alone with no cursor to measure from: the boxes each piece of its own text is drawn in — which is one read, from the item's children in one more batched call. Those boxes are wanted for an item wide enough to be a row of the view — a Content view row is given a box as wide as the view and draws its name and columns into the left end of it, and the empty tail past the region a preview is kept off is the only room the row leaves for one — as well as being what the `Avoid` setting keeps a preview off — the leftmost piece of the text, which is the `Name` column of `Details` and the name above the path of `Content`, for `Avoid Filename Column`, that same piece narrowed to the name's own width for `Avoid Filename`, and every piece of it together for `Avoid Details` — so it is measured for an item of any shape whenever a way of avoiding is on: the label under an icon is a box of its own, and the name of the item the keyboard is on is the file the preview is about. The pointer's item is asked the same question at the moment a preview is about to be shown for it, and not with every probe (see Preview Window Placement). Nothing is looked up by name on either path and nothing is walked: a name is the one thing a search across folders shares between files, and two results that share one are told apart by where they are, not what they are called.

The view is found by the window first: the Shell windows are matched against the frame the item's window belongs to — the root window under the pointer, or the frame of the window the focused item is drawn in — rather than against focus or a rectangle, so a background Explorer window and another application's window are excluded by that one comparison. What the window names is not always a single view. A window that holds tabs registers one Shell window per tab and every one of them answers with the frame's own window, so the frame names a *set* of views; and the tabs that are not showing cannot be told from the showing one by their windows — the Windows 11 frame reports both of its views as visible — so the item is what settles which of them it is: each candidate view is asked for the file at the item's position under the item's name, and a view holding some other folder's items has nothing there to answer with. What two of them answer has to agree, because two tabs showing the same folder are one answer and either of them is the right one, while two tabs whose items differ are a question the item cannot settle — and no answer is better than the wrong tab's file. The view that answered last is kept and asked first while it is the window's *only* registration: with one view there is no second one for it to disagree with, and a window holding tabs is never answered from the cache, because a cached tab is one of several and the cache cannot say which of them is showing.

The file itself is the one the Shell hands over for that item's position (`IFolderView2::GetItem` → `GetDisplayName(SIGDN_FILESYSPATH)`) — for a search result, the real file wherever it lives — but the two questions are asked in order and are not the same question. First, which view holds the item: a candidate claims it when the item at that position goes by the name the accessibility tree reported, and a folder claims it exactly as a file does, because what an item *is* says nothing about which view is showing it. Then, and only of the views that claimed it, the file: the path the Shell hands over, gated to a file this app previews. A view that holds the item but has nothing to show for it — a folder, an executable, an archive — is a *match with no file*, not a view that failed to match, and that distinction is the whole of it: read the other way, the tab that owns the item abstains, the other tab's media file is the only answer left, and hovering a folder previews another tab's picture. Tabs that disagree — about the file, or about whether there is one at all — are a question the item cannot settle, and no answer is better than the wrong tab's file. A pointer asks the view twice and takes the answer only when both looks found the same item, which is what keeps a list that scrolled under a parked cursor from answering with its neighbour's file. Each path has one other witness: the item's own accessible value, when that value is a whole path — which is where a search result states its file, and what answers when no position is reported at all. Nothing else is tried: an item no witness can vouch for is left without a preview rather than guessed at, which is why a search of several hundred results costs both paths the same work a folder does.

## DPI Awareness

The app sets per-monitor DPI awareness v2 on startup, with a fallback to per-monitor DPI awareness if v2 is unavailable. This avoids scaling artifacts on layered windows when Windows UI scaling is above 100%.

## Preview Window Placement

The preview is bounded to the display nearest the hovered cursor or focused item rather than the whole virtual desktop. Bounds are resolved through `MonitorFromPoint`/`GetMonitorInfoW`, falling back to the virtual screen when the monitor lookup fails, so the window no longer spills onto a neighboring display.

Each update repositions the window before installing the new frame or spinner. Crossing between displays of different scale raises `WM_DPICHANGED`, which discards the frame that was on screen — one composed for the display the window has left, and the wrong size and scale for the one it is on now — so installing the content first would discard it and leave the previous display's image stranded on screen. What the discard leaves is put back rather than left until the pointer moves: the window proc can only throw the frame away, so it raises a flag the loop reads, and the loop replays the hover the frame came from — which lays it out again at the scale of the display the pointer is on now. For the same reason, the layered surface is painted before the window is revealed.

Preview size is derived from the media's native dimensions and the `preview_scale` setting, which is either a percentage of the native size or `fit` for the largest size the display area allows. The requested scale is always capped by the free space on the chosen side or quadrant, so a preview can never be clipped by the display edge — a large image at a small scale shrinks to fit, and a small image at 400% or fit-to-screen is reduced to whatever the display can hold. The same scaling is applied to the decode request, so image, GIF/WebP, and video previews all land at the computed size. The one rule a size can come from besides those is a reduction of the fit itself, which is what a PDF page and a rendered Office page follow below `100%`: the room the display has, reduced to the configured share of it. `scale_in_room` is the one place that answers it — for the size a preview is given and for the room a position mode chooses between — so the size the layout plans and the size the renderer draws at cannot come apart.

Where the preview lands on that side differs between the two position modes. `Follow Cursor` fills the roomiest quadrant around the cursor, growing away from it in both axes. `Best Position` places the preview beside the cursor or the focused item — on whichever side has more room for it — and centers it on the same line: `centered_top` puts the preview's middle on the cursor's own row (or the focused item's), and clamps that to the display, so a preview that fits under a cursor near the top edge sits where the cursor is, and one tall enough to reach an edge moves only as far as the edge allows. Before that, both modes centered the preview on the *display*, which for a cursor near the top put most of the preview below it and away from what was being hovered. The rule is shared by every format — image, GIF/WebP, video, PDF and text — because it is part of the layout both mouse and keyboard previews are computed from. It is also what a preview that is still on its way follows the pointer with: `compute_mouse_layout` is asked again for the cursor as it moves, at the hover's own size and `Avoid` region, which is what keeps a spinner with the hand while a render runs (see Office Previews). The one placement no position mode decides is that spinner's own: a waiting spinner carries `flush_at_cursor`, and is placed by it at the pointer's own corner — a pixel off it, so the pointer's own messages stay with the file it is waiting on — in whichever quadrant the display has room for it, rather than the quadrant the mode would have filled.

One rule is applied on top of whichever placement a mode chose, for the `Avoid` setting: a placement that came out over the region its own item draws — the name the file is listed under at `Avoid Filename` (the default) and `Avoid Filename Column`, with the columns a row writes beside it at `Avoid Details` — is moved by the shortest step that clears that region, past its right edge, past its left, under it or over it, and a step is only taken where the display has room for the preview it moves. A preview too large for any of those rooms is *resized* into the roomiest of them instead, by the same rule that sized it in the first place applied to the room that is left, which is what answers the case a preview filling the display lands in: nothing can be moved clear of the region while the preview is as wide and as tall as the display, so the size is what gives. A room too small to be worth having — the sliver of tail past a name that fills its row, the last strip of a display under a row at its bottom — is not taken at all, so a preview is never squeezed into a sliver to get off a name it would have covered anyway. At `Avoid Filename` that region is cut to the width the name itself is drawn at, because a view reports the room a name is *given* — one width for every row of a `Details` folder, a long name and a short one alike — so the name is measured where it is drawn, extension and all: the icon font the shell gives folder views, scaled to the display the item is on and taken at the larger of the two sizes a view draws a name at — the font itself in `Details`, 125% of it in the `Content` view, whose rows give the name a line of its own — with a font and a memory DC made for the one call and let go again (see Item Resolution). The larger size is what makes one measurement serve both views; a `Details` row is left keeping a quarter more room than its name takes. `Avoid Filename Column` is that room as the view reported it, without the cut. The cut only ever narrows the box, so a name that fills the room it was given, or is drawn truncated to it, is left as the view reported it. The text is a region the Explorer hook measured, so it comes with the hover rather than being anything the preview thread can see: for the pointer's own item it is read at the moment a preview is about to be shown, which is once per preview rather than with every probe, and a keyboard hover carries the box the walk already measured the item's text in (see Item Resolution). A view that reports no text for an item leaves the item's own box as the region, since the name is drawn inside that box whatever the view says about it. The distance the placement keeps from whatever it is beside is what the text is cleared by, so it is stepped off rather than touched at its edge. The waiting spinner is the one placement the rule passes over: it is put at the pointer's own corner by its flush rule and left there, over the name, rather than stepped a margin off the file whose page it is waiting on (see Office Previews).

Keyboard previews are placed next to the focused item, which can put them over a parked pointer. That is allowed: while a keyboard preview is up it stays topmost and the pointer is not treated as hovering it, so it cannot be cancelled or made to blink by a cursor that happens to sit underneath. The placement anchors on the item's own edges — which is what keeps a preview off the file it describes — because that reading holds for an item that is a box. An item that is far wider than it is tall and at least half the display across is not one: Content view draws every item as a row as wide as the view, so the row's own right edge *is* the view's, and what lies beside it is the space the view is not using, a sliver at the window's edge. What such a row does leave is the empty tail past the region the `Avoid` setting keeps a preview off — at `Avoid Filename` that region is the name alone, so the columns drawn after it are the room the preview takes, while at `Avoid Details` it is the whole of what the row draws, which is the tail the placement has always been measured from — and that region is what the keyboard's placement is measured from, since it is the hook's own read of the row's text elements (see Item Resolution): the preview takes its place and its size from the tail, `Best Position` centring it on the row's own line just past that edge and `Follow Cursor` growing it from the row's corner. A row with no tail to place a preview in — a narrow view, a name long enough to fill it — and a row with nothing kept off at all, since `Don't Avoid` places a preview by the position mode alone, are anchored at their *middle* instead, the way the mouse path anchors on the cursor, and are allowed to cover the rest of the row. The hook confirms this from the preview's own box (`preview_screen_rect`, taken from the layered window or the `ffplay` window once visible) rather than from a cursor position test, and holds the pointer off until the mouse is moved on purpose.

## Configuration

Configuration is stored at `%APPDATA%\rust-hover-preview\config.ini`. Changes are detected by the config watcher thread and applied without restarting the app.

The file is written in a fixed shape: the `[settings]` section first, the sections that hold the file lists after it in alphabetical order, and the keys of every section alphabetical within it. The INI reader the values are collected in keeps sections and keys in hash maps and writes them in whatever order those hand back, which is a different order on every write — so a file the user is meant to read and edit by hand was being reshuffled under them on each save. What `write_ordered` emits is the same text that writer produced, in an order that does not move, and a saved file read back and saved again is byte for byte the same.

Which files each kind of preview covers is a list in the file, one section per kind — `[image]`, `[video]`, `[text]` (which carries the extensionless names beside its extensions), `[archive]` and `[office]` — written from the built-in list on first run and read back from there, so a format the app does not know is a file edit rather than a rebuild. `image_formats`, `video_formats`, `text_formats`, `archive_formats` and `office_formats` own them, each with the normalization that keeps a hand-edited entry safe to match against, and the hook and the renderer read the same lists rather than classifying a file twice.

A list is repaired rather than lost. A key that is gone — its line deleted, or its whole section with it — comes back with the built-in entries, and the file is written out again with them, which is what makes a hand-edit that removes too much recoverable: the reload that finds a key missing is also the write that puts it back. An empty value is not a missing one and is kept as written, because that is how a user asks for no files of that kind at all — the `Preview Types` gate is a switch over behavior, while an empty list is the kind configured away. A list that still holds exactly the built-in entries is read as the built-in list, order and all, which is how a file written before those entries were put in alphabetical order is brought into line; a list anyone has edited keeps its own entries and its own order. That comparison is on the order as well as the entries, because an entries-only test would rewrite a file that already agreed with it on every reload — the write moves the mtime, the watcher reloads, and the file would be written out again for as long as the app ran. Nothing else in the file is preserved across a write: `save` builds a fresh `Ini` from the known fields, so a hand-added section, key or comment is dropped the next time the app writes.

A list the app itself has changed is read through the history beside it. `svg` and `svgz` were added to the built-in image list, and a file holding exactly the entries the app shipped before they existed is the app's own older list rather than the user's — nobody has touched it — so it is read as the current built-in list and written out again with the new entries in it. Without that, an entry added to a built-in list would reach a fresh installation only: every `config.ini` already written holds the list as it was, and a list that differs from the built-in one is otherwise taken for the user's own. A list with any one entry changed — added, removed or spelled differently — matches neither and is kept exactly as it is. `IMAGE_EXTENSIONS_BEFORE_SVG` is that older list, and the check that uses it is `configured_list_over_history`; a list whose built-in entries change again is added to that history rather than left to reach new installations alone.

Themes the user adds live in `%APPDATA%\rust-hover-preview\theme`, beside `config.ini` and created on first run: a `.tmTheme` file there is listed by the tray under its own file name (the stem, `atom-one-light` for `atom-one-light.tmTheme`), read from disk the first time a preview asks for it, and re-read whenever the tray menu is built, so a file added, edited or repaired is one menu-open away from taking effect rather than a restart. The folder itself is only ever listed — a file's contents are not touched until it is chosen — and it cannot shadow a bundled theme: a file theme is written `theme=custom:<name>`, while `light` and `dark` on their own always mean the bundled Atom One Light and One Dark Pro. A file that cannot be read or is not a theme is painted with the default, which is what the menu marks while the name it was chosen under stays in the file.

## Build And Packaging Notes

- The MSVC toolchain uses `rust-lld` via .cargo/config.toml for faster, more consistent linking.
- Windows resources are set in `build.rs` through `winres`.
- A release build ends a running copy of the app before the crate is linked, because Windows will not let the linker replace an open binary. `src` is watched so the rebuild an edit asks for is the one that gets it; debug builds are left alone.
- Release installers are produced by `cargo packager` (NSIS `.exe` setup).
- The NSIS setup is built from `packaging/nsis/installer.nsi`, cargo-packager's own template with its "Already Installed" page removed: an older installation is uninstalled silently before anything is copied, and a running copy of the app is closed without asking. The cargo-packager version the template was written against is pinned in `build-installers.ps1` and the deploy workflows, so moving to a newer one is a deliberate pin bump and a diff of that file.
