# Architecture

## Overview

Rust Hover Preview is a Windows 11 tray application that watches File Explorer focus and hover state, then renders a non-activating preview window near the cursor or focused item. It is split into a tray UI, an Explorer hook, and a preview renderer that communicate through lightweight shared state and message passing.

## Runtime Topology

- Main thread claims the single-instance mutex, initializes COM, config, DPI awareness, then runs the tray event loop.
- Preview thread owns the layered preview window and media decoding/rendering.
- The preview thread idles on its own channel rather than on a tick. While nothing is on screen there is nothing to animate, nothing to repaint and no pointer region to keep in step, so it waits on the preview channel itself and wakes when a hover arrives; the interval it waits on is only a ceiling on how long a window message — a resume, a display change — goes unnoticed. While a preview is up it keeps its sixty-a-second tick, which is what services animation frames, the streaming overlay and the pointer region.
- Explorer hook thread polls Explorer state with UI Automation and Shell COM APIs, and uses EnumWindows with CabinetWClass/ExplorerWClass class matching to count and classify Explorer browser windows so idle polling never spins up Explorer's shell automation providers.
- Wheel watcher thread installs a system-wide low-level mouse hook (`WH_MOUSE_LL`) and pumps the messages it needs, publishing a wheel-tick counter that the Explorer hook consumes so wheel scrolling refreshes the hovered item.
- Config watcher thread reloads `config.ini` when it changes on disk.
- Office engine thread is spawned by the first render request and ends itself once every engine it holds — one per family — has gone idle. It is the one apartment-threaded, pumped thread in the app — OLE automation marshals calls back into the thread that made them, and a thread that is not pumping them deadlocks — and nothing ever waits on it; see Office Render Engine.

## Single Instance

The app runs as a single instance per user session. `main` claims a session-local named mutex (`Local\rust-hover-preview-single-instance`) as its first step, before DPI awareness, COM initialization, config loading, and any thread is started. A second launch — from a desktop shortcut, the Start menu, the startup entry, or the `.exe` directly — finds the name already taken, closes its own handle, and returns from `main` without creating a tray icon, Explorer hook, or preview window. The guard handle is held for the lifetime of the process, so the name is released when the app exits, including after a crash or a forced kill, and the next launch becomes the primary instance. The `Local\` prefix scopes the guard to the signed-in session, so a second user signed in over Remote Desktop still gets their own instance and tray icon.

## Core Modules

- `main.rs`: single-instance guard, process startup, COM lifecycle, DPI awareness, thread orchestration.
- `single_instance.rs`: named-mutex guard that limits the app to one running instance per user session.
- `engine_processes.rs`: every process this app starts that it does not own the lifetime of — an Office engine, the browser that draws an SVG document, the player a video preview runs in. Each is put in a job object, so that whatever ends the app ends it, and written down in a file of its own run, so that a run which never got to end them is answered for by the next one; see Started Processes.
- `explorer_hook.rs`: resolves hovered/focused Explorer items, handles path normalization, and sends preview messages.
- `cloud_files.rs`: whether a file's content is on this machine at all, so a preview never turns into the download a synchronizing provider would start.
- `wheel_input.rs`: system-wide mouse-wheel hook thread that publishes a tick counter, so a scroll that moves the list under a parked pointer is visible to the polling loop.
- `preview_window.rs`: layered window rendering, scale-aware sizing, animation streaming for GIF/WebP, video previews — played by FFmpeg's `ffplay` with verified-PID process supervision where it is installed, and decoded by the media engine and drawn by this window where it is not (see Video Preview Engines) — monitor-bounded placement with paint-before-show presentation, and the display-change and WM_POWERBROADCAST handling that resets state when the display under a preview changes, on system resume, and on suspend.
- `pdf_preview.rs`: first-page PDF rendering through the PDF engine that ships with Windows (`Windows.Data.Pdf`), with the page size cached per file, the page it drew held in memory up to `pdf_cache_mb`, and the file's own header confirmed before a path reaches the OS renderer.
- `image_formats.rs`: the gate for image previews, holding the built-in extension list that is written to `config.ini` and read back from there, and the normalization that keeps a hand-edited list safe to match against. Nothing is probed here: the decoder has the last word on whether a file is a picture at all, and it is handed one only after this gate has claimed it. `svg` and `svgz` were entries of this list while the kind that draws them had a name of its own, and are entries of the vector list now: what draws one is the browser engine rather than a decoder, so the list it is named by is the list of the kind it belongs to. A file the app wrote before that is brought over to that list, and an `svg` a hand-edited list still names here is answered by what it is rather than by the list — see `svg_preview`, `vector_formats` and `webview_preview`.
- `svg_preview.rs`: SVG documents, for the two questions the rest of the app asks before it hands one over — whether a file is one, and the size it asks to be drawn at. Nothing is rasterized here and nothing is decoded. The size is the root element's own `width` and `height`, with the `viewBox` answering where they are relative or missing, and the 300-by-150 viewport a browser assumes for a replaced element where a document names neither; a `.svgz` is inflated on this side rather than by the browser, and a file that will not parse is answered with no preview. The measurements are held between hovers, keyed by the file and the version of it that was read; the drawing is `webview_preview`'s.
- `metafile_image.rs`: the Windows metafiles the drawing layer plays — `.wmf` and `.emf` — read as records this app hands to `PlayEnhMetaFile` rather than as anything it decodes: the placeable header a `.wmf` may open with, the conversion of an old-style metafile into the enhanced form the layer plays, the DIB surface a drawing is played into, and the two plays over a black page and a white one the coverage of a frame is recovered from. Nothing is rasterized on this side and nothing is compiled in for the format; what a preview of one is, is the drawing replayed at the size the preview is shown at. See Vector Previews.
- `eps_image.rs`: the picture an encapsulated PostScript file carries of itself, which is the only part of one this app reads — no PostScript is parsed, evaluated or run. The two shapes a preview comes in are read for what they hold: the Windows container, whose header names where its metafile and TIFF previews are, and the comment block a Mac writer leaves hexadecimal between `%BeginPreview` and `%EndPreview`. What it holds is handed on — a drawing to `metafile_image`, a picture to the decoder every other picture goes through — and a program with neither shows nothing. One shape of picture is read here rather than by that decoder, because the decoder turns it down whole: a colour table with a sample of alpha beside its index, which is what a document written from Photoshop carries, read by walking the picture's own directory for the table, the strips and the alpha, and looked up on this side. See Vector Previews.
- `vector_formats.rs`: the gate for vector previews, holding the built-in extension list that is written to `config.ini` and read back from there, and the normalization that keeps a hand-edited list safe to match against. The kind it gates holds both the documents the browser engine draws and the ones the drawing layer replays — `svg` and `svgz` are entries of this list, and were entries of the image list until the kind that draws them grew a list of its own — and nothing is probed: the readers have the last word on whether a file holds a drawing at all. What the list names is both halves, so every caller that asks it has to ask the document half first: the readers of the drawing half turn a document down, and a hover that reached them with one shows nothing at all. See Vector Previews.
- `font_formats.rs`: the gate for font previews, holding the built-in extension list that is written to `config.ini` and read back from there, and the normalization that keeps a hand-edited list safe to match against. Nothing is probed here: the reader has the last word on whether a file is a font at all, and it is handed one only after this gate has claimed it.
- `font_preview.rs`: fonts, for the three things the rest of the app asks before a specimen is drawn — whether a file is a font it can describe, the lines that font's own character map covers, and the file the browser can be pointed at. The two tables it reads are the character map and the `name` table, out of whichever container the file turned out to be — an sfnt, one face of a collection, a WOFF's per-table zlib or a WOFF2's one Brotli stream — under the budget every other read is answered under, with the answers held between hovers the way a document's measurement is, per file version and per face. A line is drawn only where the font covers every character of it, which is the one thing a browser cannot be asked: it falls back per glyph and says nothing about it. A collection is answered with the face the setting names written out as a font of its own, because a page has no syntax for naming a face inside one. See Font Previews.
- `wic_image.rs`: the picture formats this app has no decoder of its own for — HEIF (`.heic`, `.heif`), AVIF (`.avif`), JPEG XL (`.jxl`), a still WebP and a `.dds` — read by the codec the machine has rather than by one compiled in. One imaging factory per decoding thread, the decoder asked for a file rather than for a format (so what a file is, is its own header's business), and the box the layout planned handed to the codec, so what is decoded is the preview and not the file: the transform a codec offers for scaling during decode where it has one, WIC's own scaler where it does not, and the format converter that turns whatever the codec produced into the BGRA a frame is composed in. A machine without the codec is answered with no preview, which is what a file that will not decode gets; the extension packages that carry those codecs are named in the README and the app never sends anyone to the Store itself. Nothing is probed for a signature and nothing is held: the codec is the authority on what a file is, and it is asked once to measure and once to decode; see Codec Previews. A `.dds` is the one format here this app also carries a decoder of its own for, and the codec is still asked first: what the DDS codec reads is BC1, BC2 and BC3, and what it gives in exchange is the size, since a texture asked of it at the preview's own box costs the box rather than the file's sixty-four megabytes of texels — the formats it does not read are answered by `dds_image`, and the header is what each of them is asked about; see DDS Previews.
- `dds_image.rs`: the DirectDraw Surface formats the codec Windows has no answer for — every uncompressed one, in the classic header and behind a `DX10` one alike, and every block format from BC4 up — decoded on this side: the header read for the file's shape and its format, one mip level of the first face read and nothing after it — the level nearest the size the preview is drawn at — and the blocks turned into the BGRA a frame is composed in, resampled there because a block decodes to a 4x4 square and nothing can be scaled as it is read. The name a format is written under is read as it comes: a four-character code, the `D3DFMT` number a pre-DX10 tool wrote in its place, or the DXGI format a `DX10` header names, all of them answered by the decoder of the layout they stand for. BC1, BC2 and BC3 are left to the codec, which decodes them at the size of the preview rather than at the size of the file (see `wic_image`), and the block formats themselves are `bcn`'s; both variants of BC6H are read, the signed one drawn as light like the unsigned one, and with them the packed HDR formats and the depth buffers. See DDS Previews.
- `design_formats.rs`: the gate for design previews, holding the built-in extension list that is written to `config.ini` and read back from there, and the normalization that keeps a hand-edited list safe to match against. Nothing is probed here: the readers have the last word on whether a file holds a picture this app can show, and one is handed to them only after this gate has claimed it. `ai` is in the list although an Illustrator document is usually a PDF: the PDF gate is asked first and claims every one saved with PDF compatibility, so what this list catches is the ones saved without it — which are encapsulated PostScript, and are read by `eps_image`.
- `bcn.rs`: the block-compressed formats and how one 4x4 block becomes sixteen texels — BC1, BC2 and BC3 with the alpha their later variants carry, BC4 and BC5 for the one- and two-channel data a normal map or a mask is, BC6H for light, in both of the variants a file can name, and BC7's eight modes. Nothing of the container is here: a block is sixteen bytes with nothing to carry from the one before it, so these are functions over a block and the tables the formats are defined by, and the things that need them — a `.dds` this app decodes itself — are what hand them one. Every one of them is checked against the machine's own decoder and against two independent ones, block for block, over random data: BC7 agrees with both to the byte, BC6H differs only in values below the smallest ordinary half, which is a difference no preview can show, and the signed variant of it agrees with an independent decoder to the bit over four hundred thousand blocks of every mode.
- `tone_map.rs`: the curve a picture whose samples are light — an EXR, a Radiance HDR, a texture of one of the float formats — is brought into eight bits with, as `hdr_tone_map` and `hdr_exposure` name it: an exposure in stops, a curve (Reinhard, ACES, the sRGB transfer alone, or the bare clamp), and the transfer that turns a light back into a level. It is the one place those files and no others pass through. See Tone Mapped Previews.
- `webview_preview.rs`: the browser engine that draws every SVG document and every font specimen — the WebView2 runtime Windows 11 ships with — held warm on a thread of its own with a window of its own, because a layered window has no window tree to put a child in (the same shape as the video path, where the player's window is the preview). The preview loop measures the file, hands it over with the box the layout came out with, and the engine's window is the preview: this app draws neither, so what stands in for one while a browser starts is the waiting spinner and nothing else. What it is pointed at is a page of this app's own, written per file and per backdrop: a document goes in as an image that fills the box, and a font goes in through `@font-face` under the heading and lines `font_preview` worked out. One engine is kept per app and let go after `webview_idle`, ten minutes by default, or as soon as both kinds it draws are switched off; its settings are the app's rules rather than a browser's — script off, nothing fetched from anywhere (a resolver rule that answers for no host), no context menus, devtools, accelerator keys or zoom — and it keeps a profile folder of this app's own under the local profile, which is also where a collection's extracted face is written. The browser process it starts is adopted like an Office engine, so that neither a crash nor a kill can leave it running; see Started Processes.
- `codecs.rs`: what this machine has of everything a preview leans on — whether FFmpeg's player is installed, whether the media stack is up, which video decoders are registered, which codec extensions claim a picture format, and which applications and runtimes answer for a document, a specimen or a page. Nothing here starts anything: an Office engine is asked for by its ProgID rather than by starting one, and a decoder by enumerating what is registered rather than by decoding. Two callers ask — the tray's `Codecs` submenu, which asks for the whole list once when the menu is built, and the video path, which asks the one question of its own once per hover and is what the one cached answer is for.
- `video_player.rs`: the media engine Windows has, for a video preview on a machine without FFmpeg — the engine created in frame-server mode, the bitmap its frames are delivered into, and the loop that takes them; see Video Preview Engines.
- `video_formats.rs`: the gate for video previews, holding the built-in extension list that is written to `config.ini` and read back from there, and the MPEG-TS sync-byte probe that settles the `.ts` and `.mts` the text lists share — a list a user edits, so an extension added to it is a video from the next read, with only those two ambiguous names costing a probe.
- `archive_formats.rs`: the gate for archive previews, holding the built-in extension list that is written to `config.ini` and read back from there, the dotted-tail rule that makes a `tar.gz` entry mean a tarball, and the normalization that keeps a hand-edited list safe to match against.
- `archive_listing.rs`: reading an archive's own table of contents — zip's central directory, 7z's header block, RAR's header walk, tar's 512-byte headers — into one list of entries, with the entry cap, the name cap, the cancel flag every scan asks, and the listing cache.
- `archive_preview.rs`: turning a listing into a page — the tree the entries imply, the collapse of single-child folders, the sort, the capped rows, the summary line, and the paint through the text painting layer.
- `office_formats.rs`: the gate for Office previews, holding the built-in extension list that is written to `config.ini` and read back from there, the normalization that keeps a hand-edited list safe to match against, the container probe that asks a file's own header whether it is an OOXML package or an OLE compound file, the engine each family is rendered by, and the box a preview is placed for while its page is on the way.
- `office_preview.rs`: measuring and drawing the page the render tier produced — how large the source may be drawn, and the frame it is drawn into. Nothing is held in memory here: the page belongs to the render tier, and what this module does with it is read its size once and draw it.
- `office_render.rs`: the render tier — the apartment-threaded engine thread and its recovery, the engine it holds for each family, the late-bound automation that exports page 1 and takes a workbook's picture where no page can be exported, the temp-copy hygiene for the paths and zone identifiers Office will not open, the scratch file every render passes through, the in-memory cache the rendered pages live in, and the diagnostic test that drives one document of each family through the real path when one of them refuses.
- `project_image.rs`: the picture a project container holds of the whole document, read out of the container rather than composited — the flattened document a Krita or OpenRaster file keeps as `mergedimage.png`, the file-manager thumbnail OpenRaster keeps under `Thumbnails/`, and the previews other containers write under names of the same kind, whichever of them a file actually holds. Nothing is unpacked to disk: a member is inflated into memory under `decode_budget_gb`, decoded from there and resampled into the box the layout planned, with the size read from the member's own header and held between hovers per file version, so a container's table of contents is walked once rather than on every hover. See Design Previews.
- `psd_image.rs`: the merged picture at the end of a Photoshop document, read past the layers rather than through them — the colour mode section, the image resources section and the layer and mask section each stepped over by the length it declares, and the planar picture that follows decoded into the box the layout planned. Every channel is reduced on the way past, one row of the document at a time, so what a hover holds is the preview and a row of the source whatever the size of the document — and the source is walked once whatever the box is, which is what lets a document smaller than its box be enlarged rather than being asked for rows it does not have; all four compressions the format writes are read, the sixteen- and thirty-two-bit depths and every colour mode this reader has an answer for are brought into screen values, and Lab, multichannel, and a document saved without `Maximize Compatibility` — which holds no merged picture at all — are answered with no preview. See Design Previews.
- `text_formats.rs`: the gate for text previews, holding the built-in extension and file-name lists that are written to `config.ini` and read back from there, the dot-file rule that makes a `gitignore` entry mean `.gitignore`, and the normalization that makes a hand-edited list safe to match against.
- `text_preview.rs`: reading and decoding a text file, styling a window of it on demand, laying that window out, and painting it — with a scrollbar when the file is longer — into the same BGRA frame an image arrives in, and the cache those painted frames are held in.
- `text_paint.rs`: the painting both painted previews share — the top-down DIB surface, the font metrics and the fonts grown from them, the color helpers the themes are read through, and the one function that puts a run of text on the surface.
- `text_theme.rs`: the color themes — the two bundled TextMate themes and the user's own `.tmTheme` files, each parsed once and kept — plus the scope lookups that answer "what color is a heading in this theme?", the fallback that keeps a broken file from taking the preview with it, and the reading counter that tells a cached document which version of a file it was colored against.
- `theme_files.rs`: the `theme` folder beside `config.ini` — which of its files are themes, the names they are listed and written under, and the path a name resolves to.
- `tray.rs`: tray icon and menu, configuration toggles, exit flow, WM_POWERBROADCAST handling to re-add the icon after DWM/Explorer restart on resume, and the `TaskbarCreated` broadcast that re-adds it when Explorer itself restarts — the restart the Explorer hook is told about, since the Shell objects it resolves through belonged to the process that is gone.
- `config.rs`: INI-backed configuration with defaults and input sanitization.
- `startup.rs`: registry integration for the Run-at-startup setting.

## Media Pipeline

- Images (static, GIF, WebP) are decoded in the preview thread — a still WebP by the codec Windows has for it rather than by a decoder of this app's — with animated formats streaming frames into a shared queue. A picture of a format this app has no decoder for is decoded by the codec Windows has, at the box the layout planned; see Codec Previews. A `.dds` is the one format of that kind with a decoder of this app's behind the codec's, because the codec reads less of the format than the app does; see DDS Previews.
- A picture whose samples are light rather than levels — an `.exr`, a Radiance `.hdr`, a float texture — is tone mapped into eight bits before anything is done with it, with the curve and the exposure `hdr_tone_map` and `hdr_exposure` name; see Tone Mapped Previews.
- A decoded still image is kept between hovers, keyed by the file, the version of it that was read and the pixel size it was decoded at, and dropped least recently used first when it no longer fits `image_cache_mb`. See Image Previews.
- An animated preview opens on its first frames rather than on a startup buffer: the handover decides when the preview appears, not how much of the animation is played, and the decoder runs on ahead of playback once it has been handed over.
- An animation is held whole where it fits what one animation may keep decoded — every frame decoded once, the file played through, and a wrap a jump back into frames already in hand rather than a read of the file again. What does not fit plays through a sliding window instead: the frames behind the playhead are given back so that decoding stays inside that budget, and the decoder that was given them starts the file over. Both sides of that arrangement are settled under the one lock the frames are shared through, so a release and the end of a decode cannot pass each other — the player is left either with the whole animation or with a decoder that is still feeding it, and never holding the last frame of a file nothing will decode again.
- A frame's own delay is the unit its playhead is kept in: a frame a file asks to be held for a long time — a GIF frame of a second or more — is a frame waiting, not a playhead that has fallen behind, and only lateness past that delay is treated as drift and snapped forward.
- The preview window uses GDI and `UpdateLayeredWindow` to draw to a topmost, no-activate surface.
- Video previews are played by FFmpeg's `ffplay` where it is installed, and by the media engine Windows has where it is not: two engines, one preview, decided once per file by `codecs` and taken apart below. FFmpeg's path launches the player for playback and queries `ffprobe` for video geometry at the same time as the cropdetect pass that finds the letterboxing: neither needs the other's answer until the crop is validated against the dimensions, so a hover waits for the slower of the two rather than for both in turn. The player's lifetime is supervised as described in Video Process Lifecycle. The media engine's path measures the file with a source reader and draws the frames it is handed, in this app's own window; see Video Preview Engines.
- PDF previews render page 1 through `Windows.Data.Pdf`; see PDF Previews for the split between measuring a page and rendering it, and for the cache a rendered page is kept in.
- SVG previews are measured in-process for the box the layout places them at, and drawn by the browser engine the machine already has, in a window of its own; a document that moves needs nothing of its own, because that engine is what draws it too. See SVG Previews for what a document is not allowed to reach, and for what a machine without the runtime gets.
- Font previews are described in-process — the name the font calls itself, and the sample lines its own character map covers — and drawn by the same engine, the font itself in a page of this app's own under those lines. See Font Previews.
- Text previews are read, decoded, highlighted and painted in-process; see Text Previews for the split between the document, the layout and the frame, and for the cache a painted frame is kept in.
- Archive previews read the archive's own table of contents and paint a page from it, on the same worker thread and into the same BGRA frame; see Archive Previews for what a scan is allowed to read and how far it goes.
- Office documents are previewed from the page the render tier produced — a PDF page, a slide's image or a workbook's picture, drawn into the same BGRA frame; see Office Previews.

## What A Hover Is Allowed To Read

Everything that reads a file's bytes is bounded, and the bounds sit at the two places a read can start: the hook's resolution gate, and the loader that actually opens the file. Both ask the same questions, the way both already ask what kind of file something is, so a file one of them refuses cannot be reached through the other. What the ceiling on any of those reads *is* is one number rather than one per format — `decode_budget_gb` in `config.ini`, a gigabyte by default, and the tray's `Performance → Decode Budget` — and every reader is handed it before it allocates, so what a hover may cost is bounded the same way whatever the file turned out to be.

A file whose content is not on this machine is refused before anything opens it. OneDrive, SharePoint, Dropbox and the other synchronizing providers leave a placeholder in the folder — a few kilobytes of metadata carrying the name, size and dates — and pull the content down the first time something reads it. Nothing about the file says so: an ordinary open is what starts the transfer and the reader simply waits for it. That wait is unbounded, it is a download the user never asked for, and on a metered connection it is a bill, so a placeholder is answered with no preview instead of with a read. `cloud_files.rs` asks the file's *attributes*, which is a question about its directory entry and is the same question the shell asks to draw the cloud state in a file's icon; unlike opening the file, it does not start the download.

An image is bounded by what decoding it may ask for rather than by its own shape. Its header is still read first, but for the box the frame is decoded into rather than for a yes or no: what a decoder is handed is that budget, and it is asked before anything is allocated, so a seven-thousand by ten-thousand illustration, which is an ordinary thing to hover, is decoded at its own size, while a file that asks for more memory than a preview could justify is answered with no preview. That is the shape a decompression bomb has, and it is the shape of this bound for a reason: `catch_unwind` turns a decoder that returns an error into a missing preview, while an allocation as large as a huge image asks for is an abort rather than an unwind, and an abort takes the tray icon with it. Every reader is therefore handed the budget before it allocates — the decoders through `image`'s own limits, and the three that allocate a canvas of their own, the GIF's, the animated WebP's and the codec Windows is asked for a picture's pixels, through the same check. A header that will not report its dimensions is not a reason to refuse the file — the decoder has the last word on whether it is an image at all — so those are decoded as they always were and simply are not held in the cache. A texture is bounded the same way and read more narrowly still: a `.dds` hover is a header of a hundred and forty-eight bytes at most and the first mip level of the first face, a size the header's own format and shape work out to, so a cubemap of six faces and ten mip levels costs what one face's first level costs and a file that claims more than it holds is answered by a short read rather than by an allocation the size of what it claimed. See DDS Previews.

An archive is bounded by its own table of contents, which is the only part of it a listing reads. Nothing is decompressed: a zip's central directory is one read at the end of the file, a 7z's header is one read at its end, a RAR's headers walk from the front skipping each member's data, and a tar's headers are the 512-byte blocks between the data — so a hover onto an archive of five gigabytes costs what a hover onto a small one does. A scan stops at twenty thousand entries and cuts a name that has run past three hundred characters, and every loop asks the same cancel flag the load worker already holds, so a pointer that has moved on leaves the reading behind. The one format that cannot be read this way is a `.tar.gz`, whose table is not addressable at all: it has to be inflated to be walked, so its stream is capped at sixty-four megabytes, and past that the page says the listing stopped early rather than reading on.

An Office document is not read by this app at all. What a hover shows is the page Office drew for it, so the only thing this side does with the file is ask its own header what it is — an OOXML package or an OLE compound file, from eight bytes — before a path is handed to an engine, which is what keeps a file that is not a document at all from starting one. Everything a document holds is read by Word, Excel or PowerPoint, in its own process.

That process is bounded on this side instead. A document whose content is still in the cloud is never handed over, because the engine's open would be the download; a file carrying a zone identifier — the Protected View trigger — or a path longer than Office can take is rendered from a temp copy, which also keeps the engine from locking a file the user is working in; documents are opened read-only, without touching the recent-files list, in a hidden window; and a page is asked for the moment a hover exists rather than after the pointer has rested on the file, so the dwell a page waits for is the same hover delay every other preview waits for.

UI Automation is bounded by a timeout, set on the client when it is created. Every probe crosses into the shell's own thread, so a shell that has stopped answering would hold the hook inside a probe for as long as it likes, and the slow-probe backoff cannot see a probe that has not returned yet, which leaves an unbounded wait with nothing watching it.

The bound belongs to the client object rather than to the query, so the client has to be one that carries it: `CUIAutomation8` is created rather than the legacy `CUIAutomation`, which does not answer for `IUIAutomation2` at all. That distinction is not academic. Treating the missing interface as fatal — on the reasoning that a client which cannot be bounded looks bounded while able to block forever — is what answered every hover with no preview, because refusing the client left the resolver with no automation at all rather than with a slower one. A client that cannot be bounded is therefore still used, with the legacy object behind it as the fallback: what a client that ignored the timeouts costs is the wait this was meant to remove, which is the behavior the app had before, and not a dead app. A probe that times out is a probe that found nothing, which is what the rest of the hook already handles.

An SVG document is read by this app only to be measured, and by the browser to be drawn. The measurement has no cap of its own — a file is read whole and parsed whole, and what bounds it is the budget every other read is answered under, inflated size included, which a `.svgz` needs: it is a few kilobytes that can inflate to a great many, and both counts are asked for before they are allocated. The reading the drawing costs is the engine's, and it is bounded by the rules the engine is given rather than by anything this app counts: script off, a resolver rule that answers for no host, the document drawn as an image in a page of this app's own — where it cannot run anything, cannot take the pointer, and cannot open a file beside it — and a profile folder of this app's own for the browser to keep its state in.

A font is read by this app for two tables and by the browser to be drawn, and both halves of that are bounded the same way. The file is read whole under the budget every other read is answered under — the containers are a few kilobytes to a few megabytes — and of what is read only two tables are parsed: the character map, which is what the sample lines are checked against, and the `name` table, which is what the specimen is headed with. Both webfont containers inflate under the budget rather than by what they claim: a WOFF's tables are deflated one at a time, and a WOFF2's are one Brotli stream, which is decompressed only as far as the last table the specimen needs and only up to what one hover may decode for — a stream is free to say it expands to any size at all, so what stops it is the same ceiling a picture and an `.svgz` are answered with. Nothing is rasterized, nothing is shaped and nothing is drawn on this side; the drawing is the engine's, under the rules below. A collection is the one file this app writes anything for: one of its faces — the one `ttc_face` names, the first by default — is copied out as a font of its own into the browser's own profile folder for this run, named for the file, the version of it and the face, where the next start clears it away with the rest of what a run leaves behind.

## Image Previews

A still image is decoded, resampled to the size the layout asked for and converted twice — to RGBA and then to BGRA — and a file list is a place a pointer is swept back and forth over, so the frame that was already built for a file is handed back rather than built again. What a held frame is valid for is the file, the version of it that was read, and the pixel size it was decoded at. The version is there because a file edited in place has to be decoded again, and the *size* is there because a frame is stored decoded and scaled: the same photo shown at 100% and at fit-to-screen really is different pixels, and only the size that was asked for can be handed back for it. A header that will not report its dimensions cannot name that size, so a file measured that way is decoded as it always was and simply not held.

The cache is bounded by bytes rather than by entries, because what a preview holds is its pixels and a folder of thumbnails and a folder of wallpapers are not the same number of files. `image_cache_mb` in `config.ini` is the budget — 32 MB by default, capped at 2048, and `0` for a cache that holds nothing — and it is read from the configuration each time the cache is used rather than captured, so an edit applies without a restart. It is trimmed to that budget on every use, least recently used first, with a counter for the order rather than a clock so the order cannot be changed by the system clock moving; trimming on use is also what makes lowering the setting, to zero included, release what it no longer covers instead of leaving it held until something else happens to be stored. A frame larger than the whole budget is not held at all, because it would evict everything else and still not fit.

The cache is consulted *before* the decode rather than after it, which is what the header read buys: the size the frame would be decoded into is known before anything is decoded, so a hit never pays for a decoder at all.

## Tone Mapped Previews

A picture whose samples are light rather than levels — an `.exr`, a Radiance `.hdr`, a `.dds` of one of the float formats — is not shown as it is written. What a preview is composed in is eight bits to the channel and already display-encoded, and the two things those files need, and a PNG has already been through, are the transfer function that says how a light is written down and a curve that brings a range wider than the display's into it rather than clipping what is past it. What the app did without them was neither: what the `image` crate's own conversion is, measured rather than assumed, is a bare clamp, so a linear `0.5` — a light grey, and `188` as a level — was drawn as `128`, and everything from `1.0` up was drawn as white. On the files the format is actually written as, `[0.25, 0.5, 1.0, 4.0]` came out `[64, 128, 255, 255]` and comes out `[124, 156, 188, 231]` now.

`tone_map` is the whole of it: an exposure in stops, a curve, and the sRGB transfer, in that order. The curve is `hdr_tone_map`, and it is a setting because what a picture should look like is the user's answer rather than the app's: `reinhard` by default, which is `x / (1 + x)` — a value the display can already show is left very nearly where it was, and the whole of the positive range is brought into `0..1`, so a render whose lamp is a hundred times white is a picture rather than a white patch — `aces` for the filmic answer, darker in the shadows and more saturated, `srgb` for the transfer alone, which is right for a picture already graded for a screen and a clip for one that is not, and `off` for the bare clamp, kept because the grading a file was given is a thing a user may want to see rather than correct. `hdr_exposure` shifts the picture before any of them, which is what a file far darker or brighter than a display can be is brought into range with; a name that is not one of the four is answered with the default rather than with a curve picked at random.

Where it is applied is the one place both kinds of file pass through, and it is applied before anything else is done with them: a picture this app's reader decodes is tone mapped at the top of `load_static_image`, before the resample — which is the order that costs least, since an eight-bit buffer is a quarter of the memory of the floats it came from and resamples in a fraction of the time — and a texture of one of the float formats is tone mapped by `dds_image` sample by sample as it is read. What is not put through the curve is alpha: coverage is not light, and a picture composited over a backdrop with a curve put on its alpha fades differently from every other picture beside it. What is not put through any of it is a picture that holds levels already — a PNG, a JPEG, a BMP, a 16-bit TIFF — because a level sent through a transfer function a second time is a washed-out picture rather than a corrected one.

## DDS Previews

A `.dds` holds a texture, and what one is made of is one of two things: blocks compressed by S3TC — BC1, BC2 and BC3, which the older files call DXT1, DXT3 and DXT5 — or one of the formats those were joined by, which is BC4 and BC5 for the single- and dual-channel data a normal map or a mask is, BC6H for a range past the display's, BC7 for a photograph-quality colour at half of BC1's size, and the uncompressed formats a tool writes a texture in when it wants none of that. Two readers answer for the format, and the order they are asked in is about cost rather than about coverage.

The codec Windows has for a DDS is asked first, and what it reads is narrower than the format is: measured, BC1, BC2 and BC3 are decoded — behind the classic header and behind a `DX10` one alike — while every DXGI format from BC4 on and every uncompressed one, whatever flags it sets, is refused with "the image header is unrecognized". What it gives in exchange is the size, which is the reason it is asked at all: a texture is handed to it at the box the layout planned, so a four-thousand-square one costs the preview rather than sixty-four megabytes of texels and a resample — the same trade the HEIF, AVIF, JPEG XL and WebP codecs are asked on, and the same reason no decoder is compiled in for those either (see Codec Previews).

`dds_image` is the reader for the rest of it: the uncompressed formats, whose channels are read out of the masks a classic header declares or out of the DXGI format a `DX10` header names, and the block formats the codec has no answer for — BC4, BC5, BC6H and BC7 — which are decoded by `bcn`. A block decodes to a 4x4 square of texels, so nothing can be scaled as it is read the way a codec scales: the level is decoded whole and resampled afterwards, which is the same price every other picture this app decodes for itself pays. BC6H is two formats — the same blocks, read as light above zero or as light either side of it — and both are read here. What that leaves unread is what holds neither colour nor light: the integer formats, whose channels are plain numbers, and the depth-stencil pair a texel of which is sixty-four bits wide, both answered with no preview like any format neither reader has.

Some of the formats hold data rather than colour. A `_SNORM` variant's channel is a signed number either side of zero — the x and y of a normal map, a height that goes below its plane, the difference between two renders — and there are six of them uncompressed (R8, R8G8, R8G8B8A8, R16, R16G16 and R16G16B16A16) and two blocked, BC4 and BC5, whose blocks are the unsigned ones read the other way. What is drawn for one is the remap every tool that opens such a file draws: the sample's own range stretched over the display's, so a negative value is dark, zero is the middle and a positive one is light, with no curve on top of it, because this is data and not light. Two smaller decisions follow from the same reasoning. The channel a two-channel signed format does not carry is drawn at the level that kind measures nothing at — the middle of the range rather than black, since the zero of a signed channel is the middle — and a four-channel signed format is drawn opaque, its fourth sample being another signed number rather than an alpha, where `image_dds` composites that channel as though it were coverage. Signed light is the one that is drawn the other way round: a signed BC6H's range goes below zero, and what is made of it is the same curve every other kind of light is put through (`hdr_tone_map` and `hdr_exposure`), which lands a light below zero on black — a level is drawn as the data it holds whatever its sign, while light below zero is light that is not there. Two more kinds join those. The packed HDR formats (`R11G11B10_FLOAT`, `R9G9B9E5_SHAREDEXP`) spend a word on three partial floats rather than four bytes on each of them, and what they hold is light, so they take the curve every other light takes; and a depth buffer is read as the single channel it is and drawn the way the colour format with the same packing is drawn — `D16_UNORM` as a level, `D32_FLOAT` as light, and `D24_UNORM_S8_UINT`'s depth half, the low twenty-four bits of its word, as a level — with the stencil beside it left out of the picture and the stencil-only views not read at all, an index into a stencil buffer being no picture of anything.

All eight of those formats were settled against `image_dds`, which reads every one of them: files of random data in each, at whole and at ragged shapes, decode to the same bytes by both. The signed codebook's arithmetic is that reference's rather than a derivation of its own, which is why it rounds where the unsigned codebook beside it truncates — the unsigned one having been checked against the decoder whose own test vectors it follows instead.

What a hover reads of the file is its header and one mip level of its first face, and nothing after either — so a cubemap is six faces and a texture array is however many slices its header declares, and what a preview shows of one is the first. Which level of a chain is read is the size the preview is drawn at rather than the size of the file: it is the smallest level still at least as large as the box, which is the file's own answer to what the texture looks like at that size and, for a four-thousand-texel texture shown eight hundred wide, a sixteenth of the blocks to decode with nothing lost that the box could have shown. A file that declares a chain it does not carry is read from its first level, which is the one every file has. The header is a hundred and forty-eight bytes at most, and the level that follows it is a size the header's own format and shape work out to, checked against the budget every other read is handed before a byte of it is asked for, and against the length of the file itself: a file that says it holds more than it does is answered by its own size rather than by an allocation the size of what it claimed, and the frame the level decodes into is asked of that budget the same way a picture's is. A file that is not a DDS, a format neither reader has, and a read that comes back short are one answer: no preview.

A `DX10` header is the one place a file can say what its alpha channel is *for*, and the one thing it can say that is acted on is that it is opaque: a file whose alpha mode is `DDS_ALPHA_MODE_OPAQUE` is drawn as any other opaque picture is, because that is a file whose channel holds nothing — what a tool that never touched it leaves behind, and otherwise a faithful decode of a picture nothing can be seen through. The rest of what it can say is left alone: a straight or a premultiplied channel is composited as it always was, so a premultiplied file is drawn at the strength its colour already carries *and* its alpha, which is darker than it should be; and a file that declares nothing at all — every classic-header file, and most of what tools write — is drawn exactly as its texels have it.

What a texture is composited *over* is a setting of its own — `dds_background`, the tray's `Background → DDS Background` — rather than the backdrop a picture gets, and a `.dds` is therefore a kind of its own under `MediaType` the way a document is. The reason is the format's rather than the picture's: a texture's alpha channel is very often not alpha at all — a mask, a height, the roughness of a material, or a channel a tool never filled in and left at zero — so a hover onto one is the case where what is behind the frame is most likely to be worth choosing, and the case where a reader is least likely to want a picture's own answer.

## Codec Previews

A picture of a format this app has no decoder of its own for is decoded by the codec Windows has: HEIF (`.heic`, `.heif`), AVIF (`.avif`), JPEG XL (`.jxl`), a still WebP (`.webp`) and a `.dds`. Nothing is bundled for them and nothing is installed beside the app — the extension packages that carry those codecs (the HEIF Image Extension with the HEVC codec for one compression and the AV1 codec for the other, the JPEG XL Image Extension, and the WebP Image Extension, which Windows 11 has and Windows 10 usually has to be given) are named in the README, and where one is missing the file simply has no preview. That is the answer a file that will not decode gets, a hover says nothing about it, and nothing sends anyone to the Store. Two of them are exceptions in that direction: a WebP, because the codec is the one Windows 11 ships and Windows 10 usually has to be given — a still the codec has no answer for is decoded by libwebp, in the binary for the picture that moves, and asked for the still where the codec is missing (`webp_image`), while the picture that moves never reaches this path at all, since libwebp is asked for it first — and a `.dds`, because the codec reads less of that format than the app does: what it has no answer for is decoded by `dds_image` rather than answered with nothing, one reader behind the other rather than one instead of the other. The DDS codec is Windows' own rather than a package, so it is the one codec here that is not named in the README as something to install.

What the codec is asked for is the box the layout planned rather than the file's own size, which is the shape a PDF page and a page Office rendered already take and the reason this path exists at all rather than a decoder being compiled in: a phone's photograph is forty megapixels and a preview is a fraction of one, and a codec that can scale as it decodes — the HEIF one can, through the transform interface it exposes — decodes the fraction. Where a codec cannot, WIC's scaler takes the size the rest of the way, and the format converter turns whatever the codec produced, ten-bit or wide-gamut or without an alpha channel, into the 32-bit BGRA a frame is composed in. That is the format the preview wants in the first place, so the three things every other picture pays for — the resample, the conversion to RGBA and the conversion back — are not paid for here at all.

The reader is bounded the way the rest of them are, and by the same number. The frame's own size is read before anything is allocated and handed to `decode_budget_gb`, taken in `u64` so a shape that overflows a `u32` cannot wrap into a size that would pass, which is what keeps the illustration nobody could hover and the decompression bomb at one answer. A codec that is not installed, a file a codec will not open and a frame that will not decode are one answer as well: no preview.

The picture is held in the cache every other still picture is held in — the file, the version of it that was read, and the pixel size it was decoded at — so a second hover costs a lookup rather than a codec, and the size is part of the key for the reason it is there for a photo: what is stored is decoded *and scaled*, and the same file at two preview sizes is two frames. What is not done to it is orientation: a photograph from a phone carries the rotation it is to be shown at, in its container or its EXIF and sometimes both, and this app applies one to no format yet — so a picture whose bytes are stored sideways is drawn sideways. Which of the two a codec has already applied is the question a fix turns on, and it is a question for a file written by a phone rather than for a guess.

## Design Previews

A layered design document — a Photoshop `.psd` or `.psb`, a Krita or OpenRaster project, a container another drawing tool saves — is not drawn by compositing its layers, and none of the blend modes, masks, clipping, groups or effects behind them is implemented anywhere in this app. None of it has to be: every one of these formats keeps a picture of the whole document inside itself, and the preview *is* that picture, decoded into the box the layout planned. Which of the two readers is asked is settled by the file's own header rather than by its extension — `psd_image` and `project_image`, behind the `design_formats` gate — and a file neither of them answers for is a file with no preview, the same answer every format this app has no reader for gets.

A Photoshop document is the format's own merged image. The colour mode section, the image resources and the layer and mask section are each stepped over by the length each declares — the length a writer declares is what its own reader walks, so a padded section still ends where it says it does — and what is decoded is the planar picture the format writes after them. That picture is written at the document's own size, which for a layered document can be enormous: a `.psb` is the format's own answer to a document past the 30,000-pixel side a `.psd` allows, and 300,000 is what it allows. So it is decoded straight into the preview's box and never at the size it is — each channel, as it streams past, is reduced into the target by a box filter that averages every source pixel into the target pixel it belongs to, and what a hover holds is the preview and a row of the source whatever the size of the document. All four compressions the format writes are read: raw, the PackBits rows that carry the row-length table which finds them (bounded, so a count can never be an allocation), and the two zipped forms — one stream holding every channel's rows in order, read as the rows themselves rather than sought into, so nothing has to be located before it is decoded — where the predicted form has each row's difference unwound before the row is used: byte by byte at eight bits a sample, as whole two-byte samples at sixteen, and at thirty-two through the gathered byte order that form writes a row in. What is brought into screen values is an eight-bit sample as it is, a sixteen-bit one by its high byte, a thirty-two-bit one by its clamp, and the colour modes this reader has an answer for: RGB, CMYK with the four inks read as the light they leave, grayscale, duotone read as the gray it is built on, indexed with the palette averaged rather than the indices, and bitmap. Every channel is averaged on its own, which is the same reading of straight alpha a PNG gets from the picture path. What is refused is refused whole rather than guessed at: Lab and multichannel, and a document saved with `Maximize Compatibility` off, which holds no merged picture at all — compositing the layers is exactly the work this path exists to avoid.

A project container is a zip with the finished picture in it, so its preview is a member read rather than a decode of this app's own: the flattened document a Krita or OpenRaster file keeps as `mergedimage.png`, the file-manager thumbnail OpenRaster keeps under `Thumbnails/`, and the previews other containers write under names of the same kind — whichever of them a file actually holds, compared whatever case it is written in. What those are worth differs and the difference is not hidden: `mergedimage.png` is the document at the size the work was made at, while a thumbnail is a few hundred pixels the application wrote for its own file dialog, and a thumbnail is shown at the size it is rather than stretched to the room the display has, since there is nothing in it to enlarge. A member is inflated into memory under `decode_budget_gb` and decoded from there, nothing is written to disk, and the picture's size is read from the member's own header and held between hovers per file version, so a container's table of contents is walked once rather than on every hover.

An Illustrator `.ai` needs no reader of its own. Saved with `Create PDF Compatible File` — the default since Illustrator 9 — the document *is* a PDF whose page 1 is the artwork, so it is drawn by the PDF path and follows `pdf_scale` like any page; what is asked of the bytes is the `%PDF-` signature that path already asks, and it is asked of the `.ai` name alone so a `.pdf` is still answered without opening anything. What that compatibility leaves is a document saved as PostScript, and one of those is an encapsulated PostScript file under a different name: the PDF gate turns it down, the design list claims it, and it is read by `eps_image` for the preview the Illustrator that wrote it left inside. A file that left none shows nothing — which is what a document this app has no reader for gets — and what makes it worth reading at all is that Illustrator saved a preview with these files by default for as long as it wrote them that way.

Everywhere else a design preview is a frame of this app's own, drawn like a picture and asked for like a document: the frame is composed like a picture's, held in the image cache like one under the file, its version and the pixel size it was made for, and composited over the backdrop the tray keeps for this kind — `design_background`, a setting of its own, because what is previewed is the picture the document keeps of itself and a designer's transparency is the document's rather than a photograph's. The size it is drawn at is a share of the *display* — `design_scale`, `fit` by default — which is what separates it from a picture: what a hover is given is a document's own picture at whatever size the document happens to be, so the question is how much of the screen to give it, and `effective_preview_scale` answers with `fit_reduced` the way it does for a page or a specimen. The gate is its own under `Preview Types` (`Design`), since a user who wants none of these is not asking for pictures to be off, and the list behind it is `design_extensions` in `config.ini`.

## PDF Previews

A PDF preview shows page 1, rendered by `Windows.Data.Pdf` — the PDF engine that ships with Windows — so the app bundles no renderer and the user installs nothing. Two threads do this work, and both initialize a multithreaded apartment (`CoInitializeEx(COINIT_MULTITHREADED)`) before their first call, which is what WinRT requires of the calling thread.

The preview thread measures the page before anything is decoded, because the preview is positioned and sized first: the page size the engine reports (DIPs, 96 per inch) is what the layout is computed from, the same way video geometry is resolved up front. That probe is cached per path, failures included, so a file is parsed once and an unreadable file is not re-parsed on every hover. The render records the page size it read in the same cache, because both steps open the document: what the render already read is what the next measure would otherwise have opened the file again to find. Before a path is handed to the renderer it has to carry a `%PDF-` header in its first kilobyte, which is what keeps a mislabeled file out of the OS parser.

The document is opened from a stream over the file itself — not from a copy of it read into memory first, and not through `StorageFile`. `StorageFile.GetFileFromPathAsync` rejects the verbatim `\\?\` form the hook canonicalizes shell paths to: it fails with `ERROR_BAD_PATHNAME` while the same file opens through a plain path, which is why a PDF previewed from a search result but not from a folder view. A PDF is read by seeking in any case — the object graph is found from a table at the end of the file, and a page's own content and the resources it names can be anywhere in it — so reading it into memory bought nothing a seek could not have, and what it cost was the whole file held, twice over, while the page was parsed. `SHCreateStreamOnFileEx` is handed the path directly rather than the WinRT broker being asked to resolve it, so it accepts every path form the rest of the app produces, long and UNC paths included, and `CreateRandomAccessStreamOverStream` wraps that COM stream as the `IRandomAccessStream` the engine asks for. What a hover onto a large PDF costs is now proportional to the page rather than to the file.

The decode worker then renders page 1 into exactly the pixel size the layout asked for, after fitting the page's own aspect ratio into that box, so a page that is not the shape the layout assumed is letterboxed instead of stretched. Rendering at the target size is also what keeps a scaled-up preview sharp: `100%` is a 96 DPI page, while 200% or fit-to-screen is rendered larger rather than enlarged afterwards. Because of that, a PDF is laid out as a share of the room the display has rather than as a percentage of the page: `pdf_scale` names that share, and it starts at the whole of the room — the largest size the display allows is also the most legible one, and every value at or above `100%` reads as that fit — while a value below `100%` is a size the user picked, and reduces the fitted size rather than being ignored: `25%` shows a quarter of what fit-to-screen would. `effective_preview_scale` is the single place that decides it, so the layout and the render can never disagree about the size. The renderer is asked for its BMP encoder, which turns the decode on this side into a header parse instead of a PNG inflate, and the page is painted on an opaque white background so its text stays readable over any `image_background` mode. From there the result is an ordinary static frame: the existing spinner covers the wait, and a render that finishes after the cursor has moved on is dropped by the same generation check as every other load.

What was drawn is kept between hovers, keyed by the file, the version of it that was read and the box it was drawn into — a page is stored as the pixels it was rendered as, so the same PDF at fit-to-screen and at `25%` really is different pixels, and a file edited in place has to be drawn again. `pdf_cache_mb` is the budget — `32` by default, capped at `2048`, and `0` means a cache that holds nothing rather than a preview tier that is switched off, since the page is drawn for the hover that asks for it either way — read from the configuration each time the cache is used so an edit applies without a restart, trimmed to that budget least recently used first on every use, with a counter for the order rather than a clock, and a page larger than the whole budget is not held at all because it would evict everything else and still not fit. The cache is consulted before anything is opened, so a hit never pays for the engine, the header probe or the parse.

## Vector Previews

A vector drawing is not decoded: it is *drawn*, by something that turns shapes into pixels at whatever size it is asked for, and this app carries no rasterizer and no vector parser of its own. What it carries is two ways of asking something else to draw one, and the kind the tray calls **Vector** holds both of them: an SVG document, which the browser engine draws (see SVG Previews, below — that half of the kind is described there and is not repeated here), and a Windows metafile, which the drawing layer plays. All of it is one setting in the tray — one gate, one scaling, one background — because the question a user answers is the same either way: whether drawings are previewed at all, how much of the screen one may take, and what it stands on. The two halves are asked apart, and in one order: the document first, because the one list names both and neither reader of the drawing half would take a document — a hover that asked them first would show nothing at all for an `.svg`, which is a file the gate had already claimed and the layout had already measured.

A `.wmf` and an `.emf` are lists of drawing records rather than pictures, and Windows ships the player: `PlayEnhMetaFile` draws the records into any device context, and a memory context holding one of this app's own DIB sections is one — the same 32-bit BGRA surface every other frame is composed in. Nothing is rasterized on this side and no decoder is compiled in for the format; what a preview of one is, is the drawing replayed at the box the layout planned, which is why a metafile stays sharp at any size the display has rather than only at its own. The older form is read for its placeable header first — the one place a `.wmf` declares how large its drawing is and how many twips it counts to the inch — and a file without one is handed to the drawing layer as it comes, since the layer works the bounds out from the records themselves; either way the records are converted to the enhanced form the layer plays, which is also how a headerless file is measured.

Two plays are made for every frame, over a black page and over a white one, and the coverage the device context never writes is recovered from what the two disagree about: a pixel the drawing put something on is the same colour over either page, and a pixel it left alone is the page itself, so the difference between the plays *is* how much of the page the drawing covered. That is what lets a drawing stand on whatever the tray says is behind it — including nothing, for a text-free drawing over a desktop — exactly as a picture's alpha channel does, and it is why a metafile whose marks are black on white does not have to be given a white page by this app to be legible.

An encapsulated PostScript file is the other half and the more awkward one, because an `.eps` is a PostScript *program* and this app has no interpreter for one — nothing in it is parsed, evaluated or run. What is read is the preview the format exists to carry for on-screen display, in either of the two shapes a writer leaves it in: a Windows container, which opens with a signature no PostScript file does and a header naming where the program starts and where two previews of it may be (a metafile and a TIFF, either of which may be missing), or the comment block the format already has, where a Mac writer puts the same picture as hexadecimal between `%BeginPreview` and `%EndPreview`. Each is read for what it holds rather than for what it says it holds — every offset is measured against the file's own length and the decode budget before a byte of it is read, and the file is read for that preview rather than whole, so a hover onto a `.wmf` costs a header before this reader gives up on it. What the preview holds is then a drawing (replayed as above) or a picture (decoded and resampled like any other), and the drawing is preferred where a file carries both, because it is the drawing rather than a picture of it. One shape of picture is read on this side rather than by that decoder, because the decoder refuses it whole: an eight-bit index into a colour table with eight bits of alpha beside it is what a document written from Photoshop carries, and it is read by walking the picture's own directory — the table, the strips, the sample that is the alpha — and looking the table up here, with the alpha the decoder would have ignored kept and an associated (premultiplied) one divided back out of the colour it was multiplied into. A program with neither shape inside it — a plot, a typeset figure, a converted file, an Illustrator document saved without compatibility — has no preview in it to show, which is the same answer every file this app has no reader for gets.

## SVG Previews

An SVG is not a picture to a decoder but a document of shapes, gradients, texts and images, and this app does not draw one. What draws a document is the browser engine Windows 11 ships with — the WebView2 runtime, which is Chromium — in a window of its own. The two halves are the PDF path's shape with the renderer moved out of the process: `svg_preview` answers the two questions the rest of the app asks before it hands a document over — whether a file is one, and what size it asks to be drawn at — the layout places that size, and the box that comes out is the box the engine's window is given. What it is asked for is a share of the room the display has rather than a share of the size the file asks for — `vector_scale`, the whole of that room by default, with `100%` or more read as that whole room too, since nothing drawn at whatever size it is asked for needs to be enlarged past the display, and a share below it reducing what the room would have given. A page follows the same rule at a share of its own, which is `pdf_scale` and `office_scale` — see PDF Previews and Office Previews. What a document is drawn over is a setting of its own — `vector_background`, the tray's `Background → Vector Background`, which the document half of the kind shares with the metafiles the drawing layer replays (see Vector Previews) — rather than the backdrop a picture gets, because a document is drawn on a page where a picture's transparency is the picture's. Three of those four backdrops are the controller's to apply; the checkerboard is the page's own, because a checkerboard is drawn by whatever composites the frame and the engine composites its own.

Nothing is rasterized here, and that is what the arrangement is for: the release binary carries no rasterizer at all — no `usvg`, no `tiny-skia`, none of the font and shaping stack under them — and a document is drawn by the one renderer on the machine that implements the whole of SVG, SMIL animation and CSS animation included, rather than by a subset of it compiled into the app. What that costs is the runtime being there: a machine without it has no SVG preview at all, which is the answer a file that will not decode gets, and the tray's `SVG Engine TTL` is greyed out where it is missing. Windows 11 ships the runtime. There is no "does it move?" question anywhere in the path either: a still document and one that moves are drawn the same way, so an animation needs nothing of its own.

A measurement is all this app does with a document. The size is the root element's own — `width` and `height`, with a `viewBox` answering where they are relative or missing, and the 300-by-150 viewport a browser assumes for a replaced element where a document names neither — and a `.svgz` is inflated on this side rather than by the browser. The answer is held between hovers, keyed by the file and the version of it that was read, so a pointer swept back and forth over a folder does not re-read a document it met a moment ago; a version that turned out not to be a document is remembered as that. Nothing drawn is held: the document belongs to the engine, which is handed the file and not anything this app parsed out of it. A file that will not parse as XML, or whose root is not an `svg`, is answered with no preview — which is also what keeps a box the engine would draw nothing in from opening at all.

What a document may reach is bounded, though not by its size: this side reads a file whole to measure it, under the budget every other read is answered under, and the browser reads the document itself under rules the engine is given rather than ones it chooses — script off, a resolver rule that answers for no host, no context menus, no devtools, no accelerator keys, no zoom. What the engine is pointed at is a page of this app's own with the document in it as an image, and that is what makes the document the size of the preview box. A browser lays a standalone SVG out at the size the document asks for and does not stretch it to the window — a 120-pixel document in a display-sized window is a 120-pixel picture with the rest of the window empty, and a document with no size of its own fills the window and is magnified by any factor put on top of that — so the two disagree at every scale except the one that happens to match. An image, on the other hand, is drawn to the box it is given whatever its own size is, by layout rather than by magnification: `100%` is the document at the size it asks for, `50%` is the whole of it at half size, fit-to-screen is the whole of it as large as the display allows, and what is on screen is a document and not a corner of one. Nothing is given up for it, and something is gained: an SVG drawn as an image is animated and not scripted, cannot take the pointer, and cannot reach anything outside itself — not a file beside it, not a URL — so the engine's rules are the image's rules, which is why the page is written rather than the document being put in it as markup. The page is a few hundred bytes in the run's own folder, rewritten for each document, pointing at the document through a URL versioned by the file's modification time so that an edited file is never answered out of the browser's cache.

A hover shows the engine's window and nothing else: this app draws no document, so what stands in for one while a browser starts is the waiting spinner every other long wait is shown as, and a document whose page never arrives leaves nothing on screen rather than a still picture. Beginning the engine costs a browser start — a quarter of a second measured on this machine, nearly all of it the controller — so the first hover of a while pays it and every hover after that does not: one engine is kept warm between documents and let go after `webview_idle`, ten minutes by default. A wait that follows the pointer takes the engine's window with it, so what the document is drawn in is where the wait ended up rather than where the hover began.

What that page and its image are pointed at is a URL rather than a path, and the path a hover carries is the Shell's — the verbatim `\\?\…` form, which no browser will open and which a browser refuses silently — so the prefix comes off and a share keeps its server on the way (`file:///C:/…`, `file://server/share/…`). `webview_preview` is where the accounting continues: the window, the warm holder, the idle timeout and the rules the engine runs under.

The engine's state lives in one user data folder, and one folder is one browser at a time: an environment pointed at a folder another browser is holding is answered with `ERROR_INVALID_STATE` when it asks for its controller. That other browser can be a leftover — one left by a run that ended badly, whose app is gone and which holds the folder for as long as it lives — so the folder is a *folder per run* (`%LOCALAPPDATA%\rust-hover-preview\webview\<pid>`), and the folders earlier runs left are cleared at startup, best effort, since one still held cannot be removed and is not this run's to insist on. No run can therefore be blocked by any other, and the worst a leftover costs is disk until the next start.

What remains is defence in depth for an engine that fails for any other reason. The controller is asked for four times over a couple of seconds before the attempt is given up, and a failure is remembered for a minute, during which an SVG hover opens nothing at all rather than a box nothing would be drawn into — there is no reader behind the engine to fall back to. A document the engine could not put up, whose page could not be written or which it did not arrive at, costs that hover and nothing else: the wait comes down, and the next document is drawn as this one was meant to be. A tracer (`RHP_WEBVIEW_TRACE`) and a folder override (`RHP_WEBVIEW_PROFILE`, which is what the probes use so they can run beside a running app) exist for the same reason the other probes do: an engine that does not come up says nothing by itself.

A document is under the `Vector` kind in `Preview Types`: `svg` and `svgz` are entries of the vector list beside the metafiles and the encapsulated PostScript files, and what draws one is not a decoder, so the switch for them is not the switch for pictures. They were entries of the image list until the kind that draws them grew a list of its own, and a file this app wrote then is brought over to the vector list rather than left naming a document among pictures (see `config::configured_list_over_history`).

## Font Previews

A hover on a font shows a specimen of it: the name the font calls itself, the pangram *The quick brown fox jumps over the lazy dog.*, and a line each for as many of Japanese, Chinese, Korean, Cyrillic, Greek, Arabic, Hebrew, Thai and Devanagari as the file's own character map covers. It is drawn by the engine the SVG path uses — nothing on this side rasterizes a glyph, shapes one, or carries a font parser of the kind that draws text — and the page it is drawn in is this app's own, with the font in it through `@font-face`. That engine reads all five formats a font goes by, so the drawing costs no reader at all; and a machine without the WebView2 runtime has no font preview, which is the answer a file that will not decode gets.

The one question a browser cannot be asked is what a font *covers*. It falls back per glyph and says nothing about it: a page that draws 「いろは」 in a Latin-only font draws it in a system font, at the same size and in the same layout, so a preview that showed it would be claiming something about the font that is not true. The coverage is therefore parsed on this side, out of the font's own `cmap`, and the rule is all or nothing: a line is drawn where every character of it is in the font, and the space between two words is not a character a font has to have. Each line is the closest thing its script has to a pangram — the Arabic and Hebrew ones are the pangrams those scripts are sampled with, the Thai and Devanagari ones their openings, the rest of each pangram being words a font is as likely to be asked for as it is to have, and a line is drawn whole or not at all — so a font of a script there is no line for, a Georgian or a symbol one, is drawn from the characters its own map holds instead, which is the same rule reached the other way round; a file with no character map at all is answered with no preview rather than with a page of another font's text.

What that costs is one read of the file and a parse of two of its tables: the character map, and the `name` table the specimen is headed with — the family and style, a Windows English record preferred, and the file's own name where the font names itself nothing. Both webfont containers are read as well as the two open formats and a collection: a WOFF's tables are deflated one at a time with the reader the archives already use, and a WOFF2's are one Brotli stream, decompressed only as far as the last table a specimen needs and only up to the budget every other read is answered under (see What A Hover Is Allowed To Read). What the parse answers is held between hovers, keyed by the file, the version of it that was read and the face it was read at, so a pointer swept back and forth over a folder does not re-read a font it met a moment ago, and the two faces of one collection are two answers rather than one; a file that turned out not to be a font is remembered as that.

A font has no size it asks to be drawn at — what a file holds is outlines, and the text they are drawn as is whatever size a caller asks for — so the box the layout places is this app's own: the shape a specimen wants, and the share of the room `font_scale` names, half the display by default, the same rule a document's share follows, though a drawing's own starts at the whole of the room rather than at half of it. Every size in the page is a viewport unit, so the window that comes out of the layout *is* the size the type is drawn at: a larger share is larger type, which is what scale means for a picture and a document as well — and a font that covers more lines than that box was shaped for is drawn at smaller type rather than past the bottom of it. The page carries its own colours rather than getting them from the controller, because a specimen is a page of text and not a picture with transparency of its own: light ink on the black backdrop, dark on the white one and on the checkerboard's squares, and light ink with a soft dark shadow where there is no backdrop at all to be read against. What it is drawn over is `font_background`, a setting of its own — the tray's `Background → Font Background` — for the reason a document has one. Each line carries its own direction, which is what a browser settles a block of text from anyway: a right-to-left line is laid out from the right, so its punctuation ends it where the script ends it, and a line of any other script is drawn as it was.

A collection is the one case the engine cannot be handed the file for. A `.ttc` holds several faces that share one table pool and are found by offsets into it, and a page has no syntax for naming a face inside one, so one face is written out as a font of its own — a header and a directory of that face's tables with the tables copied where the new offsets say — beside the browser's own profile folder, named for the file, the version of it and the face. Which face that is, is a choice rather than a property of the file: `ttc_face` names it, from the first face to the tenth, and a collection with fewer faces than the setting names is drawn from the last one it has. The specimen's heading carries both halves of that — the face's own name and `(2 of 4)` — so a collection hovered shows that it is one and which of its faces is on screen; and the page is named for the face as well, so switching faces is a page the browser has not seen rather than the one before it out of its cache. Nothing else is written for a font, and what is written goes at the next start with the rest of what a run leaves in that folder.

A font is its own kind under `Preview Types` — a gate of its own, a list of its own in `config.ini` (`[font]`, `otf,ttc,ttf,woff,woff2`) — and both halves of the app ask in the same order: the hook's media gate asks the font list after the text lists and before the image list, and the renderer asks the same place in the same order, so a `.ttf` is under `Fonts` rather than under `Images` and the two cannot disagree about which gate a file is under.

## Text Previews

A text preview shows the first screenful of a text file, colored by the syntax definition its extension names. Which files those are lives in `config.ini`, written from the built-in lists on first run and read back from there, so a user can add a format or remove one without a rebuild; `text_formats.rs` owns both lists and the normalization that keeps a hand-edited entry from matching anything but a bare extension. Both the Explorer hook's "is this previewable" gate and the renderer consult it, so the two cannot disagree about what a file is.

There are two lists because one cannot reach the files a repository is recognized by. Extensions are matched the way the filesystem reads them, which leaves out `LICENSE` and `Makefile` (no dot at all) and, less obviously, `.gitignore` — a leading dot begins a *name*, not an extension, so `Path::extension` reports none for it. The extension lookup therefore falls back to the name minus a leading dot, which is what makes a `gitignore` entry mean `.gitignore`; and a second list of names carries the extensionless files, matched whole, case-insensitively, with the same dropping of a leading dot on both sides so that `gitignore` and `.gitignore` are one entry in either list. A file is in when either list claims it, so `.eslintrc.json` is still read by its extension while `.eslintrc` is read by its name. `is_text_file` is the one gate both sides ask, so a file the hook offers is a file the renderer can draw.

Text has no size of its own, so the two-step shape of the PDF path is repeated with a different measurement: `measure` resolves the box the first screenful wants, bounded by the display it will be shown on, the layout fits that box into the space beside the cursor or focused item, and `render` is handed the box that came out and fills it. What differs is what the box means. A PDF page is a vector and is drawn at whatever size the layout asks for; text is drawn at a fixed font size scaled by the display's DPI (`GetDpiForMonitor` on the monitor under the hover, falling back to 96), so scaling the box would only stretch the window around text that stays the same size. `effective_preview_scale` therefore answers `100%` for text — never enlarged, reduced only when the space beside the cursor cannot hold it — and the renderer reads the box it is given as "as many lines and columns as fit". What the fit must not do to a text box is shrink it whole: the lines wrap at the width the box ends up with, and a narrower box needs more rows than the proportional height leaves — a long line that took two rows at the display's width takes three in the box that comes back, and a frame sized for the two showed only the first of them, which is a long line that looks unwrapped. The document is therefore measured again at the width the box came out with, and that box is placed again from the measurement, so its height is the height the text really takes at the width it wraps in. A two-line file gets a two-line window — more when its lines wrap — and a long file takes the largest box the display allows, which is the same thing fit-to-screen does for a PDF.

The tray's `Text Preview → Font Size` setting multiplies into that: `TextMetrics` scales the display DPI by the configured percentage into one scale, so the glyphs, the line spacing and the page margin grow together and a preview at 200% is the same page twice the size rather than the same page in a larger box. The size is deliberately not part of the parsed document's cache key — the styled lines are identical at any scale, and only the layout changes, so changing the size repaints from the cache instead of re-reading the file. The combined scale is bounded (0.25x to 16x), which is what lets a hand-edited `text_font_scale` of any percentage be used as written without asking GDI for a glyph taller than the screen.

Previews are also gated by kind, from the tray's `Preview Types` submenu: `image_preview_enabled`, `video_preview_enabled`, `text_preview_enabled`, `pdf_preview_enabled`, `archive_preview_enabled`, `office_preview_enabled`, `svg_preview_enabled` and `font_preview_enabled`, all on, switched through `config::PreviewType`. A gate is only whether previews of that kind may be shown at all — the lists and settings that decide which files of that kind are previewed are untouched, so a kind switched off and back on restores what was configured. Both halves of the app ask: the Explorer hook's media gate asks the kind of a file — video first, because only content settles the `.ts`/`.mts` the text list shares, then PDF, then the text lists, then the image list — and the renderer asks the same question when it measures a preview, so a preview cannot be laid out for a kind that is off. A document is asked about in the same order and by both halves — the image list first, then whether the file is one — so `svg` and `svgz` are under `SVG` rather than under `Images`: pictures switched off leave a document previewing, and a document switched off leaves pictures alone. `text_preview_enabled` is checked in `text_formats::is_text_file` ahead of both lists, so turning text previews off is one gate the hook and the renderer both already consult, and the lists survive for when it is turned back on. A kind switched off takes the preview of that kind with it: the tray hands the preview thread a type change, and a preview whose own kind is the one that changed is rebuilt from the hover it came from, which drops it because the layout finds no size for a file whose kind is off — a preview of any other kind is left as it is, so a running video is not restarted by a toggle it has nothing to do with. The engine behind a kind goes with it as well, since what an engine is for is previews of its own kind: `Office` ends the Office processes, and `SVG` or `Fonts` — the two kinds the browser draws, which is why it is kept while either is on — lets the browser go. The Office ones are ended from the tray rather than asked of the worker — a worker inside a COM call it cannot cut short would hold one of them for good, and the tray may not wait on one — while the browser is let go by its own thread, which reads the gate rather than being told about it. A gate written into `config.ini` rather than clicked in the tray is answered the same way, by each engine's own thread, so the switch is the same switch however it is thrown.

The colors come from the theme selection, and the selection can be a file the user wrote: `text_theme` answers from one of the two bundled TextMate themes, or from the `.tmTheme` a selection names in the `theme` folder beside `config.ini` (see Configuration). Both are read by the same reader, and a file is read when it is asked for rather than when the folder is listed, so a folder of themes costs nothing until one is chosen; the menu is what lists the folder, and opening it is also what drops the parsed files so that the next preview reads them again. A file that is missing, unreadable, or not a theme is answered with the default — Atom One Light — instead of nothing: the renderer is handed a theme it can paint with, the item keeps its place in the menu, and the selection stays in `config.ini` until another theme is chosen, so a repaired file is used as soon as the menu is opened again.

The parsed document is cached per path, modification time, length, theme and Markdown mode — plus, for a theme that came from a file, the reading of it the document was colored against, since a file can be edited under a name that does not change — so a second hover, a repaint, or a theme switch costs a layout rather than a parse. What is cached is the *text and where its lines start*, not styled lines: the line table is eight bytes per line and no parsing at all, which is what lets a preview know how tall a document is — and how far it can scroll — before anything has been colored. Styled lines are built per window by `styled_window`, kept in a small per-document cache, and indexed by absolute line number, so a window that already covers a scroll position costs nothing and the window the layout asks for is sized from the box. For a source file the parser runs from wherever it left off, or from the nearest of the checkpoints taken every few dozen lines, and only the requested lines are kept: nothing past the window is ever styled, and a jump in either direction is bounded by the checkpoint spacing. The parse state itself cannot live in the shared cache — syntect's `ParseState` holds pointers into Oniguruma's match regions and is not `Send` — so it is kept per thread in a `thread_local`, and the windows, which are plain data, are shared between the threads that measure and paint. Four producers fill that model: `syntect`, with the syntax definitions `two-face` adds on top of the ones it bundles, colors source and markup files; `pulldown-cmark` turns a `.md` file into the document it describes, handing fenced code back to `syntect` and asking the theme for the color of a heading, a quote or a link by scope, so a rendered document and a highlighted source file share one palette — it is the one producer that reads all of its input, because a rendered line's place in the document is only known once the block before it has been walked, and it keeps only the window's lines as it goes; an RTF control-word stripper reduces a `.rtf` file to the text it carries, skipping Word's own tables, once, at load; and an NFO reader decodes CP437 art and consumes its ANSI escapes into colors toned toward the page they are drawn on. The one producer whose lines are not the file's own is the rendered Markdown document: a paragraph is one line, a heading is one, and the blank line between two blocks is one the source does not have, so the walk that renders the document is also what counts what it drew — once, when the document is built — and the preview's scroll range, its scrollbar and the lines it says are left out are all measured in those lines. Reading is bounded — 2 MB and a 2000-line scroll range — and decoding decides the encoding from the file: byte order marks first, then UTF-8, then the legacy code page CP437 belongs to. Two guards keep non-text out: NUL bytes mean the file is not UTF-8 text (a UTF-16 file is recognized from where its NULs fall, and anything else is binary), and a decode that is mostly control characters is a binary file that happened to pass.

What is painted is kept as well, keyed by the file and its version, the options a preview was painted with — theme, Markdown mode, font scale, full mode — the box and the DPI it was painted in, and the line it starts at: a frame is pixels, so unlike a parsed document the font scale really is part of what makes it, and a scroll position really is a different frame. `text_cache_mb` is the budget — `0` by default, capped at `2048`, and `0` means a cache that holds nothing rather than a preview that is switched off, since a frame is painted for the hover that asks for it either way — read from the configuration each time the cache is used so an edit applies without a restart, and trimmed to it least recently used first on every use, with a counter for the order rather than a clock. The cache is consulted before the document is even looked up, so a hit costs a clone rather than a layout and a paint, and a frame larger than the whole budget is not held at all because it would evict everything else and still not fit. A frame a selection was painted into is never held: that is a picture of a drag rather than of the file, and it is different for every one of them.

Layout keeps a document readable inside the box rather than filling it. A line wider than the page continues on the next one, wrapped between words, and a word wider than the page — a URL, a hash — is cut at the edge: nothing in a text preview scrolls sideways, so whatever ran past the right edge would be out of reach for good, and that is as true of a source file, a block of NFO art or a paragraph no grammar claims as it is of a rendered document. The wrap goes only as far as the frame could draw — the lines it has room for, and no scroll position reaches past them, because a position is a document line and a frame always starts at a line's own first visual line — so a minified file, one line of megabytes, costs a frame's worth of wrapping rather than the whole file's. A frame is pulled back until it can be filled from where it starts, so the last screenful of a document is full instead of showing two lines at the top of an otherwise empty box — the lines above a frame that would end early are walked backwards from its top while the box has room for another, which measures the pull-back in the document's own lines rather than in the lines that fit: one line can take two of the box's, and a pull-back by the number of lines that fit left the end of the document out of reach, both as a wall a few lines too high and, past the end, as a frame that painted nothing. What that leaves is one rule for the end of a document: the frame whose tail fills the box is the last one, its last line is on screen, and a position past it — a thumb dragged to the bottom of its track, a line left over from a file that was longer when the preview opened — resolves to that same screenful rather than to an empty box. A line is kept at the end for a note whenever the frame cannot show everything and no scrollbar is going to say so: a file that was cut at the read cap, whose remainder cannot be reached by scrolling either, or any document at all in a preview that does not scroll.

A document longer than its frame gets a scrollbar, drawn into the same frame the text is: a groove and a thumb whose length is the share of the document the frame shows and whose position is the share above it. The bar's geometry comes from one function used by both the painter and the hit test, so what is drawn and what a drag lands on cannot drift apart. The wheel reaches the preview through the low-level mouse hook rather than the window, because the preview never has focus and Windows delivers wheel messages to the focused window — Explorer — instead; the hook asks the preview for the pointer region, swallows the message when the pointer is inside it, and leaves the notches for the preview thread. The delta comes from the hook structure's `mouseData`: a low-level hook is handed the message identifier and a pointer to that structure, and the delta a window would find in the high word of `wParam` is not filled in there. Dragging the thumb is ordinary mouse input, which the layered window does receive: a press on the bar starts a drag with capture, a move maps the pointer back to a document line in the range the bar was drawn for — the lines the preview can reach, not every line the file holds — and a release ends it, so the bar and the thumb's drag cannot disagree about where the end of the document is.

The same messages carry a selection. A press that is not on the bar starts one, a drag extends it, and both ends of it are places in the text rather than points on the screen: the frame hands back the lines it painted with where each run of each line landed, and a point is turned into a (line, character) against those, so a selection survives the window being repainted and a point that runs off the text takes the nearest end of the line instead of being lost. The selection is painted into the frame rather than drawn over it — the run under it is split and drawn in up to three pieces, the middle one over the theme's own highlight colour — which means changing a selection costs a re-render of the window on screen; a screenful of lines is cached by then, so it is a repaint rather than a re-parse. Copying reads the same painted runs, so what is copied is what was on screen, and the lines a selection touches are joined with Windows line endings. The clipboard itself is the system one: a movable block of UTF-16 handed over with `SetClipboardData`. Keyboard copy is the piece of text editing that cannot arrive as a message — the preview never takes focus, so it would never receive the keystroke — so it is polled the way the rest of the app reads keys that belong to it: `Ctrl+C` only while there is a selection to copy. Selecting everything is the menu's `Select All` instead, which takes the whole frame, the range a Copy with nothing selected would have taken anyway. The right-click menu is asked for its command rather than posting one, so it needs no message loop and the preview never has to activate.

All of it is full mode's. With the tray's `Text Preview → Full Mode` off, the renderer is handed a frame that does not scroll — the text a box cannot hold is said in a line on the end of it, the way it was before any of this — the preview keeps no state to select into, and the pointer over it closes it the way it closes any other preview.

What makes all of that possible is one published pair of regions: the journey from the point a text preview was opened from — the cursor that hovered the file, or the middle of the focused item — to the preview, and the preview itself, both in screen coordinates, with the margin a hand that overshoots needs beyond the preview's far edge. Their shape is the point. A preview is placed *beside* what it belongs to rather than over it, so the pointer has to travel to reach it, across a gap and sometimes against the side the placement chose, and the journey is what that crossing is: it reaches the preview's *nearest* point and stops there, so everything it covers away from the preview is the row of the file list the pointer crosses, and it is as tall as the crossing rather than as tall as the preview. Reaching across to the preview's far corner instead — the box around both rectangles — covers the whole column of the list between the pointer and the preview, and inside the region nothing under the pointer is resolved: a text preview as tall as the display put every file in that column out of reach for as long as it was up, which read as previews failing at random in a list beside a text preview and never in one beside an image. The one place the pair reaches past the preview is the edge the journey ends at — the right edge for a preview placed to the right of the cursor, the left edge for one placed to the left — because the pointer is still moving when it arrives and what waits there is usually the scrollbar, a thin target at the very edge of the frame: the `text_scroll_far_edge_grace_pixels` setting is what keeps a hand that overshoots it from taking the preview down with it — forty logical pixels at the display's DPI, read from the configuration each time the regions are published rather than baked in, so the distance is a setting as well as a constant. Nothing past the near edge is added, since the pointer has already stopped there. The pair is published for any text preview in full mode, scrollable or not — resting on a preview is how it is selected from, and a document that happens to fit still needs that. It is recomputed from the preview loop on every tick, so it tracks the window as it is moved, and two flags published beside it say whether the preview on screen can scroll and whether the pointer is being held at all. Both are atomic reads, so the hook's check for them costs nothing until a text preview is actually up.

The Explorer hook asks whether the pointer is inside that region, and answers exactly one question with it: whether the pointer is on its way to the preview. A move is normally what resolves the item under the pointer and drops a preview whose file is no longer under it, and on the way to a preview the item under the pointer is the preview rather than a file, so while the pointer is inside the region and over no file the preview stays, and the sweep of the mouse-delay path that would raise a preview for nothing is skipped. It does not decide what is *under* the pointer: another file takes the preview over the moment one is under it, inside the region or out of it. Nothing is held over from one poll tick to the next either — the answer is read from the region as it is published, so a pointer outside it is treated as it was before the pointer ever touched the preview — and a pointer that is over the preview rather than over Explorer is not read as the user having left Explorer, since a preview is drawn on top of the window it belongs to and the check that asks whether the pointer is over Explorer cannot see under it. The wheel hook asks for the preview's own region before deciding whose wheel it is — the wheel belongs to the preview while the pointer is on it or just past its edge, not while the pointer is still crossing the row in front of it, where the wheel is Explorer's. The regions are withdrawn when the preview is hidden, so nothing else in the app has to know which previews scroll.

A theme or Markdown-mode change is different from a background change, and the preview loop treats it as such: a text preview's colors and glyphs are in its painted frame, so `Refresh` rebuilds the visible preview from the hover it came from (recorded when it was shown) instead of recompositing the frame it already has, while every other format only needs the recomposite.

Painting goes through GDI into a surface of its own: a memory DC with a top-down 32-bit DIB section, filled with the theme's background, block decorations written directly into the pixels, and every run drawn with `ExtTextOutW` against an opaque background rectangle — which is also how a code block's band and an inline code span get their fill. Fonts are created per style and size, once per paint, and the DC is handed back its original object before they are deleted, so a hover leaves no GDI objects behind. The frame that comes out is forced opaque on the alpha byte on its way out: a text preview is a page, not a cut-out, and the same composition path that paints a PDF's white page then composites it unchanged in every `image_background` mode.

## Archive Previews

A hover on an archive shows what is inside it: a summary line, a hairline, and a tree of the archive's own entries — folders first, each row indented by its depth, every file's size right-aligned, and a note at the end when the page could not hold everything. The page is painted rather than composited: it goes through the same GDI layer a text preview does (`text_paint`), which is what gives it the same font, the same margins and the same theme — the bundled One Dark Pro and Atom One Light, or a `.tmTheme` of the user's own — and no syntax highlighter anywhere in the path, because there is nothing in a listing to highlight.

What the page is built from is the archive's table of contents and nothing else, so no member of it is ever decompressed (see What A Hover Is Allowed To Read). `archive_listing` reads that table per format — zip through the `zip` crate's central-directory view, 7z through `sevenz-rust2`'s header parse, RAR through RARLAB's official UnRAR sources compiled in by `unrar_sys`, tar through the `tar` crate and `flate2` — and answers one shape for all of them: names, sizes, whether each is a directory, and whether the archive could be read to the end. A name is cleaned up to be drawn and nothing else: separators normalized, control characters dropped, the whole thing cut to three hundred characters. It is never resolved, joined or opened, so an archive cannot use its own contents to reach anything.

Which reader opens a file is settled by the file's own header first and by its name second, and the two answer different questions. The gate a hover passes — `archive_formats` — asks only what the file is called, because it asks it of every item the pointer touches and a synchronizing provider's placeholder is a directory entry that can be answered for but a file that must not be opened. Which of the readers can open it is a question for the loader, which is already past the cloud gate: a `.jar` is a zip under a name the zip crate has never heard of, and a `.zip` that turns out to hold a 7z is still a 7z. An archive whose own file table is encrypted is answered with a page that says so rather than with nothing, and one whose entries are encrypted but listed is marked as such.

The tree is built from the entries' paths rather than from the order they arrive in. A folder that exists only as a prefix — a zip written without a directory entry for `docs/`, holding `docs/report.pdf` — is still a folder, which is why the header counts folders the way a file manager would and not the way the archive happens to be stored. Children sort folders first and then by name, case-insensitively and with digit runs compared as numbers, so `report2` sits before `report10`. A folder holding nothing but the next folder collapses with it into a single row, `a/b/c/`, so a deep and narrow path costs one line instead of one per level. The rows carry a glyph from the icon face Windows ships — Segoe Fluent Icons on Windows 11, the MDL2 set it replaced on Windows 10 — chosen by what an entry is and what it is called: a folder, a page, a picture, a film, a note, a brace for code, a zipped folder for an archive, and the archive's own glyph in the summary line. The face is asked for once, and a machine that has neither is drawn without icons rather than in a face that does not exist, because a missing icon font is a row of boxes.

The page is drawn to a cap. A hundred rows are laid out, the box the display allows may show fewer, and the rest is said in one muted line at the end — `… and 46 more items`, or `… and at least 46 more items (the listing stopped early)` when the scan rather than the page is what ran out, because past that point everything counted is a floor and the page says so.

Nothing about the page is interactive. It does not scroll, nothing in it can be selected, and the pointer resting on it closes it the way the pointer resting on an image does: those are text full mode's, and a listing is a thing to glance at rather than a thing to work in. The listing is cached by the file's path, modification time and length, so the measure pass, the render pass and a second hover read the archive once between them, and the frame is rebuilt from the hover it came from when the theme, the font size or the `Archives` gate changes — a painted frame, like a text preview's.

## Office Previews

A hover onto a Word, Excel or PowerPoint document shows a page of it, drawn from the one source there is: the page the render tier produced and is holding in memory. What a document saves inside itself — the `docProps/thumbnail.*` metafile or bitmap an OOXML package carries, the summary information stream a legacy compound file keeps — is deliberately not read. It is a thumbnail, a couple of hundred pixels across: either tiny in a preview or an enlargement of something that small, and it costs a zip or a compound-file parse to reach. The page is the whole of it. A workbook is the one page that is not simply read out of the file: Excel lays a sheet out for printing from the values in it, and it works those values out again as it opens the workbook — so a page of a workbook is the page its values come out as, which is not necessarily the page the file was saved holding. Holding Excel in manual calculation first does not prevent that: a workbook is recalculated as it is opened whatever the application's calculation mode says, which is measured rather than assumed, and setting the mode at all costs a workbook opened and closed for the asking, since Excel answers for neither reading nor writing it while none is open. `office_render::excel_calculation_probe` measures both halves of that.

Everything a hover draws is held in memory. `office_preview::measure` reads the source's own size — a PDF page's DIPs from the PDF engine, an image's pixels from its header, both parsed out of the bytes the render tier is holding — and `office_preview::render` draws it into the box the layout planned. The size is kept on the page it was read from, so the layout's several questions in one hover cost one parse between them, and a size cannot outlive the page it belongs to: a document that is saved again is a different page, and its size is read from that one. What that costs is worth bounding, and a picture can be far larger than the box it is shown in — a worksheet's corner at screen resolution is millions of pixels — so shrinking one uses the box filter, which is the fast one, and enlarging the smooth one. What is drawn is checked before it is used, too: a page that will not give up its size — bytes a render cut short, or bytes something else has corrupted — is dropped and the document rendered again, because a page that cannot be drawn would otherwise be handed to every later hover, and each of them would blink. That check lives on this side rather than where the page is held because it is the side that may ask the PDF engine: these threads are multithreaded apartments, while the engine thread is not.

What the render tier keeps is memory, and only memory. `office_cache_mb` is the budget, pages are dropped least recently used first when it is exceeded, and the page a hover is waiting for is never one of them: a budget of nothing means nothing is kept *between* hovers, not that a page cannot be shown at all. It is `64 MB` by default — producing a page costs an Office start and an export, so a document that has been drawn comes back without another render — while `0` is the size for a machine that would rather keep nothing: at `0` a page lives from the moment the render produces it until the moment the hover that asked for it ends (`hover_ended`), and the next hover of that document renders it again. Nothing here switches the tier off either way: an Office document has no other source for its preview, and the `Office` gate under `Preview Types` is the switch. Office's export calls take a file name rather than a stream — `ExportAsFixedFormat`, `Presentation.Export` and `CopyPicture` all write to a path — so one render does pass through a file: a scratch name of this render's own in the temp folder (`page-<pid>-<n>.<ext>`, which is what keeps a file left behind by a process that was ended mid-render from being mistaken for a page this one wrote), read into memory and deleted in the same breath, with every candidate extension removed whether or not it was the one written, so a failed export leaves nothing behind for the next attempt to find. Nothing is ever read from that file twice. The user's own cache folder is not a cache location at all any more: what an earlier version left under `%LOCALAPPDATA%\rust-hover-preview\office` — and any scratch file a killed process left in the temp folder — is deleted at startup, before anything can write there again.

Which shape the source is decides how large it may be drawn. A page Office exported, and a slide's PNG, are vector or near enough, so they take the room the display has, at the share of it `office_scale` names — the rule a PDF follows, a share below `100%` included. The bitmap a workbook is answered with where no printer can export a page is the exception: it is only as good as the pixels it holds, so a share of the display is read for it as the same share of its own size, and a fit as the bitmap at the size it is rather than as an enlargement to fill the screen. That decision is `effective_preview_scale`'s office arm, which is why `office_preview::source_kind` exists — the layout has to know which kind of source it is placing before it places it.

While a page is on its way there is nothing to measure, so the preview is the spinner's own box — `office_preview::WAITING_BOX`, the size of the arc and the halo that fades past it — placed at the size it is rather than fitted to the display, which for a box of that size would be a screen-sized square with a spinner in the middle of it. The box is the spinner's frame and nothing more, and the wait is placed flush at the pointer's own corner — the one of the four quadrants the display has room for the spinner in, and a pixel off the pointer, because the preview window is what a mouse message at the pointer lands on and the pointer has to keep clicking and probing the file it is waiting on rather than the spinner that is waiting on it — rather than by the margin a preview keeps and the avoid-step that keeps it off the name: a wait is the wait for the file under the hand, so it is the wait at the hand, and one placed a cursor's width away from it, in a frame the arc floated in the middle of, said less about what was being waited on than the empty space it left. Every kind of wait is placed that way — the arc's own box at the pointer's corner, a decode's and a browser's as much as a page's (`waiting_placement`) — so what stands in for a preview that is not ready is one thing to read wherever it appears, and the box the preview will arrive in is kept for the preview. The spinner itself is the arc and nothing else: its frame is transparent, so what is behind it is the desktop rather than a backdrop, and its composition skips the backdrop setting — `image_background` and `vector_background` alike — for that reason: the configured backdrop would put back the square the transparent frame exists to avoid. The arc carries a soft dark halo so that it reads over a light file list as well as over a dark one. The spinner goes up once the wait has run past `spinner_delay_ms` — a quarter of a second by default, and the one delay every kind of preview is answered by, a page Office is rendering included. What the delay is for is the load that may be about to finish: the window is hidden while one runs, so a decode that takes a few milliseconds goes straight from nothing to the preview rather than flashing a spinner on the way. A page is never that load — nothing can be shown until it lands, and a page is an Office start away — but a wait is a wait to the pointer that is on the file, so a render is shown as one by the same delay every other preview is. A preview that is still on its way follows the pointer, so the wait stays with the hand instead of sitting behind: the spinner is placed again as the cursor moves along the item it belongs to, and the page that arrives replaces it where the pointer is. Moving within the item never reaches the load at all — the hook answers a move over the file it is already showing with nothing but a fresh hover delay, so no `Show` is sent, no generation moves and nothing is cancelled while a cursor keeps moving over the file it is waiting on. A pointer that moves *onto* the spinner is the same case reached the other way round: the box sits a pixel off the hand and follows it, so a hand that settles into it — or a move the box has not caught up with — puts the pointer over this app's own window, where the file under it cannot be read at all. The spinner therefore publishes the region it occupies as one that holds the pointer, the way a scrollable text preview does, so a hover is not dismissed from there and the page it is waiting for is not thrown away with it: dismissed, the render still finishes, but it lands for a hover that is gone, and what the user sees is a spinner that came to nothing and a preview that waits to be asked for a second time. Leaving the item and coming back is a `Hide` (which cancels the load, not the render) and a re-show the same-file rehover latch holds off; a render that is still running is never abandoned by either, and a request that arrives for a document whose page landed while it waited is answered from the cache rather than by Office again. Only the place is recomputed — the size the hover measured, its `Avoid Filename` region and its scale are what it is placed with — so a tick of following costs a cursor read and a placement, and the window is moved only when the place it comes out at has changed. A keyboard hover's preview is the item's own and follows nothing. The page is asked for in the box that family's pages have (`office_formats::default_page_size`), which is what a slide's export width comes from: the spinner's box says nothing about how large the page will be drawn, so it is not what the render is asked for.

The render tier is asked for by the preview loop rather than by a hover, because the loop is what knows which hover is on screen: a request is made the moment a document is missed, so what a page costs is its render and not a wait in front of it, and the tier drops a request that has been superseded rather than rendering every one asked for. When the page exists, `OfficeRenderReady` arrives through the same channel every other message does and the hover is replayed — the measure now finds the page, the load draws it, and the window is given the page's own box and frame by the one `UpdateLayeredWindow` that paints it, never resized ahead of that paint: a layered window shows the frame it already holds, stretched into whatever box the window has, so a spinner resized into the page's box first would be a bar across the screen until the page landed. That replay is an *upgrade*, not a new preview: what is on screen stays while the page is loaded, because hiding the spinner for the second a large picture takes to decode is a blink the user reads as the preview failing. A render that lands after its hover has gone is dropped, and the page it produced is released with the hover it was meant for — kept only as far as the budget allows, which at nothing is not at all. The wait is capped at twenty-five seconds from the hover: past that the preview comes down rather than spinning for good, and the file is left alone for two minutes so it is not asked for again on every pass.

A rendered page is drawn by the existing PDF path — Word and Excel export page 1 to PDF, and `pdf_preview` renders it — so a rendered document and a PDF preview are the same picture drawn by the same code. PowerPoint is the exception and exports slide 1 as a PNG, because the alternative is a PDF of every slide in the deck; it is exported at the width the preview asked for, bounded between 640 and 1920 pixels.

Two members of the object model are not what their VBA spelling suggests, and both were found by the diagnostic below rather than by reading: a slide is reached through the collection's item, `Slides.Item(1)`, because asking `Slides` itself for one is answered with "member not found"; and Excel's export needs a printer on the machine, because what a workbook's page is is what it prints. Where there is no printer, `printer_installed` says so up front — Excel answers `ActivePrinter` with the sentence "unknown printer (check your Control Panel)" — and the workbook is answered with `CopyPicture` of the used range's top-left instead, written out as a BMP: the one image format that is exactly the bytes the clipboard holds. A refused copy is asked for again a moment later, because the first ask of a workbook Excel has just opened is regularly refused — "unable to get the CopyPicture property of the Range class" — while the sheet is still being laid out, and the next ask is answered. The picture is taken off the clipboard rather than left on it, because leaving it there is what makes Excel ask, on its way out, whether a large amount of information should stay on the clipboard — a dialog no one is present to answer. What it shows is the corner of the sheet rather than its printed layout, which is the most a machine without a printer can produce, and it is copied only as far as a preview could ever show it: a report whose rows are tall — wrapped headings, merged cells — or whose columns are wide would otherwise be several million pixels, slow to copy, slow to write and slow to draw, all for a corner no preview can hold. The window is cut down in proportion until what it would draw fits a budget smaller than any display — 900 by 700 pixels, because a picture is shown at its own size rather than fitted to the screen the way a page is — so tall rows keep as many of them as the budget allows instead of being halved until only a sliver is left. Only the range's own measurements are asked for to cut it down, never its cells, so a sheet of a million rows costs the same as a small one. On a machine that has a printer, an export that comes to nothing is taken as the instance declining rather than the document failing — the instance a retry is about to replace — so no picture is asked for there until an attempt is already a retry, where it is the last thing tried before the document is given up on. Copying out of an instance that has just refused to export is a detour of its own: the copy is refused by the same instance, after the retries the clipboard needs, and what the first attempt should be is the fresh instance the retry is going to ask anyway.

## Office Render Engine

The engine is the Office application itself, driven late-bound through `IDispatch` and called by name, so nothing here depends on a type library, a build step, or the installed version. One engine is created per family on the first render that needs it and kept for `office_engine_idle` after that family's last one — ten minutes by default, `0` for one let go as soon as it has drawn a page, or `indefinitely` — then quit; a family never has two, because an engine is started only once no process this app began for that family is still running, and a replacement waits for the process it replaces to be gone before it is asked for; the families are held side by side rather than one at a time, so a folder holding a document, a workbook and a deck costs one Office start each rather than one every time the pointer crosses between them, and each is let go on its own clock, so the family asked for most recently is the one that outlives the others. The thread that owns them ends with the last one, so an app left alone ends up with neither an Office process nor a polling thread — an engine kept indefinitely being the one setting that is asking for both. That thread is apartment-threaded and pumped, which is the opposite of every other worker in the app: OLE automation marshals its calls back into the thread that made them, and a thread that is not retrieving messages deadlocks.

Automation may attach to an instance the user already has running — these applications are registered for multiple use — so the engine is careful with what it touches. Whether the instance was already visible is read first: a visible one is the user's, and is neither hidden, quit, nor ended, while the settings it is given (dialogs suppressed, macros switched off) are taken for each render and put back the moment that render is over, so an engine sitting warm between documents is holding nothing of the instance's own — which is what makes keeping one for an hour, or for as long as the app runs, safe to do to an instance that is the user's own Word or Excel. Only an instance this app created is hidden and quit, and the process it started is recorded — the process list is walked before and after creation, and the one that appeared is the app's — so that a render which never returns can end every engine the worker was holding. Documents are opened read-only, without touching the recent-files list, in a hidden window that Word, Excel and PowerPoint all support even in a visible application, and are closed without saving.

None of those calls can be cancelled or bounded: a modal dialog inside Office holds the COM call for as long as it is up. What that costs is one render, never the tier. Ending an engine counts as work like any other, so it happens inside the same marker, and a worker that has been inside one piece of work for longer than any of them takes is given up on when the next hover arrives — every Office process this app started is ended, since a worker being given up on is holding all of its engines, the worker generation moves on, and a fresh worker takes the request. The abandoned thread is left where it is, since nothing in user mode can end a call it is inside, and everything it does on the way out is conditional on it still being the current worker: it can neither clear the live worker's thread id nor end an engine the new worker is using. A panic is contained the same way — one document's failure is that document's, and the thread goes on to the next hover — and the thread id is handed back however the thread ends, because losing it would leave every later request posted to a thread that is gone.

Letting an engine go is a call of its own, and an Office application finishes quitting while its automation client is pumping: one that is told to quit and then abandoned can sit there for good, which is what a left-behind Excel instance looks like. So the quit is given a moment of pumping on the worker thread, and a process that is still there after it — one this app started, verified as still being that application — is ended rather than left running. That is the idle path: an engine being let go because it has refused a page is not asked to quit at all. A quit is another call into the instance that refused, and one that is not answered is pumped for seconds before the process is ended anyway, while a process about to be ended has nothing left that needs putting back — so the process this app started is ended where it stands, and the engine the retry asks is a new instance, which is the point of the retry. An instance that is the user's own is never ended by this, whatever it answered: `attached` is what stops it, the same as everywhere else. A superseded request is dropped rather than queued behind, and the newest hover is the one that runs.

A render is not quite invisible, either: Office shows a progress window of its own while a page is exported — the wide, short "Publishing…" bar — and none of the settings an engine holds keeps it off the screen. Alerts, screen updating and the automation security mode were each measured against it, and it is shown whether or not the application it belongs to is visible, so a hover used to see the bar for the whole of a slow export. What it is, though, is a progress bar: nothing about the export depends on it being seen, so a render watches that process for the window being *shown* — `EVENT_OBJECT_SHOW`, filtered to the process, with the class as the check, since a window's title is the machine's language and this is not — and hides it the moment it is put up, which is what keeps it out of a frame a display is drawing; a sweep of the process's windows runs beside the hook as the half that does not depend on an event arriving. Only a process this app started is watched: an instance the user is working in keeps every window it owns, the same as it keeps its dialogs and its macros.

## Video Preview Engines

A video is played by one of two engines, and the one it is played by is decided once per file by `codecs`, from the single question of whether `ffplay` is installed: FFmpeg's player where it is, and the media engine Windows has where it is not. The two are the same preview to the user — the same box, the same placement, the same backdrop, the same spinner while it is on its way — because they are the same preview to the app: what differs is only which side of the window the picture comes from.

Measuring a video is a probe, and the probe is the one thing about a video that is done off the preview thread. It is `ffprobe` and an `ffmpeg` cropdetect pass — two external processes, run at once, with the hover waiting for the slower of them — so a hover that read it would spend that time inside the layout with nothing it could draw: the size the probe answers is what the layout is *for*, so the hover cannot be placed before the answer is in hand. What is done instead is what a document with no page rendered for it does: `get_media_dimensions` answers the waiting box for a video it has no probed answer for, the hover is laid out as the wait for the probe — the spinner at the pointer — and the probe itself runs on a thread of its own. When it answers, the hover is replayed from the message it came from (see `VideoProbed`, and `replay_where_the_pointer_is` for the anchor a replay keeps), and that second pass finds the geometry in the cache: the layout has a shape again, and the load that follows is the video's own. The replay is a continuation rather than a new preview, so the spinner that was up stays up — the same clock, so a probe answered inside `spinner_delay_ms` does not start that delay over, and the same frame on screen. The answer is held whether or not anything is still waiting for it: a geometry and the lack of one are both answers, and holding the lack is what keeps a file neither reader will open from being probed on every hover (`ProbedGeometry`). What is left on the preview thread is a cache lookup, which is what `start_video_playback` reads its crop filter from — the one thread that must not wait for two processes never does.

How large a video is shown is `video_scale`, a share of the file's own size — and it is a size for the waiting box and the player's window alike, because what the layout places is one box that both are put in. The share is the rule a picture follows rather than the rule a page does, for the reason the probe exists at all: what a video preview is measured and placed by is a frame of it, a bitmap, so a percentage of it is a percentage of its pixels and a fit is the largest size the room beside the pointer allows. `effective_preview_scale` is where that is decided, so the measure and the render cannot disagree — the video arm of it sits beside the picture arm and reads its own key — and it is a setting of its own because the size that suits a photograph is not always the size one wants to watch a file at. The one case it is not asked about is the hover that is still waiting for the probe: there is no video to place yet, so what is on screen is the spinner's own box whatever the setting says, and the setting is read when the replay lays the measured video out.

An animated picture has a size of its own the same way, and the one thing that cannot be read from its name. `animated_scale` is asked for a GIF, a WebP or a PNG that holds more than one frame, and `preview_scale` for one that does not — a still GIF and an animated PNG are both files a name cannot settle — so `image_is_animated` walks the file's own structure without decoding anything: the frame blocks of a GIF, the `ANIM` chunk of a WebP, the `acTL` chunk of a PNG, which are the same things the loader insists on before it calls a file an animation at all (a GIF whose second frame never arrives is loaded as a still picture, and the setting follows the loader rather than the name). It is asked from `effective_preview_scale`'s picture arm — the one format where the scale cannot be read off the path alone — and the frames are decoded at the size it answers, because the loader is handed the same scale the layout was. Where the two settings name the same share, which is the state a fresh install is in because both start at `100%`, nothing is read at all: a file is only opened for this when the answer could change what is drawn, so a hover's cost is unchanged for anyone who has not asked animations for a size of their own.

**FFmpeg's.** `ffplay` is started per hover and its own window *is* the preview, the layered window staying hidden while it is up; both are described in Video Process Lifecycle. It is the path that plays everything FFmpeg can demux, and its geometry comes from `ffprobe` and a cropdetect pass, so a video letterboxed inside its own frame is cropped to what is in it.

**The media engine's.** This one is drawn by the app. `video_player` creates the media engine in *frame-server mode*, which is the mode it is in when no playback window or visual is named, and then asks it for frames rather than letting it draw: it decodes, paces itself, plays the audio and loops — the engine's own `SetLoop`, so a preview loops without anything here arranging it — while this side calls `OnVideoStreamTick` once a tick and takes the frame it says is due with `TransferVideoFrame`, into a bitmap of this app's own. That frame is then an ordinary one: it is composed and drawn by the same code every other frame goes through, which is why a video the engine plays lands in `Follow Cursor`, `Best Position`, each `Avoid` mode, the keyboard path and the backdrop setting for free rather than through a second implementation of each. What it does not have is FFmpeg's crop: cropdetect is an FFmpeg filter, so what the engine is handed is the frame as the file holds it, and a video letterboxed inside its own frame keeps its bars.

Two things about the engine are worth stating because neither is what a first reading suggests. Frame-server mode is the *default*: it is rendering mode that has to be asked for, by naming a playback window, and what the engine requires of a frame-server caller instead is an event sink (`MF_MEDIA_ENGINE_CALLBACK`) and the format the frames are to come in (`MF_MEDIA_ENGINE_VIDEO_OUTPUT_FORMAT`) — the format being the one this app already composes in, a D3D `A8R8G8B8`, whose bytes are the same in the same order as the BGRA the rest of the app works in. And a frame is only there to be taken once the engine has current data: `OnVideoStreamTick` reports a frame as due some while before one is queued, and a transfer asked for in that window is *failed* rather than answered late, so the session asks `GetReadyState` first. That is not a detail — without it an `.mp4` never plays at all, which is the format a first cut of this path was tried against.

Nothing about it is a process. There is no player to start, no window of its own, no PID to record, no job object to adopt it into and no style monitor to keep it out of the way — every one of those belongs to the FFmpeg path because a player is a separate program drawing in a window this app does not own. What it costs instead is one copy of each frame into the bitmap the engine delivers into, which is the one thing per frame that is not free, and what it is bounded by is the same rule as everything else here: the file is opened as a stream over the file rather than read into memory, and the source reader that measures it is dropped before anything is played.

Measuring is a question of its own, and it is asked of the *source reader* rather than of the engine, because the layout has to know a video's size before it can place one and because the answer is also what decides whether there is a preview at all: a file no reader claims — an `.flv`, an `.rmvb`, an MPEG program stream — is answered with no size, which is how the layout drops it rather than opening a box nothing would be drawn into. That is a difference from FFmpeg's path, where a file `ffprobe` cannot measure is still placed at a 16:9 default because `ffplay` will play it anyway. Where FFmpeg is the one installed, a probe that comes back empty falls through to the engine's own measurement rather than to the default, so a machine with `ffplay` but no `ffprobe` measures the way a machine with neither does.

The engine's frames come back into the load the ordinary way, so a video preview is installed like any other: it is the media kind that is new (`NativeVideo` rather than `Video`), and the two kinds are what tell `render_layered_preview_at` whether the frame it is holding is one this window draws or one a player is drawing over it. What ends a video is unchanged either way — the pointer leaving the file, another preview taking its place, the `Videos` gate closing, a display change, a resume from sleep, the app exiting — because every one of those already ends a video through the same call, and the media engine is let go there rather than killed there. Its shutdown asks nothing of an outside process, so it needs none of the kill-only discipline that stopping `ffplay` does.

Which files the engine will play is a property of the machine rather than of this app: whatever Windows 11 decodes out of the box, plus whatever a codec extension from the Microsoft Store has added to it. That is what the tray's `Codecs` submenu is for — see below — and it is why the app names no codec of its own here and bundles no decoder. What the engine cannot play is a file with no preview, which is the answer a file that will not decode already gets.

## The `Codecs` Submenu

The tray's `Codecs` submenu lists the engines and codec extensions a preview can lean on, grouped as `Videos`, `Images` and `Engines`, with a row that is present carrying a check glyph and a row that is missing carrying a cross and being greyed. It is a diagnostic rather than a setting: nothing in it does anything when it is picked, and there is no `config.ini` key behind it, because there is nothing to configure — what it reports is what the machine has.

What it is for is the question a user asks when a preview does not appear, which is now answerable without reading a log: a `.heic` with no preview is a greyed `HEIF (HEIC)`, and an `.mp4` with no preview on a machine that has neither engine is both rows greyed. It is also how the app can name a codec it does not carry without the app ever sending anyone to the Store: the row says what is missing, and the README says what to install and where from.

Each row is asked of the place the thing would be used from rather than of a package list, so a row is checked only where the capability really is there. A video decoder is asked of the media stack's own registry of decoders (`MFTEnumEx`, filtered to the compressed format that decoder takes as input), which is the same question the engine answers when it is handed a file — so a codec extension that is installed but not registered answers honestly as missing. A picture format is asked of the imaging factory's own components (`IWICBitmapCodecInfo` and the MIME types it claims), which is how a `.heic` is found out to need *two* packages rather than one: the HEIF extension carries the container, and the HEVC or AV1 decoder carries what is inside it, so the `HEIF (HEIC)` row is the container and its decoder together. An application that draws a page is asked for by its ProgID, which is the same test the render tier makes before it drives one and does not start it; the browser is asked through the loader's own version query; and the PDF engine is asked whether its WinRT class is registered at all, because it is opened with a stream rather than with nothing and there is no cheaper way to ask it something.

The one answer that is kept is whether FFmpeg is installed. It is asked on every video hover — it is what routes a video to one engine or the other — and a hover must not go looking through the `PATH` for it, so it is read from a cache the tray's menu build clears. That is also what makes installing FFmpeg take effect without a restart: the next time the menu is opened, the answer is asked again, and the next video hovered is played by the player that was just installed.

## Video Process Lifecycle

`ffplay` is the only long-lived external process the app starts itself — an Office engine is another long-lived process, but COM is what starts it, and its discipline is its own (see Office Render Engine). It is started per hover, its own window is used as the preview surface while the layered window stays hidden, and it is stopped when the hover ends — switching to another video, switching to an image, leaving the file, disabling previews, a display change, or system suspend.

A player is a process, and a process has a window to create before anything of the file is on screen — so what stands in for the video while it starts is the waiting spinner, at the pointer every other wait is shown at (`VideoStart`). The frame the player was started for is held until its window is there rather than handed to `CURRENT_MEDIA` with the process: a wait is what this app's window is, and the frame would be what the spinner was showing instead of the arc. The handover happens on the first tick the player's own window is up — `VIDEO_HWND`, the handle the no-activate monitor already finds and styles — and this app's window goes with it, because a video's preview is the player's window and not this one. A player that never puts a window up is not waited for forever: one that has exited, or one whose hover has moved on before its window was there, is ended where it stands — `kill_stray_video_process` and the job object are what answer for a process this app started — and one that outlives `VIDEO_START_WAIT_SECS` without a window is given up on, since a spinner that never ends is worse than the desktop it leaves behind (see `player_wait`).

Stopping is kill-only: the app requests termination and never waits for exit, because a process stuck in kernel I/O cannot be terminated by anyone in user mode, and an unbounded `wait` on the Explorer hook thread would freeze hover tracking for good. The PID of the last spawned player is therefore kept until the process is confirmed gone rather than cleared on the spot, and two checks recover a player that survived its stop: the Explorer hook re-checks the recorded PID once a second while no file is hovered and no keyboard preview is up, and the preview thread re-checks it before spawning a new `ffplay`, so a new preview cannot stack a second player next to a stalled one. Both checks terminate only when the recorded PID still belongs to `ffplay.exe`, read from the same process handle that is terminated, so a recycled PID can never hit an unrelated process; the record is cleared only after the process is gone, through a compare-exchange so a freshly spawned player's PID cannot be wiped by a stale check.

## Started Processes

Three things this app starts are not its own to keep: the Office application that draws a document's page, the browser that plays an animated document, and the `ffplay` a video preview runs in. Each of them is ended where it is ended deliberately — an idle engine let go, a player stopped — and what `engine_processes.rs` is for is the ways an app does not get to choose: ended from Task Manager, taken down by a crash, closed by a logoff. A process that outlives the app that started it holds a profile folder, an Office licence seat or a file handle, and a leftover Office engine is also the thing a new engine would be a duplicate of.

Two mechanisms cover that, and they cover different halves of it. A job object with `KILL_ON_JOB_CLOSE` holds every process this app adopts, and its handle is deliberately never closed by the app: what closes it is this process ending, however it ends, and the system ends everything in the job with it. That is the only mechanism that asks nothing of a process that is dying, which is exactly what a crash is — and it is why the video player is adopted even though its own supervision already ends it while the app runs. What the job cannot take — a process already inside a job that will not nest is how that happens — is covered by a record on disk: each run writes what it started to `%LOCALAPPDATA%\rust-hover-preview\engines\<pid>.state`, and the next run reads every file there and ends what the runs that are gone left behind. A run that is still alive is another session of the same user, and its engines are its own; a browser left by a version of this app that wrote no record is reached the same way, through the profile folders a run leaves, each named for the run that made it.

Finding each of them is its own question, and all three answers rest on something the runtime guarantees rather than on a name. An Office engine is the process that appeared across `CoCreateInstance` — the same walk that tells an instance this app created from one the user already had open — and the browser is the `msedgewebview2.exe` whose parent is this process, because the WebView2 loader starts it from here; a browser another app started is a child of that app, which is what keeps the sweep from reaching past this app's own.

What is never done is acting on a process id by itself. An id recorded hours ago may belong to something else by now, so a record is acted on only when the process still runs the image the record names *and* started when the record says it did — a creation time is what the checks that hold a process in hand never needed and a file cannot do without. The sweep runs at startup before anything else, so a leftover engine is gone before this run can start a process of its own, and never beside one.

## Explorer Hook Flow

1. Detect active Explorer window and focused or hovered item via HWND/class matching and UI Automation, with input-grace helpers (should_probe_keyboard_focus, should_probe_hover_resolver, should_probe_stationary_hover) throttling probes to recent user activity and a stationary_hover_probe_done latch capping stationary-hover work to a single probe per parked cursor. An item is found by the box the view gives it rather than by the text drawn inside it, so the metadata line a Content row writes is not what answers for that row: the name is consulted afterwards, as the check that the position and the file agree, and only when the name could be one of the files this app previews. A view reports a row's metadata exactly as it reports a name, and a name like that is passed over rather than taken for the file. A shell that answers a cursor probe too slowly too often (three probes over 700 ms) puts the cursor probes on a pause — the pause stops the asking and nothing else: the preview that is up stays, because it belongs to the file the cursor was on, the keyboard's turn is left as it is, and the preview is withdrawn only when the cursor leaves that file, which would otherwise strand it on a file the pointer is no longer on. The keyboard's item is one too: the focused element, or the item its list has selected when the view reports the list itself as focused — the search results view does — read from that element and walked up to the item that holds it exactly as the pointer's is. One batched UI Automation read gives the item's box, the name the view shows it under, its position in the view and the value its accessible pattern carries, and the position is turned into a path by the same view lookup the pointer uses, tab rules and all. No name is looked up for either path and nothing is walked: a search result whose file lives in another folder is answered by the item itself, and two results that share a name are told apart by where they are, not what they are called.
2. Treat a wheel tick as input when the wheel is driving Explorer (the pointer is over it, or over a preview window that covers the pointer while Explorer still receives the wheel). The wheel moves the list under a stationary cursor, which changes the hovered item without any mouse movement: the stability window restarts while the wheel turns and the latch is reopened, so when the list settles the item that landed under the cursor is resolved and previewed (or the preview is dropped when that item is not media). A `ScrollSettleProbe` only acts on an item that survives two consecutive probes, because Explorer can still be animating the scroll. A scroll also ends keyboard ownership: the keyboard preview is closed, the pointer freeze is released, and the recent-keyboard-input window ends, so the mouse preview takes over the item under the cursor.
3. Treat clicks, Enter and the navigation keys as user navigation. A folder probe runs at the active cadence for a moment after such a press, so a folder that press opens is recognized before the user's next key press rather than up to a full idle interval later. Once the new view has settled the post-folder-change suspension lifts on its own, so the item that landed under a parked cursor previews without a mouse move, and the first navigation key press after the change previews the item it selects — the gate lifts on a fresh press transition (never on key-down state left over from the navigation that opened the folder), so that press is no longer swallowed as a focus baseline. A folder change that no input precedes (a programmatic renavigation, a network refresh) still waits for user input, and the auto-focused first item still never previews without a key press.
4. Normalize the resolved path and validate the file extension. The `.ts` and `.mts` extensions are shared with TypeScript sources, so those two are additionally confirmed by a short MPEG-TS sync-byte probe (`src/video_formats.rs`) before a video preview is started. The gate is what the file *is*, asked the way the renderer asks it — a video first, then a PDF, then an archive, an Office document, a design document, a vector drawing, the text lists, the font list, and the image extensions last — with that kind's `Preview Types` gate applied on top, so a file whose kind is switched off resolves to nothing rather than to another kind's preview. Every question the renderer asks about a file is asked in that order as well — which reader draws it, what size it is, what share of the display it takes, and what it is drawn over — so a name written into two lists belongs to the earlier of them wherever it is asked about, and the tray's switch for that kind is the switch that applies to it. That is the rule the move of a format from one list to another has to keep: the kind a name is moved to is asked in a new place, and every caller that asks a list question has to ask it there too.
5. Send `Show` or `Hide` messages to the preview thread via channel.
6. Resolve a file from the item that stands for it, and read nothing else. The folder index, the down-the-tree descent, the search-root index and the Shell view name index that stood here are gone: a name is looked up nowhere, and the hook never touches the filesystem to find a file. What is cached about a view is only what answers a question a view has already been asked — the folder a window remembered, and which window is one of Explorer's — and it is dropped when the location changes, because both describe the place the window has left.
7. Keep keyboard and mouse precedence explicit: an arrow-key preview owns the screen and is never dismissed by the parked pointer (a wheel scroll does end it, handing the screen back to the mouse), while a mouse preview is still dismissed the moment the cursor touches it. Each keyboard spawn measures the preview's own on-screen box (`preview_screen_rect`) and, when that box covers the cursor, freezes the pointer-driven triggers — `should_probe_keyboard_focus`'s companion `should_probe_preview_hover`, the hover resolver/folder probe, and mouse hover previews — until the cursor is moved more than the pointer tolerance (20 px), so jitter cannot end a keyboard preview. That tolerance is what a move has to clear for the whole of the keyboard's turn, not only while the box happens to cover the cursor: a navigation key press puts the keyboard in charge of the screen (`keyboard_screen_owner`), the state survives the keyboard previews it opens and closes, and while it holds the pointer-driven hover path is skipped even with no preview on screen. Without it, a focused item that cannot produce a preview — a file whose kind is switched off, a result whose path could not be resolved — ended the keyboard preview and left the parked pointer free to raise a preview of whatever it sat on, which the next key press dismissed in turn: on a large search-result view, where the items the keyboard walks are the ones still being resolved, that read as the two previews fighting over the screen. The focused-item baseline — its name *and* its box, so two results that share a name are two items — is cleared on mouse movement, and the focus observed after that acts immediately, so the first navigation key switches to the keyboard preview instead of being swallowed as a fresh baseline. When the mouse does take over, the file that was shown is latched (`SuppressedHover`) the way any dismissed hover is: held off the mouse path for the same-file rehover delay — long enough that the hand-over cannot flash it straight back — and released sooner when the cursor resolves a different file. A probe that meets the latch stays open instead of being spent, so a pointer left parked on that file previews it as soon as the delay has passed.

Explorer restarting is the one thing the hook cannot recover from by itself. Every Shell object it resolves items through — the window collection it asks which views a window holds, and the view that answered for one — is served by explorer.exe, and a proxy into a process that is gone does not reconnect: it answers no call for the rest of the run. That is what left every hover after a restart with nothing while the app looked alive, since the tray icon was re-added and the window counting that decides whether Explorer is up never used the shell's objects at all. A restart is therefore counted where it is already noticed: the tray window is sent `TaskbarCreated` when the shell builds its taskbar again — the same broadcast its icon is re-added on — and the hook builds the collection again when that count has moved, dropping the view that answered through it and the caches keyed by window handles that belonged to the process that is gone, hiding whatever preview was up, and re-arming the folder-change gate the way a folder change does, so the probes wait for the windows the new shell is still putting up. A collection that came out missing when it was asked for is built again on a slow retry rather than kept missing for the rest of the run: it is asked for while the shell may still be coming up — the tray retries its own icon for that same reason — and a missing collection answers exactly as a dead one does.

## Item Resolution

Both paths resolve a file the same way: from the *item* that stands for it rather than from its name. The item is read with one batched UI Automation request — its box, the name the view shows it under, Explorer's own `ItemIndex` (the position it holds in the view), and the value its legacy accessible pattern carries — and the position is turned into a path by the view that is showing it. A pointer takes its item from the point, walking up from the element under the cursor to the nearest list row or data item whose box holds it (the whole row is the target, which is what Explorer itself highlights when an item is selected); a keyboard preview takes it from the focused element, or from the item its list has selected when the view reports the list itself as focused, walking up the same way because what a view says about an item is kept on the item and not on the text it draws inside it. A keyboard item is asked one thing more, because its preview is placed from the item alone with no cursor to measure from: the boxes each piece of its own text is drawn in — which is one read, from the item's children in one more batched call. Those boxes are what the `Avoid` setting keeps a preview off — the leftmost piece of the text, which is the `Name` column of `Details` and the name above the path of `Content`, for `Avoid Filename Column`, that same piece narrowed to the name's own width for `Avoid Filename`, and every piece of it together for `Avoid Details` — and, with the item's shape, what says whether the item is a row of its view at all: a row is one by the columns it draws *beside* its name, not by how wide its box comes out against the display, since a `Details` or `Content` row writes its text into the left end of a box as wide as the view and the empty tail past the region a preview is kept off is the only room it leaves a keyboard preview. They are read for an item of any shape whenever a way of avoiding is on: the label under an icon is a box of its own, and the name of the item the keyboard is on is the file the preview is about. The pointer's item is asked the same question at the moment a preview is about to be shown for it, and not with every probe (see Preview Window Placement). Nothing is looked up by name on either path and nothing is walked: a name is the one thing a search across folders shares between files, and two results that share one are told apart by where they are, not what they are called.

The view is found by the window first: the Shell windows are matched against the frame the item's window belongs to — the root window under the pointer, or the frame of the window the focused item is drawn in — rather than against focus or a rectangle, so a background Explorer window and another application's window are excluded by that one comparison. What the window names is not always a single view. A window that holds tabs registers one Shell window per tab and every one of them answers with the frame's own window, so the frame names a *set* of views; and the tabs that are not showing cannot be told from the showing one by their windows — the Windows 11 frame reports both of its views as visible — so the item is what settles which of them it is: each candidate view is asked for the file at the item's position under the item's name, and a view holding some other folder's items has nothing there to answer with. What two of them answer has to agree, because two tabs showing the same folder are one answer and either of them is the right one, while two tabs whose items differ are a question the item cannot settle — and no answer is better than the wrong tab's file. The view that answered last is kept and asked first while it is the window's *only* registration: with one view there is no second one for it to disagree with, and a window holding tabs is never answered from the cache, because a cached tab is one of several and the cache cannot say which of them is showing.

The file itself is the one the Shell hands over for that item's position (`IFolderView2::GetItem` → `GetDisplayName(SIGDN_FILESYSPATH)`) — for a search result, the real file wherever it lives — but the two questions are asked in order and are not the same question. First, which view holds the item: a candidate claims it when the item at that position goes by the name the accessibility tree reported, and a folder claims it exactly as a file does, because what an item *is* says nothing about which view is showing it. Then, and only of the views that claimed it, the file: the path the Shell hands over, gated to a file this app previews. A view that holds the item but has nothing to show for it — a folder, an executable, an archive — is a *match with no file*, not a view that failed to match, and that distinction is the whole of it: read the other way, the tab that owns the item abstains, the other tab's media file is the only answer left, and hovering a folder previews another tab's picture. Tabs that disagree — about the file, or about whether there is one at all — are a question the item cannot settle, and no answer is better than the wrong tab's file. A pointer asks the view twice and takes the answer only when both looks found the same item, which is what keeps a list that scrolled under a parked cursor from answering with its neighbour's file. Each path has one other witness: the item's own accessible value, when that value is a whole path — which is where a search result states its file, and what answers when no position is reported at all. Nothing else is tried: an item no witness can vouch for is left without a preview rather than guessed at, which is why a search of several hundred results costs both paths the same work a folder does.

## DPI Awareness

The app sets per-monitor DPI awareness v2 on startup, with a fallback to per-monitor DPI awareness if v2 is unavailable. This avoids scaling artifacts on layered windows when Windows UI scaling is above 100%.

## Preview Window Placement

The preview is bounded to the display nearest the hovered cursor or focused item rather than the whole virtual desktop. Bounds are resolved through `MonitorFromPoint`/`GetMonitorInfoW`, falling back to the virtual screen when the monitor lookup fails, so the window no longer spills onto a neighboring display.

Each update repositions the window before installing the new frame or spinner. Crossing between displays of different scale raises `WM_DPICHANGED`, which discards the frame that was on screen — one composed for the display the window has left, and the wrong size and scale for the one it is on now — so installing the content first would discard it and leave the previous display's image stranded on screen. What the discard leaves is put back rather than left until the pointer moves: the window proc can only throw the frame away, so it raises a flag the loop reads, and the loop replays the hover the frame came from — which lays it out again at the scale of the display the pointer is on now. For the same reason, the layered surface is painted before the window is revealed.

Preview size is derived from the media's native dimensions and the `preview_scale` setting, which is either a percentage of the native size or `fit` for the largest size the display area allows. The requested scale is always capped by the free space on the chosen side or quadrant, so a preview can never be clipped by the display edge — a large image at a small scale shrinks to fit, and a small image at 400% or fit-to-screen is reduced to whatever the display can hold. The same scaling is applied to the decode request, so image, GIF/WebP, and video previews all land at the computed size. The one rule a size can come from besides those is a reduction of the fit itself, which is what a preview drawn at whatever size it is asked for — an SVG document, a PDF page, a page Office rendered, a font specimen — follows below `100%`: the room the display has, reduced to the configured share of it. Which share that is belongs to the kind: `vector_scale`, `pdf_scale`, `office_scale`, `font_scale` and `design_scale` each name their own, so a picture's scale leaves every drawing, every page, every specimen and every design document alone, and what a specimen's share is of is the box `font_preview` measures a font at — a font having no size of its own. `scale_in_room` is the one place that answers it — for the size a preview is given and for the room a position mode chooses between — so the size the layout plans and the size the renderer draws at cannot come apart.

Where the preview lands on that side differs between the two position modes. `Follow Cursor` fills the roomiest quadrant around the cursor, growing away from it in both axes. `Best Position` places the preview beside the cursor or the focused item — on whichever side has more room for it — and centers it on the same line: `centered_top` puts the preview's middle on the cursor's own row (or the focused item's), and clamps that to the display, so a preview that fits under a cursor near the top edge sits where the cursor is, and one tall enough to reach an edge moves only as far as the edge allows. Before that, both modes centered the preview on the *display*, which for a cursor near the top put most of the preview below it and away from what was being hovered. The rule is shared by every format — image, GIF/WebP, video, PDF and text — because it is part of the layout both mouse and keyboard previews are computed from. It is also what a preview that is still on its way follows the pointer with: `compute_mouse_layout` is asked again for the cursor as it moves, at the hover's own size and `Avoid` region, which is where the media is placed when it arrives. The wait itself follows a place of its own, and no position mode decides it: a waiting spinner carries `flush_at_cursor`, and is placed by it at the pointer's own corner — a pixel off it, so the pointer's own messages stay with the file it is waiting on — at the arc's own size in whichever quadrant the display has room for it, rather than at the size the preview will be and in the quadrant the mode would have filled (see `waiting_placement`).

One rule is applied on top of whichever placement a mode chose, for the `Avoid` setting: a placement that came out over the region its own item draws — the name the file is listed under at `Avoid Filename` (the default) and `Avoid Filename Column`, with the columns a row writes beside it at `Avoid Details` — is moved by the shortest step that clears that region, past its right edge, past its left, under it or over it, and a step is only taken where the display has room for the preview it moves. A preview too large for any of those rooms is *resized* into the roomiest of them instead, by the same rule that sized it in the first place applied to the room that is left, which is what answers the case a preview filling the display lands in: nothing can be moved clear of the region while the preview is as wide and as tall as the display, so the size is what gives. A room too small to be worth having — the sliver of tail past a name that fills its row, the last strip of a display under a row at its bottom — is not taken at all, so a preview is never squeezed into a sliver to get off a name it would have covered anyway. At `Avoid Filename` that region is cut to the width the name itself is drawn at, because a view reports the room a name is *given* — one width for every row of a `Details` folder, a long name and a short one alike — so the name is measured where it is drawn, extension and all: the icon font the shell gives folder views, scaled to the display the item is on — the display of the region itself, since a view need not report a window for an item, and a name measured at the system's scale on a scaled display is half the name — and taken at the larger of the two sizes a view draws a name at — the font itself in `Details`, 125% of it in the `Content` view, whose rows give the name a line of its own — with a font and a memory DC made for the one call and let go again (see Item Resolution). The larger size is what makes one measurement serve both views; a `Details` row is left keeping a quarter more room than its name takes. `Avoid Filename Column` is that room as the view reported it, without the cut. The cut only ever narrows the box, so a name that fills the room it was given, or is drawn truncated to it, is left as the view reported it. The text is a region the Explorer hook measured, so it comes with the hover rather than being anything the preview thread can see: for the pointer's own item it is read at the moment a preview is about to be shown, which is once per preview rather than with every probe, and a keyboard hover carries the box the walk already measured the item's text in (see Item Resolution). A view that reports no text for an item leaves the item's own box as the region, since the name is drawn inside that box whatever the view says about it. The distance the placement keeps from whatever it is beside is what the text is cleared by, so it is stepped off rather than touched at its edge. The waiting spinner is the one placement the rule passes over: it is put at the pointer's own corner by its flush rule and left there, over the name, rather than stepped a margin off the file whose page it is waiting on (see Office Previews).

Keyboard previews are placed next to the focused item, which can put them over a parked pointer. That is allowed: while a keyboard preview is up it stays topmost and the pointer is not treated as hovering it, so it cannot be cancelled or made to blink by a cursor that happens to sit underneath. The placement anchors on the item's own edges — which is what keeps a preview off the file it describes — because that reading holds for an item that is a box. An item that is far wider than it is tall and draws columns beside its name is not one: a `Details` or `Content` row is a box as wide as the view with its name and its columns written into the left end of it, so the row's own right edge *is* the view's, and what lies beside it is the space the view is not using, a sliver at the window's edge. The columns are what says the item is a row — the label under an icon, a tile's stacked lines and a name on its own have none — and not the item's own width against the display, which reads the row of a window narrower than half the display as a box however that row is drawn. What such a row does leave is the empty tail past the region the `Avoid` setting keeps a preview off — at `Avoid Filename` that region is the name alone, so the columns drawn after it are the room the preview takes, while at `Avoid Details` it is the whole of what the row draws, which is the tail the placement has always been measured from — and that region is what the keyboard's placement is measured from, since it is the hook's own read of the row's text elements (see Item Resolution): the preview takes its place and its size from the tail, `Best Position` centring it on the row's own line just past that edge and `Follow Cursor` growing it from the row's corner. A row with no tail to place a preview in — a narrow view, a name long enough to fill it — and a row with nothing kept off at all, since `Avoid Nothing` places a preview by the position mode alone, are anchored at their *middle* instead, the way the mouse path anchors on the cursor, and are allowed to cover the rest of the row. The hook confirms this from the preview's own box (`preview_screen_rect`, taken from the layered window or the `ffplay` window once visible) rather than from a cursor position test, and holds the pointer off until the mouse is moved on purpose.

## Configuration

Configuration is stored at `%APPDATA%\rust-hover-preview\config.ini`. Changes are detected by the config watcher thread and applied without restarting the app. The app is the only writer of that file: the installer seeds nothing into it, so the file a fresh installation gets is the one the app's first run writes — the settings of that build — rather than the defaults of whenever the installer was packaged. The registry entry that runs the app at startup is written by the app on that same first run, from the setting that asks for it and at the path it is running from (see `sync_startup_setting`), so the installer writes nothing there either.

The file is written in a fixed shape: the `[settings]` section first, under one heading per menu of the tray — a comment naming the menu, in the order the tray lists them, with the keys of a heading alphabetical — and then the sections that hold the file lists, in alphabetical order, with their keys alphabetical within them. A heading is a comment and nothing reads it back, which is what the grouping is for: the menu a setting is changed from is the menu it is found under, so a file of fifty keys reads the way the tray does, and a menu that is renamed or moved is an edit to `SETTING_GROUPS` rather than a migration of a file that already exists. The settings the tray has no item for — a decode curve, a face of a collection, the spinner's delay — are kept together under `Advanced`, and a setting `save` writes that the table does not name is written last of all under `; Ungrouped`, which is where a heading that was forgotten shows up rather than a key landing under a menu it has nothing to do with. The INI reader the values are collected in keeps sections and keys in hash maps and writes them in whatever order those hand back, which is a different order on every write — so a file the user is meant to read and edit by hand was being reshuffled under them on each save. What `ordered_text` returns is the same text that writer produced, in an order that does not move, and a saved file read back and saved again is byte for byte the same.

What the file has wrong or missing is put right as it is read, and the file is written out again where it does not say what the app is using. Two of the differences are put right before the read: a setting the file holds under a name this build no longer writes is moved to the name it reads (`repair_older_names`: `off_trigger_key`, `svg_background`, `svg_scale`, `svg_preview_enabled`, the yes-or-no `avoid_filename`, the one backdrop every kind shared, and the picture scale a video's and an animation's were before each had one of its own), and a list that is this app's own from before it grew is brought up to the list of now (`repair_older_lists`). The third is the read's own answer, and it is asked of every file: what this app would write for what it has just read is held up against the file, key by key (`differs`, over what `to_ini` holds). A file that is missing a setting — the line deleted, the whole section gone, a setting this build has that the file was written before it existed — is a file to write, and so is one holding a value the app does not read back as its own: a tone map that is not one of them, a delay past its ceiling, a face of a collection past the last one there is. What the file holds that the app does not write is the user's and is not compared — a key of their own, a comment, the order the keys are written in — so a file with one of those is left alone. Nothing here moves a value a user has: a default this app has changed its mind about is no reason to write anything, and a build that prefers another one writes it where there is nothing to overwrite, which is a fresh installation and nowhere else. The check is made at a start and on every reload of the file the watcher sees, so an edit that names an older key, or writes a value the app cannot read, is put right where it is made rather than at the next start.

The tray and the file read one default each. A setting a menu offers values for starts at a `DEFAULT_*` constant in `config`, and what that constant names is read everywhere the value would otherwise be written out a second time: what an untouched setting is worth, what the tray's own item is marked `(Default)` for (`default_label`), and — for a value a setting no longer offers — what a file naming one is read as. The texture's half of the `Background` submenu is where the last of those is put to work: a texture is offered the two backdrops that are a page, black and white, because its alpha channel is as often a mask or a height as it is transparency, and a file that names one of the other two from before the half listed all four is read as `DEFAULT_DDS_BACKGROUND` (`sanitize_dds_background`). A default that moves is one edit, and the mark and the fallback move with it rather than staying where they were written.

Which files each kind of preview covers is a list in the file, one section per kind — `[image]`, `[video]`, `[text]` (which carries the extensionless names beside its extensions), `[archive]`, `[office]` and `[font]` — written from the built-in list on first run and read back from there, so a format the app does not know is a file edit rather than a rebuild. `image_formats`, `video_formats`, `text_formats`, `archive_formats`, `office_formats` and `font_formats` own them, each with the normalization that keeps a hand-edited entry safe to match against, and the hook and the renderer read the same lists rather than classifying a file twice.

A list is repaired rather than lost. A key that is gone — its line deleted, or its whole section with it — comes back with the built-in entries, and the file is written out again with them, which is what makes a hand-edit that removes too much recoverable: the reload that finds a key missing is also the write that puts it back. An empty value is not a missing one and is kept as written, because that is how a user asks for no files of that kind at all — the `Preview Types` gate is a switch over behavior, while an empty list is the kind configured away. What is read otherwise is exactly what the file says: a list anyone has edited keeps its own entries and its own order, and the entries a kind has gained since a file was written, and the order a file written earlier holds them in, are the repair's business rather than the read's. That check writes a list only where the entries differ from the built-in list's, because a write moves the mtime, the watcher reloads, and a file written out for a change that was not one would keep the app writing for as long as it ran. Nothing else in the file is preserved across a write: `save` builds a fresh `Ini` from the known fields, so a hand-added section, key or comment is dropped the next time the app writes — which is one more reason the file is written only where the repair left something to write.

A list the app itself has changed is brought up by the repair rather than by the read. `svg` and `svgz` were added to the built-in image list, and a file holding exactly the entries the app shipped before they existed is the app's own older list rather than the user's — nobody has typed it — so the repair reads it as the current built-in list and the file is written again with the new entries in it. Without that, an entry added to a built-in list would reach a fresh installation only: every `config.ini` already written holds the list as it was, and a list that differs from the built-in one is otherwise taken for the user's own. A list with any one entry changed — added, removed or spelled differently — matches neither and is kept exactly as it is, and an empty value is kept empty, which is how a user asks for none of that kind at all. `IMAGE_EXTENSIONS_BEFORE_DDS`, `IMAGE_EXTENSIONS_BEFORE_CODEC_FORMATS`, `IMAGE_EXTENSIONS_BEFORE_SVG` and `IMAGE_EXTENSIONS_WITH_SVG` are those older lists and `repair_older_lists` is the check that reads them; the image, design and vector kinds are the ones with a history, and a kind whose built-in entries change again is added to it. Asking the question this way costs one thing, and it is worth saying out loud: an entry a user took out can come back, because a list trimmed to exactly the entries this app shipped before that entry existed is this app's own as far as the check can tell, and is read as one. What that buys is the other half — the formats added since, which a list nobody had touched would otherwise never be given.

Themes the user adds live in `%APPDATA%\rust-hover-preview\theme`, beside `config.ini` and created on first run: a `.tmTheme` file there is listed by the tray under its own file name (the stem, `atom-one-light` for `atom-one-light.tmTheme`), read from disk the first time a preview asks for it, and re-read whenever the tray menu is built, so a file added, edited or repaired is one menu-open away from taking effect rather than a restart. The folder itself is only ever listed — a file's contents are not touched until it is chosen — and it cannot shadow a bundled theme: a file theme is written `theme=custom:<name>`, while `light` and `dark` on their own always mean the bundled Atom One Light and One Dark Pro. A file that cannot be read or is not a theme is painted with the default, which is what the menu marks while the name it was chosen under stays in the file.

## Build And Packaging Notes

- The MSVC toolchain uses `rust-lld` via .cargo/config.toml for faster, more consistent linking.
- Windows resources are set in `build.rs` through `winres`.
- A release build ends a running copy of the app before the crate is linked, because Windows will not let the linker replace an open binary. `src` is watched so the rebuild an edit asks for is the one that gets it; debug builds are left alone.
- Release installers are produced by `cargo packager` (NSIS `.exe` setup).
- What the installers and the released `.exe` are built from is the `github` profile rather than `release`: `build-installers.ps1` packages with `--profile github` and the packaging metadata builds and reads that profile's output (`target/github`), so the artifact is optimized as one program over one codegen unit while `cargo build --release` keeps the thin-LTO profile the edit-build-test loop is short on.
- The NSIS setup is built from `packaging/nsis/installer.nsi`, cargo-packager's own template with its "Already Installed" page removed: an older installation is uninstalled silently before anything is copied, and a running copy of the app is closed without asking. The cargo-packager version the template was written against is pinned in `build-installers.ps1` and the deploy workflows, so moving to a newer one is a deliberate pin bump and a diff of that file.
